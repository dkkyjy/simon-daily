你是只使用一个会话，还是在终端中保持两个会话打开？你是否每次提示都开启新会话？你何时使用 [compact](https://platform.claude.com/docs/en/build-with-claude/compaction)、rewind 或 [subagents](https://code.claude.com/docs/en/sub-agents)？什么会导致糟糕的 compact 或糟糕的会话？

这里面的细节数量惊人，它们确实能塑造你在 [Claude Code](https://code.claude.com/docs/en/overview) 中的体验，而几乎所有细节都源于[管理你的上下文窗口](https://code.claude.com/docs/en/how-claude-code-works)。

## **关于上下文、压缩与上下文腐化的快速入门**

上下文窗口是模型在生成下一个响应时能“看到”的全部内容。它包括你的系统提示、此前的对话、每次工具调用及其输出，以及每个被读取的文件。Claude Code 的上下文窗口为一百万个 token。

不幸的是，使用上下文会对性能产生轻微影响，这通常被称为上下文腐化（context rot）。上下文腐化是指随着上下文增长，模型性能下降的现象，因为注意力被分散到更多 token 上，而较旧的、不相关的内容开始干扰当前任务。

上下文窗口是一个硬性上限，因此当你接近上下文窗口末尾时，你正在处理的任务会被自动总结成更小的描述，模型会在新的上下文窗口中继续工作。我们称之为压缩（compaction）。你也可以自行触发压缩。

## **每一轮对话都是一个分支点**

假设你刚刚让 Claude 做了一件事，它已完成——现在你的上下文中有了信息（工具调用、工具输出、你的指令），而接下来你有数量惊人的选项：

* **继续** —— 在同一会话中发送另一条消息
* **`/rewind`（esc esc）** —— 跳回之前的某条消息，并从那里重新开始
* **`/clear`** —— 开启新会话，通常带有一份你从刚才所学中提炼出的简报
* **压缩** —— 总结到目前为止的会话，并在总结之上继续
* **子代理** —— 将下一块工作委派给一个拥有自己干净上下文的代理，只将其结果拉回来

虽然最自然的做法是直接继续，但其他四个选项的存在正是为了帮助你管理上下文。

## **何时开启新会话**

你是保持一个长时间运行的会话，还是开启新会话？我们的一般经验法则是：当你开始一项新任务时，也应该开启一个新会话。

虽然 100 万上下文窗口意味着你现在可以更可靠地完成更长的任务，例如从头构建一个全栈应用，但上下文腐化仍可能发生。

有时你会执行一些相关任务，其中部分上下文仍然是必要的，但并非总是如此。例如，为你刚刚实现的功能编写文档。虽然你可以开启新会话，但 Claude 将不得不重新读取你刚刚实现的文件，这会更慢且更昂贵。

## **用回退代替纠正**

在 Claude Code 中，双击 Esc（或运行 `/rewind`）可以让你跳回任何先前的消息并从那里重新提示。该点之后的消息会从上下文中丢弃。

回退通常是比纠正更好的方法。例如，Claude 读取了五个文件，尝试了一种方法，但没有成功。你的直觉可能是输入“那没成功，试试 X 吧”。但更好的做法可能是回退到刚读完文件之后的位置，并用你学到的东西重新提示。“不要用方法 A，foo 模块没有暴露那个——直接走 B。”

你还可以使用 *“从这里总结”* 或 `/rewind` 斜杠命令，让 Claude 总结其学习成果并创建一条交接消息，就像来自未来自我的 Claude 给上一次迭代的 Claude 发消息说“我试过了，但没成功”。

## **压缩与开启全新会话**

一旦会话变得很长，你有两种方式来摆脱多余的上下文：`/compact` 或 `/clear`（然后重新开始）。它们感觉相似，但行为却截然不同。

**压缩** 要求模型总结到目前为止的对话，然后用该总结替换历史记录。它是有损的，但你不需要自己写任何东西，而且 Claude 在包含重要学习成果或文件方面可能更彻底。你也可以通过传递指令来引导它（`/compact 专注于 auth 重构，丢弃测试调试`）。

使用 `/clear` 时，*你* 写下重要的内容（“我们在重构 auth 中间件，约束条件是 X，关键文件是 A 和 B，我们已经排除了方法 Y”），然后干净地开始。这需要更多工作，但最终上下文是你决定相关的部分。

## **什么会导致糟糕的自动压缩？**

如果你运行大量长时间会话，你可能已经注意到有时压缩效果特别差。在这种情况下，我们经常发现，当模型无法预测你工作的方向时，就可能发生糟糕的压缩。

在上面的例子中，自动压缩在一次冗长的调试会话后触发，总结了调查过程，而你的下一条消息是“现在修复我们在 bar.ts 中看到的那个其他警告”。

但由于会话专注于调试，那个其他警告可能已从总结中被丢弃。

这尤其困难，因为由于上下文腐化，模型在压缩时正处于其智能水平的最低点。有了 100 万上下文，你有更多时间主动使用 `/compact` 并附上你想做什么的描述。

## **子代理与全新的上下文窗口**

[子代理](https://claude.com/blog/subagents-in-claude-code) 往往在你事先知道某块工作会产生大量你不再需要的中间输出时表现良好。

当 Claude 通过 Agent 工具生成子代理时，该子代理会获得自己全新的上下文窗口。它可以做尽可能多的工作，然后综合其结果，只将最终报告返回给父代理。

我们在 Anthropic 使用的思维测试是：*我还会需要这个工具输出吗，还是只需要结论？*

虽然 Claude Code 会自动调用子代理，但你可能希望明确告诉它这样做。例如，你可以告诉它：

* “启动一个子代理，根据以下规范文件验证这项工作的结果”
* “分出一个子代理，通读另一个代码库并总结它如何实现 auth 流程，然后你自己以同样的方式实现”
* “分出一个子代理，根据我的 git 变更为此功能编写文档”

**综合运用**

为了帮助你选择使用哪种上下文管理功能，我们整理了这个有用的表格，概述了常见情况、应使用的工具以及原因。

| 情况 | 考虑使用 | 原因 |
| --- | --- | --- |
| 同一任务，上下文仍然相关 | 继续 | 窗口中的所有内容仍然至关重要；不要为重建它付出代价。 |
| Claude 走错了路 | 回退（双击 Esc） | 保留有用的文件读取，丢弃失败的尝试，用你学到的东西重新提示。 |
| 任务中途但会话充斥着过时的调试/探索内容 | `/compact <提示>` | 低投入；Claude 决定什么重要。如有需要，用指令引导它。 |
| 开始一项真正的新任务 | `/clear` | 零腐化；你精确控制哪些内容继续保留。 |
| 下一步将产生大量你只需要结论的输出（代码库搜索、验证、文档编写） | 子代理 | 中间工具噪音留在子代理的上下文中；只有结果返回。 |
