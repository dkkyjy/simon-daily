正如许多数据科学和数据工程团队可以证实的那样，实现自助式业务分析传统上一直是一个艰难的过程。

通过宽表和反范式化表格让数据模型对技术能力较弱的同事更易访问，往往会导致业务规模扩大时出现定义不一致的重叠视图（而且对于那些不太愿意学习 SQL 的员工来说，缩小差距的效果甚微）。或者，为用户创建更封闭的环境常常会遗漏长尾业务问题，并导致指标和仪表盘膨胀，因为团队将工作各自孤立。

LLM 的兴起为自助式分析提供了一条避免这些挑战的新路径。然而，直接将 Claude 指向数据仓库并让代理执行，可能会造成一种虚假的精确感。

最初从临时请求中解放出来的欣喜会转变为恐惧，因为人们意识到这种设置将利益相关者与之前引导他们使用精心策划数据集的底层基础设施、文档和专业知识隔离开来。

在 Anthropic，95% 的业务分析查询通过 Claude 实现自动化，总体准确率约为 95%。通过将这些通常繁琐重复的工作交给 Claude，我们的数据科学团队可以专注于更具战略性的工作，如因果建模、预测和机器学习。

在会见了数十位 Anthropic 顶尖的 Claude Code 用户并观察了大量分析代理的设计模式后，我们为其他使用 LLM 的数据团队总结出了一些最佳实践。在这篇文章中，我们将分享这些技巧和方法，以最大化 Claude 驱动自助业务洞察的能力，包括：

* 为什么分析准确性是一个上下文和验证问题，而不是代码生成问题；
* 导致大多数错误的三种失败模式；
* 我们为解决这些错误而构建的代理分析堆栈；
* 我们如何衡量有效性；以及
* 我们创建大多数技能的基本模板（见附录）

## **数据不是软件**

LLM 的生成能力是一把双刃剑：能够为复杂问题提供创造性解决方案的机制，也可能产生错误的输出。要完全理解分析代理面临的挑战，将其与编码代理进行比较是有用的。

编码是一个开放的解决方案空间，奖励模型的创造力，而文档和测试则提供了防止幻觉的自然防护栏。相比之下，对于分析用例，通常只有一个正确的答案，来自一个唯一正确的来源，并且没有确定的方法来证明其正确性。

对于自助式代理业务分析而言，复杂性主要在于数据的模糊性。核心问题归结为***将用户的问题映射到数据模型中特定且最新的实体，并知道正确处理它们的方法***。如果能做到这一点，那么后续的执行和 SQL 就变得微不足道了。

我们确定了这一问题的三个属性，它们导致了绝大多数不准确的响应：

1. **概念 <> 实体模糊性**：数据模型中有数百个可行选项（在数百万个字段中），代理无法选择最能回答用户问题的正确字段。例如，在衡量活跃用户数量时：什么样的行为构成“活跃”？是否包含欺诈用户？使用什么回溯窗口？

2. **数据过时**：数据源、业务定义和模式不断变化；资产和代理知识变得陈旧，开始返回细微的错误答案。

3. **检索失败**：正确的信息可能确实存在于数据模型中并已正确注释，但由于搜索空间巨大，代理根本没有找到它。
