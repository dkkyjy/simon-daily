# 何时使用多智能体系统（以及何时不应使用）

**日期：** 2026-01-23 00:00 UTC
**链接：** https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them

---

多智能体系统是一种架构，其中多个LLM实例在独立的对话上下文中运行，通过代码进行协调。存在多种协调模式（智能体群组、基于能力的系统和消息总线架构），但本文聚焦于编排器-子智能体模式：一种分层模型，其中主导智能体为特定子任务生成并管理专门的子智能体。这种模式提供了一种直接的协调模型，是刚接触多智能体系统的团队的良好起点。我们将在下一篇文章中详细探讨其他模式。

如今，多智能体系统常常被应用于单个智能体表现更好的场景，不过随着模型改进，这种权衡也在不断变化。在Anthropic，我们看到团队花费数月时间构建复杂的多智能体架构，却发现改进单个智能体的提示词就能达到同等效果。

在构建多智能体系统并与在生产环境中部署它们的团队合作后，我们确定了三种多智能体始终优于单个智能体的情形：当上下文污染降低性能时、当任务可以并行运行时、以及当专业化能改进工具选择或任务聚焦时。在这些情形之外，协调成本通常超过收益。

在本文中，我们将分享如何识别单个智能体的局限性、确定多智能体系统表现出色的三种场景，以及避免常见的实现错误。

## 从单个智能体开始的理由

一个设计良好的、配备适当工具的单个智能体所能完成的工作远超许多开发者的预期。

多智能体系统会引入开销。每增加一个智能体就意味着多了一个潜在的故障点、多了一套需要维护的提示词、以及多了一个意外行为的来源。

我们观察到，团队构建了复杂的多智能体系统，为规划、执行、审查和迭代分别设置独立的智能体，结果却发现每个交接点都会丢失上下文，并且用于协调的令牌比用于执行的还多。在我们的测试中，多智能体实现通常比单智能体方法多消耗3到10倍的令牌来完成同等任务。这种开销源于在智能体之间复制上下文、智能体之间的协调消息以及为交接而总结结果。

## 多智能体系统的决策框架

多智能体架构在解决单个智能体无法克服的特定约束时能提供价值。这意味着多智能体架构应保留给那些能带来明确收益、足以证明额外成本合理的情况。

以下模式代表了我们在其中持续观察到积极投资回报的案例。

### 上下文保护

大型语言模型具有有限的上下文窗口，随着上下文增长，响应质量可能会下降。当智能体的上下文累积了与后续子任务无关的某个子任务信息时，就会发生上下文污染。子智能体提供了隔离，每个子智能体在其自己的、聚焦于特定任务的干净上下文中运行。

考虑一个需要检索订单历史同时诊断技术问题的客户支持智能体。如果每次订单查询都向上下文添加数千个令牌，智能体推理技术问题的能力就会下降。

**单智能体方法：**

```
# 单个智能体将所有内容累积在上下文中
对话历史 = [
    {"role": "user", "content": "我的订单#12345无法使用"},
    {"role": "assistant", "content": "让我查看您的订单..."},
    # 工具结果添加了2000+令牌的订单历史
    {"role": "user", "content": "... (订单详情、过往购买记录、配送信息) ..."},
    {"role": "assistant", "content": "现在让我诊断技术问题..."},
    # 上下文现在被智能体不需要的订单详情污染了
]
```

智能体必须在上下文中维护2000+令牌的无关订单历史的同时推理技术问题，这会稀释注意力并降低响应质量。

**多智能体方法：**

```
from anthropic import Anthropic

client = Anthropic()

class 订单查询智能体:
    def 查询订单(self, 订单ID: str) -> dict:
        # 具有自身上下文的独立智能体
        messages = [
            {"role": "user", "content": f"获取订单{订单ID}的基本详情"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=1024,
            messages=messages,
            tools=[获取订单详情工具]
        )
        # 仅返回必要信息
        return 提取摘要(response)

class 支持智能体:
    def 处理问题(self, 用户消息: str):
        if 需要订单信息(用户消息):
            订单ID = 提取订单ID(用户消息)
            # 仅获取所需信息，而非完整历史
            订单摘要 = 订单查询智能体().查询订单(订单ID)
            # 注入紧凑摘要，而非完整上下文
            上下文 = f"订单{订单ID}: {订单摘要['状态']}, 购买日期{订单摘要['日期']}"

        # 主智能体上下文保持干净
        messages = [
            {"role": "user", "content": f"{上下文}\n\n用户问题: {用户消息}"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=2048,
            messages=messages
        )
        return response
```

订单查询智能体处理完整的订单历史并提取摘要。主智能体仅接收其实际需要的50-100个令牌，保持上下文聚焦。

当子任务产生大量上下文（超过1000个令牌）但大部分信息与主任务无关时、当子任务定义明确且具有清晰的提取信息标准时、以及对于需要先过滤再使用的查询或检索操作时，上下文隔离最为有效。

### 并行化

并行运行多个智能体可以探索比单个智能体更大的搜索空间。这种模式对于搜索和研究任务尤其有价值。

我们的[研究功能](https://www.anthropic.com/engineering/multi-agent-research-system)使用了这种方法。主导智能体分析查询并生成多个子智能体，以并行调查不同方面。每个子智能体独立搜索，然后返回提炼后的发现。通过允许在更大的信息空间中进行探索，多智能体搜索相比单智能体方法显示出显著的准确性提升。

核心实现是将一个问题分解为独立的方面，并发运行子智能体，然后综合结果。

```
import asyncio
from anthropic import AsyncAnthropic

client = AsyncAnthropic()

async def 研究主题(查询: str) -> dict:
    # 主导智能体将查询分解为研究方面
    方面 = await 主导智能体.分解查询(查询)

    # 生成子智能体并行研究每个方面
    任务 = [
        研究子智能体(方面) 
        for 方面 in 方面
    ]
    结果 = await asyncio.gather(*任务)

    # 主导智能体综合发现
    return await 主导智能体.综合(结果)

async def 研究子智能体(方面: str) -> dict:
    """每个子智能体拥有自己的上下文窗口"""
    messages = [
        {"role": "user", "content": f"研究: {方面}"}
    ]
    response = await client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=4096,
        messages=messages,
        tools=[网络搜索, 读取文档]
    )
    return 提取发现(response)
```

这种覆盖范围的改进是有代价的。多智能体系统通常比单智能体方法多消耗3到10倍的令牌来完成同等任务。这是因为每个智能体需要自己的上下文、智能体必须交换消息进行协调、以及在智能体之间传递结果时需要总结。虽然并行性有助于减少总执行时间（与顺序运行所有工作相比），但多智能体系统通常比单智能体系统耗时更长，因为总计算量大幅增加。

并行化的主要好处是彻底性，而非速度。当您需要搜索大量信息空间或调查复杂问题的多个角度时，并行智能体可以比在其上下文限制内工作的单个智能体覆盖更多领域。代价是更高的令牌使用量和通常更长的总执行时间，以换取更全面的结果。

### 专业化

不同任务有时受益于不同的工具集、系统提示或专业领域。与其为单个智能体提供数十种工具的访问权限，不如为智能体配备与其职责相匹配的聚焦工具集，这可以提高可靠性。

#### **工具集专业化**

当智能体拥有过多工具时，性能会下降。三个信号表明工具专业化会有所帮助：

1. **数量。** 拥有过多工具（通常20+）的智能体难以选择正确的工具。
2. **领域混淆。** 当工具跨越多个不相关的领域（数据库操作、API调用、文件系统操作）时，智能体会混淆适用于给定任务的领域。
3. **性能下降。** 添加新工具会降低现有任务的性能，表明智能体已达到其工具管理能力的上限。

#### **系统提示专业化**

不同任务有时需要不同的人物角色、约束或指令，这些在组合时会产生冲突。客户支持智能体需要富有同理心和耐心；代码审查智能体需要精确和批判性。合规检查智能体需要严格的规则遵循；头脑风暴智能体需要创造性的灵活性。当单个智能体必须在冲突的行为模式之间切换时，将其拆分为具有定制系统提示的专业化智能体可以产生更一致的结果。

#### **领域专业知识专业化**

某些任务受益于会压垮通用智能体的深度领域上下文。法律分析智能体可能需要关于判例法和监管框架的广泛上下文。医学研究智能体可能需要关于临床试验方法的专业知识。与其将所有领域上下文加载到单个智能体中，不如让专业化智能体携带与其特定职责相关的聚焦专业知识。

**示例：多平台集成。** 考虑一个集成系统，其中智能体需要跨CRM、营销自动化和消息平台工作。每个平台有10-15个相关API端点。拥有40+工具的单个智能体常常难以正确选择，混淆跨平台的类似操作。拆分为具有聚焦工具集和定制提示的专业化智能体可以解决选择错误。

```
from anthropic import Anthropic

client = Anthropic()

# 具有聚焦工具集和定制提示的专业化智能体
class CRM智能体:
    """处理客户关系管理操作"""
    system_prompt = """您是CRM专家。您管理联系人、 
    机会和账户记录。在更新前始终验证记录所有权， 
    并维护相关记录间的数据完整性。"""
    tools = [
        crm_获取联系人,
        crm_创建机会,
        # 8-10个CRM特定工具
    ]

class 营销智能体:
    """处理营销自动化操作"""
    system_prompt = """您是营销自动化专家。您 
    管理活动、潜在客户评分和邮件序列。优先考虑 
    数据卫生并尊重联系人偏好。"""
    tools = [
        营销_获取活动,
        营销_创建潜在客户,
        # 8-10个营销特定工具
    ]

class 编排器智能体:
    """将请求路由到专业化智能体"""
    def 执行(self, 用户请求: str):
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=1024,
            system="""您协调平台集成。将请求路由到适当的专家：
- CRM：联系人记录、机会、账户、销售管道
- 营销：活动、潜在客户培育、邮件序列、评分
- 消息：通知、警报、团队通信""",
            messages=[
                {"role": "user", "content": 用户请求}
            ],
            tools=[委托给CRM, 委托给营销, 委托给消息]
        )
        return response
```

这种模式反映了有效的专业协作，其中配备与其角色匹配工具的专家协作比试图在所有领域维持专业知识的通才更有效。然而，专业化引入了路由复杂性。编排器必须正确分类请求并委托给正确的智能体，路由错误会导致糟糕的结果。维护多个专业化智能体也增加了提示维护开销。专业化在领域可清晰分离且路由决策明确时效果最佳。

## 超越单智能体架构

除了通用框架之外，某些具体信号表明单智能体模式已被超越：

**接近上下文限制。** 如果智能体常规使用大量上下文且性能正在下降，则上下文压力可能是瓶颈。请注意，上下文管理的最新进展（[例如压缩](https://platform.claude.com/cookbook/tool-use-automatic-context-compaction)）正在减少这一限制，使单个智能体能够在更长的范围内维持有效记忆。

**管理众多工具。** 当智能体拥有15-20+工具时，模型会花费大量上下文和注意力来理解其选项。在采用多智能体架构之前，请考虑使用[工具搜索工具](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/tool-search-tool)，它允许Claude按需动态发现工具，而不是预先加载所有定义。这可以将令牌使用量[减少高达85%](https://www.anthropic.com/engineering/advanced-tool-use)，同时提高工具选择准确性。

**可并行化的子任务。** 当任务自然分解为独立部分（跨多个来源的研究、多个组件的测试）时，并行子智能体可以提供显著的加速。

这些阈值将随着模型的改进而变化。当前限制代表实践指南，而非根本性约束。

## 以上下文为中心的分解

在采用多智能体架构时，最重要的设计决策是如何在智能体之间分配工作。我们观察到，团队常常错误地做出这一选择，导致协调开销抵消了多智能体设计的好处。

关键见解是采用**以上下文为中心的观点**，而非以问题为中心的观点来分解工作。

**以问题为中心的分解（通常适得其反）。** 按工作类型划分（一个智能体编写功能、另一个编写测试、第三个审查代码）会产生持续的协调开销。每次交接都会丢失上下文。编写测试的智能体缺乏对某些实现决策原因的了解，代码审查者缺乏探索和迭代的上下文。

**以上下文为中心的分解（通常有效）。** 按上下文边界划分意味着处理某个功能的智能体也应处理其测试，因为它已经拥有必要的上下文。只有在上下文可以真正隔离时才应拆分工作。

这一原则源于对多智能体系统失败模式的观察。当智能体按问题类型拆分时，它们会参与"传话游戏"，在每次交接中来回传递信息，保真度不断下降。在一个按软件开发角色（规划者、实现者、测试者、审查者）专业化的智能体实验中，子智能体在协调上花费的令牌比在实际工作上更多。

**有效的分解边界包括：**

* **独立的研究路径。** 调查"亚洲市场趋势"与"欧洲市场趋势"可以并行进行，无需共享上下文。
* **具有清晰接口的独立组件。** 有了定义良好的API契约，前端和后端工作可以并行进行。
* **黑盒验证。** 只需运行测试并报告结果的验证器不需要实现上下文。

**有问题的分解边界包括：**

* **同一工作的顺序阶段。** 同一功能的规划、实现和测试共享太多上下文。
* **紧密耦合的组件。** 需要持续来回沟通的组件应属于同一智能体。
* **需要共享状态的工作。** 需要频繁同步理解的智能体应保持在一起。

## 验证子智能体模式

一种跨领域始终表现良好的多智能体模式是**验证子智能体**。这是一个专用智能体，其唯一职责是测试或验证主智能体的工作。

值得注意的是，更强大的编排器模型（如Claude Opus 4.5）越来越能够直接评估子智能体的工作，而无需单独的验证步骤。然而，当使用能力较弱的编排器时、当验证需要专用工具时、或者当您希望在流程中强制执行明确的验证检查点时，验证子智能体仍然很有价值。

验证子智能体之所以成功，是因为它们规避了传话游戏问题。验证本质上需要最少的上下文传递，因此验证器可以对系统进行黑盒测试，而无需了解其构建的完整历史。

### 实现

主智能体完成一个工作单元。在继续之前，它会生成一个验证子智能体，附带要验证的工件、明确的成功标准以及执行验证的工具。

验证器不需要理解工件为何以某种方式构建。它只需要确定工件是否满足指定的标准。

```
from anthropic import Anthropic

client = Anthropic()

class 编码智能体:
    def 实现功能(self, 需求: str) -> dict:
        """主智能体实现功能"""
        messages = [
            {"role": "user", "content": f"实现: {需求}"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=4096,
            messages=messages,
            tools=[读取文件, 写入文件, 列出目录]
        )
        return {
            "代码": response.content,
            "更改的文件": 提取文件(response)
        }

class 验证智能体:
    def 验证实现(self, 需求: str, 更改的文件: list) -> dict:
        """独立智能体验证工作"""
        messages = [
            {"role": "user", "content": f"""
需求: {需求}
更改的文件: {更改的文件}

运行测试套件并验证：
1. 所有现有测试通过
2. 新功能按指定方式工作
3. 没有明显错误或安全问题

您必须在标记为通过之前运行完整的测试套件。
在仅运行少数测试后不要标记为通过。
运行: pytest --verbose
仅当所有测试都通过且没有失败时才标记为PASSED。
"""}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=4096,
            messages=messages,
            tools=[运行测试, 执行代码, 读取文件]
        )
        return {
            "通过": 提取通过失败(response),
            "问题": 提取问题(response)
        }

def 实现并验证(需求: str, 最大尝试次数: int = 3):
    for 尝试次数 in range(最大尝试次数):
        结果 = 编码智能体().实现功能(需求)
        验证结果 = 验证智能体().验证实现(
            需求,
            结果['更改的文件']
        )

        if 验证结果['通过']:
            return 结果

        需求 += f"\n\n上次尝试失败: {验证结果['问题']}"

    raise Exception(f"在{最大尝试次数}次尝试后验证失败")
```

### 应用

验证子智能体在以下方面有效：

* **质量保证。** 运行测试套件、检查代码风格、根据模式验证输出。
* **合规检查。** 验证文档满足政策要求、根据规则检查输出。
* **输出验证。** 在交付前确认生成的内容符合规格。
* **事实核查。** 让独立智能体验证生成内容中的声明或引用。

### 早期胜利问题

验证子智能体最显著的失败模式是在没有彻底测试的情况下将输出标记为通过。验证器运行一两个测试，观察到它们通过，然后宣布成功。

缓解策略包括：

* **具体标准。** 指定"运行完整的测试套件并报告所有失败"，而非"确保它能工作"。
* **全面检查。** 要求验证器测试多个场景和边界情况。
* **负面测试。** 指示验证器尝试应该失败的输入并确认它们确实失败。
* **明确指令。** 指令"您必须在标记为通过之前运行完整的测试套件"至关重要。如果没有关于全面验证的明确要求，验证智能体会走捷径。

## 前进方向

多智能体系统功能强大，但并非普遍适用。在增加多个协调智能体的复杂性之前，请确认：

1. **存在真正的约束**，多智能体可以解决这些约束，例如上下文限制、并行化机会或专业化需求。
2. **分解遵循上下文而非问题类型。** 按所需上下文对工作进行分组，而非按工作类型。
3. **存在清晰的验证点**，子智能体可以在无需完整上下文的情况下验证工作。

我们的建议？从最简单有效的方法开始，仅在证据支持时才增加复杂性。
