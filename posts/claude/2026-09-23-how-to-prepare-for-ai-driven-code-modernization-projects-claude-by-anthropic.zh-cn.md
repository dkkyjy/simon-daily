# 如何为 AI 驱动的代码现代化项目做准备   | Claude by Anthropic

**日期：** 2026-09-23 00:00 UTC
**链接：** https://claude.com/blog/how-to-prepare-for-ai-driven-code-modernization-projects

---

*在我们的* ***实地笔记*** *系列中，Anthropic 的前线部署工程师分享从真实客户部署中汲取的最佳实践。在本文中，我们分享管理大型代码现代化项目的经验。*

过去需要多年全员投入的[代码现代化](https://claude.com/blog/how-ai-helps-break-cost-barrier-cobol-modernization)项目，现在可以在几个月（甚至[几周](https://claude.com/blog/ai-code-migration)）内完成，但项目前后的组织工作往往仍然相同。

例如，对关键银行系统的每次更改都必须经过变更管理、审查和批准。这是一个稳健的流程，因为监管机构、审计师和业务部门都要求如此。

正是这些流程让关键系统值得信赖，它们建立在这样一个假设之上：每次更改都由人类编写，每次差异都由人类审查。一旦智能体加速了更改的编写，瓶颈就从产生更改转移到了动员组织围绕这些更改展开工作。

本文涵盖企业在现代化开始之前必须完成的工作：定义"完成"的含义、更改必须携带哪些证据、经过认证的更改如何到达生产环境，以及需要预先准备什么以便运行可以开始。

我们将这一流程分为六个步骤：

1. **定义目标：** 现代化代码必须具备的技术栈和行为。
2. **创建证书：** 更改必须满足的条件，才能在目标状态下被视为正确。
3. **设定晋升策略：** 经过认证的更改以生产速度进入生产环境的路径。
4. **落实前提条件：** 环境、CI/CD、审查能力和审批。
5. **构建并完善智能体工作流：** 自定义 Claude Code [动态工作流](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code)，将现代化工作分发到许多并行的小规模子智能体工作流中，从而产生更改。这是围绕目标、证书和晋升策略构建的。
6. **执行现代化：** 在代码库的小分区上端到端验证工作流，然后扩展。

## **步骤 1：定义目标**

**目标**是现代化的最终状态。期望的最终状态决定了您要做的是三种现代化中的哪一种，详见下表。

### **确定现代化类型**

| 类型 | 定义 | 适用场景 | 目标为 |
| --- | --- | --- | --- |
| **升级（Uplift）** | 同一技术栈的版本升级（例如 C++11 → C++20）。 | 技术栈没问题，但版本已落后：运行时的生命周期已结束、未修补的安全问题、无法再升级的依赖项。 | 运行时版本和包集合。 |
| **转换（Transform）** | 保持行为不变的跨技术栈重写（例如 COBOL → Java）。 | 技术栈是需要解决的问题，而行为是可信的。 | 升级所需的一切，外加新代码必须遵循的语言、框架和架构惯例。 |
| **重构（Reimagine）** | 在新架构上进行绿地重建，并修改行为。 | 行为需要随代码一起更改。 | 转换所需的一切，外加新系统的书面行为规范。 |

组织内部经常就采用哪种现代化类型进行争论。根据我们的经验，离生产最近的人希望替换技术栈但保持行为不变以控制风险（转换型现代化）。另一方面，往往是那些长期接触代码库的工程师，他们希望现代化能偿还技术债务，还有其他业务利益相关者希望借此机会提出新需求（重构型现代化）。

两种立场都有道理，但如果这个问题得不到解决，它会在以后以"某个更改是否正确"的争论形式重新出现。就采取哪条路径达成共识会增加初期的摩擦，但会使整个项目更加顺畅。

### **映射代码库并创建行为规范**

了解当前系统通常是定义目标的良好第一步。提取旧代码实际执行的操作并创建当前行为清单，可以轻松决定哪些部分应该更改或丢弃，从而确定现代化是转换还是重构。这通常还会揭示未知的业务逻辑和边界情况。

Claude 可以通过[映射依赖关系并记录无人记得构建的工作流](https://claude.com/blog/how-ai-helps-break-cost-barrier-cobol-modernization)来完成大部分发现工作。[代码现代化插件](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)的*assess*、*map*和*extract-rules*命令可以挖掘带有源代码引用的业务规则，供工程师审查。

然而，仅靠 Claude 的发现可能无法完全捕获遗留系统的行为。与业务用户和开发人员的访谈以及内部文档可以填补这些空白。前期收集上下文可能需要一些时间，但这些上下文的质量会影响工作流后续做出的每个决策。

对于重构型现代化，定义目标需要额外的工作：应编写详细的行为规范并与用户群体达成一致。

### **确立项目的合理性和目标**

在定义目标的同时，组织应考虑为什么值得进行现代化。现代化遗留系统可以降低持续的维护和运营成本，然而，根据我们的经验，成本降低并不是大多数现代化项目的主要驱动力。

> 风险降低通常是最重要的现代化收益。在讨论是否进行现代化项目时，请考虑不进行现代化的风险。

例如，一个携带未修补漏洞的系统可能意味着网络入侵或严重到足以危及业务本身的停机。不受支持的运行时或理解该系统的工程师池缩小都会加剧风险。

像 Claude Code 这样的智能体编码工具缩短了现代化时间线，但预算仍然难以估算，这导致了惰性。我们已经公开了一些[大规模现代化](https://claude.com/blog/ai-code-migration)的成本，[其他公司](https://claude.com/customers/lg-cns)也是如此。这些可以作为粗略的基线，我们在本指南底部还提供了有关预算预测的额外指导。

启动这些项目的主要挑战通常是建立内部共识，并获得拥有系统的团队以及依赖该系统的团队的承诺。建立商业案例并设定项目目标（通常在领导层层面）会使这一部分更容易。这还有助于锚定随后证书和晋升策略中的权衡。当利益相关者对更改可以承担多少风险存在分歧时，不进行现代化的风险就是平衡砝码。

## **步骤 2：定义证书**

**证书**是每个现代化更改必须满足的条件或测试集。选择那些能提供最强累积证据表明更改相对于目标是正确的条件。

每个条件都应可以在没有人类参与的情况下检查，以便智能体工作流可以迭代更改，直到它满足证书，或者如果无法满足则标记以供人工审查。

证书包含什么取决于目标，但通常会从以下列表中选择：

* 原始测试套件通过
* Claude 在现代化期间编写的测试全部通过
* 测试覆盖率达到约定的阈值
* 性能基准保持在约定的范围内
* Claude 进行的独立对抗性审查（每次在新的上下文窗口中）未发现阻塞性问题
* 对于用户界面，Claude 驱动的计算机使用未发现回归
* 当前版本和目标版本对相同输入产生相同输出，可以是实时的、录制的或 Claude 生成的
* 持久化状态和线格式在当前版本和目标版本之间往返转换
* 更改在暂存环境中运行约定的一段时间，错误率、延迟或警报没有回归
* 静态分析和安全扫描没有显示新的发现
* 对于编译型目标，构建干净且类型检查通过

> **与将审查和晋升更改到生产环境的人一起编写证书。** 在证书和智能体工作流仍在设计阶段时，就引入依赖该代码库的开发人员、用户群体和业务负责人。

他们的专业知识塑造了证书衡量的内容，他们的早期参与是在更改到达审查时获得他们支持的关键。对完成的证书的一个良好检查是：他们是否会仅凭证书的证据就放心合并。如果他们在其中看到了自己的标准，那么步骤 3 中的晋升策略就可以更轻量。

证书检查的内容以及方式取决于现代化类型。

* **对于升级型现代化**，一致性针对原始代码库，原始测试套件可以作为证书的核心。
* **对于转换型现代化**，一致性也针对原始代码库，但原始测试套件很少在新技术栈上运行。生产流量重放、新旧之间的差异测试以及生产并行部署承担了大部分工作。
* **对于重构型现代化**，证书以行为规范为基础。这是最困难的情况。规范相对于要比较的现有系统来说客观性较低，因此涉及更大程度的模型判断，这可能导致更可变的结果。在这里，证书依赖于从规范编写的测试、Claude 进行的独立对抗性审查（检查每个更改是否符合规范），以及新系统保留旧系统行为的差异检查。预期随着规范的明确化，证书会被修订：规范的差距会首先在这里显现。

旧系统通常测试覆盖率低、测试不稳定且遥测数据少。定义证书的一部分是识别这些差距。如果支持强证书会很困难，那么在这一步最有用的事情之一就是使用 Claude 构建缺失的证据，无论是建立生产并行设置、构建重放框架还是编写更多测试。

## **步骤 3：设定晋升策略**

智能体产生更改的速度远远超过任何人类团队逐个差异审查的速度。晋升策略是一个分层审查路径——事先书面记录并达成一致——它设定了更改的人类审查深度，以便现代化可以在可接受的时间线内完成。

与证书一样，与审查者一起完成这一步，并尽可能将其纳入组织现有的变更管理流程。具体细节会因组织和其面临的风险权衡而异，但有一些规则处处适用：

* **按爆炸半径和智能体信心对更改进行分层。** 如果组织有自己的变更或风险分类，请使用它。对关键路径保持完整的人工审查。
* **在源头修复反复出现的标记。** 按时间分组和分析标记的更改。当同一种标记反复出现时，在智能体工作流或证书中修复原因，而不是审查每一个。
* **与审查者一起设计输出格式。** 就哪些信息和格式使审查最快达成一致，哪些信号比其他信号提供更多信心。让他们在步骤 5 中审查早期的样本输出。
* **有效分配主题专家时间**。主题专家不会阅读每个最终差异，但他们的判断仍然是稀缺的投入。让他们能够直接到达最高风险层中的更改，以及每个层中标记的智能体决策，而无需浏览大型差异。少量专家小时数就能覆盖风险最大的更改。

这些规则中的许多通过在项目早期让主题专家参与来前置他们的工时。他们的反馈在全面现代化开始之前调整了证书和智能体工作流。

他们对样本的签字也成为对高信心情况下更轻量审查路径的进一步证明。这与传统的非智能体模式相反，在传统模式中审查发生在最后。

*更改从生成到生产的路径。*

晋升策略还应反映现代化在速度与审查深度光谱上的位置。一个赶在硬性截止日期前的现代化（例如运行时失去支持）需要更快的策略，人类审查更轻量，并明确同意每次更改接受更多风险。

时间线较长的现代化可以承受更深的人工审查和更慢的切换。利益相关者会根据其风险偏好和约束在这个光谱上落在不同的点，因此在工作开始之前锁定它是有价值的。

在受监管的环境中，对任何更改采取更轻量的人工审查路径都可能引起真正的不适。个别批准者犹豫是否签字，因为他们承担糟糕更改的风险，而领导层承担老化系统的更大风险。

根据我们的经验，最好让晋升策略的指令来自组织的最高层。最好事先就达成一致，这样到达生产的 bug 的责任是共享的，而不是压在批准更改的人身上。

> **所有这些都仍然依赖于足够详细的证书，使其能作为真正的证据，以及足够理解 Claude 如何得出更改以信任它的审查者。**

## **步骤 4：落实前提条件**

这一步的许多工作涉及现代化之外的团队：平台或基础设施团队负责主机，QA 或发布工程团队负责测试能力，安全和合规团队负责审批。这些团队中的每一个通常都有自己的积压或审批流程，因此尽早开启对话，一旦确定了需求就进行，通常在步骤 1 至 3 仍在进行时。

### **环境**

* 用于运行工作流的专用远程主机，Claude 可以访问代码库和其他相关资源
* 证书要求的测试能力
* 任何能强化证书的东西：生产遥测、生产并行设置或用于重放的生产数据

### **代码库和 CI/CD**

* 代码库的依赖关系图，基于构建和编译日志；导入分析；或运行时跟踪。注意：插件的*map*命令是一个好的起点，但根据代码库的大小和年龄，可能需要进行更广泛的前期工作
* 作为目标定义的一部分，对任何依赖项或包的计划处理方式
* 如果需要，准备好添加到 CI/CD 的兼容性检查
* 如果要在原地进行现代化，则要有约定的代码冻结策略
* 覆盖任何代码冻结和新兼容性要求的活跃开发人员沟通计划

### **团队和审查**

* 依赖代码库的其他团队就如何参与的协议，例如签署证书或在晋升策略下审查，并预留审查者时间

### **安全和合规**

* 经批准用于源代码的 Claude Code 模型访问路径
* 智能体工作流的最小权限访问：仅写入现代化分支，没有生产凭据
* 现代化分支中的密钥和个人身份信息被清除或掩码
* 每个更改可追溯，PR 链接到智能体转录和证书证据
* 新依赖项的许可证和漏洞检查

## **步骤 5：构建并完善智能体工作流**

使用 Claude Code 开发用于现代化代码库的自定义[动态工作流](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code)。

我们建议从[代码现代化插件](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)开始，将工作流可能需要的一切放在文件系统上或通过 MCP，让 Claude 可以访问。这包括目标、证书、晋升策略、代码库、文档以及证书所需的任何数据源或工具。您也可以将本文作为上下文提供给 Claude。这构成了项目的中央知识库。

有了这些，[构建现代化工作流](https://claude.com/blog/ai-code-migration)就是容易的部分。让主题专家根据需要审查 Claude 的工作，包括任何代码库特定的技能或提取的规则，然后再让下游依赖它们。

通过将其应用于代码库的小部分来完善您构建的内容，让主题专家审查它产生的更改、智能体的过程以及证书被满足的证据。

> 当问题出现时，您应该修改工作流，而不是每个更改。目标是建立信心，一旦扩展，更改几乎在所有地方都会满足证书，审查者会在晋升策略下放心合并。

## **步骤 6：执行现代化**

首先，在代码库的小部分上端到端完成现代化，包括通过晋升策略审查和落地更改。在仍然便宜时修复任何不起作用的东西，重复这个过程直到您有信心，然后扩展到整个代码库。

转换型和重构型现代化涉及在现有系统旁边构建目标，完成后切换，而升级型现代化有第二个选项：在开发继续的同时，在实时代码库上原地进行现代化。

当系统不能停机时，或者当代码库变化如此之快以至于难以保持单独的现代化副本更新时，这是通常的选择。我们看到在这种情况下有效的方法是将代码库从叶子向内分割成逻辑分区；一次冻结和现代化一个分区；并门控 CI/CD，使新提交不能撤销已现代化的分区。

## **关于成本的说明**

我们经常被问到这样的现代化会消耗多少 token。每个现代化工作都不同，但主要的成本驱动因素包括：

* 代码库中有多少需要读取而非更改；
* 证书有多复杂（验证，而非编写更改，通常在受监管环境中占更大份额）；
* 证书要求多少新测试编写和测试修复；以及
* 运行进行时，其他团队在您周围合并产生多少协调工作。

> 当在代码库的小部分上完成现代化时，测量 token 使用量并据此外推整个运行。将试点无法看到的东西（如实时代码库上的协调）视为未知。这样您就可以获得完整现代化成本下限的估算。

试点的测量还显示了在哪里优化智能体工作流以降低成本。找到消耗最多 token 的工作流部分，考虑如何使它们更高效。将计算密集型验证信号移到更便宜的门控后面，这样它们只在更简单的检查通过后运行。

考虑使用像 Sonnet 这样的模型，它们在证书完全检查的机械性、高容量工作上平衡成本和能力。将更智能的模型保留用于困难的转换和验证正确性的对抗性审查。

当较便宜的模型无法满足证书时，您也可以升级到更昂贵的模型，但在试点期间仔细分析重试率，因为几次便宜的尝试可能比一次昂贵的尝试成本更高。如果您给 Claude 访问工作流和试点数据的权限，它可以与您一起完成大部分分析。

## **现代化之后**

现代化的代码库是一个输出。其他输出是产生它的工作流、关于什么算正确的书面证书、您的变更管理流程已经接受的晋升策略，以及每个落地更改的证据链。将 playbook 编码为可重用资产，以便为下一次升级或重写做好准备。
