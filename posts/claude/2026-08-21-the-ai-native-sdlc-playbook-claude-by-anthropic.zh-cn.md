## 代码不再是瓶颈

各组织已开始以一年前难以想象的速度使用AI编写代码，但围绕代码的流程却未能以同样的速度演进。

许多工程团队仍然沿用相同的审批关卡、评审、交接和策略，这阻碍了通过使用类似[Claude Code](https://claude.com/product/claude-code)的智能体编码解决方案所获得的生产力提升。

软件开发生命周期（SDLC）是将软件从想法带到生产环境的过程。大多数组织运行着相同六个阶段的某种版本，涵盖规划、设计、构建、测试、部署和维护软件。传统上，每个阶段都是由不同角色负责的独立环节。产品经理编写需求，技术架构师将其转化为设计，工程师实现设计，受监管企业的QA团队进行验证，发布团队负责交付，运维团队监控运行中的系统。工作通过文档、工单和签核在各阶段之间流转。

传统软件开发生命周期（SDLC）流程繁重，以确保每一步的问责和控制。然而，传统SDLC是在编写和实现代码是最耗时、最昂贵阶段的时代为最大化效率而设计的，而如今情况已不再如此。PRD、估算仪式和产品安全评审的存在，都是为了在可能持续数周、数月甚至数季度的开发工作中强制对齐。

传统SDLC还具有假设每一步都由人类执行的管控机制。产生最大价值的组织已经围绕智能体AI现在能做什么重建了流程，同时确保人类保持在环路中。在本指南中，我们将介绍我们Applied AI团队在SDLC各阶段内部集成Claude的一些最佳实践，以加速开发并让流程运行更快，这些实践源自与客户的合作经验。

当代码不再是瓶颈，构建阶段运行速度超过传统SDLC允许的范围时，三件事将成为现实：

* 瓶颈转移到构建阶段左右两侧的步骤。这主要是规划、评审/测试和部署，这些仍然以人类速度运行。
* 管控机制不再匹配现实，变得难以处理。当代码由人编写时，逐行审查是有意义的，但一旦智能体编写了大部分差异代码，这种方式就无法跟上。
* 治理成本增加，因为例外情况仍然需要通过每周或每月召开的会议和委员会。

构建不再是约束——围绕它的人类速度步骤才是。人类速度阶段保持其时长，而构建则压缩至数小时。

以安全瓶颈为例。安全团队的规模是针对人类产出设计的，因此当智能体成倍增加代码产出时，要么评审队列堆积，要么代码在评审不足的情况下交付。受监管组织无法接受任何一种结果，因此其安全和策略检查必须跟上智能体的速度。

为了更好地实现智能体AI的生产力收益并确保其安全，传统SDLC生命周期需要经历与实现阶段同等程度的转型。

## 什么是AI原生SDLC？

AI原生SDLC是一种重新构想的流程，将旧的管控目标与新的执行方式相结合。该流程不再是线性流转，而是成为一个循环，AI嵌入在每个节点。AI原生SDLC促进了自动化交接和后续实践的触发，有助于解决传统SDLC各阶段之间手动且笨拙的交接问题。

你也会听到这种转变被称为智能体SDLC、AI SDLC，或简称为智能体软件开发——标签不同，但它们描述的是同一件事。

### AI原生SDLC六个阶段的转变

下表展示了由Claude支持的传统SDLC与AI原生SDLC之间的光谱两端。大多数组织位于两列之间的某个位置。

| 阶段 | 传统SDLC | AI原生SDLC |
| --- | --- | --- |
| 规划 | 需求由委员会收集，通过研讨会和签核提炼，手工编写 | Claude直接从源头综合痛点，并将其捕获在`intent.md`中，该文件人类可读且机器可执行 |
| 设计 | 规格由分析师编写，由设计师解析 | 需求和设计压缩为与智能体的单次工作会话，由编码为技能的标准指导，在git中进行版本管理 |
| 构建 | 测试和代码为手写，文档在主开发完成后编写 | 测试和代码由AI生成，机构知识以版本化的机器可读`CLAUDE.md`文件和技能形式维护 |
| 测试 | QA在阶段边界进行门禁 | 持续评估贯穿实现过程 |
| 部署 | 人类审查每一行代码，治理在评审周期中进行，往往不一致 | 多层智能体评审，人类评审保留给受监管和关键代码。治理在AI行动时强制执行，以钩子作为审批门禁 |
| 维护 | 人类监控生产环境中的缺陷 | 智能体监控实时部署。任何被突破的控制带都会被诊断并作为新的`intent.md`写回循环中 |

贯穿右列的主线是已提交的工件。每个阶段以向版本控制提交一个工件结束（包括`intent.md`、`spec.md`、`plan.md`、差异代码及其测试、带有评审发现的PR以及事件记录），下一阶段以读取该工件开始。对于早期阶段，.md文件是主要工件，因为产品负责人和智能体都可以读取并操作同一文件。从构建阶段开始，工件是代码及其记录。提交链也是审计追踪：谁要求了什么、智能体产出了什么、谁批准了什么。

人类仍然对每个需要判断力的决策负责。在智能体SDLC世界中，人类注意力随着需要评审的工件一起转移。

每个阶段都提交一个下一阶段可以读取的工件。意图、规格、计划、差异代码和评审发现共同构成审计追踪。

## 实践

实践是手册的核心，分为六个非线性阶段（规划、设计、构建、测试、部署、维护），共同覆盖完整生命周期。

每个实践涵盖：

* 什么发生了变化；
* 入门指南；
* 实施的具体步骤；
* 治理考量；以及
* 如何衡量是否有效。

这些步骤是模块化的，组织可以根据自身独特需求选择在不同时间优先转型不同阶段。每个实践在“前置条件”下列出其依赖项，依赖关系图进一步说明了这一点。

一个阶段以提交工件结束，该提交触发下一阶段。被接受的`intent.md`触发需求和设计流程，被批准的`spec.md`触发计划模式，合并的PR触发流水线，生产环境中的控制带被突破则写入下一个`intent.md`，如此循环继续。

首先，你手动提示每个步骤，最终状态是一个循环，其中每个被接受的工件触发下一个门禁。人类注意力集中在门禁处，评审智能体标记的内容，而不是从头开始每个阶段。

实践按阶段列出；箭头给出了采用顺序。两者并不相同。从任何“黏土”实践开始——没有箭头指向它，因此它不需要先决条件。对于任何其他实践，指向它的箭头所代表的实践是需要先采用的。

## 规划

想法不再需要等待有人将其写下来。意图被一次性捕获，以发起人自己的语言，作为版本控制的工件供下一阶段操作。

### 捕获为intent.md

启动软件开发流程的`intent.md`可以通过不同途径进入。一个人有想法，提交工单，或通过警报发现事件（参见阶段6：维护）。

当一个人有想法时，他们与Claude进行头脑风暴并生成一个markdown原型规格。在传统SDLC中，同一个人必须说服产品团队成员与他们一起或代表他们编写想法。

由Claude生成的原型规格是人类可读的、版本控制的，并且立即可供下一阶段使用。原型规格保存为`intent.md`。

无论意图是来自事件触发还是智能体，相同的步骤适用：产品负责人在提交之前审查并纠正智能体编写的`intent.md`。

传统一个想法在任何人可以行动之前，需要经过待办事项条目、用户故事、故事点和细化会议。所有权在每次交接时转移，因此到达工程团队的内容与发起人的原始意图已经相隔多个环节。

AI原生发起人与Claude进行头脑风暴，并将结果以`intent.md`形式写下，这是以发起人自己的语言编写的原型规格。该工件包含想要什么、为什么以及在哪些约束条件下。重复流程通过技能进行编码。

入门指南

**前置条件**

无。

**基础设施**

为非工程师人员提供Claude访问权限（claude.ai或[Cowork](https://claude.com/product/cowork)）；商定的`intent.md`模板；一个共享的、版本控制的意图存储位置，由产品负责人监控。对于单一产品，最简单的存储位置是产品仓库中的`intent/`文件夹。这种设置使工件链紧邻由其派生的代码。只有当意图跨越多个仓库时，专门的意图仓库才值得增加开销，而在单体仓库中它只是一个目录。阶段3：构建的侧边栏涵盖了此存储位置与已保存记录的Jira或需求工具之间的关系。

设置这是一次性任务，由平台或工程团队完成。技术团队成员需要建立意图存储位置并决定谁可以写入，因为许多贡献者将来自组织各处。

一旦仓库存在，没有git经验的贡献者不需要直接使用git。相反，连接到版本控制系统（例如GitHub）的连接器让Claude代表他们从claude.ai或Cowork提交markdown文件。

#### 如何执行

1. 发起人用自己的话向Claude描述问题。发起人可以说明目前无法做到的事情、受该想法影响的人群、理想状态应是什么样的，或哪些内容不在范围内。无需使用正式语言。
2. 进行头脑风暴，直到想法具体化。Claude会提出分析师会问的问题：范围、用户、限制条件以及成功的标准是什么。
3. 请Claude使用组织的模板将结果写成`intent.md`，该模板可由技术团队成员编码为技能集，并由负责人签署。这可以涵盖问题、预期成果、受影响的用户和系统、限制条件以及未解决的问题。
4. 发起人纠正Claude误解的任何内容。
5. 将`intent.md`提交到共享的主目录。作者和时间戳会加入记录，产品负责人会从那里接手这个想法。

## 设计

需求与设计在一次会话中完成。策略在编写规格时即被应用，而非在数周后的评审中才发现。

### 需求与设计

经产品负责人批准后，Claude 接收已接受的 `intent.md` 并生成需求与设计规格。此过程由组织的[技能](https://code.claude.com/docs/en/skills)（涵盖品牌、安全、合规及用户体验）指导。

产品负责人评审该规格，但不负责编写。此流程的目标是创建一份工程团队可据此规划的规格，并标注出关注领域。

前端工作是最清晰的示例。一旦 `intent.md` 被接受，产品负责人使用 [Claude Design](https://claude.com/product/design)（测试版）根据 `intent.md` 制作设计原型，迭代完善后导出至 Claude Code 进行构建。

传统方式需求与设计是由不同团队执行的独立阶段。分析师将想法正式化为需求，设计师再将其解析为设计。这种分离是为了问责制，但过程缓慢且信息有损。

AI 原生方式两个阶段在一次提示会话中完成。Claude 接收 `intent.md` 并生成需求与设计规格，受组织技能约束，并标注关注领域。

开始使用

**前置条件**

编写 `intent.md` 文件，并将品牌、安全、合规及用户体验策略编写为技能。

**基础设施**

具备 Claude 访问权限的产品负责人。无需工程技能。

#### 执行方式

1. 产品负责人开启一个会话，加载组织的技能并附加 `intent.md`。
2. 产品负责人的提示指向 `intent.md`，指明约束条件，并要求标注关注点。先手动运行，然后将其固化为组织级斜杠命令。此后，将意图主仓库中 `intent.md` 的接受作为触发器，在合并时触发非交互式任务，加载组织技能运行该流程，并将 `spec.md` 作为拉取请求提交（阶段 5：部署中的 CI/CD 方案涵盖相关管道配置）。从此时起，产品负责人的首次介入即为评审。
3. 同一产品负责人对照原始想法评审规格。该规格是否解决了所述问题？`intent.md` 中的待解决问题是否已解答或延续？
4. 首先处理标注的关注点，因为这些是分析师本会上报的内容。产品负责人在工程团队看到规格之前，与各策略负责人逐一解决。
5. 将 `spec.md` 与 `intent.md` 一同提交。文件对记录了所请求的内容与所决定的内容。
6. 产品负责人决定规格与意图是否进入构建阶段，对于组织归类为较高风险的事项需咨询技术负责人。此决定始终由人类团队成员做出，接受规格即启动阶段 3：构建中的计划模式方案。

#### 实际效果（提示示例）

```
阅读所附的 intent.md，并生成一份将其集成到我们现有代码库中的需求与设计规格。应用你可用的技能，使计划符合我们的品牌指南、安全策略和用户体验标准。将规格完整记录为 spec.md，准备交给工程团队。清晰描述任何关注领域，尤其是无法同时满足相互冲突的策略时。
```

#### 治理考量

实时策略在编写规格时即被读取和应用，而非在数周后的评审中才发现。组织的技能作为约束条件应用于规格。规格、生成规格的提示以及生效的技能版本均记录在版本控制中。产品负责人签署规格，并将标注的关注点转交给指定的策略负责人。

如何衡量

**先行指标**

同一变更的 `intent.md` 提交与 `spec.md` 提交之间的耗时（两个 git 时间戳），与旧的需求加设计周期相比。

**滞后指标**

构建开始后的需求返工。统计同一变更在首个 `plan.md` 提交之后的 `spec.md` 提交数量。Git 日志可直接提供此数据。

## 构建

未经接受的计划不得实施任何内容。机构知识成为代理可读取的文件，护栏以代码而非习惯的形式运行。

### Claude Code 计划模式作为默认起点

工程师以[计划模式](https://code.claude.com/docs/en/permission-modes)启动 Claude Code 会话，向 Claude 提供阶段 2：设计中已批准的 `spec.md`，让其进行访谈式交流，迭代完善计划直至工程师满意。

传统方式工程师阅读设计后直接开始编写代码。变更的实施方式（具体到哪些文件和哪些测试）仅存在于工程师的脑海中，至多是一条工单评论。其他人无法评审。评审者首先看到的是最终差异，此时返工已十分缓慢。

AI 原生方式工作始于 Claude 在计划模式下生成的书面计划，该模式下 Claude 可读取代码库但不会做任何更改。工程师在代码编写前修正计划，批准版本提交为 `plan.md`，供后续阶段对照检查。

开始使用

**前置条件**

意图工件（如存在则为 `intent.md` 或 `spec.md`），`CLAUDE.md` 文件亦有帮助。

**基础设施**

可访问代码仓库的 Claude Code。

#### 执行方式

1. 工程师以计划模式与 Claude 开启会话。
2. 工程师向 Claude 提供 `intent.md` 和 `spec.md`，要求生成一份指明变更文件、工作顺序及验证测试的实施计划。
3. 通过询问变更可能破坏什么、哪一步风险最高、Claude 选择了哪些其他方案来质询计划。
4. 迭代直至从未见过该对话的工程师也能仅凭计划实施变更。
5. 将批准的计划提交为 `plan.md`。计划加入审计追踪，PR 评审方案（阶段 5：部署）将据此检查最终差异。
6. 接受计划并让 Claude 实施。有了扎实的计划，实施通常一次即可完成。
7. 当实施偏离计划时，在同一提交中更新 `plan.md`。可考虑使用钩子强制两者同步。

3. 接入门户导航。

## 风险
claims-core API 速率限制为 50 rps；面板必须进行缓存。

## 验证
test_status.py 覆盖四种理赔状态；截图与已批准原型一致。
```

#### 治理考量

设计评审在任何代码生成之前进行，此时改变方向仍只是编辑文档的问题。计划模式本身即强制执行此流程，因为 Claude 在工程师接受计划之前无法编辑文件。计划及其修订版本连同接受者信息一并记录。常规变更由工程师批准，组织归类为较高风险的事项则交由技术负责人或架构师处理。

如何衡量

**先行指标**

首次实施即合并的变更占比，以及从计划批准到合并 PR 的时间（所需数据包含在 PR 元数据中）。

**滞后指标**

每项变更的返工周期（同样来自 PR 元数据），以及合并后的差异与已提交的 `plan.md` 的匹配频率。

### Claude Code 自动模式

Claude Code 也可在自动模式下运行，工程师批准计划后，在满意并迭代完成后，Claude 无需逐次编辑确认即可应用每项更改。随着后续方案中的护栏日趋成熟（调优的 `CLAUDE.md`、编码策略的技能、阻止不安全操作的钩子，以及 Claude 可运行的测试套件），自动接受成为常规工作的默认方式：紧凑的 `spec.md`、较小的影响范围，以及测试已覆盖的代码。

现在的转变是从用户观察代理进行编辑并审查操作，转向在更长的自主会话后审查工件。自动接受模式结合工作树使用时，可进一步实现个人和团队层面的并行操作，是自主运行 SDLC 及闭环执行阶段 6：维护中所述流程的基础。

侧栏

### 遗留系统与事实来源

*适用于流程产生的所有工件。*

现有 SDLC 流程可能已在追踪工件，只是并非以 Markdown 文件形式。工作项可能在 Jira 中，需求在具备法规可追溯性的工具中，设计在 Figma 中，变更审批由变更委员会处理。这些系统难以替换，因为审计人员和监管机构已接受它们，且其他团队依赖它们，因此 AI 原生 SDLC 必须适应现有环境。

在向 AI 原生 SDLC 过渡时，对于流程产生的每个工件，需指定一个系统作为事实来源，其他系统仅保存副本或指向原件的链接。可通过以下配置实现单一事实来源，且不同工件的选择可有所不同：

**仓库作为事实来源。** Markdown 工件是权威记录，而遗留系统引用提交中的文件。对于工程主导的组织来说，这可能是最简洁的配置之一，因为所有记录都存在于一个工具中，且只有一个时间戳权威。

**遗留系统作为事实来源。** Jira、ServiceNow 或需求工具持有权威记录，而 Markdown 工件是工作副本。Claude 在会话开始时读取记录，并通过 [MCP](https://code.claude.com/docs/en/mcp) 连接器在同一会话中将结果写回，该会话生成了规格或计划。

**链接作为最低标准。** 所有工件都注明记录 ID，且所有遗留记录都包含 Markdown 文件的提交 SHA。在过渡到 AI 原生 SDLC 时，链接是一个不错的起点，同时接受存在两个事实来源的事实。

遗留系统和 Markdown 优先系统可以共存，只要两者之间有链接，或者其中一个被声明为事实来源。

### CLAUDE.md

[`CLAUDE.md`](https://code.claude.com/docs/en/memory) 为 Claude 提供了新成员所需的情境，涵盖约定、命令、架构以及团队最常犯的错误。过去存在于人们头脑中和 Wiki 上的知识，变成了代理在每次会话开始时读取的文件，由整个团队维护，并在每次犯错时进行迭代。

入门指南

**前提条件**

无。

**基础设施**

一个仓库、已安装的 Claude Code，以及一位熟悉代码库的工程师。

#### 如何执行

1. 在仓库中运行 `/init`。Claude 根据发现的内容生成一个初始的 `CLAUDE.md`。
2. 将生成的文件精简到新成员第一天所需的内容。保留构建、测试和 lint 命令、重要的约定，以及 Claude 经常出错的地方。
3. 将 `CLAUDE.md` 提交到仓库根目录的 git 中，以便整个团队共享一个版本，并且更改像代码一样经过审查。
4. 一个有效的规则在这里很有帮助。当 Claude 犯了两次同样的错误时，修正就会进入 `CLAUDE.md`。
5. 保持在一页以内，因为 Claude 在会话开始时读取全部内容，任何过时的信息都在占用上下文而毫无益处。

#### 它看起来像什么（CLAUDE.md）

```

# 支付服务

## 命令
- 构建：make build
- 测试：make test（单元测试），make itest（集成测试，需要 docker）
- 代码检查：make lint（在 CI 中运行；推送前修复）

## 约定
- Java 21，Spring Boot 3。不使用新的 Lombok。
- 金额一律使用 BigDecimal，绝不使用 double。
- 每个端点都需要在 src/itest 中有一个集成测试。

## 架构
- api/ 存放 REST 控制器，core/ 存放领域逻辑，
  adapters/ 与外部系统通信。
- Kafka 事件在 schemas/ 中定义；切勿编辑生成的类。

## Claude 容易出错的地方
- 不要升级依赖版本；平台团队负责管理这些版本。
- 旧版 v1/ 包已冻结；更改应放入 v2/。
```

#### 治理考量

`CLAUDE.md` 受版本控制，因此代理遵循的指令是可审查和可审计的。团队约定通过该文件应用，对其的更改记录在 git 历史中，代码所有者会在 PR 审查中批准这些更改。

如何衡量

**领先指标**

Claude 重复本应由 `CLAUDE.md` 捕获的错误的频率。对 `CLAUDE.md` 的更正或更改应在 git 历史中跟踪。

**滞后指标**

新团队成员从 PR 历史中首次合并 PR 的时间。

### 技能作为机构知识

技能是组织使其机构知识可操作化的方式。指令是明确的、受版本控制的、广泛应用的，并在政策变更时集中更新。经验法则：为必须一致应用的机构知识编写技能；不要为属于 `CLAUDE.md` 或提示的组件编写技能。

入门

**先决条件**

无必需条件。拥有 `CLAUDE.md` 会有所帮助，因为它将代理的工作知识保留在仓库中，但技能并不依赖它。

**基础设施**

一项具有指定负责人和书面事实来源的政策。

#### 如何执行

1. 选择一条当前执行不一致的知识。这可以是安全标准、API 设计约定或品牌规则。
2. 将其编写为技能，即一个包含 `SKILL.md` 的文件夹，其 frontmatter 说明触发时机，正文说明要做什么。工程师根据政策负责人的事实来源编写，并使用 Claude 协助。
3. 将技能放入仓库的 `.claude/skills/<name>/` 中，使其随代码一起发布，或通过[插件](https://code.claude.com/docs/en/plugin-marketplaces)在组织范围内分发。
4. 测试技能是否触发。以不同方式要求 Claude 执行相关任务，并确认技能每次都加载。
5. 当政策变更时，修改技能并让政策负责人签署该更改。
6. 工程师会在下一次会话中自动获取新版本。

#### 示例（.claude/skills/secure-api-review/SKILL.md）

```
---
name: secure-api-review
description: 应用 API 安全标准。在创建或修改面向外部的端点、
  审查 API 代码或生成 OpenAPI 规范时使用。
---
# 安全 API 审查

当您创建或更改 API 端点时：
1. 身份验证：每个端点都需要网关 JWT；
   不允许 /health 之外存在匿名路由。
2. 输入验证：根据 OpenAPI 架构验证请求体并拒绝未知字段。
3. 审计：每个更改状态的端点都会发出包含操作者、操作、实体和时间戳的审计事件。
4. 数据分类：架构中标记为 pii 的字段绝不能出现在日志或错误消息中。

运行 scripts/check-endpoints.sh 并将其输出包含在您的摘要中。
```

#### 治理考量

技能是一种控制，尽管是建议性的。它使 Claude 在编写代码时可能应用政策，但没有任何机制强制会话遵守它。必须始终成立的政策需要技能背后有确定性的东西，例如阻止操作的钩子或在 PR 时重新检查政策的审查环节。技能使违规变得罕见，钩子使其几乎不可能发生。技能调用记录在会话跟踪中，政策负责人像审查代码一样审查技能更改。

如何衡量

**领先指标**

从政策负责人批准政策变更到更新后的技能合并的时间，取自技能文件夹上的 PR。

**滞后指标**

引用政策的 PR 审查发现，一旦技能在编写代码时应用政策，这些发现应趋于零。如果发现没有趋于零，要么技能未触发，要么其文本已偏离官方政策。

### 钩子作为构建时护栏

技能是建议性控制，而[钩子](https://code.claude.com/docs/en/hooks)是其背后的确定性层。Claude 的大部分操作是实施过程中的文件编辑和 shell 命令，因此构建阶段是钩子最常触发的地方。

构建阶段钩子可以：

* 阻止对受保护路径（如生成的类或冻结的包）的编辑；
* 在文件编辑后运行格式化器和代码检查器，使偏差不会累积；
* 防止凭据出现在差异中。

为任何必须无例外成立的政策提供技能支持。钩子在每次匹配的操作上运行，因此构建阶段钩子应快速且限定在更改的文件范围内。更重的检查（如完整测试套件）属于提交或 PR 阶段。

要求人工批准的钩子属于第 5 阶段：部署中的门禁，因为构建期间的批准提示会将人员重新置于所有并行会话的关键路径上。

### 并行会话和子代理

一名工程师可以同时驱动多个工作流。

并行会话是另一个完整的 Claude Code 实例，在其自己的 [git worktree](https://code.claude.com/docs/en/worktrees) 中处理独立任务。每个独立会话对其他会话一无所知，指导它们的工程师是它们唯一的共享点。

[子代理](https://code.claude.com/docs/en/sub-agents)在单个会话内作为具有自己的上下文窗口和工具限制的范围化助手运行，适用于多个任务中重复出现的工作，例如验证应用按预期运行。

并行会话提高了工程师可以同时进行的任务数量，而子代理使每个会话专注于自己的任务。工程师的工作是指导和审查所有这些内容。

传统方式一名工程师一次处理一个任务，并将一天或一周的很大一部分时间花在构建、测试和审查上。等待时切换任务是可能的，但上下文切换足够累人，很少有人选择这样做。

AI 原生方式一名工程师同时运行多个 Claude 会话，每个会话在自己的 worktree 中处理自己的任务。重复的工作成为具有自己的上下文和工具限制的子代理。工程师的工作转向编排，最终转向构建和监控循环。

入门

**先决条件**

`CLAUDE.md`，因为所有会话都会读取该文件。反馈循环（第 4 阶段：测试）在这里也有帮助，因为当会话可以验证自己的工作时，工程师需要的监督更少。

**基础设施**

一个 git 仓库，因为隔离来自 worktrees 和权限设置，这些设置经过调整，使会话不会等待组织认为安全的命令的批准提示。

#### 如何执行

1. 工程师使用计划模式玩法（第 3 阶段：构建）中的计划将工作拆分为涉及不同文件的任务，以查看工作在哪里是独立的。共享文件的任务在单个会话中一个接一个地运行。
2. 每个并行任务都有自己的 worktree，例如在一个终端中 `claude --worktree feature-auth`，在另一个终端中 `claude --worktree fix-rate-limit`。Worktree 是在自己的分支上的单独检出，可防止会话在文件上冲突。
3. 两到三个会话是合理的起点。实际上限是一个人能正确审查多少个流，因此只有在审查跟得上时才添加会话。
4. 将重复的工作转化为子代理，定义在 `.claude/agents/` 中的 markdown 文件中，每个都有名称、何时使用的描述以及可以接触的工具。示例包括：代码简化器（在主代理完成后去除不必要的复杂性）、验证器（运行应用并检查行为）、研究员（探索代码库并报告而不淹没主上下文）。将定义检入 git，以便整个团队共享。

#### 示例（.claude/agents/verifier.md）

```
---
name: verifier
description: 运行应用并检查更改有效，然后会话报告完成
tools: Bash, Read
---
使用 make run 启动应用。测试更改的行为以及两个最近的相邻流程。报告您运行了什么、看到了什么，以及任何与 plan.md 不匹配的行为。不要修复任何内容；仅报告。
```

#### 治理考量

更多会话意味着更多输出，因此控制必须来自仓库中的配置。那里的钩子和权限设置适用于所有会话，会话所做的操作会被记录并归属于运行它的工程师。

如何衡量

**领先指标**

在审查质量保持的情况下，每位工程师的并发会话数，从 OpenTelemetry 导出中统计，以及一天中用于指导而非等待的时间比例。

**滞后指标**

每位工程师每周合并的更改数与根据 PR 历史确定的返工率一起解读。

**04**

## 测试

每个会话在人工查看之前检查自己的工作，指导代理的配置会像其编写的代码一样进行回归测试。

### 给 Claude 一个反馈循环

始终给 Claude 一种验证自己工作的方式，无论是测试、构建还是截图差异。会话在工程师看到之前检查自己的工作并修复自己的错误。

反馈循环不应与验证器子代理（第 3 阶段：构建）混淆。反馈循环在整个任务中根据工作需要运行多次。而验证器子代理是在会话认为工作完成后，通过运行新的上下文窗口来打包最终检查的一种方式。这样，结论不会受到产生代码的假设的影响。

传统方式代码有效的信号来得晚。CI 几分钟后，测试人员几天后，生产环境几周后。当代理产生代码时，延迟的信号意味着人员必须检查其所有输出，而该人员成为瓶颈。

AI 原生方式会话在人员看到之前被赋予检查自己工作的方式。运行测试、运行构建、截图。Claude 迭代直到检查通过，因此到达工程师手中的内容已经通过了检查。设置循环是运行会话的工程师的责任，以下步骤是为他们编写的。

入门

**先决条件**

无。

**基础设施**

一套测试套件和一个构建，各自只需一条命令即可在本地运行。对于界面工作，让Claude看到结果至关重要，要么通过浏览器工具，要么通过MCP接入的截图工具。

#### 如何执行

1. 如果今天检查工作需要一系列命令和一定的环境知识，请将其封装到单个目标中，例如“make test”或“npm test”，并在失败时以非零状态退出。
2. 在`CLAUDE.md`的“命令”部分，列出每条命令，并附上一个健康输出的示例。
3. 设定一个目标并使其可量化，以便Claude无需询问您即可检查工作，例如：“test\_status.py中的所有测试均通过”，“截图与附带的模拟图匹配”，或“端点返回200并包含新字段”。
4. 对于错误修复，先编写失败的测试。请Claude将错误重现为测试，运行它，并确认它因您预期的原因失败。提交该测试。然后才请Claude在不编辑测试的情况下使其通过，并通过最后一步中的测试文件钩子强制执行该限制。修复前就已存在且代理无法重写的测试，是错误已消除的证明。
5. 对于界面工作，通过视觉检查来闭环。给Claude一个浏览器或截图工具，给它模拟图，让它迭代。实现、截图、比较并调整。两到三轮是正常的，结果应每轮都有所改善。
6. 将验证视为“完成”的一部分。指令位于`CLAUDE.md`中。在报告任务完成前运行测试，并显示输出。
7. 最后，循环本身需要保护，因为修复代码的代理绝不能削弱对该代码的检查。在修复任务期间阻止对测试文件进行编辑的钩子可以做到这一点。替代方案是在审查中检查差异，并拒绝任何触及测试的更改。

#### 其外观（CLAUDE.md验证块）

```

## 验证你的工作

- 构建：make build（必须以“构建成功”结束）
- 测试：make test（全部通过；切勿跳过或删除失败的测试）
- 代码检查：make lint（零警告）

在报告任何任务完成之前，运行以上全部三项，并粘贴输出结果。
如果测试失败，请修复代码，而不是测试。
```

治理考量

**强制执行的内容**

在任务报告完成之前进行验证，以及在修复期间阻止代理编辑测试文件的机制，这两者均以钩子的形式在组织希望确保的位置实施。

**证据是什么**

“make test”的字面输出、构建日志或 Claude 运行并粘贴的截图差异，因此证据来自工具链。

**记录位置**

记录在会话记录中，OpenTelemetry 导出会将其转发到组织的可观测性堆栈，同时也记录在 PR 的检查运行中，审查者和任何后续审计者都能看到。

**谁批准**

审查 PR 的代码所有者，由于机械证据已附加，他们可以专注于意图和风险。

如何衡量

**领先指标**

代理编写变更的首次 CI 成功率，CI 系统已支持该指标。

**滞后指标**

每个 PR 的审查时间（来自 PR 元数据），一旦测试捕获了审查者过去捕获的问题，该时间应下降；以及来自事件跟踪器的变更失败率。

### CI 中的持续评估

评估是 AI 原生的阶段门 QA 等效物。在实践中，这意味着每当代理的配置发生变化时，都会运行一套测试套件。当换入新模型或重写提示词时，评估套件会判断代理是否仍以相同标准完成工作。

评估应被视为实时套件。随着模型的改进，曾经具有区分度的案例不再有效，必须根据持续监控添加新的案例。

根据用例的不同，一些团队可能更倾向于按固定节奏离线运行这些评估，而不是在每次变更时运行。以下步骤适用于持续评估。

入门

**先决条件**

`CLAUDE.md` 和反馈循环（阶段 4：测试）。

**基础设施**

能够非交互式运行 Claude Code 的 CI，以及具有评估运行预算的 API 密钥。

#### 如何执行

1. 平台工程师从近期工作中收集 20 到 50 个真实任务及其预期/可接受的结果。
2. 将每个任务编写为评估，即提示词加上定义可接受标准的检查（测试通过、代码检查干净、行为不变、策略遵循）。
3. 该套件在 CI 中按计划非交互式运行，并在 `CLAUDE.md`、技能或钩子发生任何变更时运行，因为该配置引导代理，值得获得代码所获得的回归测试。
4. 根据结果对配置变更设门禁。降低通过率的技能变更在合并前需要经过审查。
5. 每个生产事件都会获得一个评估，由拥有该事件的团队编写，并作为回归测试保留在套件中。

#### 示例（.github/workflows/agent-evals.yml）

```
name: 代理评估
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @anthropic-ai/claude-code
      - name: 运行评估套件
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' $eval)" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
          done
```

#### 治理考量

评估为 QA 提供了一个跟上代理输出的门禁。通过率阈值作为合并检查强制执行，运行会被记录以便随时间比较结果，拥有配置变更的团队批准该变更。

如何衡量

**领先指标**

评估通过率随时间的变化，由套件在每次运行时报告，以及生产事件成为永久评估所需的时间。

**滞后指标**

CI 中捕获的回归与从事件跟踪器得出的生产环境中发现的回归的比较。

**05**

## 部署

审查在两个方向上运行，治理在代理行动时强制执行。代理执行到生产门禁之前的所有操作，不越过该门禁。

### PR 审查循环中的 AI

Claude 既提供审查也接受审查。它根据组织的策略审查传入的 PR，并处理其自身 PR 上的审查评论。这使工程师能够在 PR 审查中专注于行为，即判断意图和风险。

传统方式审查容量围绕人工输出进行规划。PR 等待审查者阅读全部内容，审查质量随审查者的负载而变化，作者在积压增长时不断催促。

AI 原生方式所有 PR 都获得一组相同的审查遍次，发现按严重程度排序。人工注意力提升一个层级，即变更是否符合计划的意图以及风险是否可接受。

入门

**先决条件**

来自阶段 3：构建的更新版 `CLAUDE.md` 文件；如果审查遍次强制执行书面策略，则需要技能、定义的子代理。

**基础设施**

安装了 Claude 集成的仓库，可以是管理员启用的托管 [代码审查](https://code.claude.com/docs/en/code-review)（研究预览）服务，也可以是在您自己的 CI 中运行的 [claude-code-action](https://code.claude.com/docs/en/github-actions)，在需要时通过 AWS Bedrock、Google Vertex 或 Microsoft Foundry 进行模型调用（CI/CD 剧本涵盖部署选项）。要求代码所有者批准的分支保护策略也值得设置。

#### 如何执行

1. 托管代码审查服务是最快的入门方式。管理员启用它并选择仓库。当您需要控制流水线或希望 API 调用通过您自己的云协议路由时，请使用 claude-code-action 在您自己的 CI 中运行审查（CI/CD 剧本涵盖该管道）。
2. 技术负责人将审查策略编写为仓库根目录下的 `REVIEW.md`，分为组织关心的遍次：错误和逻辑缺陷；安全和漏洞；对照规范（来自需求剧本的 `spec.md`）、实施计划（来自计划模式剧本的 `plan.md`）和设计原则的合规性。`REVIEW.md` 还定义了什么是“重要”而非“琐碎”，以及应跳过什么。
3. 技术负责人设置人工阈值。发现本身不会批准或阻止 PR，分支保护仍要求代码所有者批准。希望根据发现门禁合并的平台工程师可以读取检查运行发布的机器可读严重性计数。
4. 当审查者或作者在审查评论中标记 `@claude` 时，Claude 会处理该评论并推送修复。PR 线程记录请求和变更。此修复循环通过 claude-code-action 运行。在托管服务中，评论 `@claude review` 请求新的审查。对于 Claude 打开的 PR，更进一步让 Claude 照看 PR 直至合并。团队将循环封装在自定义斜杠命令中，该命令扫描 PR 上未解决的审查评论和失败的检查，处理它们并推送修复，直到 PR 变绿且仅等待代码所有者批准。
5. 审查发现反馈到 `CLAUDE.md`。当审查第二次标记错误时，更正将作为该审查的一部分进入 `CLAUDE.md`，由于审查读取 `CLAUDE.md`，从下一个 PR 起该错误就会被捕获。审查还会标记变更何时使 `CLAUDE.md` 过时。
6. 每月一次，技术负责人通过评级发现来调整设置，以便审查者改进，并在 `REVIEW.md` 中限制琐碎评论的数量。生成的路径和 CI 已强制执行的任何内容均被排除。

#### 示例（REVIEW.md）

```
# 审查说明

## 遍次
运行三个遍次，并用其遍次标记每个发现：
- 错误：逻辑错误、损坏的边界情况、微妙的回归
- 安全：注入风险、认证漏洞、日志中的 PII
- 合规性：变更符合 spec.md、plan.md 和我们的设计原则

## 此处“重要”的含义
将“重要”保留给会破坏行为、泄露数据或违反策略的发现。风格和命名为琐碎问题。

## 限制琐碎评论
每次审查最多报告五条琐碎评论；其余以计数形式汇总。

## 不报告
src/gen/ 下的生成文件以及 CI 已强制执行的任何内容。
```

#### 治理考量

职责分离得以保留，因为编写代码的代理无法批准它。`REVIEW.md` 中的审查策略应用于所有 PR，发现、修复、评级和批准均记录在 PR 历史中，因此 PR 即审计记录。批准来自通过分支保护的人工，依据发现做出决策。

有关这些控制在生产规模下如何组合，请参阅 [在 Anthropic 保护 AI 原生 SDLC](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)。

如何衡量

**领先指标**

首次审查时间，应降至分钟级别，以及在无需人工直接操作 Git 分支的情况下解决的审查评论比例。

**滞后指标**

合并前捕获的缺陷和漏洞与逃逸到生产环境的缺陷和漏洞的比较，来自 PR 历史记录和事件跟踪器。

### 钩子作为批准门禁

构建阶段使用钩子作为护栏，在无人参与的情况下允许或阻止操作（阶段 3：构建）。钩子也可以询问，暂停操作直到特定人员批准，这正是发布门禁所需。

该剧本位于阶段 5：部署，因为发布门禁是最清晰的用例，但钩子并非部署专属：它们在 Claude 行动的任何地方运行。例如，钩子可以在阶段 3：构建期间阻止在没有变更工单的情况下编辑迁移和基础设施，并在阶段 4：测试的修复任务期间阻止代理编辑测试文件。

入门

**先决条件**

无。

**基础设施**

变更流程所需批准的书面清单。

#### 如何执行

1. 工程领导层与变更管理和合规部门一起，列出必须保留的人工批准门禁，例如变更管理签字、发布授权以及对受保护路径的编辑。
2. 平台工程师将每个门禁表达为钩子，即在 Claude 行动之前运行的脚本，可以允许、询问或阻止。
3. 团队钩子放在 git 中的 `.claude/settings.json` 中，不可协商的钩子放在平台或 IT 管理员拥有的托管设置中，个人工程师无法关闭它们。
4. 阻止应解释自身原因，因此当钩子停止操作时，原因和批准途径会出现在 Claude 的输出中。

#### 示例（.claude/settings.json）

{
    "hooks": {
      "PreToolUse": [
        {
          "matcher": "Bash",
          "hooks": [
            { "type": "command",
              "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/production-gate.sh" }
          ]
        }
      ]
    }
}
```

#### 以及门禁本身（.claude/hooks/production-gate.sh）

```
#!/bin/bash

# 生产部署需要具名的发布授权
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
   if [ -z "$RELEASE_APPROVAL" ]; then
     echo "生产部署需要发布授权。" >&2
     exit 2 # 退出码2阻止该操作；消息会发送给Claude
   fi
fi
exit 0
```

#### 治理考量

钩子是审批闸门。闸门条件每次都会强制执行，对所有人都适用。允许和阻止的决定都会带有时间戳记录。闸门还定义了什么算作批准，无论是已批准的变更工单还是发布经理的签字。

实际示例

### 受监管企业的托管设置

*由平台团队通过MDM或管理控制台部署；工程师无法编辑或覆盖其中的任何内容。*

{
"permissions": {
"deny": [
"Read(.env\*)", "Read(./secrets/\*\*)",
"WebFetch", "Bash(curl \*)", "Bash(wget \*)"
],
"allow": [
"Bash(git \*)", "Bash(make build)",
"Bash(make test)", "Bash(make lint)"
],
"disableBypassPermissionsMode": "disable"
},
"allowManagedPermissionRulesOnly": true,
"sandbox": {
"enabled": true,
"failIfUnavailable": true,
"allowUnsandboxedCommands": false,
"network": { "allowedDomains": ["git.internal.example.com",
"registry.npmjs.org"] },
"credentials": {
"files": [
{ "path": "~/.ssh", "mode": "deny" },
{ "path": "~/.aws/credentials", "mode": "deny" }
],
"envVars": [ { "name": "GITHUB\_TOKEN", "mode": "deny" } ]
}
},
"allowManagedHooksOnly": true,
"disableSideloadFlags": true,
"allowManagedMcpServersOnly": true,
"strictKnownMarketplaces": [
{ "source": "github", "repo": "example-corp/approved-plugins" }
],
"requiredMinimumVersion": "2.1.193"
}

每一行在控制层面带来了什么

`permissions.deny` 将机密信息排除在代理的上下文之外，并通过工具阻止任意的网络出口；`permissions.allow` 预先批准了安全的内循环，这样拒绝列表就不会变成提示疲劳。

`disableBypassPermissionsMode` 加上 `allowManagedPermissionRulesOnly` 意味着没有任何工程师、项目文件或命令行标志可以扩大规则范围。

`sandbox` 弥补了权限无法覆盖的差距。工具层面的WebFetch拒绝并不能阻止shell命令访问网络；操作系统层面的域名白名单直接阻止了出口。

`failIfUnavailable` 和 `allowUnsandboxedCommands` 使沙箱成为一个闸门：当沙箱无法初始化时，Claude Code拒绝启动，而在沙箱内失败的命令不能在沙箱外重试。

`credentials` 弥补了拒绝规则留下的差距。`permissions.deny` 管理Claude的文件工具，但沙箱化的shell命令默认情况下仍然可以读取 `~/.ssh` 或 `~/.aws/credentials`；此块拒绝这些读取，并从每个沙箱化命令的环境中剥离指定的机密信息。

`allowManagedHooksOnly` 意味着本方案中的审批闸门是唯一运行的钩子；本地没有任何东西可以添加或替换它们。

`disableSideloadFlags` 和 `strictKnownMarketplaces` 意味着工程师机器上的每个技能、代理、钩子和MCP服务器都来自组织批准的插件市场，绝不会来自主目录。

`allowManagedMcpServersOnly` 使代理的工具面成为由平台团队拥有的白名单。

`requiredMinimumVersion` 拒绝在低于批准底线的版本上启动，因此这些控制措施由组织实际评估过的构建来执行。

请将以上内容视为可定制的起点，而非照搬的建议。每一次拒绝都会与能力进行权衡，正确的平衡取决于仓库的数据分类。设置参考文档详细说明了每个键，包括仅托管模式的键：[code.claude.com/docs/en/settings](https://code.claude.com/docs/en/settings)

如何衡量（针对钩子本身）

**领先指标**

等待每个审批闸门所花费的时间。每个钩子决定都会写入OpenTelemetry导出，带有时间戳和允许或阻止的判定，因此每个闸门的等待时间都是可见的。

**滞后指标**

从事件跟踪器中，在钩子之前和之后到达生产的闸门违规数量。

### CI/CD集成与部署

在CI/CD流水线中以非交互方式运行Claude Code，对执行进行沙箱化，使长时间运行的代理能够安全运行，通过MCP集成暴露部署能力，并在代理需要它们之前预演回滚路径。

传统流水线运行确定性脚本，任何需要判断的事情都要等待人工处理。例如，对不稳定测试进行分类、编写变更日志，或找出构建失败的原因。部署和回滚是人工在压力下遵循的运行手册。

AI原生Claude在流水线中以非交互方式运行，处理需要判断的步骤，在具有范围限定凭据的沙箱中运行。部署工具通过MCP暴露给代理，因此编写和测试变更的工作流也可以在组织按环境定义的闸门内交付变更并回滚。

入门指南

**前置条件**

Claude参与PR审查循环，钩子作为审批闸门，因为闸门必须先存在，自动化才能加速任何流程通过它们。

**基础设施**

安装了claude-code-action的CI平台，或任何可以调用 `claude -p` 的运行器；通过API或Bedrock、Foundry或Vertex获得模型访问权限（当流量必须保留在组织的云协议内时）；部署目标的MCP服务器；用于代理作业的沙箱配置文件，不包含常驻生产凭据。

#### 如何执行

1. 平台工程师从只读的判断步骤开始。在流水线作业中使用 `claude -p` 对失败的构建进行分类、总结不稳定的测试或起草变更日志。
2. 在现有闸门之后添加写入步骤，用于修复lint、更新生成的文档或通过 `@claude` 提及处理审查评论等作业。代理编写的任何内容都通过分支保护以PR形式到达，代理没有直接推送到main的途径。
3. 执行是沙箱化的。代理作业在具有网络策略的容器中运行，使用短期作用域令牌，默认情况下不持有生产凭据。
4. 通过MCP暴露部署能力。部署、状态和回滚成为工具，按环境进行范围限定，因此代理的部署权限是白名单，而不是带有凭据的shell脚本。
5. 按环境分层自主性。在开发环境中，代理可以自由部署。在生产环境中，代理准备发布，发布经理授权，钩子强制执行生产闸门。预发布环境介于两者之间。
6. 回滚应该是流水线中演练最多的路径，是一个代理可以运行的单一命令，并在预发布环境中定期执行。闭环方案（阶段6：维护）在控制带被突破时调用此回滚，因此必须提前验证。

#### 实际效果（流水线步骤）

```
- name: 对失败的构建进行分类
  if: failure()
  run: >
    claude -p "读取out/build.log中的构建日志。识别最可能的原因，
    说明失败看起来是偶发还是真实问题，并为PR线程写一个
    三行摘要。" >> triage.md
```

#### 治理考量

治理原则是代理可以在生产闸门之前行动，但不能越过它。以下控制措施强制执行此原则。

* 分支保护将代理编写的任何内容变成PR，没有直接通往main的路径。
* 生产部署钩子阻止发布，直到具名的发布经理授权。每次非交互运行都以代理自身的身份行动，因此流水线日志区分了代理所做的事情和触发它的工程师所做的事情。
* 按环境的权限层级设置了代理在通往闸门途中可以执行的操作范围。

如何衡量

**领先指标**

从CI/CD流水线日志中获取的、无需呼叫人工即可分类的流水线故障比例。

**滞后指标**

DevOps研究与评估（DORA）指标，CI系统和部署工具已经会输出这些指标。

**06**

## 维护

循环闭合。触发器在调用路径中没有人工的情况下调用Claude，它发现的内容以 `intent.md` 的形式重新进入流水线。

### 维护与闭环

到目前为止，我们已经讨论了如何在SDLC流程的每个阶段添加Claude，每个阶段都需要人工启动初始步骤。然而，这一阶段将重点转向Claude的自主运行以闭合循环。

例如，一个持续运行的监控代理可以在bug工单创建后，创建 `intent.md`，并流经需求、计划、构建测试和审查阶段。阶段6：维护以无头模式运行，在阶段之间设置独立的置信度闸门，通过确定性检查或对抗性审查代理来决定前一阶段的输出是继续还是升级给人工处理。

传统维护是被动阶段。所有工单或事件都等待人工处理并重新启动流程。凌晨3点触发的警报可能会被错过，工单可能会积压在待办事项中直到有人处理，如果另一个紧急事件先发生，事后复盘的行动可能根本无法到达代码库。

AI原生触发器（如控制带突破、工单、频道消息或计划任务）在没有人工参与路径的情况下调用Claude。Claude进行诊断，仅通过有闸门的路径行动，并将其发现写入 `intent.md`，然后经过上述各个阶段。人工对这项工作进行分类和审查，不再需要启动它。

### 闭环

一个确定性脚本监控生产环境，在控制带被突破时调用Claude。对突破的监控是循环自主运行模式的一个有用示例，而本阶段末尾的[Claude Tag](https://claude.com/product/tag)（公开测试版）部分涵盖了通过不同渠道到达的工作。

入门指南

**前置条件**

`Intent.md` 为循环提供了结构化的输出来重新启动。Claude加速的PR审查、作为行动边界的钩子，以及CI/CD的回滚路径（最高自主层级会调用）。

**基础设施**

检测脚本可以查询的指标存储（Prometheus、CI系统的API或等效物）、对仓库的读取权限、在CI中以非交互方式运行Claude Code的方式，或用于接收webhook的服务的[Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)。

#### 如何执行

1. 服务负责人或平台工程师选择一个具有稳定滚动基线的指标，例如 CI 测试失败率、部署后 5xx 错误率或 PR 周期时间。
2. 他们编写检测脚本，通常是在滚动窗口上计算均值和标准差，并应用规则（Western Electric 或类似规则），使频带既能捕捉缓慢漂移，也能捕捉突发峰值。脚本进行版本控制并附带单元测试，检测过程完全确定性，不涉及任何模型。
3. 响应层级在版本控制的配置中定义（如下面的 `bands.yaml`）。在 1σ 时，脚本仅记录日志；在 2σ 时，它调用 Claude 进行只读诊断；在 3σ 时，Claude 可以采取行动，但仅限于向审查门禁提交 PR 或触发预先批准的运行手册。
4. 触发层可以是 GitHub 或 GitLab 中的定时工作流、现有监控堆栈的 webhook，或网络内部的 Cron Job。Claude 以无状态方式运行，要么作为 CI 运行器上的非交互步骤，要么作为沙箱容器中的 Agent SDK 服务，CI/CD 实践涵盖了部署和模型访问选项。由于运行是无状态且非交互的，循环可以在无人启动的情况下开始和结束。
5. 代理将其诊断以 `intent.md` 形式写入 Stage 1: Plan 格式，涵盖异常及其证据、提议的结果、受影响的系统以及任何未解决的问题。从那里，发现结果像其他任何内容一样通过流水线。
6. 服务负责人或值班工程师对队列进行分类，将面向产品的发现结果路由给产品负责人。立即修复、安排计划或驳回。驳回会调整频带并有助于减少噪音。
7. 当修复发布时，为事件添加一个评估（持续评估实践），以确保此类问题在未来得到保护。

#### 实际示例（例如，一个监控 CI 测试失败率的 bands.yaml）

```
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose,
            routes: [pull_request, runbook:rollback-deploy] }
```

#### 治理考量

层级边界由版本控制的配置强制执行，权限和托管设置禁止生产访问。调用、发现结果和分类决策均带有时间戳记录。服务负责人进行分类和批准发现结果，由此产生的变更通过正常的 PR 审查门禁，代理可能触发的运行手册已事先获得批准。

如何衡量

**领先指标**

从频带违规到分类队列中出现 `intent.md` 的时间，与从事件发生到事后行动的传统时间相比。检测脚本的日志包含违规时间戳和事件层级。

**滞后指标**

成为合并修复的发现结果占比（分类队列与实际 PR 历史对比），以及同类事件的重复发生率，随着修复为评估套件添加案例，该比率应下降。

#### 示例

* 当 CI 测试失败率突破 3σ 时，代理隔离不稳定的测试或开启回滚 PR，由审查门禁决定。
* 当部署后 5xx 错误率在窗口期内突破 3σ 且存在部署时，代理触发现有的回滚流水线。
* 当 PR 周期时间触发漂移规则时，代理为工程领导层撰写报告，表明该机制既适用于流程指标，也适用于生产指标。

检测保持确定性。一旦频带被突破，Claude 即被调用，层级决定其可执行的操作。

### 定期代码库扫描

安全扫描是对特定模型下代码库的时点性陈述，而这两方面都会过时：代码每周都在变化，每一代模型都能发现前一代遗漏的漏洞。AI 原生的解决方案是按计划运行扫描，无需人工介入调用路径，并将发现结果像代码库的任何其他变更一样通过相同的门禁。

[Claude Security](https://claude.com/product/claude-security) 是计划扫描的托管形式。连接 GitHub 仓库后，扫描在 Anthropic 基础设施上使用 Claude Mythos 5 运行，每个发现结果在报告前均经过验证并附有置信度评级。建议的补丁在 Claude Code on the Web 中进行审查和应用。组织无需访问模型本身即可获得发现结果。

传统安全扫描是在发布或审计前启动的一次性事件。报告发送到跟踪系统，积压工作由人工逐步处理，直到下一次事件。期间编写的代码由 PR 审查所捕获的内容覆盖。

AI 原生扫描按计划针对每个连接的仓库运行，使用最先进的可用模型，发现结果在任何人阅读之前即经过验证。每个发现结果的处理方式与突破控制频带相同：适合单个 PR 的修复通过审查门禁，更大的问题则成为 `intent.md`。覆盖范围从上次运行开始计算，而非首次运行。

入门指南

**前提条件**

PR 审查门禁和钩子作为批准门禁（[Stage 5: Deploy](#sd-s5)），确保发现结果像任何其他变更一样经过审查。来自 [Stage 1: Plan](#sd-s1) 的 `intent.md` 格式适用于超出单个 PR 范围的发现结果。

**基础设施**

Claude Security 在公开测试版中可供 Claude Enterprise 组织使用。它需要在目标仓库上安装 Anthropic GitHub App（云托管的 github.com）、启用 Claude Code on the Web、开启额外用量并设置消费限额、为运行扫描的人员配备高级席位，并由管理员在 `claude.ai/admin-settings/claude-code` 开启该功能。扫描按 Mythos 5 费率按用量计费，因此消费限额应与仓库的规模和数量相匹配。

#### 如何执行

1. 安全负责人连接仓库，并按仓库、服务或团队将其组织成项目，以便从一开始就明确发现结果的所有权。
2. 对最关键仓库进行首次完整扫描，包括之前已被其他工具或早期模型扫描过的仓库。将首次扫描视为基线。首次扫描可能会在之前被认为干净的代码中浮现发现结果。
3. 为每个项目设置计划。对于活跃开发的服务，每周一次是合理的默认选择；对于大型或混合型仓库，将扫描范围限定到目录或分支。
4. 在掌握置信度评级的情况下对发现结果进行分类。驳回时附上原因，以便记录驳回决定，同一发现结果不会在下一次运行中作为新问题重新出现。
5. 对于有界发现结果，在 Claude Code on the Web 中打开建议的补丁，进行审查，并像任何其他变更一样通过 PR 审查门禁。提出修复的代理无权批准它。
6. 对于超出单个补丁范围的任何问题，例如架构弱点或跨服务重复的模式，以 Stage 1 格式将其撰写为 `intent.md`，并从 Plan 阶段开始。
7. 当修复发布到生产环境时，为漏洞类别向持续评估实践中的套件添加评估，以便从此以后针对该类别测试引导代理的配置。
8. 将发现结果导出为 CSV 或 Markdown，或使用 webhooks，以保持组织现有的跟踪和审计系统作为审计人员期望的系统记录来源。

#### 治理考量

扫描在组织的管理控制下运行，这意味着连接哪些仓库、谁持有扫描席位以及消费限额均集中设置。每个发现结果都有验证结果和置信度评级，每次驳回都有原因，因此扫描历史是发现、修复和有意识接受内容的审计记录。

修复通过 PR 审查门禁和分支保护到达生产环境，而非直接来自扫描本身。Claude Security 增强了现有的静态分析和依赖扫描。确定性检查保留在 CI 中，模型驱动的扫描覆盖这些检查无法构建的上下文相关漏洞。

如何衡量

**领先指标**

按计划运行的已连接仓库占比，以及从发现结果报告到其补丁进入 PR 审查门禁的时间，从扫描历史和 PR 元数据中读取。

**滞后指标**

计划扫描发现的漏洞与在生产环境或外部报告中发现的漏洞对比，来自事件跟踪系统；以及经过多轮扫描的仓库每次扫描的发现结果趋势，随着修复和评估的积累，该趋势应下降。

### 使用 Claude Tag 进行 Claude 值班

事件也可能通过其他方式到达，例如工作场所通信应用，如 Slack 或 Teams。事件可能表现为晚上 10 点在事件频道中发出的紧急修复 Slack 消息，现在可以立即处理。Claude Tag（目前公开测试版可在 Slack 中使用）使 Claude 以其自身身份成为这些频道的成员，因此每个新事件都有第一响应者，响应本身成为未来事件循环和记忆的一部分。

对话和机构知识保留在频道中，频道中的任何人都可以指导和执行响应。任何团队成员都可以测试假设、探索新选项并实时调查，频道历史增加了可审计性。通过 MCP 访问，Claude 验证指标已回到基线并在线程中确认，将事后分析写入版本控制的经验教训文件中，供未来调查读取。

事件不是 Claude Tag 接手的唯一工作。在 MCP 上被标记到工单或在频道中被询问时，Claude 以相同方式对工作进行分类。小而边界清晰的修复以 PR 形式通过审查门禁，更大的问题则撰写为 `intent.md` 进入 Stage 1: Plan，此时循环开始自我供给。参见：[Claude Tag 如何在 Anthropic 为 CI/CD 提供值班支持](https://claude.com/blog/ai-ci-cd-on-call)。

频道即审计线索：请求、诊断、人工授权和修复都保留在事件处理的地方。

## 结语

模型与工具链已变得更加先进，使组织不仅能够转变代码生产方式，还能重塑整个软件开发生命周期。

这种转变将人的判断力置于流程的核心，并兼顾大型企业组织的治理与监管要求。

本指南汇集了我们Applied AI团队在日常为客户服务中执行的许多真实最佳实践，希望您能从中获得实用且可操作的参考。

循环仍在继续。人的判断力始终高于一切。
