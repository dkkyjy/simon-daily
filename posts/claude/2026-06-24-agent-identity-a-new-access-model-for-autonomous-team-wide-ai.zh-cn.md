# 智能体身份：面向自主化团队级AI的新型访问模型

            **日期：** 2026-06-24 00:00 UTC
            **链接：** https://claude.com/blog/agent-identity-access-model

            ---

            为了让AI智能体在人机协作团队中发挥最佳效能，它需要访问人类所使用的相同工具、文档和上下文。

在"单人"AI体验中（即一人与一个助手对话），这很简单：你连接自己的账户，智能体代表你行事。但在像 [Claude Tag](http://anthropic.com/news/introducing-claude-tag) 这样的"多人"AI体验中，Claude 同时与多人共处一个共享频道，它使用的是属于*工作空间*而非任何个人的工具和上下文。

为了让多人体验顺畅运行，Claude 需要拥有这些工具的专属账户，由管理员设置并与工作空间绑定。我们将这种访问模型称为***智能体身份***。

在本文中，我们将解释智能体身份如何运作，它如何将权限从按用户分配转变为按频道分配，以及如何在您自己的工作空间中合理划定其范围。

## **为什么"以用户身份行事"模式会失效**

当你将AI用作个人助理时，你可以连接 Google Drive、GitHub 和日历等平台，让模型使用*你的*访问权限在这些平台上进行读写操作。

这种模式不适用于 Claude Tag，原因有二：

* **智能体自主性不断增强。** AI智能体能够独立可靠完成的任务时长，大约每四个月[翻一番](https://www.anthropic.com/institute/recursive-self-improvement)。智能体现在可以自主安排后续任务，并在请求者下线很久后响应事件。虽然用户可以设置触发智能体在特定情况下行动的例程，但智能体在很大程度上是自主运行的。

* **多人团队协作。** Claude Tag 将 Claude 置于团队已在协作的共享空间中——例如，一个三位工程师和一位产品经理共同调试问题的频道。但当多人共同指挥时，该采用谁的权限？没有任何单一的人选能始终正确。这使管理员能够独立于人类参与者，定义智能体在 Slack 中能做什么，并对 Slack 中的操作进行独立追踪。

### Claude 以自身身份行事

在 Claude Tag 活跃的频道中，Claude 并非代表单个用户行事。它在所接触的每个系统中都拥有自己的账户：它作为 Claude 应用在 Slack 中发帖，作为 Claude GitHub 应用创建拉取请求，并使用管理员配置的服务账户查询您的数据仓库。

由于不涉及个人用户凭证，共享频道永远不会成为访问他人私人文档的后门。

### 权限继承

在智能体身份模型中，管理员在工作空间层面定义一个身份——即 Claude 在所有地方持有的基础连接和技能集——每个频道默认继承该身份。然后，在合理的情况下，管理员可以在频道层面覆盖它，例如授予工程频道访问 GitHub 和数据仓库的权限，或将 CRM 连接限制在单个私人频道内。

除凭证外，管理员还定义：

* **仓库访问权限：** Claude 可以读写哪些仓库。
* **连接器：** Claude 用于完成工作的工具和 API 密钥。在整个组织中，不同的 API 密钥可以以不同的权限级别连接到同一服务（例如，Claude 可能在普通频道中被授予只读仓库访问权限，在数据团队的私人频道中被授予写入权限）。
* **技能和插件：** Claude 动态加载的指令、脚本和资源文件夹，用于提升在专业任务上的表现。
* **常设指令：** 每个频道的自定义指令和上下文。

由于该模型围绕不同的 Claude 身份运作，撤销该身份将终止 Claude 在所有使用该身份的地方的访问权限。与管理跨数十个用户账户的单个智能体操作审计相比，这大大降低了管理成本。

## 智能体身份模型如何运作

智能体身份将"这个用户能做什么？"的问题替换为"这个智能体在这个隔离区内能做什么？"这与按用户设置的访问控制列表截然不同：这意味着，如果频道的配置文件授予了Claude该权限，那么没有直接仓库访问权限的频道成员可以要求Claude读取该仓库。

这不同寻常，但我们认为这是迈向适用于自主化、多人智能体的访问模型的必要一步。下面，我们概述如何思考设定这些边界。

### 身份边界如何运作

Claude Tag 为每个私人频道创建一个独立的身份；工作空间中的公共频道共享一个工作空间级别的身份。Claude 在法律频道中的身份无法访问未被授予权限的代码，其在工程频道中的身份也无法读取未被授予权限的法律文档。记忆和访问权限都遵循这些边界：Claude 在私人频道中学到的内容永远不会出现在更广泛的工作空间中。

该身份属于频道，因此默认情况下频道中的任何人都可以@提及 Claude，管理员可以将每个频道的配置文件范围限定为权限最低的成员。在企业版计划中，基于角色的访问控制允许管理员进一步决定哪些成员可以调用 Claude，因此频道既能控制智能体可以访问什么，也能控制谁可以发出请求。

### 工具和上下文的广泛默认访问

团队在 Claude Tag 中如何划定 Claude 的工具访问范围：广泛、低风险的集成在共享频道中通过智能体身份运行，而个人或团队专属的工具则保留在私信中以用户身份运行。

在 Anthropic 内部运行 Claude Tag 时，我们发现其价值随着工具和上下文访问权限的增加而倍增。每个连接的系统都让其他系统变得更有用，因为 Claude 可以跨系统整合上下文——从 Slack 中提取线索，从 Drive 中提取文档，从追踪器中提取工单，从数据仓库中提取查询，最终整合成一个单一工具无法提供的答案。

那些从 Claude 中获得最大收益的团队，往往是从一开始就授予其慷慨的访问权限，然后根据组织的管理偏好逐步缩减权限。智能体身份为管理员提供了足够广泛的权限范围，让 Claude 能够进行有用的跨系统工作，同时边界足够牢固，确保访问权限不会扩散到未被授予的地方。我们的建议是：先在几个频道中设置一个基线配置文件，查看审计追踪，然后根据工作需求，一次一个审慎地授予扩展访问权限。

对于需要更细粒度控制的组织，管理员可以在特定频道中禁用 Claude Tag。管理员还可以应用基于角色的访问控制（RBAC），将 Claude Tag 的访问权限限制给特定用户。

### 私信

在 Claude Tag 中，私信的工作方式与共享频道不同。私信使用用户个人的 claude.ai 账户运行——包括他们的连接器、凭证以及结果上的署名。这使得私信成为与 Claude 协作处理那些绝不应出现在频道中的任务和工具的理想场所，例如电子邮件草稿或只有您拥有使用许可的软件。

### 安全与审计

当管理员向频道的配置文件添加连接时，该凭证会被独立存储并映射到该频道的身份，然后在请求时在网络边界注入。任何管理员未允许的主机的出站流量都会被直接阻止。在审计方面，使用智能体凭证进行的每次例程、内存写入和网络调用都会被记录，并且由于 Claude 使用自己的服务账户行事，这些操作也会出现在每个连接系统的日志中。

## 未来展望

智能体身份是 Claude Tag 访问模型的基础。未来，我们计划加强 Claude Tag 的安全功能，包括即时凭证授予——这样用户可以在不永久扩大智能体权限范围的情况下，即时批准单个敏感操作——以及为拥有更复杂权限结构的组织提供身份感知覆盖层。这将在智能体权限范围之上增加用户级别的检查，使得 Claude 仅在频道的配置文件和请求用户的自身权限都允许的情况下才会行动。

从单人AI到像 Claude Tag 这样的多人AI的转变，使得长期运行的团队协作成为可能。智能体身份确保 Claude 对工具的访问权限足够广泛以发挥效用，同时范围足够明确以确保企业级安全。
