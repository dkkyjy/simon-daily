# Harvey、Bolt、Shopify 与 Lovable 测试 Claude Opus 4.6 预发布版本

            **日期：** 2026-02-09 00:00 UTC
            **链接：** https://claude.com/blog/behind-model-launch-what-customers-discovered-testing-claude-opus-4-6-early

            ---

            在[新的 Claude 模型上线](https://www.anthropic.com/news/claude-opus-4-6)之前，一小部分客户会比全世界其他人提前几天获得访问权限。他们与预生产研究模型合作，针对实际工作负载进行测试，以了解该模型擅长什么、在哪里会出问题，以及它是否准备好——在 Anthropic 公开发布的那一刻——交付给他们自己的用户。他们诚实的评估——哪些有效*以及*哪些无效——直接塑造了 Anthropic 最终发布的模型版本。

审查窗口很紧。团队清空日程安排，启动作战室，开始将他们最棘手的问题抛给模型。在幕后，是深夜加班、无数杯咖啡，以及 Slack 频道在奇怪的时间亮起。他们的客户最终看到的是精致的结果——但达到这一目标的过程要混乱得多，也更有趣得多。

在这篇文章中，我们想揭开这个过程的帷幕。[Harvey](https://www.harvey.ai/)、[bolt.new](https://bolt.new/)、[Shopify](https://www.shopify.com/) 和 [Lovable](https://lovable.dev/) 都让我们一窥他们与 Claude Opus 4.6 的早期访问期：他们采取的方法、发现的突破，以及他们在其他人之前学到的东西。

## **为模型测试做准备**

团队如何启动工作很大程度上取决于他们正在构建什么。

[bolt.new](https://claude.com/customers/stackblitz) 启动了一个专用的 Slack 频道，并刻意避免早期分享印象，以免互相影响。

[Harvey](https://claude.com/customers/harvey) 的研究团队邀请了经验丰富的律师来测试模型在法律任务上的表现，同时通过 BigLaw Bench（他们用于现实世界法律工作的基准）运行模型。

[Shopify](https://claude.com/customers/shopify) 的工程师开始将模型输入到他们已经围绕 Claude 构建的迭代规划循环中。

在 [Lovable](https://claude.com/customers/lovable)，负责模型和评估的团队立即启动——运行基准测试，而工程师则预约时间进行他们所谓的“氛围检查”，用新模型构建应用程序以感受它在哪些方面更强。Lovable 的工程主管 Alexandre Pesant 说：“这有点像圣诞节。”

方法各不相同，但直觉是一样的：首先把你最棘手的问题抛给模型。

## **当结果开始出现时**

一旦测试开始，团队会关注两件事：模型在基准测试上的得分，以及它在实践中的*感觉*。两者都很重要，而且它们并不总是告诉你同样的事情。

Harvey 的 BigLaw Bench 结果回来了，达到 90.2%——这是第一个在该基准测试上突破 90% 的 Anthropic 模型，其中 40% 的任务获得了满分。但真正令人印象深刻的是定性的反应。

他们的一位内部律师运行了一个单一查询，回来说输出感觉“聪明且具有分析性，就像它真的在思考一样。”当你的结构化评估和你的主题专家都在说同样的事情时，这是一个强烈的信号。

bolt.new 将他们自动化的评估平台——测试构建质量、错误修复、代码库理解和设计美学——与动手压力测试相结合。到第一天结束时，他们有了一个共享文档，里面装满了已部署的测试应用程序和具体的观察结果。

一位开发者遇到了一个瀑布图错误，之前用之前的模型失败了五次以上。Opus 4.6 第一次就诊断出来了，发现了八个并发的 HubSpot API 搜索同时触发，以及额外的查询通过使用原始 fetch 而不是项目的限速包装器来绕过速率限制保护。

在 Shopify，Staff Engineer Paulo Arruda 描述了一个颠覆了通常动态的时刻：“我让 Opus 4.6 把某个东西从一个页面移到另一个菜单项——我就说了这些。我没有指定任何细节。它不仅移动了它，而且超出了预期，创建了许多我直到看到才知道自己想要的细节。它预判了我的下一个需求，并直接做了。我发现自己对 AI 说‘你完全正确’，而不是反过来，这以前是常态。”

Shopify Assistants 团队的 Staff Engineer Ben Lafferty 则从另一个方向推进。他让 Opus 4.6 将一个大型库从 TypeScript 移植到 Ruby，用于一个内部原型。“它创建了一个填充程序来针对仓库中现有的测试用例运行，然后几乎一次性移植了整个规范，同时对照原始测试集进行验证，”他说。“指令遵循能力显著提升。这是最早的访问期之一，我几乎没有实质性的反馈要给出。”

在 Lovable，测试在两条轨道上运行。

团队运行了设计基准测试和复杂任务评估以获得结构化图景，但他们也执行了他们所谓的“氛围检查”——工程师用新模型构建应用程序，以感受它在哪些方面更强，在哪些方面会出问题。

“发现新的粗糙边缘总是一场竞赛，”Alexandre Pesant 说。

他自己的压力测试是一个涉及复杂地铁地图和行程逻辑的副项目，他之前曾尝试用以前的模型做这个，但碰壁了。使用 Opus 4.6 并开启最大努力，模型突破了他预期会停滞的点。

“我大致知道什么时候事情不会成功，或者我们是否达到了极限，”他说。“它比其他的走得更远。”他还注意到一个更广泛的变化：凭借模型使用浏览器并在 Lovable 内部自行测试的能力，“你可以感受到自主性的差异。”

## **在另一端是什么感觉**

到早期访问结束时，团队对他们正在处理的东西有了清晰的图景。我们采访的每个团队都反复提到同一个观点：与模型的关系正在改变。

“Opus 4.6 第一次就诊断出了我们之前用以前的模型尝试了五次以上都没能修复的错误。推理深度的提升是真实的，”bolt.new 的营销副总裁 Garrett Serviss 说。

“对我来说，Opus 4.6 是 Anthropic 第一个让我在日常工作中感觉像真正协作者的模型，”Shopify 的 Ben Lafferty 说。“我可以交给模型的任务的时间跨度在持续增长。”

“Claude Opus 4.6 在设计质量上是一个提升，”Lovable 的联合创始人 Fabian Hedin 说。“它更加自主，这符合 Lovable 的核心价值观。人们应该创造重要的事物，而不是微观管理 AI。”

当然，并非所有反馈都是赞誉，而这正是重点所在。早期测试者直接告知 Anthropic 最终发布的是哪个版本的模型。整个过程之所以有效，只是因为团队对哪些不起作用与哪些起作用同样坦诚，而且他们知道这种坦诚确实会带来改变。

“我们得以塑造我们的工程组织将要使用的工具的未来，”Shopify 的 Paulo Arruda 说。“我们不是被动的测试者——我们是开发过程中的合作伙伴。当我们识别出问题或模式时，Anthropic 会倾听并迭代。”
