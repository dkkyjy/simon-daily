# 编码会话更长、上下文更多。Claude Opus 5.5 正是为此而生。 | Claude by Anthropic

**日期：** 2026-09-24 00:00 UTC
**链接：** https://claude.com/blog/claude-opus-5-5-built-for-coding-sessions-that-use-more-context

---

我们估算，对于按 Token 计费的典型工作负载，Claude Opus 5.5 的运行成本比 Opus 5 [低约 40%](https://www.anthropic.com/claude-opus-5-5)。对于开发者而言，这些节省具体*如何*累积至关重要。

如果你按 Token 付费，那么在运行时间更长、上下文更多的会话中——这正是过去六个月来越来越普遍的 Claude Code 会话类型——你将看到最大的成本差异。

本文将深入探讨 Opus 5.5 为何对开发者当前的编码方式（以及未来可能的方式）具有成本效益的机制。

## **Claude Code 趋势**

我们收集了 2026 年 3 月至 9 月开发者使用 Claude Code 的聚合数据。随着模型能力的提升，开发者正以越来越复杂的方式部署智能体。每次会话的提示数量保持稳定，但我们发现了一些有趣的行为：

* Claude 在每个提示上花费的时间是原来的 3.3 倍，每个提示的模型调用次数增加了 40% 以上。中断次数减少了 68%。
* 开发者连接工具服务器或使用技能的可能性大约翻了一番，而在提示中粘贴文本的可能性降低了三分之一。
* 每个请求的上下文增长了 2.6 倍。输入与输出 Token 的比例从 189:1 变为 324:1。

所有这些都表明，开发者正将更努力工作、信息更充分的 Claude 指向更大、更开放的任务。对于这类会话，上下文工程的经济影响被放大了。

简单来说，Claude 读取的 Token 更多了。你需要确保[提供的所有上下文都是必要的](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)，并且[尽可能多的上下文是从缓存中读取的](https://claude.com/blog/maximizing-the-value-of-your-claude-code-sessions)。

## **什么使 Opus 5.5 对长而上下文密集的会话具有成本效益**

有三项变化使长时间运行、上下文密集的会话更具成本效益：定价、模型行为和 Claude Code 框架的变化。让我们逐一查看。

### **缓存更便宜**

对于按 Token 计费的用量，我们将输入和输出 Token 的成本降低了 20%，并且*我们将读取缓存 Token 的价格降低了 60%*。后者的降低意义重大，因为缓存读取构成了智能体和编码工作成本的大部分。

正如我们刚才讨论的，每个请求的上下文在六个月里增加了约 2.6 倍，这意味着节省正朝着正确的方向发展。对于按 Token 计费的同一价格变化，在今天 Claude Code 流量上的节省比六个月前更多，因为账单中更多部分是重新读取的上下文。

截至发布之日，Opus 5.5 上的缓存 Token 成本仅为竞争模型的五分之一，同时性能更优。

### **Claude Code 更善于使用缓存**

这不太特定于 Opus 5.5，更多的是过去六个月我们添加的许多 Claude Code 功能的结果。鉴于我们刚才讨论的编码会话趋势，你可能会预期缓存未命中率更高，但事实恰恰相反。**未命中缓存的输入减少了 50% 以上。**

例如，我们使得通过刷新登录等小问题意外破坏缓存变得更加困难。我们还使得通过添加中途指令或按需加载工具等大型操作破坏缓存变得更加困难。对于 Opus 5.5 和 Fable 5.1 等较新模型，你现在可以在会话期间更改努力级别而无需重置缓存。

我们还使缓存对长时间运行和委托的会话更有用。使用 API 密钥和云提供商的开发者现在可以设置一小时的缓存生命周期（订阅者已经拥有），而派生的子智能体从父智能体的缓存开始，而不是再次为相同的上下文付费。

### **相同的任务，但更少的回合**

Opus 5.5 完成相同任务所需的回合可能比其他模型更少。Zeta Labs 发现，与 Opus 5 相比，每个任务的回合数和工具调用次数更少，但成本几乎减半，完成的最困难任务数量却翻了一番。

这不会适用于每个任务。在[Opus 5.5 上一个任务的成本](https://claude.com/blog/what-a-task-costs-on-opus-5-5)中，Addy 写道："在范围明确的任务上，两个模型大约用相同数量的回合完成，你得到的只是价格降低。差距应该在开放式的任务上最大，在那里模型可以在错误的想法上花费许多回合。没有单一的数字适用于每个代码库，所以要测量它。"

换句话说，简单、短小、机械的任务将需要相同数量的回合，而更长、更困难的任务则有更多潜力让 Opus 5.5 避免在错误的方法上燃烧 Token。减少一个回合比缓存一个 Token 更具成本效益。

同样值得注意的是，尤其是随着 Claude 长时间无人值守或不受干扰地工作，Opus 5.5 生成输出的速度比 Opus 5 快 30% 以上。虽然这不会提高缓存命中率或使用更少的 Token，但它意味着在长时间运行上等待的时间更少。

## **保护你的缓存读取**

随着智能体编码的成熟，组织已经从要求开发者不惜一切代价扩展转变为要求开发者高效扩展。在 Claude Code 中运行 /usage 来查看你的用量中有多少是缓存读取。然后保护这个数字：

* 在会话开始时选择你的模型，而不是中途切换，
* 在你离开之前而不是之后进行压缩，以及
* 如果你在使用 API 密钥或云提供商，为长时间会话设置[一小时缓存生命周期](https://code.claude.com/docs/en/prompt-caching#choose-the-ttl-yourself)。

将 Opus 5.5 指向那些习惯会产生复利效应的开放式、上下文密集的工作，并查看[Opus 5.5 上一个任务的成本](https://claude.com/blog/what-a-task-costs-on-opus-5-5)以获取详细数字。
