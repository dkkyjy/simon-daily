上周，我们在 Claude Code 中发布了[动态工作流](https://code.claude.com/docs/en/workflows)。Claude 现在可以即时编写自己的[框架](https://code.claude.com/docs/en/glossary#agentic-harness)，专门为当前任务量身定制。

虽然默认的 Claude Code 框架是为编码而构建的，但它也适用于许多其他类型的任务，因为事实证明，许多任务与编码任务相似。但存在某些类别的任务，我们必须在 Claude Code 之上构建自定义框架才能达到最佳性能，例如[研究](https://support.claude.com/en/articles/11088861-using-research-on-claude)、[安全分析](https://support.claude.com/en/articles/11932705-automated-security-reviews-in-claude-code)、[代理团队](https://code.claude.com/docs/en/agent-teams)或[代码审查](https://code.claude.com/docs/en/code-review)。

工作流允许你在 Claude Code 之上动态创建框架，使 Claude 能够更原生地解决所有这些问题。你还可以与他人共享并重复使用这些工作流。

在本文中，我将介绍我的初始工作流经验和学习心得，以便你能够充分利用。请记住，最佳实践仍在发展之中：动态工作流通常使用更多 token，最适合复杂、高价值的任务。

## 示例提示

在深入技术细节之前，我想先提供几个示例提示，让你思考工作流的可能性：

“这个测试大约每 50 次运行就会失败一次。设置一个工作流来重现它。提出相互竞争的理论来解释竞态条件，直到只有一个理论能经受住证据的考验才停止。”

“使用一个工作流，浏览我最近的 50 个会话，挖掘我不断犯的错误，并将重复出现的错误转化为 `CLAUDE.md` 规则。”

“使用一个工作流，在 Slack 中挖掘过去六个月的事故，找出没有人提交工单的重复性根本原因。”

“拿我的商业计划书，运行一个工作流，让不同的代理从投资者、客户和竞争对手的角度将其撕碎。”

“这里有一个包含 80 份简历的文件夹，使用一个工作流对它们进行排序，后端职位优先，并仔细检查前十名。使用 AskUserQuestion 工具让我面试，以制定评估标准。”

“我需要为这个 CLI 工具起个名字。使用一个工作流集思广益一堆选项，然后运行一个锦标赛选出前三名。”

“使用一个工作流将我们的 User 模型在所有地方重命名为 Account。”

“使用一个工作流检查我博客文章的草稿，并根据代码库验证每一个技术声明。我不想发布任何错误的内容。”

## 动态工作流的工作原理

动态工作流执行一个 JavaScript 文件，其中包含一些特殊函数，用于生成和协调[子代理](https://code.claude.com/docs/en/sub-agents)：

动态工作流还包含标准的 JavaScript 函数，如 JSON、Math 和 Array，以帮助处理数据。

特别有用的是，动态工作流可以决定代理使用哪些模型，以及子代理是否在自己的工作树中运行，从而让 Claude 选择所需的智能水平和隔离程度。

如果工作流被中断（例如由用户操作或退出终端引起），恢复会话将使工作流从中断处继续执行。

## 为什么需要动态工作流

当你要求默认的 Claude Code 框架执行任务时，它需要在同一个上下文窗口中同时进行规划和执行。对于许多编码任务，这非常有效，但在长时间运行、大规模并行、高度结构化和/或对抗性任务中，它可能会失效。

这是因为 Claude 在单一上下文窗口中长时间处理复杂任务时，更容易出现几种特定的失败模式：

*   **代理懒惰**：指 Claude 在完成特别复杂的多部分任务之前就停止，并在取得部分进展后宣布任务完成，例如在安全审查中只处理了 50 个项目中的 35 个。
*   **自我偏好偏差**：指 Claude 倾向于偏爱自己的结果或发现，尤其是在要求其根据评估标准验证或评判时。
*   **目标漂移**：指在经过多次交互后，原始目标的保真度逐渐丧失，尤其是在压缩之后。每次摘要步骤都有信息丢失，像边缘情况要求或“不要做 X”这样的约束可能会丢失。

创建工作流有助于应对这些问题，因为它可以编排独立的 Claude 子代理，每个子代理都有自己的上下文窗口和专注、隔离的目标。

## 动态工作流与静态工作流

你可能之前使用 Claude Agent SDK 或 `claude -p` 创建过静态工作流，以协调多个 Claude Code 实例一起工作。

但由于静态工作流需要适用于所有边缘情况，它们通常更通用。借助 [Claude Opus 4.8](https://www.anthropic.com/news/claude-opus-4-8) 和动态工作流，Claude 现在足够智能，可以编写一个为你的用例量身定制的自定义框架。

## 使用动态工作流时的有用模式

你可以直接要求 Claude 创建一个工作流来开始使用动态工作流，或者使用触发词“`ultracode`”来确保 Claude Code 创建一个工作流。

但是，建立一个关于动态工作流如何工作的心智模型，将帮助你理解何时使用它们，以及如何通过提示来引导 Claude。

在构建工作流时，Claude 可能会使用并组合以下几种常见模式：

### 分类并执行

使用一个分类器代理来决定任务的类型，然后根据任务路由到不同的代理或行为。或者，在最后使用一个分类器来确定输出。

### 扇出并综合

将一个任务分解成许多较小的步骤，在每个步骤上运行一个代理，然后综合这些结果。这在步骤数量很大，或者每个步骤都受益于自己干净的上下文窗口以避免干扰或交叉污染时特别有用。综合步骤是一个屏障——它等待所有扇出的代理，然后将它们的结构化输出合并成一个结果。

### 对抗性验证

对于每个生成的代理，运行一个单独的生成代理，以对抗性地根据评估标准或标准来验证其输出。

### 生成并过滤

就某个主题生成一系列想法，然后根据评估标准或通过验证进行过滤，去重，只返回最高质量、经过测试的想法。

### 锦标赛

不是分配工作，而是让代理在其中竞争。生成 N 个代理，每个代理使用不同的方法尝试相同的任务。然后使用评判代理以两两比较的方式评判结果，直到产生一个胜者。

### 循环直到完成

对于工作量未知的任务，循环生成代理，直到满足停止条件（没有新的发现，或日志中没有更多错误），而不是固定的通过次数。

## 使用场景

创造性地思考何时以及如何要求 Claude Code 创建动态工作流。我发现工作流有时对非技术性工作甚至更有用。

### 迁移和重构

[Bun](https://bun.com/) 使用工作流从 Zig 重写为 Rust。你可以在 [Jarred 的 X 线程](https://x.com/jarredsumner/status/2060050578026189172) 中阅读更多关于如何完成的内容。

关键在于将任务分解为一系列需要操作的步骤，例如调用点、失败的测试、模块等。为工作树中的每个修复生成一个子代理来执行修复，然后让另一个代理进行对抗性审查，并合并它们。考虑告诉代理不要使用资源密集型命令，这样你就可以在机器资源不耗尽的情况下最大限度地并行化。

### 深入研究

我们在 Claude Code 内部发布了一个深入研究技能（`/deep-research`），它使用动态工作流。具体来说，它扇出网络搜索、获取来源、对抗性验证其声明，并综合出一份带有引用的报告。

但是，你进行这种研究可能不仅仅是为了网络搜索。例如，要求 Claude 从 Slack 中的上下文编译一份状态报告，或者深入研究代码库以了解某个功能的工作原理。

### 深度验证

另一方面，如果你有一份报告，想要检查并追溯其中引用的每个事实声明，你可能希望生成一个工作流，让一个代理识别所有事实声明，然后为每个声明生成一个子代理进行详细检查。你还可以有一个验证代理检查来源子代理，以确保其来源质量高。

### 排序

你可能有一个列表项，希望根据你相信 Claude Code 擅长评估的某种定性指标进行排序，例如：按错误严重性排序的支持工单。但是，如果你尝试在一个提示中对 1000+ 行进行排序，质量会下降，而且无法容纳在上下文中。相反，运行一个锦标赛、一个两两比较代理的管道（比较判断比绝对评分更可靠），或者并行地进行桶排序然后合并。每个比较都是自己的代理，因此确定性循环持有括号，只有运行顺序保留在上下文中。

### 记忆和规则遵循

如果你有一组特定的规则，发现 Claude 即使放在 `CLAUDE.mds` 中也会遗漏或难以遵循，可以创建一个工作流，其中包含一个必须由验证代理检查的规则列表——每个规则一个验证代理。创建一个怀疑论者角色子代理来审查这些规则，确保它们合理，这将有助于避免过多的误报。

反向也同样有效：挖掘你最近的会话和代码审查评论，找出你不断犯的错误，用并行代理将它们聚类，对抗性地验证每个候选规则（这条规则本可以防止一个真正的错误吗？），然后将幸存下来的规则提炼回 `CLAUDE.md`。

### 根本原因调查

调试时，最好提出几个独立的假设并进行测试，但如果你只使用一个上下文窗口，Claude 可能会陷入自我偏好偏差。

工作流可以通过生成从不相交的证据中提出假设的代理来从结构上防止这种情况。例如，为日志、文件和数据分别设置单独的代理。然后每个假设可以面对一组验证者和反驳者。

这不仅适用于代码。工作流可用于销售（为什么三月份销售额下降了？）、数据工程（为什么这个管道失败了？）或任何事后分析。

### 大规模分类

每个团队都有支持队列、错误报告或其他人类无法完全处理的后台任务。

一个分类工作流对每个项目进行分类，与已经跟踪的项目去重，并采取行动。这可能意味着尝试修复或升级到人类用户。

分类工作流的一个有用模式是隔离。这意味着禁止读取不受信任的公共内容的代理执行高权限操作，这些操作由负责对信息采取行动的代理执行。

将分类工作流与 `/loop` 配对，让 Claude 持续执行此操作。

### 探索和品味

工作流在探索不同解决方案时很有用，尤其是当它基于品味（如设计或命名）时，并且会受益于评估标准。

尝试要求 Claude 探索一堆解决方案，并向审查代理提供一个评估标准来描述一个好的解决方案是什么样的。当审查代理认为它达到了标准时，任务完成。解决方案还可以通过基于评估标准的锦标赛进行排序或选择。

### 评估

你可以为特定任务运行轻量级评估，方法是在工作树中生成单独的代理，然后生成比较代理来比较并根据评估标准对特定输出进行评分。例如，根据特定标准评估然后完善你创建的技能。

### 模型和智能路由

创建一个针对你的任务调优的分类器代理，用于决定使用哪个模型。当你的任务将涉及许多工具调用，并且在执行之前进行研究可以确定最适合该工作的模型时，这很有帮助。

例如，对于“解释认证模块如何工作”这个任务，最佳模型取决于认证模块中的文件数量以及代码库的形状。一个分类器代理可以进行这项研究，然后根据预期任务复杂度路由到 Sonnet 或 Opus。

## 何时不使用动态工作流

工作流是新的。虽然存在许多用例可以产生超乎寻常的结果，但它们并非每个任务都需要，并且最终可能会使用更多的 token。

最好创造性地使用工作流，以你以前未曾用过的方式推动 Claude Code。对于常规的编码任务，试着问自己：它真的需要更多的计算吗？例如，大多数传统的编码任务不需要一个由 5 位审查员组成的小组。

同样的判断标准在更高一层的架构层面也适用：[多代理与单代理](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)的决策遵循类似的逻辑——并行性和专门化必须证明其协调成本是值得的。

## 构建动态工作流的提示

### 提示技巧

对动态工作流使用详细的提示，特别是我们上面描述的具体技巧，可以产生最佳结果。

工作流不仅适用于大型任务。你可以提示模型使用“快速工作流”。例如，你可以快速创建一个对抗性审查来验证一个假设。

### 结合 `/goal` 和 `/loop`

当使用可以重复的工作流时（例如分类、研究或验证），将它们与 `/loop` 配对以按固定间隔运行，并与 `/goal` 配对以设置硬性完成要求。

### Token 使用预算

你可以为动态工作流设置显式的 token 使用预算，以限制一个任务使用的 token 数量。你可以用预算提示它，比如“使用 10k token”，这将设置上限。

### 保存和共享动态工作流

你可以通过在工作流菜单中按“s”来保存工作流。你可以将它们检入 `~/.claude/workflows` 或通过技能进行分发。

要通过技能共享它们，请将你的 JavaScript 工作流文件放在技能文件夹中，并在 [SKILL.MD](http://skill.md) 中引用它们。为了允许更大的灵活性，你可能希望提示 Claude 将技能中的工作流视为模板，而不是需要逐字运行的脚本。
