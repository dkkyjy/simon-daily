# Auto 模式现已成为 Claude Code 中 Pro、Max 和 Team 套餐的默认设置 | Claude by Anthropic

**日期：** 2026-08-07 00:00 UTC
**链接：** https://claude.com/blog/auto-mode-default-in-claude-code

---

我们正在将 [auto 模式](https://code.claude.com/docs/en/auto-mode-config) 设为 Claude Code 的默认设置。从 8 月 14 日起，Pro、Max 和 Team 套餐上的新会话将以 auto 模式运行。如果你已经自行设置了其他默认模式，你可能会收到一次提示，询问是否要切换到 auto 模式。如果你固定了默认设置，则一切保持不变。auto 模式分类器每次工具调用会使用少量额外 token，而我们从今天起不再向 Pro、Max 和 Team 套餐上的 Claude Code 用户收取该分类器的开销费用。

Auto 模式目前在 Claude Enterprise、Claude API、AWS 上的 Claude Platform、Amazon Bedrock、Google Cloud 的 Agent Platform 以及 Microsoft Foundry 上仍为可选启用，以便管理员有时间审阅这一变更。在接下来的一个月里，我们将与云合作伙伴合作，计划在所有上述平台中将 auto 模式设为默认，并停止收取分类器开销费用。与此同时，Enterprise 管理员可以通过托管设置将 Claude Code 的 auto 模式设为默认。

Auto 模式旨在平衡用户不希望被打断的需求与一个有助于避免有害操作的系统：它不再弹出提示，而是将每次工具调用路由至一个分类器，该分类器专门用于阻止不可逆、具有破坏性或针对你环境之外的操作。当分类器阻止某项操作时，Claude 通常会自行找到更安全的处理方式，或直接向你请求许可；如果它无法取得进展——连续三次被阻止，或一次会话中被阻止二十次——Claude Code 将回退到手动审批模式。

在过去的几个月里，我们测试了 auto 模式是否与普通用户点击提示一样安全或更安全。我们进行了内部红队测试、第三方红队测试和提示注入评估、一项包含 1,053 名付费测试者的对照研究，以及对真实生产会话的分析。在我们测试的每项指标上，auto 模式都达到或优于手动审查。

Auto 模式还让 Claude 能够更长时间地自主工作。这使得为长时间运行工作而设计的模型（如 Claude Opus 5）在大型任务上连续运行数小时变得更加实用。减少用户的额外操作也提高了产出。在 Teams 和 Enterprise 采用者中，auto 模式用户提交的 PR 数量大约多出 25%。解除对 Claude 的限制使其能够更长时间不间断地运行任务，完成更多工作。Adobe、Nuro、Gusto 和 Garner Health 的团队已经将 [auto 模式](https://claude.com/blog/auto-mode-in-production) 作为其生产默认设置。

下面，我们分享推动这一变更的安全数据和客户结果，以及如果你更倾向于其他设置，如何更改默认模式。

## 比较手动审查与 auto 模式

数据表明，手动审查可能变成一种习惯：用户在 Claude Code 中批准了 97% 的权限提示。虽然大多数提示可能针对安全、常规的命令，但如此高的批准率表明许多用户是反射性地点击通过，而不是逐一审查每条命令。这些提示要求开发人员每天做出数十甚至数百个重要的安全决策，通常是在项目进行中，这给用户带来了审查负担，并增加了重要事项被遗漏的风险。数据还表明，用户更频繁地审查并拒绝其他类型的对话：例如，当 Claude 提出计划供批准时，用户拒绝了其中的 39%。但对于单个权限请求，拒绝率仅为 3%。

同样的模式也出现在设置文件中。截至 2026 年 6 月，49.5% 的活跃 CLI 用户手动创建了 Bash 允许规则——5% 直接允许任何 shell 命令，另有 43% 拥有诸如 `Bash(python:*)` 或 `Bash(node:*)` 之类的解释器规则，这些规则在实践中基本等同——而且这一比例大约每 5 周增长 5 个百分点。除了允许规则之外，62% 的用户使用过 `bypassPermissions` 或点击过 Bash 上的“不再询问”，25% 的交互式会话以绕过权限模式开始。

在 auto 模式下，权限规则仍会在分类器之前触发，但那些宽泛到足以授予任意代码执行的允许规则（例如 python:\*）除外。这些任意规则在 auto 模式下会被暂时搁置，因为它们会让命令完全跳过分类器。设置文件不会被修改，当你切换到其他模式时，这些规则会立即重新生效。

## 通过 auto 模式提升安全性

内部及多个第三方进行的研究表明，auto 模式比用户当前与权限提示互动的方式更安全。我们测试了 auto 模式与开发人员在点击权限提示时实际批准的内容之间的对比。在以下各项指标中——内部红队测试、第三方渗透测试和真实会话分析——auto 模式都达到或优于人工批准。

### Auto 模式在安全性上优于手动权限

*在一项包含 1,053 名付费专业测试者的对照实验中，人工审查仅捕获了 13.6% 的危险命令，而 auto 模式捕获了 89%。*

我们通过一家研究供应商聘请了 1,053 名付费测试者参与一项编码研究。这些参与者在一个专门为研究设置的测试环境中工作，而不是在他们自己的代码库或真实项目中。参与者知道他们正在接受评估，但——按照标准的盲测设计——并未被告知正在测量哪种行为。在每次会话进行到中途时，一个权限提示被替换为一条明显危险的命令，供应商记录测试者是否批准了该提示（注意：批准提示从未导致任何危险操作被执行；只有测试者看到的提示文本被更改）。

测试者仅在 13.6% 的情况下捕获了危险命令（1,053 次中的 143 次），而 auto 模式阻止了相同命令中的 89%（1,053 次中的 937 次）。正面交锋中，auto 模式阻止了 800 条被人类批准的命令，而人类仅阻止了 6 条被 auto 模式放行的命令。随着会话变长，人类的表现更差：他们在会话早期阻止了约 17% 的危险命令，在 50 次或更多先前提示后降至约 5%，而 auto 模式的阻止率无论会话长度如何都保持稳定。

### Auto 模式能防止更多有害操作

我们的研究还表明，auto 模式比手动权限模式导致的有害操作更少。

我们考察了 auto 模式在真实使用中的表现。从 2026 年 5 月到 6 月，我们检查了安全管道标记为需要审查的会话，这些会话仅来自已选择允许将数据用于训练和分析的账户。我们使用一个模型在 0–10 的两个量表上对每个会话重新评分。第一个是危害严重程度，10 分代表公司范围内的不可逆危害，例如泄露公司的全部源代码，7 分代表生产级严重程度，例如删除生产数据库中的行，0 分代表仅限于本地工作区的完全可逆操作，例如覆盖一个临时文件。第二个是用户明确要求该操作的程度，以便我们将用户直接要求的有害操作与代理在指令不太明确的情况下采取的有害操作区分开来。

在被标记的会话中，经过手动审批的会话包含严重意外危害的频率是 auto 模式会话的两倍以上。在生产级严重程度（7 分及以上）下，6.3% 的手动审批会话包含用户未明确要求的危害操作，而 auto 模式会话中这一比例为 2.4%，并且在我们测试的每个严重程度级别上差距都持续存在。

### 对抗性红队测试使 auto 模式更加强大

我们与总部位于英国的 AI 安全初创公司 Apollo Research 合作，开展了一项为期两周的试点项目，将合成攻击注入真实的编码轨迹中，涵盖三个数据集，涉及广泛故障、数据外泄和安全相关威胁。

此次合作遵循了标准的“发现-修复-验证”循环。Apollo 分享了一组成功的攻击以及加强 auto 模式的建议。我们主要通过为其提供更多关于其所保护环境的信息（仓库可见性、git 状态以及下文所述的数据处理规则）来强化分类器以抵御这些攻击。

强化后，Apollo 在一个我们从未访问过的独立保留攻击集上重新测试。Auto 模式捕获了之前遗漏的攻击中的约一半，代价是遗漏了之前捕获的攻击中的约 2%。由于我们无法针对保留集进行调整，这表明强化能够泛化到新的攻击，而不仅仅是修补 Apollo 分享的特定攻击。在共享集和保留集上，分类器的漏报率从 12% 降至 7%。

这些攻击是合成且刻意对抗性的，旨在找出分类器的失败点，比 Claude 在无提示情况下会做的任何事情都更具恶意。7% 的漏报率是针对该集合测量的，不应被视为真实流量上的漏报率。

### Auto 模式降低了提示注入风险

*启用 auto 模式后，在独立评估中，没有任何攻击能够成功针对我们的任何模型。在 Codex v0.144.5 Auto-review 权限模式下运行的 GPT-5.6 Sol 的攻击成功率为 5.83%。GPT-5.6 Sol 以“最大”推理努力运行，以测试其最高推理水平下的性能，所有 Claude 模型均以高努力运行。*

Auto 模式分类器为抵御试图迫使代理偏离用户指令的[提示注入攻击](https://www.anthropic.com/research/prompt-injection-defenses)增加了一层额外防御。在 auto 模式下运行时，工具结果会由探针扫描以查找潜在的恶意指令，并且 auto 模式会检查操作是否与用户意图一致。我们将 auto 模式与无防护模型进行了对比测试，以展示这种纵深防御方法的威力。

我们委托第三方 Trajectory Labs 进行了一项评估，他们测试了截至 2026 年 7 月 17 日 Claude Code 和 Codex 最新公开版本中的不同模型。¹ 他们测试了 72 个对 Anthropic 保密的间接提示注入场景。每个场景测试了 10 次。成功的攻击在非测试环境中将导致可能伤害用户的不可逆操作，例如敏感数据外泄、金融欺诈或凭证钓鱼。这些攻击是针对 Claude Opus 4.7 优化的，而该模型不在报告集中，因此评估中的每个模型都将这些攻击视为未见过的攻击。除了 auto 模式外，评估还考察了 Claude Code 的 *bypassPermissions* 模式和 Codex 的 *Full Access* 模式。

Codex 和 Claude Code 均使用 Trajectory Labs, PBC 生产的相同浏览器集成进行评估。该集成提供一组 MCP 工具，这些工具是常见 Chrome API（如 `navigate`）的轻量封装。未测试 OpenAI 和 Anthropic 提供的 Chrome 扩展等第一方浏览器集成中内置的安全防护。因此，这些结果应被视为对底层模型的测量，而非对特定部署中可能存在的完整安全防护措施的测量。

**在此次评估中，针对以自动模式运行的 Claude Fable 5、Opus 5 或 Sonnet 5 的 720 次攻击尝试均未成功。** 另一方面，5.83% 的攻击成功针对以 Codex *自动审查* 模式运行的 GPT-5.6 Sol。值得注意的是，这高于我们最新模型在 *bypassPermissions* 模式下运行且无额外防护时 0.09% 的平均攻击成功率。测试显示，GPT-5.6 Sol 在 *完全访问* 模式下运行时，攻击成功率为 19.03%。如下所示，工具以文本形式返回结果的任务与需要通过截图与浏览器交互的任务之间的攻击成功率有所不同。

*自动模式可防止工具调用和浏览器 GUI 使用中的提示注入。在第三方评估中，OpenAI 模型在浏览器任务中表现出更高的攻击成功率。*

### 自动模式在 Anthropic 内部阻止的三起事件

自动模式也是 Anthropic 内部所有 Claude Code 使用的默认模式。以下是分类器在内部阻止的三个操作：

* **网络外数据泄露：** 当上传到内部驱动器失败时，Claude 的回退方案是将同一报告发布到公共代码共享站点。自动模式拒绝了该回退方案，并提示用户进行后续步骤。
* **破坏性大规模操作：** 在长时间运行的会话中，Claude 尝试跨约两千个 pod 进行大规模进程终止，并排队删除操作，这将拆除数百个 GPU 正在进行的训练任务。自动模式在执行前标记了这些破坏性命令。
* **过度宽泛的权限提升：** 当被要求配置只读计费访问权限时，Claude 选择了一个在账户根级别授予完全管理控制的云角色。自动模式发现了请求内容与实际授予角色之间的不匹配。

在每种情况下，Claude 要么自行找到更安全的路径，要么在继续之前与用户确认。

### 让自动模式更加安全

我们持续投资于新的自动模式功能，使其更安全、更易于交付生产代码。近期示例包括：

* [**硬性拒绝**](https://code.claude.com/docs/en/auto-mode-config#override-the-block-and-allow-rules)：数据外泄（例如将代码或机密发送到外部）属于分类器设计为永不批准的一类操作。要执行此类操作，您必须退出自动模式或自行运行命令。硬性拒绝规则可通过设置自定义，以便添加您永远不希望被允许的更多规则，即使组织中的用户提出请求也是如此。
* **数据访问和共享规则：** 分类器现在携带明确规则，区分机密和潜在敏感/机密信息——以及每种信息可以在何处访问和共享。为使这些规则可执行，它还会在操作运行前检查 git push 或 pull request 的目标是公共、私有还是受信任的。同一推送可能是常规操作，也可能是外泄，具体取决于其目标位置：属于团队私有仓库的代码不应最终出现在公共仓库中，分类器现在设计用于在可能发生这种情况时进行标记。
* **在破坏性 git 操作前检查 git 状态：** 在执行可能丢弃未提交工作的命令（如 `git reset --hard`）之前，分类器会查看仓库当前的 git 状态，让自动模式知道正在重置什么。
* **提示注入筛查：** 当 Claude 从外部来源（如网页、文件内容或工具输出）提取内容时，API 端探针会检查该内容是否存在劫持 Claude 行为的尝试。当某些内容看起来像注入尝试时，会在结果与用户共享之前向 Claude 的上下文添加警告。

## 生产环境中的自动模式

各团队已将自动模式作为其生产环境的默认设置：

* **Adobe** 的电商平台团队负责确保 Adobe.com 上 90 多个国家和 30 多种语言的定价及促销页面准确且最新。他们构建了一个代理循环来创建并验证这些页面，并以自动模式运行，使工程师能够收到已完成的 PR 以供审查。
* **Nuro** 在其研究和工程组织中全面运行自动模式，利用它驱动夜间研究代理，这些代理会逐步优化评估指标，并在次日早晨返回已完成的 PR 供审查。
* **Gusto** 采用自动模式来消除权限疲劳，这种疲劳曾促使工程师完全绕过权限检查。自五月中旬以来，约有 10% 的会话包含分类器拒绝——这证明它在执行实际工作的同时，并未拖慢合法任务的速度。
* **Garner Health** 通过托管设置将自动模式作为默认选项推广给全部 550 名员工，从而标准化了公司范围内的软件开发生命周期（SDLC），不再依赖手工维护的命令允许列表。
