# 循环入门

            **日期：** 2026-06-30 00:00 UTC
            **链接：** https://claude.com/blog/getting-started-with-loops

            ---

            目前有很多关于"设计循环"而非提示编码代理的讨论。如果你花些时间在X上试图弄清楚循环到底是什么，你会遇到多种不同的答案。

在Claude Code团队中，我们将**循环定义为代理重复工作周期直到满足停止条件**。我们根据以下几点对不同类型的循环进行分类：

* 触发方式
* 停止方式
* 使用的Claude Code原语
* 最适合的任务类型。

我们将介绍主要的循环类型、每种类型的使用时机，以及如何在管理令牌使用量的同时保持代码质量。并非所有任务都需要复杂循环；从最简单的解决方案开始，并有选择地使用这些模式。

## **回合制循环**

* **触发方式：** 用户提示。
* **停止条件：** Claude判断任务已完成或需要更多上下文。
* **最佳用途：** 不属于常规流程或计划的较短任务。
* **使用管理方式：** 编写具体提示，并使用技能改进验证以减少回合数。**

您发送的每个提示都会启动一个手动循环，由您指导每个回合。Claude收集上下文、采取行动、检查工作、必要时重复，然后响应。我们称之为代理循环。

例如，让Claude创建一个点赞按钮。它会读取您的代码、进行编辑、运行测试，然后返回它*认为*可行的结果。然后您手动检查工作，并编写下一个提示。

您可以通过将手动步骤编码为SKILL.md来改进验证步骤，使Claude能够端到端地检查更多自身工作。这应包括允许Claude*查看*、*测量*或*与*结果交互的工具或连接器。检查越量化，Claude自我验证就越容易。

例如，在您的SKILL.md文件中，您可以指定：

```
--- 
name: verify-frontend-change 
description: 在声明完成之前，端到端验证任何UI更改。 
--- 

# 验证前端更改 
切勿仅凭成功编辑就报告UI更改已完成。请像人工审查员一样验证：

1. 启动开发服务器，在浏览器中打开已编辑的页面。

2. 直接与更改交互。对于新控件（按钮、输入框、开关）：点击它，确认预期的状态变化，并截图前后对比。

3. 检查浏览器控制台：零个新错误或警告。

4. 使用Chrome Devtools MCP，运行性能跟踪并审计核心网页指标。

如果任何步骤失败，请修复问题并从步骤1重新运行——不要交回部分验证的工作。
```

## **基于目标的循环 (/goal)**

* **触发方式：** 实时手动提示。
* **停止条件：** 目标达成或达到最大回合数。
* **最佳用途：** 具有可验证退出标准的任务。
* **使用管理方式：** 设置具体的完成标准和明确的回合上限，"5次尝试后停止"。

有时，单个回合是不够的，尤其是对于更复杂的任务。代理在能够迭代时表现更好。您可以通过使用/goal定义完成状态来延长Claude持续迭代的时间。

当您定义成功标准时，Claude不必自行判断什么是"足够好"并提前结束循环。每次Claude尝试停止时，评估器模型会检查您的条件，并将其送回工作，直到目标达成或达到您定义的回合数。

这就是为什么确定性标准（如通过的测试数量或达到特定分数阈值）如此有效的原因。

例如：

```
/goal 将首页Lighthouse得分提升至90或以上，5次尝试后停止。
```

## **基于时间的循环 (/loop 和 /schedule)**

* **触发方式：** 指定的时间间隔。
* **停止条件：** 您取消它，或工作完成（PR合并、队列清空）。
* **最佳用途：** 适用于重复性工作，或与外部环境/系统交互。
* **使用管理方式：** 设置更长的间隔，或根据事件而非时间做出反应。

某些代理工作是重复性的：任务保持不变，只有输入发生变化。例如，每天早上总结Slack消息。其他工作依赖于外部系统，与之交互的一种简单方法是按时间间隔检查并对其变化做出反应。例如，可能收到代码审查或CI失败的PR。

对于这些情况，您可以使用`/loop`触发Claude运行，该命令按时间间隔重新运行提示。例如：

```
/loop 5m 检查我的PR，处理审查评论，并修复失败的CI
```

`/loop`在您的计算机上运行，因此如果您关闭计算机，它就会停止。您可以通过使用`/schedule`创建例行程序将循环移至云端。

## **主动循环**

* **触发方式：** 事件或计划，无需实时人工参与。
* **停止条件：** 每个任务在目标达成时退出。例行程序本身会一直运行，直到您将其关闭。
* **最佳用途：** 重复性的明确定义工作流：错误报告、问题分类、迁移、依赖升级等。
* **使用管理方式：** 将例行程序路由到更小、更快的模型，并使用最强大的模型进行判断。

上述原语，连同其他Claude Code功能（如**自动模式**和**动态工作流**（研究预览））可以组合成一个用于长期运行的循环。

例如，要处理传入的反馈，您可以使用：

1. **`/schedule`**（研究预览）运行一个检查新报告的例行程序
2. **`/goal`** 定义完成状态，以及**技能**记录如何验证
3. **动态工作流**编排代理对每个报告进行分类、修复并审查修复
4. **自动模式**使例行程序无需停下来请求许可即可运行

综合起来，提示可能如下所示：

```
/schedule every hour: 检查 #project-feedback 中的错误报告。 /goal: 不要停止，直到本次运行中找到的每个报告都被分类、处理并回复。修复错误时，使用工作流在并行工作树中探索三种解决方案，并让一个评判者对抗性地审查它们。
```

## **保持代码质量**

循环输出的质量取决于其周围的系统。在设计系统时：

* **保持代码库本身的整洁**：Claude遵循代码库中已存在的模式和约定。
* **为Claude提供验证自身工作的方法**：通过[技能](https://code.claude.com/docs/en/skills)为您和您的团队编码"好"的标准。
* **使文档易于获取**：框架和库文档包含最新的最佳实践。
* **使用第二个代理进行代码审查**：具有新上下文的审查者偏见较少，且不受主代理推理的影响。您可以使用内置的`/code-review`技能或适用于Github的[代码审查](https://code.claude.com/docs/en/code-review)。

当单个结果不符合标准时，不要止步于修复单个问题，尝试将其编码以改进所有未来迭代的系统。

## **管理令牌使用量**

为了管理令牌使用量，循环应有明确的边界：

* **为工作选择合适的原语和模型**：较小的任务不需要多个代理或循环。某些任务可以使用更便宜、更快的模型。
* **定义明确的成功和停止标准**：具体说明完成状态，以便Claude能更快（但不要太快）达成解决方案。
* **大规模运行前先试点**：动态工作流可能生成数百个代理。先在一小部分工作上评估使用量。
* **对确定性工作使用脚本**：运行脚本比推理步骤更便宜。例如，PDF技能可以提供一个表单填写脚本，Claude每次运行该脚本，而不是重新推导代码。
* **不要比需要更频繁地运行例行程序**：将间隔时间与所监控事物的变化频率相匹配。
* **审查使用情况**：`/usage`命令按技能、子代理和MCP分解近期使用情况；不带参数的`/goal`显示到目前为止的回合数和令牌使用量；`/workflows`显示每个代理的令牌使用量，您可以随时停止代理。

## **入门指南**

总结如下：

| 循环类型 | 您移交的内容 | 使用时机 | 使用的工具 |
| --- | --- | --- | --- |
| 回合制 | 检查工作 | 您在探索或决策时 | 自定义验证技能 |
| 基于目标 | 停止条件 | 您知道完成状态时 | `/goal` |
| 基于时间 | 触发器 | 工作在项目外部按计划进行 | `/loop`、`/schedule` |
| 主动 | 提示 | 工作是重复性的且明确定义 | 上述所有工具，以及动态工作流 |

要开始使用循环，请查看您已经做的工作。选择一个您成为瓶颈的任务，并思考可以移交哪个部分：您能编写验证检查吗？目标足够清晰吗？工作是按计划到达的吗？

一旦有了想法，运行循环，观察结果（例如它在何处停滞或过度延伸），不要害怕对其进行迭代。
