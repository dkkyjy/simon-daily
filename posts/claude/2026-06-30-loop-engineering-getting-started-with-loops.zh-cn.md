            ## 循环入门

目前有很多关于循环工程或“设计循环”的讨论，而不是仅仅给你的编码代理写提示。如果你花时间在 X 上试图搞清楚循环到底是什么，你会遇到多种不同的答案。

在 Claude Code 团队中，我们将**循环定义为代理重复执行工作周期直至满足停止条件的过程**。我们根据以下几个方面将循环分为几种不同类型：

* 触发方式
* 停止方式
* 使用的 Claude Code 原语
* 最适合的任务类型

我们将介绍主要的循环类型、每种循环的使用时机，以及如何在管理令牌消耗的同时保持代码质量。并非所有任务都需要复杂的循环；从最简单的解决方案开始，有选择地使用这些模式。

## **回合制循环**

* **触发方式：** 用户提示。
* **停止条件：** Claude 判断任务已完成或需要额外上下文。
* **最佳用途：** 较短的、不属于常规流程或计划的任务。
* **用量管理：** 编写具体的提示，并使用技能改进验证，以减少回合数。**

你发送的每个提示都会启动一个手动循环，由你指导每个回合。Claude 收集上下文、采取行动、检查其工作、根据需要重复，并作出响应。我们称之为代理循环。

例如，要求 Claude 创建一个点赞按钮。它会读取你的代码、进行编辑、运行测试，然后交回它*认为*可行的结果。然后你手动检查工作，并编写下一个提示。

你可以将手动步骤编码为 SKILL.md 文件，从而改进验证步骤，使 Claude 能够端到端地检查更多自己的工作。（关于选择技能、钩子和子代理来进行此类自动化的更多信息，请参见我们的[引导 Claude Code 指南](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)。）

这应包括让 Claude 能够*查看*、*测量*或*与结果交互*的工具或连接器。检查越量化，Claude 就越容易自我验证。

例如，在你的 SKILL.md 文件中，你可以指定：

```
--- 
name: verify-frontend-change 
description: 在声明完成之前，端到端验证任何 UI 变更。 
--- 

# 验证前端变更 
绝不要仅仅基于成功的编辑就报告 UI 变更已完成。像人工审查者那样验证：

1. 启动开发服务器，并在浏览器中打开编辑后的页面。

2. 直接与变更进行交互。对于新控件（按钮、输入框、开关）：点击它，确认预期的状态变化，并截取前后对比截图。

3. 检查浏览器控制台：无新的错误或警告。

4. 使用 Chrome Devtools MCP，运行性能跟踪并审计核心 Web 指标。

如果任何步骤失败，修复问题并从步骤 1 重新运行——不要交回部分验证的工作。
```

## **目标驱动循环（/goal）**

* **触发方式：** 实时手动提示。
* **停止条件：** 目标达成或达到最大回合数。
* **最佳用途：** 具有可验证退出条件的任务。
* **用量管理：** 设置具体的完成标准和明确的回合上限，例如“尝试 5 次后停止”。

有时，单次回合是不够的，尤其是对于更复杂的任务。代理在能够迭代时表现更好。你可以通过定义完成标准（使用 /goal）来延长 Claude 持续迭代的时间。

当你定义了成功标准后，Claude 就不必判断什么“足够好”并提前结束循环。每次 Claude 尝试停止时，评估模型会检查你的条件，并将其送回继续工作，直到目标达成或达到你定义的回合数。

这就是为什么确定性标准（例如通过的测试数量或达到某个分数阈值）如此有效。

例如：

```
/goal 让首页的 Lighthouse 得分达到 90 或以上，尝试 5 次后停止。
```

## **时间驱动循环（/loop 和 /schedule）**

* **触发方式：** 指定的时间间隔。
* **停止条件：** 你取消它，或工作完成（PR 合并、队列为空）。
* **最佳用途：** 用于重复性工作，或与外部环境/系统交互。
* **用量管理：** 设置更长的时间间隔，或基于事件而非时间来做出反应。

有些代理工作是重复性的：任务保持不变，只有输入发生变化。例如，每天早上总结 Slack 消息。其他工作依赖于外部系统，与之交互的一种简单方法是按时间间隔检查并对变化做出反应。例如，一个可能收到代码审查或 CI 失败的 PR。

对于这些情况，你可以使用 `/loop` 触发 Claude 按时间间隔重复运行某个提示。例如：

```
/loop 5m 检查我的 PR，处理审查意见，并修复失败的 CI
```

`/loop` 在你的计算机上运行，因此如果你关闭计算机，它就会停止。你可以通过创建例行任务（使用 `/schedule`）将循环移到云端。

## **主动循环**

* **触发方式：** 事件或计划，无需实时人工介入。
* **停止条件：** 每个任务在目标达成时退出。例行任务本身会一直运行，直到你关闭它。
* **最佳用途：** 重复性的、定义明确的工作流：错误报告、问题分类、迁移、依赖项升级等。
* **用量管理：** 将例行任务路由到更小、更快的模型，并使用最强大的模型进行判断。

上述原语，连同 Claude Code 的其他特性（如**自动模式**和**动态工作流**（研究预览）），可以组合成一个用于长时间运行工作的循环。

例如，要处理传入的反馈，你可以使用：

1. **`/schedule`**（研究预览）来运行一个检查新报告的例行任务
2. **`/goal`** 来定义完成的标准，以及**技能**来记录如何验证
3. **动态工作流**来编排代理，对每个报告进行分类、修复并审查修复
4. **自动模式**使例行任务无需停止请求许可即可运行

综合起来，一个提示可能如下所示：

```
/schedule 每小时一次：检查 #project-feedback 中的错误报告。/goal：直到本次运行中发现的每个报告都已被分类、处理并回复才停止。修复错误时，使用工作流在并行工作树中探索三个解决方案，并让一个审查者进行对抗性审查。
```

## **保持代码质量**

循环输出的质量取决于其周围的系统。在设计系统时：

* **保持代码库本身的整洁：** Claude 遵循代码库中已有的模式和约定。
* **让 Claude 能够验证自己的工作：** 通过[技能](https://code.claude.com/docs/en/skills)编码你和团队认为“好”的标准。
* **使文档易于获取：** 框架和库的文档应包含最新的最佳实践。
* **使用第二个代理进行代码审查：** 一个拥有新鲜上下文的审查者偏见更少，不受主代理推理的影响。你可以使用内置的 `/code-review` 技能或 [GitHub 的 Code Review](https://code.claude.com/docs/en/code-review)。

当某个结果不符合标准时，不要只修复单个问题，尽量将其编码，以改进未来所有迭代的系统。

## **管理令牌消耗**

为管理令牌消耗，循环应有明确的边界：

* **为工作选择合适的原语和模型：** 较小的任务不需要多个代理或循环。有些任务可以使用更便宜、更快的模型。
* **定义明确的成功和停止标准：** 具体说明完成的样子，以便 Claude 能更快（但不要太快）达到解决方案。
* **在大规模运行前先进行试验：** 动态工作流可能产生数百个代理。先在一小部分工作中评估消耗。
* **对确定性工作使用脚本：** 运行脚本比逐步推理更便宜。例如，一个 PDF 技能可以提供一个表单填写脚本，Claude 每次运行时直接使用，而不是重新推导代码。
* **不要比需要的更频繁地运行例行任务：** 将间隔与你监视事物变化的频率相匹配。
* **审查用量：** `/usage` 命令按技能、子代理和 MCP 分解近期用量；不带参数的 `/goal` 显示到目前为止的回合数和令牌消耗；`/workflows` 显示每个代理的令牌消耗，你可以随时停止一个代理。

你的[模型和努力程度选择](https://claude.com/blog/claude-model-and-effort-level-in-claude-code)是影响循环成本的最大杠杆之一。

## **开始使用**

总结如下：

| 循环类型 | 你交出的部分 | 何时使用 | 使用的工具 |
| --- | --- | --- | --- |
| 回合制 | 检查工作 | 你在探索或做决定时 | 自定义验证技能 |
| 目标驱动 | 停止条件 | 你知道完成的标准是什么时 | `/goal` |
| 时间驱动 | 触发条件 | 工作在项目外部按计划进行时 | `/loop`，`/schedule` |
| 主动 | 提示 | 工作重复且定义明确时 | 以上所有，以及动态工作流 |

要开始使用循环，请先查看你已经做过的任务。选择一个你成为瓶颈的任务，问自己可以交出哪一部分：你能编写验证检查吗？目标是否足够清晰？工作是否按计划到达？

一旦有了想法，运行循环，观察结果（比如它在何处停滞或过度扩展），不要害怕迭代。

如需了解更多信息，请阅读 Claude Code 文档中关于[并行运行代理](https://code.claude.com/docs/en/agents)的内容，以及[循环](https://code.claude.com/docs/en/goal)、[计划](https://code.claude.com/docs/en/routines)、[目标](https://code.claude.com/docs/en/goal)和[动态工作流](https://code.claude.com/docs/en/workflows#orchestrate-subagents-at-scale-with-dynamic-workflows)页面。
