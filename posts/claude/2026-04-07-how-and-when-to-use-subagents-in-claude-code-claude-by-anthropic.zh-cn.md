# 如何在 Claude Code 中使用子代理以及何时使用 | Claude by Anthropic

**日期：** 2026-04-07 00:00 UTC
**链接：** https://claude.com/blog/subagents-in-claude-code

---

[Claude Code](https://code.claude.com/docs/en/overview) 能很好地处理复杂的多步骤项目，但长时间会话会累积负担。每一次文件读取、每一次偏离主题的探索、每一个未完成的想法都会留在上下文窗口中，拖慢响应速度并推高 token 成本。

假设你正在一个大型 TypeScript monorepo 中构建一个新功能。主要工作是实现，但附带任务不断出现：追踪现有服务如何处理身份验证、查找用于日期格式化的共享工具函数、检查设计系统是否已有接近你需求的组件。这些任务都不需要完整的项目上下文，在主会话中运行它们只会增加噪音。如果能让它们并行运行呢？

这就是[子代理](https://code.claude.com/docs/en/sub-agents)的用武之地。子代理是一个拥有自己上下文窗口的隔离 Claude 实例。它接收任务、完成工作，然后只返回结果。可以把子代理想象成 Claude Code 会话中的浏览器标签页：一个可以追逐旁支话题而不丢失主线的场所。

在本文中，我们将讨论何时使用子代理是有意义的、如何调用它们，以及何时这种开销不值得。

## 什么是子代理？

子代理是自包含的代理，它们在自己的上下文窗口中运行。当 Claude 生成一个子代理时，该助手会独立工作，读取文件、探索代码或进行修改。当它完成任务时，子代理只将相关结果返回给主对话。

每个子代理都是全新启动的，不受对话历史或已调用技能的影响。多个子代理可以并行运行，每个子代理可以拥有不同的权限：研究子代理可能只有只读权限，而实现子代理则拥有完整的编辑能力。

Claude Code 包含几种内置的子代理类型，包括：

* **通用代理**，用于复杂的多步骤任务
* **规划代理**，在提出实现策略之前研究代码库
* **探索代理**，针对快速、只读的代码搜索进行了优化

Claude Code 通常会自行生成子代理来处理分配的任务。也可以显式地指导这种行为，并定义可复用的专家代理，让 Claude 自动委派任务。知道何时使用子代理才是让这个功能真正有用的关键。

## 何时应该使用子代理？

某些类别的工作明显受益于子代理委派。学会识别它们能让这个功能更加有效。

### 研究密集型任务

当理解某事物的工作方式是修改它的前提时，子代理可以探索代码库并返回摘要，而不是将几十个文件倾倒进对话中。

**信号：** 收集上下文需要读取大量文件。

**好处：** 主对话保持整洁，获得的是综合后的发现而非原始内容。

### 多个独立任务

当需要修复多个文件中的错误、更新多个组件中的模式，或进行彼此不依赖的修改时，并行子代理能更快完成任务。

**信号：** 子任务之间没有依赖关系。

**好处：** 三个同时工作的子代理通常能在更短时间内完成任务。

### 需要全新视角

当目标是获得对实现的无偏见审查时，子代理提供了一块干净的画板，因为它不会继承主对话中的假设、上下文或盲点。

**信号：** 需要验证，且不希望对话历史影响分析。

**好处：** 更干净、更客观的反馈。

**专业提示：** /clear 命令也会重置上下文和对话历史，提供类似的公正视角，但代价是完全丢失那段历史。子代理在保持主对话完整的同时实现了同样的全新视角。

### 提交前的验证

在最终确定更改之前，独立的子代理可以验证实现是否过度拟合测试或遗漏了边缘情况。

**信号：** 在提交代码之前需要第二意见。

**好处：** 能捕捉到因对代码过于熟悉而可能被忽略的问题。

### 流水线工作流

当任务具有不同阶段（即设计、然后实现、然后测试）时，每个阶段都能从专注的注意力中受益。

**信号：** 具有清晰交接的连续阶段。

**好处：** 每个子代理专注于自己的阶段，不会因其他阶段的上下文而产生噪音。

**专业提示：** 当任务需要探索十个或更多文件，或涉及三个或更多独立的工作项时，这就是一个强烈信号，表明应引导 Claude 使用子代理。

## 如何引导子代理的使用

有多种调用子代理的方法，从简单的对话到自动化工作流。正确的起点取决于工作流，随着模式的出现可以逐步增加复杂度。

### 对话式调用

最灵活的方法就是直接在对话中要求 Claude 使用子代理。这适用于所有 Claude Code 界面：终端、VS Code、JetBrains、Web 和桌面应用。

能可靠触发子代理的自然语言模式包括：

* “使用子代理探索这个代码库中的身份验证是如何工作的”
* “让一个单独的代理审查这段代码的安全问题”
* “并行研究这个。同时检查 API 路由、数据库模型和前端组件”
* “启动子代理来修复不同包中的这些 TypeScript 错误”

明确表达很重要。指定范围，在任务独立时请求并行执行，并描述期望的输出。

以下是一个有效的提示结构：

```
使用子代理并行探索这个代码库：

1. 找出所有 API 端点并总结其用途
2. 识别数据库模式和关系
3. 梳理身份验证流程

返回每项的摘要，而不是完整文件内容。
```

这个提示之所以有效，是因为它清晰定义了三个独立任务，明确请求并行执行，并指定了输出格式。Claude 能理解意图并生成合适的子代理。

有效的对话式调用技巧包括：

* **清晰界定任务范围。** “探索支付是如何工作的”优于“探索一切”。
* **明确请求并行化。** 说“这些可以并行运行”或“同时处理这三项”。
* **指定应返回的内容。** 摘要、具体发现或建议。指明输出格式有助于 Claude 交付。
* **当需要无偏见分析时要求全新上下文。** “使用一个看不到我们之前讨论的子代理”可确保评估的干净性。

**专业提示：** 当子代理运行时间较长时，Ctrl+B 可将其发送到后台。对话可以继续，结果会在完成时自动出现。/tasks 命令可显示后台运行的所有内容。

### 自定义子代理

当反复需要同一种子代理时（安全审查员、测试编写者、文档校对者），可以将其定义为一次自定义子代理。

之后，只要任务与其描述匹配，Claude 就会自动委派给它，无需提示。

自定义子代理以 Markdown 文件形式存放在 `.claude/agents/`（项目级，与团队共享）或 `~/.claude/agents/`（用户级，在所有项目中可用）中。每个子代理都有自己的系统提示、工具权限，可选地还有自己的模型。

创建自定义子代理最简单的方式是使用 /agents 命令，它会以交互方式引导设置，并能根据描述生成初稿。也可以手动编写文件，例如：

```
---
name: security-reviewer
description: 审查代码更改中的安全漏洞、
  注入风险、身份验证问题和敏感数据暴露。
  在涉及身份验证、支付或用户数据的提交前主动使用。
tools: Read, Grep, Glob
model: sonnet
---

你是一位专注于安全的代码审查员。分析提供的
更改是否存在：
- SQL 注入、XSS 和命令注入风险
- 身份验证和授权漏洞
- 日志、错误或响应中的敏感数据
- 不安全的依赖或配置

返回按优先级排序的发现列表，包含 file:line 引用
以及每项的推荐修复方案。要严格批判。如果未发现问题，
请明确说明，而不是编造问题。
```

有了这个配置，Claude 会自动将匹配的工作路由给该子代理。也可以按名称调用：“让 security-reviewer 查看暂存的更改。”

自定义子代理在以下情况下效果最佳：

* 当任务匹配时，应有一个专家代理可供 Claude 自动委派
* 工作受益于严格界定的系统提示和受限工具
* 配置需要在团队中共享或在项目间复用

**专业提示：** description 字段是 Claude 用来决定何时委派的依据。要具体说明触发条件，而不仅仅是能力。“在提交前审查代码的安全问题”比“安全专家”能更好地路由。

有关完整配置参考，包括权限模式以及项目和用户子代理如何交互，请参阅我们的 [Claude Code 子代理文档。](https://code.claude.com/docs/en/sub-agents)

### CLAUDE.md 指令

自定义子代理定义了专家是谁。CLAUDE.md 文件则定义了 Claude 何时应使用它们的规则。如果每次代码审查都应通过只读子代理进行，或者每个架构问题都应先触发研究过程，那么 CLAUDE.md 就是存放这些策略的地方。Claude 在每次对话开始时都会读取它，因此行为在会话和团队成员之间保持一致，无需任何人记得去要求。

CLAUDE.md 适合存放子代理指令的情况包括：

* 代码审查应始终使用只读子代理
* 项目有 Claude 应遵循的特定研究模式
* 需要在团队成员和会话之间保持一致的行为

以下是一个简单的 CLAUDE.md 文件示例，它在特定条件下触发子代理：

```
## 代码审查标准

当被要求审查代码时，始终使用具有只读权限的子代理
（仅限 Glob、Grep、Read）。审查应始终检查：
- 安全漏洞
- 性能问题
- 是否符合 /docs/architecture.md 中的项目模式

返回按优先级排序的发现列表，包含 file:line 引用。
```

有了上述 CLAUDE.md 文件，每次代码审查请求都会自动使用定义的模式，无需每次都指定。

如需了解更多关于CLAUDE.md文件的信息，请参阅[为你的代码库定制Claude Code：设置CLAUDE.md文件](https://preview.claude.ai/chat/link)以及我们的Claude Code [CLAUDE.md](http://claude.md) [文件文档](https://code.claude.com/docs/en/memory#claude-md-files)。

### 技能

对于重复运行的复杂多步骤工作流，技能提供了可复用的接口。在.claude/skills/中定义一次技能，然后通过/skill-name调用它，或者当任务与技能描述匹配时，让Claude自动加载。

技能与CLAUDE.md文件在范围上有所不同。CLAUDE.md文件始终被加载，并影响每一次交互。技能是按需加载的，要么因为被显式调用，要么因为Claude将当前任务与技能的描述字段匹配。这使得技能成为那些应该可用但不适用于每个提示的工作流的正确选择。

技能在以下情况下非常合适：

* 某些操作定期运行
* 不同团队成员需要访问相同的复杂操作
* 在团队中标准化某些任务的执行方式很重要

以下是一个用于全面代码审查的深度审查技能示例：

# .claude/skills/deep-review/SKILL.md

---
name: deep-review
description: 全面的代码审查，并行检查安全性、
  性能和代码风格。在提交或创建PR前审查暂存更改时使用。
---

对暂存更改并行运行三个子代理审查：

1. 安全审查——检查漏洞、注入风险、
   认证问题和敏感数据泄露
2. 性能审查——检查N+1查询、不必要的迭代、
   内存泄漏和阻塞操作
3. 风格审查——检查与 /docs/style-guide.md 中记录的
   项目模式的一致性

将发现综合为一份摘要，并按优先级排序问题。
每个问题应包含文件、行号和推荐的修复方案。
```

在上面的代码片段中，/deep-review 按需触发三部分子代理分析。由于描述中提到在提交前审查暂存更改，Claude 在遇到该场景时也可以自动调用此技能。

技能是一个目录，而不是单个文件。除了 `SKILL.md` 之外，它还可以包含 Claude 填写的模板、展示预期格式的示例输出，或 Claude 在工作流中执行的脚本。旧的 `.claude/commands/` 格式是单个平面文件，因此所有内容都必须放在提示本身中。

有关在 Claude Code 中使用技能的更多信息，请参阅我们的 [Claude Code 技能文档。](https://code.claude.com/docs/en/skills#extend-claude-with-skills)

### Hooks

Hooks 是用户定义的 shell 命令、HTTP 端点或 LLM 提示，它们在 Claude Code 生命周期的特定点自动执行。[Hooks](https://code.claude.com/docs/en/hooks-guide) 可以根据事件自动化子代理工作流。Hooks 在特定操作时触发，无需手动调用即可运行子代理任务。

Hooks 是正确工具的情况包括：

* 每次提交在创建前都应自动审查
* 安全检查应在无人记得请求的情况下运行
* 类似 CI 的质量门禁应属于本地开发流程

以下是一个 Stop hook 的示例，它会阻止 Claude 在测试通过前结束回合：

```
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/check-tests.sh"
          }
        ]
      }
    ]
  }
}
```

以及 `.claude/hooks/check-tests.sh` 中的脚本：

```
#!/bin/bash
INPUT=$(cat)
STOP_HOOK_ACTIVE=$(echo "$INPUT" | jq -r '.stop_hook_active // false')

# 不要无限循环——如果本轮已经阻止过一次，则放行
if [ "$STOP_HOOK_ACTIVE" = "true" ]; then
  exit 0
fi

if ! npm test --silent > /dev/null 2>&1; then
  jq -n '{
    decision: "block",
    reason: "测试失败。运行 `npm test` 查看失败原因并在完成前修复。"
  }'
  exit 0
fi

exit 0
```

当 Claude 结束回合时，Stop 事件触发。脚本运行测试套件——如果测试失败，它会返回包含 `decision: "block"` 和 `reason` 的 JSON。Claude Code 读取该信息，不允许 Claude 停止，并将原因作为继续工作的指令反馈到对话中。顶部的 `stop_hook_active` 守卫可防止无限循环：如果 Claude 已经因之前的 stop-hook 阻止而继续，脚本会放行退出。

Hooks 代表了子代理编排中最自动化的方法。对话式调用或 CLAUDE.md 指令是更好的起点；随着工作流成熟，再引入 Hooks。

有关完整的 Hooks 配置，请参阅 [Claude Code 高级用户自定义：如何配置 hooks](https://claude.com/blog/how-to-configure-hooks) 或我们的 [Claude Code hooks 文档](https://code.claude.com/docs/en/hooks)。

## 使用子代理的实用模式

以下模式展示了将子代理指令应用于常见场景的方法。

### 实现前先研究

在向不熟悉的代码添加功能时，先让子代理进行研究，可以使实现讨论基于信息而非探索，例如：

```
在我实现用户通知之前，使用子代理研究：
- 此代码库中目前如何发送电子邮件？
- 已经存在哪些通知模式？
- 根据当前架构，新通知逻辑应放在哪里？

总结发现，然后我们一起规划实现方案。
```

收到的是综合摘要，而不是二十个文件的原始上下文，实现讨论从坚实的基础开始。

### 并行修改

当需要在多个文件中更新相同模式时，并行子代理完成得更快且保持专注，例如：

```
使用并行子代理更新这些文件中的错误处理：
- src/api/users.ts
- src/api/orders.ts
- src/api/products.ts

每个都应遵循 src/api/auth.ts 中建立的模式。
同时处理所有三个文件。
```

三个并行工作的子代理大约在一个子代理所需的时间内完成。每个子代理专注于自己的文件，不会因其他文件的上下文造成混乱或不一致。

### 独立审查

在实现复杂功能后，由未受实现过程影响的子代理进行验证，可以捕捉因熟悉而被忽视的问题，例如：

```
使用一个具有只读访问权限的全新子代理审查我对支付流程的实现。它不应看到我们之前的讨论。我希望得到无偏见的审查。

检查：安全漏洞、未处理的边界情况和错误处理缺口。要严格批评。
```

审查子代理在不知道考虑了哪些权衡、拒绝了哪些方法或做了哪些假设的情况下评估代码。这种外部视角能发现主对话可能遗漏的问题。

### 流水线工作流

对于多阶段任务，在阶段之间使用明确的交接来串联子代理，可使每个阶段保持专注，例如：

```
让我们将此功能构建为流水线：

1. 第一个子代理：设计 API 契约并写入 docs/api-spec.md
2. 第二个子代理：基于该规范实现后端端点
3. 第三个子代理：为实现编写集成测试

每个阶段应在下一阶段开始前完成。使用输出
文件作为阶段之间的交接机制。
```

使用流水线工作流，任务中的每个阶段都能获得专注的上下文。设计子代理不会被实现问题分心，实现子代理基于清晰的规范工作，测试子代理独立评估结果。

## 何时不应使用子代理？

虽然子代理是一个有用的功能，但它们会带来开销。每个子代理都会启动自己的上下文、消耗 token，并在开发者和工作之间增加一层间接性。当上下文隔离、并行性或全新视角确实有帮助时，这些成本是值得的。

对于较小或紧密顺序的任务，坚持在主对话中处理通常更简单，例如：

* **顺序、依赖性的工作。** 当第二步需要第一步的完整输出，而第三步需要两者时，单个会话处理链条通常比子代理通过文件传递状态的接力更清晰。
* **同一文件的编辑。** 两个子代理并行编辑同一文件是冲突的根源。在这种情况下，将紧密耦合的更改保留在一个上下文窗口中。
* **小任务。** 对于快速修复或聚焦的问题，委派的开销超过收益。只需在主对话中提示或提问。
* **过多的专业代理。** 为所有事情定义自定义子代理很诱人，但用过多选项淹没 Claude 会使自动委派变得不太可靠。大多数团队会选择少数几个范围明确的代理，而不是庞大的名单。
* **需要代理之间相互协调的工作。** 子代理向主对话报告，但无法相互通信。对于子代理需要通信的任务，请使用 [agent teams](https://code.claude.com/docs/en/agent-teams)。使用 agent teams，子代理在单独的会话中协调，而不是在单个会话内，这使得它们更重且更昂贵。有关何时使用子代理与 Agent Teams 的更多指导，请参阅我们的 [Claude Code agent teams 文档](https://code.claude.com/docs/en/agent-teams)。

前面描述的信号（即需要第二意见、子任务之间没有依赖关系以及广泛的研究）清楚地表明何时值得委派给子代理。

## 从对话式开始，之后自动化

子代理在有意使用时才能发挥全部价值。Claude 提供的自动调用很有帮助，但知道何时委派研究、并行化工作和请求全新视角，比听天由命能产生更好的结果。

使用子代理时，从对话式提示开始。注意哪些请求反复出现，并在这些模式清晰后构建自动化。目标是让子代理委派变得轻松自如，这样你的注意力就能保持在重要的工作上。
