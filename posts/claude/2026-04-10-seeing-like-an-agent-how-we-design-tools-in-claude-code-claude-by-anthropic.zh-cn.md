# 像智能体一样观察：我们如何设计 Claude Code 中的工具 | Claude by Anthropic

**链接：** https://claude.com/blog/seeing-like-an-agent

构建智能体框架最难的部分之一，就是构造它的工具。

Claude 完全通过[工具调用](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)来行动，但在 Claude API 中，可以通过多种方式使用诸如 [bash](https://platform.claude.com/docs/en/agents-and-tools/tool-use/bash-tool)、[技能](https://code.claude.com/docs/en/skills)和[代码执行](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)等原语来构造工具。（你可以在 [@RLanceMartin 的新文章](https://x.com/RLanceMartin/status/2027450018513490419)中阅读更多关于 Claude API 中编程式工具调用的内容）。

那么，你如何设计智能体的工具呢？是给它一个像 bash 或代码执行这样的通用工具？还是五十个专用工具，每个对应一个用例？

要站在模型的角度思考，想象一下被给了一个困难的数学问题。你希望拥有哪些工具来解决它？这将取决于你自己的技能水平！

纸是最低要求，但你会受到手动计算的限制。计算器会更好，但你需要知道如何操作更高级的选项。最快、最强大的选择是电脑，但你必须知道如何使用它来编写和执行代码。

这是一个设计智能体的有用框架。你想给它提供与其自身能力相匹配的工具。但你怎么知道这些能力是什么呢？你要留意、阅读它的输出、进行实验。你要学会像智能体一样观察。

如果你正在构建一个智能体，你会面临和我们一样的问题：何时添加工具、何时移除工具，以及如何区分这两者。以下是我们构建 Claude Code 时给出的答案，包括我们最初出错的地方。

## 使用 AskUserQuestion 工具改进引导提问

在构建 AskUserQuestion 工具时，我们的目标是提高 Claude 提问的能力（通常称为引导提问）。

虽然 Claude 可以用纯文本直接提问，但我们发现回答这些问题感觉花费了不必要的时间。我们如何降低这种摩擦并提高用户与 Claude 之间的沟通带宽呢？

### 尝试 1：编辑 ExitPlanTool

我们尝试的第一种方法是在 ExitPlanTool 中添加一个参数，使其在计划之外附带一组问题。这是最容易实现的修复方案，但它让 Claude 感到困惑，因为我们同时要求它提供计划以及关于计划的问题。如果用户的回答与计划内容冲突怎么办？Claude 是否需要调用两次 ExitPlanTool？我们知道这种策略行不通，于是回到了绘图板。（你可以在[我们关于提示缓存的文章](https://x.com/trq212/status/2024574133011673516)中阅读更多关于我们为何创建 ExitPlanTool 的内容）

### 尝试 2：更改输出格式

接下来，我们尝试更新 Claude 的输出指令，使其输出一种稍作修改的 Markdown 格式，以便用来提问。例如，我们可以要求它输出一个带方括号内备选项的要点问题列表。然后我们可以将该问题解析并格式化为面向用户的 UI。

Claude 通常能生成这种格式，但不够可靠。它会附加多余的句子、遗漏选项，或者完全放弃该结构。于是我们转向下一种方法。

### 尝试 3：AskUserQuestion 工具

最终，我们决定创建一个 Claude 可以在任何时刻调用的工具，但在计划模式下会特别提示它这样做。当该工具被触发时，我们会显示一个模态框来展示问题，并阻塞智能体的循环，直到用户回答。

这个工具让我们能够提示 Claude 输出结构化内容，并帮助我们确保 Claude 为用户提供多个选项。它还为用户提供了组合此功能的方式，例如在 [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 中调用它，或在技能中引用它。

最重要的是，Claude 似乎喜欢调用这个工具，我们发现它的输出效果很好。毕竟，即使是最好的设计工具，如果 Claude 不理解如何调用它，也无法发挥作用。

这是 Claude Code 中引导提问的最终形式吗？我们对此表示怀疑。随着 Claude 能力的增强，为其服务的工具也必须随之演进。下一节将展示一个曾经有帮助的工具如何开始变得碍事。

### 随能力更新：任务与待办事项

当我们首次发布 Claude Code 时，我们意识到模型需要一个[待办事项列表](https://platform.claude.com/docs/en/agent-sdk/todo-tracking)来保持其工作进度。待办事项可以在开始时写入，并在模型完成工作时逐项勾选。为此，我们为 Claude 提供了 TodoWrite 工具，它可以写入或更新待办事项并向用户展示。

但即便如此，我们经常看到 Claude 忘记它需要做什么。为了适应这种情况，我们每 5 轮插入一次系统提醒，提醒 Claude 其目标。

随着模型能力的提升，它们发现待办事项列表具有局限性。被发送待办事项列表的提醒会让 Claude 认为它必须坚持该列表，而不是在意识到需要改变方向时修改它。我们还看到 Opus 4.5 在使用子智能体方面变得更加出色，但子智能体如何在共享的待办事项列表上进行协调呢？

看到这一点，我们用[任务工具](https://x.com/trq212/status/2014480496013803643)取代了 TodoWrite 功能。待办事项侧重于让模型保持正轨，而任务则帮助智能体之间相互沟通。任务可以包含依赖关系、在子智能体之间共享更新，模型也可以修改和删除它们。

随着模型能力的提升，你的模型曾经需要的工具现在可能会限制它们。不断重新审视关于需要哪些工具的先前假设非常重要。这也是为什么坚持支持一小部分能力特征较为相似的模型是有用的。

## 设计搜索界面

我们构建的最具影响力的工具，是那些能让 Claude 自行寻找上下文的工具。

当 Claude Code 首次在内部发布时，我们使用了 RAG：向量数据库会预先索引代码库，框架会在每次响应前检索相关片段并将其交给 Claude。虽然 RAG 功能强大且快速，但它需要索引和设置，并且在一系列不同环境中可能很脆弱。最重要的是，Claude 是*被给予*这些上下文，而不是自己找到上下文。

但如果 Claude 能在网上搜索，为什么它不能搜索你的代码库呢？通过为 Claude 提供 Grep 工具，我们可以让它自行搜索文件并构建上下文。

随着 Claude 变得越来越聪明，在获得正确工具的情况下，它越来越擅长构建自己的上下文。

当我们引入 [Agent Skills](https://agentskills.io/home) 时，我们正式确立了渐进式披露的理念，它允许智能体通过探索逐步发现相关上下文。

Claude 现在可以读取技能文件，而这些文件可以引用模型可以递归读取的其他文件。事实上，技能的一个常见用途是为 Claude 添加更多搜索能力，例如给它关于如何使用 API 或查询数据库的指令。

在一年时间里，Claude 从无法真正构建自己的上下文，发展到能够在多个文件层级中进行嵌套搜索，以找到它确切需要的上下文。

渐进式披露现在是我们用来在不添加工具的情况下添加新功能的常用技术。在下一节中，我们将解释原因。

## 渐进式披露：Claude Code 指南智能体

Claude Code 目前约有 20 个工具，我们的团队会经常重新审视是否需要所有这些工具才能让 Claude 发挥最大效能。添加新工具的门槛很高，因为这会给模型多一个需要考虑的选项。

例如，我们注意到 Claude 对如何使用 Claude Code 了解不够。如果你问它如何添加 MCP 或某个斜杠命令的作用，它无法回答。

我们可以将所有信息放入系统提示中，但鉴于用户很少询问这些内容，这会增加上下文腐化并干扰 Claude Code 的主要工作：编写代码。

相反，我们尝试了渐进式披露：我们给 Claude 一个指向其文档的链接，它可以在需要时加载和搜索。这很有效，但 Claude 会将大块文档拉入上下文，只为找到一个用户一句话就能得到的答案。

因此，我们构建了 Claude Code 指南——一个每当用户询问 Claude Code 本身时 Claude 就会调用的子智能体。该子智能体在自己的上下文中进行文档搜索，遵循关于如何搜索和提取什么的详细指令，并且只返回答案。主智能体的上下文保持干净。

虽然这不是一个完美的解决方案（当你问 Claude 如何设置自身时，它仍然可能感到困惑），但我们能够在 Claude 的行动空间中增加内容，而无需添加新工具。

### 像智能体一样观察是一门艺术，而非科学

为你的模型设计工具既是一门艺术，也是一门科学。它在很大程度上取决于你使用的模型、智能体的目标以及它所运行的环境。

我们最好的建议是什么？经常实验、阅读你的输出、尝试新事物。最重要的是，试着像智能体一样观察。
