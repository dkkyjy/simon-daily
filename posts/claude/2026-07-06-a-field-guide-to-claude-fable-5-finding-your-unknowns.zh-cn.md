# Claude Fable 实战指南 5：发现你的未知

            **日期：** 2026-07-06 00:00 UTC
            **链接：** https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns

            ---

            在使用 Claude Code 时，我常常想起地图与疆域之间的区别。

地图，即待完成工作的表征，是我的提示词、技能和上下文——这是我给 Claude 的东西。疆域则是工作实际发生的地方——代码库、现实世界及其实际约束。

地图与疆域之间的差距，我称之为*未知*。当 Claude 遇到未知时，它需要基于对我意图的最佳猜测来做决策。工作越多，Claude 可能遇到的未知也就越多。

Claude Fable 是第一个让我觉得工作质量受限于我澄清其未知能力的模型。

重要的是，仅仅提前规划并不总是足够的。你可能会在实现深处发现未知，或者你的未知可能指向一个事实——你其实应该用完全不同的方式来解决这个问题。

我发现，与 Fable 合作是一个在实现之前、之中和之后不断发现未知的迭代过程。

## 了解你的未知

你的未知是什么？当我带着问题来找 Claude 时，我倾向于将其分解为四种方式：

* **已知的已知：** 这基本上就是我提示词中的内容。我告诉代理我想要什么？
* **已知的未知：** 我还没弄清楚什么，但我意识到自己还没弄清楚？
* **未知的已知：** 什么东西显而易见到我从不会写下来，但看到时却能认出来？
* **未知的未知：** 我完全没有考虑过什么？我不了解哪些知识？我知道某件事可以好到什么程度吗？

最优秀的代理式程序员拥有相对较少的未知。观察像 [Boris](https://www.linkedin.com/in/bcherny) 或 [Jarred](https://www.linkedin.com/in/jarred-sumner-a8772425) 这样的人编写提示词，我明显感觉到他们非常清楚自己想要什么，细节详尽。他们与代码库和模型行为都深度同步。

但他们也假设存在未知。在很多方面，减少并规划你的未知正是代理式编程的**技能**。但幸运的是，这是一项你可以通过与 Claude 合作来提升的技能。

## 帮助 Claude 帮助你

指导 Claude 是一种微妙的平衡。如果你过于具体，Claude 会遵循你的指令，即使转向可能更合适。如果你过于模糊，Claude 往往会根据行业最佳实践做出选择和假设，而这些可能并不适合你的任务。

当你没有考虑自己的未知时，你会以两种方式失败。你不知道道路何时会布满障碍，也不知道道路何时会畅通无阻，但你仍然希望 Claude 能够转向。

Claude 可以帮助你更快地发现自己的未知。它可以极快地搜索你的代码库和互联网，并且对一般主题的了解远多于你。它还能更快地从失败中迭代。

这个过程最重要的部分是给 Claude 提供关于你起点的上下文。例如，告诉它你处于思考过程中的哪个阶段；透露你对问题和代码库的经验；让它像思想伙伴一样与你合作。

在本文中，我将详细介绍一些用于发现这些未知的模式，包括：

**实现前：**

* 盲点扫描
* 头脑风暴与原型
* 访谈
* 参考资料
* 实现计划

**实现中：**

* 实现笔记

**实现后：**

* 推介与说明
* 测验

## 实现前

### 盲点扫描

开始工作时，你能做的最有用的事情之一就是了解自己的盲点。例如，如果你正在代码库的新部分编写功能，或者使用 Claude 帮助你完成不熟悉的工作（如迭代设计），你很可能会有很多**未知的未知**。

你可能不知道该问什么问题、不知道什么算好、不知道做过哪些历史工作、也不知道要避开哪些坑。

在这些情况下，你可以请 Claude 帮你找到你的未知的未知，并向你解释。我喜欢直接使用“盲点扫描”和“未知的未知”这些字眼。提供关于你是谁以及你知道什么的上下文，通常对 Claude 理解如何最好地开始与你合作很重要。

**示例提示词：**

* “我正在添加一个新的认证提供者，但我对这个代码库中的认证模块一无所知。你能做一次盲点扫描，帮我找出相关的未知的未知，并帮助我更好地向你提问吗？”

* “我不知道什么是色彩校正，但我需要给这段视频做色彩校正。你能教我了解关于色彩校正的未知的未知，以便我能更好地提问吗？”

### 头脑风暴与原型

当我在一个充满**未知的已知**的领域工作时——涉及那些我只有看到才能定义的标准——我喜欢请 Claude 与我一起进行头脑风暴和原型设计。

在原型设计阶段尽早识别并表述出未知的已知非常有价值，因为在实现过程中才发现它们会（相对）昂贵。功能或规格的微小变化可能导致代码实现天差地别，而你的代理更难撤销之前的更改。

例如，你可能只是想看看添加一个按钮到框架上的效果，而不想连接后端路由或在前端维护额外状态。

另一个例子是视觉设计，对我来说，这很难用语言表达，但看到时我就知道我想要什么。在这些情况下，我会要求对一个工件提供几种设计方案。

我几乎每次编码会话都会从探索或头脑风暴阶段开始。这有助于我带着明确意图来定义项目范围。Claude 经常能找到我可能会错过的高价值方法，但有时也会只见树木不见森林。头脑风暴可以防止我将范围设定得过窄或过宽。

**示例提示词：**

* “我想要一个用于这些数据的仪表盘，但我没有视觉品味，也不知道有什么可能性。给我做一个包含 4 种截然不同设计方向的 HTML 页面，这样我可以对它们做出反应。”

* “在连接任何东西之前，先用虚假数据制作一个模拟新编辑器工具栏的单一 HTML 文件。我想在接触真实应用之前先对布局做出反应。”

* “这是我的粗略问题：用户在上手后流失。搜索代码库，头脑风暴出 10 个我们可以干预的地方，从最便宜到最雄心勃勃。我会告诉你哪些能引起我的共鸣。”

### 访谈

一旦我做了足够的头脑风暴，我可能仍然有未知。

在这种情况下，我请 Claude 就任何未知或模糊之处对我进行访谈。当要求 Claude 访谈你时，尽量提供关于你问题的上下文，以引导它的问题。

**示例提示词：**

* “一次一个问题地访谈我，关于任何模糊之处，优先考虑那些我的回答会改变架构的问题。”

### 参考资料

有时你无法详细描述你想要的东西。例如，你可能没有相应的语言，或者它太复杂，需要花很长时间才能说清楚。

在这种情况下，最好的方法是提供参考资料。虽然你可以包含图表、文档或图片，但最好的参考资料是*源代码*。

如果你有一个以特定方式实现某功能的库，或者一个你非常喜欢的设计组件，只需将 Fable 指向该文件夹，告诉它要查找什么，即使它是用不同语言编写的。与截图相比，这为 Claude 提供了关于标记和结构的更丰富细节。

**示例提示词：**

* “vendor/rate-limiter 中的这个 Rust crate 实现了我想要的精确退避行为。阅读它，并在我们的 TypeScript API 客户端中重新实现相同的语义。”

### 实现计划

当我认为准备好实现时，我倾向于请 Claude 整理一个实现计划供我审查。计划侧重于最可能改变的部分，例如数据模型、类型接口或用户体验流程。这让 Claude 能够提出我可能实际需要修改的内容。

**示例提示词：**

* “用 HTML 写一个实现计划，但把我最可能调整的决策放在前面：数据模型变更、新的类型接口，以及任何面向用户的内容。把机械性的重构工作埋在底部，这部分我相信你。”

## 实现中

### 实现笔记

一旦我对计划满意，我会创建一个新会话，并将所有工件传递给提示词。这给了 Claude 一个全新的上下文窗口，但包含了你在规划过程中编译的所有信息。例如，我可能会传递一个规范文件和一个原型，然后让代理实现它。

但事实是，无论你做多少规划，总会有未知的未知潜伏着。代理可能在工作中发现，由于在代码中找到了一个边缘情况，它需要采取不同的策略。

我要求 Claude Code 维护一个临时的 'implementation-notes.md'（或 .html）文件，在其中记录它所做的决策，这样我们可以在下次尝试时学习。

**示例提示词：**

* “维护一个 implementation-notes.md 文件。如果你遇到一个迫使你偏离计划的边缘情况，选择保守的方案，将其记录在‘偏差’部分下，然后继续。”

## 实现后

### 推介与说明

交付某样东西最重要的部分之一是获得认可和批准。在最终文档中构建推介和说明工件有助于：

* 当审查者从与你相同的未知开始时，加速理解
* 当专家想看到你考虑了他们本会预见的未知和常见失败点时，加速批准

**示例提示词：**

* “将原型、规范和实现笔记打包成一个文档，我可以放到 Slack 里来获得认可。以演示 GIF 开头。”

### 测验

经过长时间的工作会话后，Claude 可能已经完成了比我意识到的多得多的内容。阅读代码差异只能让我对发生的事情有肤浅的理解，因为很多行为将取决于现有的代码路径。

在提供大量上下文后，请 Claude 就变更内容对我进行测验，这有助于我理解发生了什么。只有在我完美通过测验后，我才会合并代码。

**示例提示词：**

* “我想确保我理解这次变更中发生的一切。给我一份关于变更的 HTML 报告，让我阅读和理解，包含上下文、直觉、做了什么等，并在底部附上一个我必须通过的关于变更的测验。”

## 这一切如何结合：发布 Fable

[Fable 的发布视频](https://x.com/ClaudeDevs/status/2064399512664526853) 是使用 Claude Code 从头到尾编辑的。这对我来说是一个新领域，我绝非专家。

所以我从我知道的东西开始。我知道 Claude 可以使用代码编辑视频和转录，但我不确定它是否足够准确。然后我请 Claude 解释像 Whisper 这样的转录技术是如何工作的，以及我是否能够使用 ffmpeg 精确地剪掉像“嗯”或长时间停顿这样的内容。

我希望 Claude 创建一个与我说话内容同步的 UI，但不确定是否可能，所以我请 Claude 使用 Remotion 和转录创建一个原型视频，看看是否可行。

最后，视频本身看起来有点暗淡，我知道这是色彩校正的结果，但我并不真正了解什么是色彩校正。我的第一次尝试是让 Claude 做几个变体让我挑选，但我意识到我不知道色彩校正的“好”是什么样子的。所以，我转而请 Claude 教我关于色彩校正的知识，以发现我的未知。

## 让地图与疆域匹配

模型越好，用正确的方法能实现的就越多。当一个长周期任务返回错误结果时，很可能你需要花更多时间定义你的未知，或者创建一个允许你和 Claude 共同适应它们的实现计划。

每一个说明、头脑风暴、访谈、原型和参考资料，都是在问题变得昂贵之前，以低成本发现你不知道的东西的方式。

所以，开始你的下一个项目时，先请 Claude 帮你找到你的未知。
