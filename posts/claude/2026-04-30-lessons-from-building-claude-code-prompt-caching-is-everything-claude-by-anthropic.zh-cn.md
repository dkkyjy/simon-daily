**日期：** 2026-04-30 00:00 UTC
**链接：** https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything

---

工程界常说“缓存主宰一切”，这条规则同样适用于智能体。

像 Claude Code 这样长期运行的智能体产品之所以可行，正是得益于[**提示缓存**](https://x.com/RLanceMartin/status/2024573404888911886)，它让我们能够复用之前往返计算的结果，从而显著降低延迟和成本。

在 Claude Code 中，我们围绕提示缓存构建了整个运行框架。高提示缓存命中率能降低成本，并帮助我们为订阅计划提供更慷慨的速率限制，因此我们对提示缓存命中率设置告警，如果命中率过低就会触发 SEV。

以下是我们从大规模优化提示缓存中学到的（往往反直觉的）经验教训。

## **为缓存而布局提示词**

Claude Code 的系统提示词经过精心组织，使稳定部分保持缓存状态，只有对话本身逐轮增长。

提示缓存通过前缀匹配工作——API 会缓存从请求开始到每个 `cache_control` 断点之间的所有内容。这意味着内容的排列顺序至关重要，你希望尽可能多的请求共享相同的前缀。

提示词的结构不仅影响缓存命中率，也影响输出质量——[提示工程基础](https://claude.com/blog/best-practices-for-prompt-engineering)是这门学问的另一半。

最佳做法是：静态内容在前，动态内容在后。对 Claude Code 而言，结构如下：

1. **静态系统提示词** 与工具（全局缓存）
2. **CLAUDE.md**（项目内缓存）
3. **会话上下文**（会话内缓存）
4. **对话消息**

这样我们就能最大化多个会话之间的缓存命中率。

但这种方法可能出奇地脆弱。我们曾因多种原因打破过这种排列顺序，包括：在静态系统提示词中加入详细的时间戳、以非确定性方式打乱工具顺序定义、以及更新工具参数（例如 Agent 工具可以调用哪些代理）。

## **使用消息进行更新**

有时提示词中的信息可能会过时，例如时间信息或用户修改了文件。你可能会想更新提示词，但这会导致缓存未命中，最终可能让用户付出相当高的代价。

请考虑是否可以通过智能体下一轮的消息来传递这些信息。在 Claude Code 中，我们会在下一条用户消息或工具结果中添加 `<system-reminder>` 标签，将更新后的信息提供给模型，这样有助于保持缓存。

## **不要在会话中途切换模型**

提示缓存是模型特有的，这会让提示缓存的成本计算变得相当反直觉。

例如，如果你与 Opus 的对话已进行到 100k token，想提出一个相当容易回答的问题，此时切换到 Haiku 实际上比让 Opus 回答更昂贵，因为我们需要为 Haiku 重建提示缓存。

如果需要切换模型，最佳方式是通过子代理来实现；延续上面的例子，你可以部署一个子代理，让 Opus 准备一条“交接”消息，将需要完成的任务传递给另一个模型。我们在 Claude Code 的 Explore 代理中经常这样做，这些代理使用 Haiku。

## **切勿在会话中途添加或移除工具**

在对话中途更改工具集是人们破坏提示缓存最常见的方式之一。这看起来似乎很直观——你应该只给模型提供你认为它当前需要的工具。但由于工具属于缓存前缀的一部分，添加或移除工具会使整个对话的缓存失效。

**使用计划模式围绕缓存进行设计**

[计划模式](https://code.claude.com/docs/en/common-workflows)是围绕缓存约束设计功能的绝佳示例。直观的做法是：当用户进入计划模式时，将工具集替换为仅包含只读工具，但这会破坏缓存。

相反，我们始终在请求中保留*所有*工具，并将 EnterPlanMode 和 ExitPlanMode 本身作为工具使用。当用户切换计划模式时，智能体会收到一条系统消息，说明它处于计划模式及其指令：探索代码库、不要编辑文件、计划完成后调用 ExitPlanMode。工具定义从不改变。

这还有一个额外好处：由于 EnterPlanMode 是模型可以自行调用的工具，它可以在检测到难题时自主进入计划模式，而无需破坏缓存。

**使用工具搜索来延迟而非移除**

同样的原则也适用于我们的[工具搜索工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)。Claude Code 可能加载了数十个 MCP 工具，在每次请求中都包含所有这些工具会非常昂贵，但在对话中途移除它们又会破坏缓存。

我们的解决方案：`defer_loading`。我们不移除工具，而是发送轻量级存根（仅包含工具名称，并设置 `defer_loading: true`），模型可以在需要时通过工具搜索“发现”这些工具。完整的工具模式仅在模型选择它们时才加载。这样缓存前缀保持稳定，因为相同的存根始终以相同的顺序存在。

你也可以通过我们的 API 使用[工具搜索工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)来简化这一过程。

## **在不破坏缓存的情况下进行压缩**

当上下文窗口填满时，Claude Code 会分叉一个缓存调用来总结对话，然后以摘要替代原始消息继续运行。

[压缩](https://platform.claude.com/docs/en/build-with-claude/compaction)发生在上下文窗口耗尽时。我们会总结到目前为止的对话，并以该摘要继续新的会话。

压缩与提示缓存的交互方式很容易出错。要压缩一段对话，你必须将完整对话发送给模型，以便它编写摘要。最简单的方法是使用独立的 API 调用，附带自己的系统提示词（类似“总结以下内容”）且不附加任何工具，但这正是成本陷阱所在。提示缓存仅在请求的前缀与已缓存内容从开头逐字节匹配时才生效。你的主对话在某个系统提示词和工具集下被缓存；而摘要调用使用不同的系统提示词且没有工具，因此前缀从第一个 token 就开始分叉，所有缓存都不适用。你最终需要为发送的整个对话支付完整的未缓存输入费率——而且对话越长（即你越需要压缩），这一次调用的成本就越高。

**解决方案：缓存安全的派生**

当我们执行压缩时，使用与父对话*完全相同*的系统提示词、用户上下文、系统上下文和工具定义。我们先前置父对话的消息，然后在末尾将压缩提示词作为新的用户消息追加。

从 API 的角度来看，这个请求与父对话的最后一次请求几乎相同——相同的前缀、相同的工具、相同的历史记录——因此缓存前缀被复用。唯一的新 token 是压缩提示词本身。

但这确实意味着我们需要预留一个“压缩缓冲区”，以便在上下文窗口中有足够空间容纳压缩消息和摘要输出 token。

压缩很棘手，但幸运的是，你不需要自己摸索这些经验——基于我们从 Claude Code 中学到的经验，我们已将[压缩](https://platform.claude.com/docs/en/build-with-claude/compaction#prompt-caching)直接构建到 API 中，因此你可以在自己的应用中应用这些模式。

## **经验总结**

以下是我们发现的对构建智能体时优化提示缓存有用的一些模式：

1. **提示缓存是前缀匹配。** 前缀中任何位置的任何更改都会使之后的所有内容失效。围绕这一约束设计你的整个系统。排列顺序正确，大部分缓存工作就会自动完成。
2. **使用消息而非修改系统提示词。** 你可能会想通过编辑系统提示词来实现进入计划模式、更改日期等操作，但实际上更好的做法是在对话过程中将这些内容插入到消息中。
3. **不要在对话中途更改工具或模型。** 使用工具来建模状态转换（如计划模式），而不是更改工具集。延迟工具加载而非移除工具。
4. **像监控正常运行时间一样监控缓存命中率。** 我们对缓存破坏设置告警并将其视为事故。几个百分点的缓存未命中率就可能对成本和延迟产生巨大影响。
5. **派生操作需要共享父级的前缀。** 如果需要运行侧计算（压缩、摘要、技能执行），请使用相同的缓存安全参数，以便在父级前缀上获得缓存命中。

Claude Code 从第一天起就围绕提示缓存构建；为了在构建智能体时获得最佳效果，我们建议你也这样做。
