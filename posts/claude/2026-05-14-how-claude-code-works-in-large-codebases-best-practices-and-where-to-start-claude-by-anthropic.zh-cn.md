---

Claude Code 已在生产环境中运行于数百万行级的单体仓库、运行数十年的遗留系统、横跨数十个仓库的分布式架构，以及拥有数千名开发者的组织。这些环境带来了小型、简单代码库所不具备的挑战——无论是每个子目录都不同的构建命令，还是分散在文件夹中、没有共享根目录的遗留代码。

本文涵盖了我们观察到的、能够在大规模环境中成功采用 Claude Code 的模式。我们使用“大型代码库”一词来指代广泛的部署场景：拥有数百万行代码的单体仓库、跨越数十年积攒的遗留系统、分布在独立仓库中的数十个微服务，或上述任意组合。这还包括团队并不总是将其与 AI 编码工具联系起来的语言所编写的代码库，例如 C、C++、C#、Java、PHP。（Claude Code 在这些场景下的表现通常超出大多数团队的预期，尤其是在近期模型版本中。）虽然每个大型代码库的部署都受其特定版本控制、团队结构和积累的约定影响，但本文的模式可以跨这些场景推广，是考虑采用 Claude Code 的团队的良好起点。

## Claude Code 如何导航大型代码库

Claude Code 导航代码库的方式与软件工程师类似：它遍历文件系统、读取文件、使用 grep 精确查找所需内容，并在整个代码库中追踪引用。它在开发者的本地机器上运行，无需构建、维护或将代码库索引上传到服务器。

基于 RAG 的 AI 编码工具通过嵌入整个代码库并在查询时检索相关片段来工作。在大规模环境下，这些系统可能会失败，因为嵌入管道无法跟上活跃工程团队的步伐。当开发者查询索引时，它反映出的是代码库数周、数天甚至数小时前的状态。随后检索可能会返回团队两周前重命名的函数，或引用上一个冲刺中删除的模块，并且没有任何迹象表明这些信息已过时。

智能代理搜索避免了这些故障模式。无需维护嵌入管道或集中式索引，即便数千名工程师在不断提交新代码。每位开发者的实例都基于实时代码库工作。

但这种方法存在一个权衡：当 Claude 拥有足够的起始上下文来知道去哪里查找时，效果最佳。这意味着 Claude 的导航质量取决于代码库的搭建方式——通过 CLAUDE.md 文件和技能来叠加上下文。如果你要求它在一个十亿行代码库中查找某个模糊模式的所有实例，在开始工作之前就会达到上下文窗口限制。在代码库搭建方面投入的团队会获得更好的结果。

## 工具链与模型本身同样重要

关于 Claude Code 最常见的误解之一是，其能力完全由所使用的模型决定。团队关注模型的基准测试结果及其在测试任务上的表现。实际上，围绕模型构建的生态系统——工具链——对 Claude Code 表现的影响远大于模型本身。

该工具链由五个扩展点构建而成——CLAUDE.md 文件、钩子、技能、插件和 MCP 服务器——每个都服务于不同的功能。团队构建它们的顺序很重要，因为每一层都建立在前一层的基础上。另外两个能力——LSP 集成和子代理——完善了整体设置。下面我们解释每个组件和能力的作用：

[**CLAUDE.md**](https://code.claude.com/docs/en/memory) **文件首先出现。** 这些是上下文文件，Claude 在每个会话开始时自动读取：根文件用于总体概况，子目录文件用于本地约定。它们为 Claude 提供了做好任何事情所需的代码库知识。由于它们会在每个会话中加载，无论任务是什么，保持它们专注于广泛适用的内容，将防止它们成为性能的拖累。

[**钩子**](https://code.claude.com/docs/en/hooks-guide) **使设置能够自我改进。** 大多数团队将钩子视为防止 Claude 做错事的脚本，但它们更有价值的用途是持续改进。停止钩子可以在会话期间反思所发生的事情，并在上下文仍然新鲜时提出 CLAUDE.md 更新建议。启动钩子可以动态加载团队特定的上下文，这样每位开发者无需手动配置就能获得其模块的正确设置。对于像 lint 和格式化这样的自动化检查，钩子能够确定性地执行规则，比依赖 Claude 记住指令产生更一致的结果。

[**技能**](https://code.claude.com/docs/en/skills) **在需要时提供正确的专业知识，而不会让每个会话变得臃肿。** 在拥有数十种任务类型的大型代码库中，并非所有专业知识都需要在每个会话中存在。技能通过[渐进式披露](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)解决了这个问题，将本会争夺上下文空间的专门工作流和领域知识卸载出去，并且仅在任务需要时才加载。例如，安全审查技能会在 Claude 评估代码漏洞时加载，而文档处理技能会在代码变更需要更新文档时加载。

技能还可以限定到特定路径，因此它们只在代码库的相关部分激活。拥有支付服务的团队可以将部署技能绑定到该目录，这样当有人在单体仓库的其他部分工作时，它就不会自动加载。

[**插件**](https://code.claude.com/docs/en/plugins) **将有效的配置分发开来。** 大型代码库面临的一个挑战是，*好的*设置可能会停留在小圈子内。插件将技能、钩子和 MCP 配置打包成一个可安装的包，这样当新工程师第一天安装该插件时，他们将立即拥有与已经在使用 Claude 的用户相同的上下文和能力。插件更新可以通过[托管市场](https://support.claude.com/en/articles/13837433-manage-claude-cowork-plugins-for-your-organization)在整个组织内分发。

例如，我们合作的一家大型零售组织构建了一项技能，将 Claude 连接到他们的内部分析平台，这样业务分析师无需离开工作流即可提取绩效数据。他们在向业务部门广泛推广之前，将其作为插件进行了分发。

**语言服务器协议（LSP）集成让 Claude 拥有与开发者在 IDE 中相同的导航能力。** 大多数大型代码库的 IDE 已经运行了 LSP，为“转到定义”和“查找所有引用”提供支持。将这一能力暴露给 Claude，使其能够获得符号级别的精度：它可以跟踪函数调用到其定义，跨文件追踪引用，并区分不同语言中同名的函数。没有它，Claude 会基于文本进行模式匹配，可能定位到错误的符号。我们合作的一家企业软件公司在 Claude Code 推广之前，全组织部署了 LSP 集成，专门为了使 C 和 C++ 导航在大规模环境下可靠。对于多语言代码库，这是最具价值的投资之一。

**MCP 服务器扩展一切。** MCP 服务器是 Claude 连接到内部工具、数据源和 API 的方式，这些工具、数据源和 API 是它无法通过其他方式访问的。最成熟的团队构建了 MCP 服务器，将结构化搜索作为 Claude 可以直接调用的工具暴露出来。其他团队则将 Claude 连接到内部文档、工单系统或分析平台。

[**子代理**](https://code.claude.com/docs/en/sub-agents) **将探索与编辑分离。** 子代理是一个独立的 Claude 实例，拥有自己的上下文窗口，它接受一个任务，完成工作，并且只将最终结果返回给父代理。一旦工具链就位，一些团队会启动一个只读子代理来映射子系统并将发现写入文件，然后由主代理在掌握全局的情况下进行编辑。

*Claude 代码的扩展层概览。*

下表总结了每个组件的作用、加载时机以及我们发现的每个组件最常见的误区：

| 组件 | 它是什么 | 何时加载 | 最适合 | 常见混淆 |
| --- | --- | --- | --- | --- |
| CLAUDE.md | Claude 自动读取的上下文文件 | 每个会话 | 项目特定约定、代码库知识 | 将本应属于技能的可复用专业知识放在这里 |
| 钩子 | 在关键时刻运行的脚本 | 由事件触发 | 自动化一致行为、捕获会话学习成果 | 使用提示词来做本应自动运行的事情 |
| 技能 | 针对特定任务类型的打包指令 | 按需加载，相关时触发 | 跨会话和项目的可复用专业知识 | 将所有内容加载到 CLAUDE.md 而非技能中 |
| 插件 | 打包的技能、钩子和 MCP 配置 | 配置后始终可用 | 在组织中分发有效的设置 | 让好的设置停留在小圈子内 |
| 语言服务器协议 (LSP)\* | 通过特定语言的服务器提供的实时代码智能 | 配置后始终可用 | 在类型化语言中进行符号级导航和自动错误检测 | 认为它是自动启用的 |
| MCP 服务器 | 连接外部工具和数据 | 配置后始终可用 | 让 Claude 能够访问它无法通过其他方式到达的内部工具 | 在基础功能正常工作之前就构建 MCP 连接 |
| 子代理\* | 用于特定任务的独立 Claude 实例 | 被调用时 | 将探索与编辑分离、并行工作 | 在同一会话中进行探索和编辑 |
| \*LSP 通过插件层访问。子代理是一种委托能力，而非配置好的扩展点。 | | | | |

## 成功部署中的三种配置模式

为大型代码库配置 Claude 的方式在很大程度上取决于该代码库的结构。尽管如此，在观察到的部署中，有三种模式始终如一地出现。

### 使代码库在大规模下可导航

Claude 在大型代码库中提供帮助的能力受限于其找到正确上下文的能力。在每个会话中加载过多上下文会降低性能，而加载过少上下文则会让 Claude 盲目导航。最高效的部署会在前期投入，使代码库对 Claude 而言易于理解。有几种模式始终如一地出现：

* **保持 CLAUDE.md 文件精简且分层。** Claude 在代码库中移动时会增量加载这些文件：根文件用于总体概况，子目录文件用于本地约定。根文件应该只包含指针和关键注意事项；其他所有内容都会变得嘈杂。
* **在子目录中初始化，而不是在仓库根目录。** Claude 在限定到与任务实际相关的代码库部分时表现最佳。在单体仓库中，这可能会违反直觉，因为工具通常假设根访问权限，但 Claude 会自动向上遍历目录树并加载沿途找到的每个 CLAUDE.md 文件，因此根级别的上下文永远不会丢失。
* **为每个子目录限定测试和 lint 命令的范围。** 当 Claude 只改动了一个服务时运行完整套件会导致超时，并在不相关的输出上浪费上下文。子目录级别的 CLAUDE.md 文件应指定适用于该部分代码库的命令。这对于面向服务的代码库效果很好，其中每个目录都有自己的测试和构建命令。在具有深度跨目录依赖关系的编译语言单体仓库中，按子目录限定范围更难实现，可能需要特定于项目的构建配置。
* **使用 `.`ignore 文件排除生成的文件、构建产物和第三方代码。** 在 `.claude/settings.json` 中提交 `permissions.deny` 规则意味着排除项是版本控制的，因此团队中的每位开发者无需自行配置就能获得相同的噪声减少效果。在某些代码库中，生成的文件本身就是开发工作的对象。从事代码生成器开发的开发者可以在其本地设置中覆盖项目级别的排除项，而不影响团队的其他成员。
* **当目录结构本身不足以说明问题时，构建代码库地图。** 对于代码未整合到传统目录结构的组织，在仓库根目录放置一个轻量级 markdown 文件，列出每个顶级文件夹并附上一行说明，这样 Claude 在打开文件之前就能扫描到一个目录。对于拥有数百个顶级文件夹的代码库，这最好作为分层方法使用：根文件只描述最高级别的结构，而子目录 CLAUDE.md 文件提供下一级详细信息，在 Claude 在树中移动时按需加载。对于更简单的情况，通过 @-mention 引用 Claude 应参考的特定文件或目录可以完成同样的工作。
* **运行 LSP 服务器，让 Claude 按符号搜索，而非按字符串搜索。** 在大型代码库中对一个常见函数名进行 grep 会返回数千个匹配项，Claude 需要打开文件来确定哪些匹配项是有意义的，从而消耗上下文。LSP 只返回指向同一符号的引用，因此过滤发生在 Claude 读取任何内容之前。设置此功能需要为你的语言安装一个[代码智能插件](https://code.claude.com/docs/en/discover-plugins#code-intelligence)和相应的语言服务器二进制文件；Claude Code 文档涵盖了可用的插件和故障排除。

**一个注意事项：** 存在一些边界情况，即使是分层 CLAUDE.md 方法也会失效，例如拥有数十万个文件夹和数百万个文件的代码库，或使用非 Git 版本控制的遗留系统。我们将在本系列的未来文章中讨论它们的挑战。对于遗留资产，请参阅 AI 如何[*打破 COBOL 现代化的成本障碍*](https://claude.com/blog/how-ai-helps-break-cost-barrier-cobol-modernization)。

### 随着模型智能的演进主动维护 CLAUDE.md 文件

随着模型的演进，为当前模型编写的指令可能会限制未来的模型。那些曾引导 Claude 克服它过去难以处理的模式的 CLAUDE.md 文件，在下个模型发布时可能会变得不必要，甚至具有约束性。例如，一条告诉 Claude 将每次重构拆分为单文件更改的 CLAUDE.md 规则，可能帮助了早期模型保持正轨，但却会阻止新模型执行它擅长的协调性跨文件编辑。

为弥补特定模型限制（无论是模型推理能力还是 Claude Code 自身工具的限制）而构建的技能和钩子，一旦这些限制不复存在，就会变成开销。例如，一个拦截文件写入以在 Perforce 代码库中强制执行 p4 edit 的钩子，在 Claude Code 添加了原生 Perforce 模式后变得冗余。

团队应预计每三到六个月进行一次有意义的配置审查，但在主要模型发布后感觉性能达到平台期时，也值得进行一次审查。

### 为 Claude Code 管理和采用分配所有权

仅靠技术配置并不能推动采用。做对了的组织也在组织层面进行了投入。

传播最快的推广活动在广泛开放访问之前，都有专门的基础设施投入。一个小团队，有时甚至只有一个人，搭建了工具链，使得 Claude 在开发者第一次接触时就已经适应了他们的工作流。在一家公司，几位工程师构建了一套插件和 MCP，在第一天就可以使用。在另一家公司，一个完整的团队专注于管理 AI 编码工具，在推广开始前就已经搭建好了基础设施。在这两种情况下，开发者的首次体验都是富有成效的而非令人沮丧的，采用率由此扩散开来。

如今从事这项工作的团队通常隶属于开发者体验或开发者生产力部门，这通常是负责新工程师入职和构建开发者工具的功能团队。在多家组织中出现的一个新兴角色是代理经理：一个兼具项目经理和工程师职能的角色，专门负责管理 Claude Code 生态系统。对于没有专门团队的组织，最低可行版本是 DRI（直接责任人）：一个人拥有 Claude Code 配置的所有权，有权决定设置、权限策略、插件市场和 CLAUDE.md 约定，并有责任使其保持最新。

自下而上的采用能激发热情，但如果没有一个中心点来整合有效的方法，就会导致碎片化。你需要一个个人或团队来汇编和推广正确的 Claude Code 约定（例如标准化的 CLAUDE.md 层次结构或一组精心策划的技能和插件）。如果没有这项工作，知识将停留在小圈子内，采用率也会停滞不前。

在大型组织中，尤其是在受监管行业，治理问题会早早出现，例如：谁控制哪些技能和插件可用，如何防止数千名工程师独立重建相同的东西，如何确保 AI 生成的代码经过与人工编写代码相同的审查流程？为尽早解决这些问题，我们建议从一组明确的经批准技能、强制代码审查流程和有限的初始访问权限开始，然后随着信心增强逐步扩大。

我们观察到，在那些早期就建立跨职能工作组（汇集工程、信息安全和管理代表共同定义需求并制定推广路线图）的组织中，部署过程最为顺畅。

## 将这些模式应用于你的组织

Claude Code 针对传统的软件工程环境设计，在这些环境中，工程师是代码库的主要贡献者，仓库使用 Git，代码遵循标准目录结构。大多数大型代码库符合这种模式，但非传统设置（例如包含大型二进制资产的游戏引擎、使用非传统版本控制的环境，或有非工程师贡献代码库）需要额外的配置工作。我们的指导假设采用传统设置，并且我们描述的模式已在众多客户中奏效。任何剩余的复杂性都需要针对你的代码库、工具和组织进行具体判断。这正是 Anthropic 的应用 AI 团队直接与工程团队合作，将这些模式转化为你组织特定需求的地方。
