# 构建 Claude Code 的经验教训：提示缓存至关重要

            **日期：** 2026-04-30 00:00 UTC
            **链接：** https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything

            ---

            在工程领域常有人说"缓存主宰一切"，这个规则同样适用于智能体。

像 Claude Code 这样长时间运行的智能体产品之所以可行，要归功于 [**提示缓存**](https://x.com/RLanceMartin/status/2024573404888911886)，它允许我们重用之前往返的计算结果，显著降低延迟和成本。

在 Claude Code 中，我们整个框架都围绕提示缓存构建。高提示缓存命中率能降低成本，并帮助我们为订阅计划创建更慷慨的速率限制，因此我们会对提示缓存命中率设置警报，如果命中率过低就会宣布 SEV（严重事件）。

以下是我们从大规模优化提示缓存中学到的（通常反直觉的）经验教训。

## **为缓存布局你的提示**

Claude Code 的系统提示经过组织，使得稳定部分保持缓存状态，只有对话本身会逐轮增长。

提示缓存通过前缀匹配工作——API 会缓存从请求开始到每个 `cache_control` 断点之前的所有内容。这意味着内容的排列顺序极其重要，你需要尽可能让多个请求共享相同的前缀。

最佳做法是将静态内容放在前面，动态内容放在最后。对于 Claude Code 来说，这看起来像：

1. **静态系统提示** 和工具（全局缓存）
2. **CLAUDE.md**（项目内缓存）
3. **会话上下文**（会话内缓存）
4. **对话消息**

这样我们就能最大化共享缓存命中的会话数量。

但这种方法可能出奇地脆弱。我们曾因多种原因打破过这种排序，包括：在静态系统提示中放入详细的时间戳、非确定性地打乱工具顺序定义、以及更新工具参数（例如 Agent 工具可以调用的智能体）。

## **使用消息进行更新**

有时你放入提示中的信息可能会过时，例如你设置了时间，或者用户更改了文件。你可能会想更新提示，但这会导致缓存未命中，最终可能给用户带来高昂成本。

考虑是否可以在智能体的下一轮中通过消息传递这些信息。在 Claude Code 中，我们在下一条用户消息或工具结果中添加一个 `<system-reminder>` 标签，其中包含模型的更新信息，这有助于保护缓存。

## **不要在会话中途切换模型**

提示缓存是模型独有的，这可能会使提示缓存的成本计算变得相当反直觉。

例如，如果你与 Opus 的对话已经进行了 10 万个 token，现在想询问一个相当简单的问题，那么切换到 Haiku 实际上会比让 Opus 回答更昂贵，因为我们需要为 Haiku 重建提示缓存。

如果需要切换模型，最佳方式是通过子智能体来实现；延续上面的例子，你可以部署一个子智能体，提示 Opus 准备一条"交接"消息给另一个模型，说明需要完成的任务。我们在 Claude Code 的 Explore 智能体中经常这样做，这些智能体使用 Haiku。

## **永远不要在会话中途添加或移除工具**

在对话中间更改工具集是人们破坏提示缓存最常见的方式之一。这看似直观——你应该只给模型提供你认为它当前需要的工具。但由于工具是缓存前缀的一部分，添加或移除工具会使整个对话的缓存失效。

**使用计划模式围绕缓存进行设计**

[计划模式](https://code.claude.com/docs/en/common-workflows)是一个围绕缓存约束设计功能的绝佳例子。直观的方法会是：当用户进入计划模式时，将工具集替换为仅包含只读工具，但这会破坏缓存。

相反，我们始终保持*所有*工具存在于请求中，并将 EnterPlanMode 和 ExitPlanMode 本身作为工具使用。当用户切换计划模式时，智能体会收到一条系统消息，说明它处于计划模式以及相关指令：探索代码库、不编辑文件、计划完成后调用 ExitPlanMode。工具定义从不改变。

这还有一个额外的好处：因为 EnterPlanMode 是模型可以自行调用的工具，所以当它检测到难题时，可以自主进入计划模式，而无需破坏缓存。

**使用工具搜索来延迟加载而非移除**

同样的原则也适用于我们的[工具搜索工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)。Claude Code 可能加载了数十个 MCP 工具，在每个请求中都包含所有工具会很昂贵，但在对话中途移除它们会破坏缓存。

我们的解决方案：`defer_loading`。我们不移除工具，而是发送轻量级的存根（仅工具名称，带有 `defer_loading: true`），模型可以在需要时通过工具搜索"发现"这些工具。完整的工具模式仅在模型选择它们时才加载。这保持了缓存前缀的稳定性，因为相同的存根始终以相同的顺序存在。

你也可以通过我们的 API 使用[工具搜索工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)来简化这一过程。

## **在不破坏缓存的情况下进行压缩**

当上下文窗口填满时，Claude Code 会分叉一个缓存调用以总结对话，然后用摘要替换原始消息继续执行。

[压缩](https://platform.claude.com/docs/en/build-with-claude/compaction)发生在上下文窗口耗尽时。我们会总结到目前为止的对话，然后用该摘要继续新的会话。

压缩与提示缓存的交互方式很容易出错。要压缩对话，你必须将完整的对话发送给模型，以便它编写摘要。最简单的方法是使用独立的 API 调用，带有自己的系统提示（如"总结这个"）且不附加工具，但这正是成本陷阱所在。提示缓存仅在请求的前缀与已缓存的内容逐字节匹配时才生效。你的主对话是在一个系统提示和工具集下缓存的；而摘要调用使用不同的系统提示且没有工具，因此前缀从第一个 token 开始就不同，所有缓存都不适用。最终你需要为发送的整个对话支付完整的未缓存输入费率——而对话越长（即你越需要压缩），这一调用的成本就越高。

**解决方案：缓存安全的分叉**

当我们执行压缩时，我们使用与父对话*完全相同*的系统提示、用户上下文、系统上下文和工具定义。我们预先添加父对话的消息，然后在末尾附加压缩提示作为新的用户消息。

从 API 的角度来看，这个请求看起来与父对话的上一个请求几乎相同——相同的前缀、相同的工具、相同的历史——因此缓存的前缀被重用。唯一的新 token 就是压缩提示本身。

但这确实意味着我们需要保存一个"压缩缓冲区"，以便在上下文窗口中有足够的空间来容纳压缩消息和摘要输出 token。

压缩很棘手，但幸运的是，你不需要自己学习这些经验教训——基于我们从 Claude Code 中学到的知识，我们直接将[压缩](https://platform.claude.com/docs/en/build-with-claude/compaction#prompt-caching)功能构建到了 API 中，因此你可以在自己的应用程序中应用这些模式。

## **经验教训**

以下是我们发现对构建智能体时优化提示缓存有用的一些模式：

1. **提示缓存是前缀匹配。** 前缀中任何位置的任何更改都会使其之后的所有内容失效。围绕这一约束设计你的整个系统。排序正确，大部分缓存就能自动生效。
2. **使用消息而非更改系统提示。** 你可能想编辑系统提示来做诸如进入计划模式、更改日期等操作，但实际上更好的做法是在对话过程中将这些内容插入到消息中。
3. **不要在对话中途更改工具或模型。** 使用工具来建模状态转换（如计划模式），而不是更改工具集。延迟加载工具而非移除工具。
4. **像监控正常运行时间一样监控缓存命中率。** 我们对缓存破坏设置警报，并将其视为事件处理。几个百分点的缓存未命中率会显著影响成本和延迟。
5. **分叉操作需要共享父级的前缀。** 如果需要运行辅助计算（压缩、摘要、技能执行），使用相同的缓存安全参数，以便在父级前缀上获得缓存命中。

Claude Code 从第一天起就围绕提示缓存构建；为了在构建智能体时获得最佳结果，我们建议你也这样做。
