如果你使用 AI 编程代理，你会面临同样的挑战：如何在不重复说明的情况下，为它们提供足够的上下文来理解你的架构、约定和工作流程？

随着代码库的增长，这个问题会变得更加复杂。复杂的模块关系、特定领域的模式以及团队约定并不容易显现出来。你最终不得不在每次对话开始时解释相同的架构决策、测试要求和代码风格偏好。

[CLAUDE.md](https://www.anthropic.com/engineering/claude-code-best-practices) 文件通过为 Claude 提供关于你项目的持久上下文来解决这个问题。你可以把它看作一个配置文件，Claude 会自动将其纳入每次对话，确保它始终了解你的项目结构、编码标准和工作流程偏好。

在本文中，我们将介绍如何构建你的 [CLAUDE.md](http://claude.md) 文件，分享最佳实践，以及使用它们来充分利用 Claude Code 的技巧。

## 什么是 CLAUDE.md 文件？

CLAUDE.md 是一个特殊的配置文件，存放在你的代码仓库中，为 Claude 提供项目特定的上下文。你可以将其放在仓库根目录以与团队共享，放在父目录中以支持 monorepo 设置，或放在你的主目录中以在所有项目中通用。

以下是一个你可能放在仓库中的 CLAUDE.md 示例：

```
# 项目上下文

在处理此代码库时，优先考虑可读性而非花哨的技巧。在进行架构更改之前，先提出澄清性问题。

## 关于此项目

用于用户认证和个人资料的 FastAPI REST API。使用 SQLAlchemy 进行数据库操作，使用 Pydantic 进行验证。

## 关键目录

- `app/models/` - 数据库模型
- `app/api/` - 路由处理器
- `app/core/` - 配置和工具

## 标准

- 所有函数都需要类型提示
- 使用 pytest 进行测试（fixtures 位于 `tests/conftest.py`）
- PEP 8，每行 100 个字符

## 常用命令
```bash
uvicorn app.main:app --reload  # 开发服务器
pytest tests/ -v               # 运行测试
```

## 备注

所有路由使用 `/api/v1` 前缀。JWT 令牌在 24 小时后过期。
```

一个配置良好的 CLAUDE.md 可以改变 Claude 处理你特定项目的方式。该文件有多种用途：提供架构上下文、建立工作流程，以及将 Claude 连接到你的开发工具。每一项添加都应该解决你实际遇到的问题，而不是关于 Claude 可能需要什么的理论性担忧。

此文件可以记录常用的 bash 命令、核心工具、代码风格指南、测试说明、仓库约定、开发环境设置以及项目特定的警告。没有强制要求的格式。建议保持此文件简洁且易于阅读，将其视为人类和 Claude 都需要快速理解的文档。

你的 CLAUDE.md 文件会成为 Claude 系统提示的一部分。每次对话都会在已加载此上下文的情况下开始，无需重复解释基本的项目信息。

## **使用 /init 开始**

从头创建 CLAUDE.md 可能会让人望而生畏，尤其是在不熟悉的代码库中。

`/init` 命令通过分析你的项目并生成一个入门配置来自动化此过程。

在任何 Claude Code 会话中运行 `/init`：

```
cd your-project
claude
/init
```

Claude 会检查你的代码库——读取包文件、现有文档、配置文件和代码结构——然后生成一个针对你项目定制的 CLAUDE.md。生成的文件通常包括构建命令、测试说明、关键目录以及它检测到的编码约定。

将 `/init` 视为起点，而非最终产品。生成的 CLAUDE.md 捕获了明显的模式，但可能会遗漏你工作流程中的细微差别。请审查 Claude 生成的内容，并根据你团队的实际实践进行完善。

你也可以在已有 CLAUDE.md 的现有项目上使用 `/init`。Claude 会审查当前文件，并根据它从探索你的代码库中学到的内容提出改进建议。

运行 `/init` 后，请考虑以下后续步骤：

* 审查生成内容的准确性
* 添加 Claude 无法推断的工作流程说明（分支命名约定、部署流程、代码审查要求）
* 删除不适用于你项目的通用指南
* 将文件提交到版本控制，以便你的团队受益

`/init` 命令对于快速了解情况非常有效，但真正的价值在于随着时间的推移对生成的文件进行迭代。当你使用 Claude Code 时，使用 `#` 键添加你发现自己反复重复的说明——这些添加会累积成一个真正反映你团队工作方式的 CLAUDE.md。

## 如何构建你的 CLAUDE.md

以下部分将向你展示如何构建内容以获得最大影响：导航复杂架构、跟踪多步骤任务的进度、集成自定义工具，以及通过一致的工作流程防止返工。

### 为 Claude 提供地图

为每个新任务解释你的项目架构、关键库和编码风格会变得乏味。你需要 Claude 在无需手动强化的情况下，保持对你代码库结构的一致上下文。

在你的 CLAUDE.md 中添加项目摘要和高层目录结构。这能让 Claude 在导航你的代码库时立即获得方向感。

一个显示关键目录的简单树状输出有助于 Claude 理解不同组件的位置：

```
main.py
├── logs
│   ├── application.log
├── modules
│   ├── cli.py
│   ├── logging_utils.py
│   ├── media_handler.py
│   ├── player.py
```

包含关于你的主要依赖、架构模式以及任何非标准的组织选择的信息。如果你使用领域驱动设计、微服务或特定框架，请记录下来。Claude 会利用这张地图做出更好的决策，了解在哪里查找代码以及在哪里进行更改。

### 将 Claude 连接到你的工具

Claude 继承你的完整环境，但需要指导以了解应使用哪些自定义工具和脚本。你的团队很可能拥有 Claude 应该了解的用于部署、测试或代码生成的专业工具。

在 CLAUDE.md 中记录你的自定义工具并附上使用示例。包括工具名称、基本用法模式以及何时调用它们。如果你的工具通过 `--help` 标志提供帮助文档，请提及这一点，以便 Claude 知道去查看。对于复杂工具，请添加你团队经常使用的常见调用示例。

Claude 作为 MCP（模型上下文协议）客户端运行，连接到扩展其能力的 MCP 服务器。通过项目设置、全局配置或已检入的 `.mcp.json` 文件来配置这些。当工具未按预期出现时，`--mcp-debug` 标志有助于排查连接问题。

例如，如果你为组织配置了 Slack MCP 服务器，并且需要 Claude 了解如何使用它，请在 CLAUDE.md 中包含类似以下内容：

```
### Slack MCP
- 仅发布到 #dev-notifications 频道
- 用于部署通知和构建失败
- 不要用于单个 PR 更新（这些通过 GitHub webhooks 处理）
- 速率限制为每小时 10 条消息
```

了解更多关于 MCP [基础知识和最佳实践](https://www.anthropic.com/engineering/building-effective-mcp-servers) 的信息。

有关为 Claude Code 设置权限的更多信息，请参阅 [code.claude.com](https://code.claude.com/docs/en/settings) 上的 settings.json 文档。

### **定义标准工作流程**

让 Claude 在没有规划的情况下直接进行代码更改会造成返工。Claude 可能会实现一个遗漏需求的解决方案，选择错误的架构方法，或做出破坏现有功能的更改。

你需要 Claude 在行动之前先思考。在你的 CLAUDE.md 中定义 Claude 应针对不同类型任务遵循的标准工作流程。一个可靠的默认工作流程在进行更改之前解决四个问题：

1. 这是否是一个需要先进行调查的关于当前状态的问题？
2. 这是否需要在实施之前制定详细计划？
3. 还缺少哪些额外信息？
4. 如何测试有效性？

具体的工作流程可能包括：针对功能的 explore-plan-code-commit、针对算法工作的测试驱动开发，或针对 UI 更改的可视化迭代。记录你的测试要求、提交消息格式以及任何审批步骤。当 Claude 提前了解你的工作流程时，它会按照你团队的实际流程来组织工作，而不是猜测。

一个示例工作流程说明可能是：

```
1) 在修改以下位置的代码之前：X, Y, Z
	- 考虑它可能如何影响 A, B, C
	- 制定实施计划
	- 制定将验证以下函数的测试计划...
```

## **使用 Claude Code 的其他技巧**

除了配置你的 CLAUDE.md 文件之外，还有三种额外技巧可以改善你使用 Claude Code 的方式。

### **保持上下文新鲜**

长时间使用 Claude Code 会积累不相关的上下文。早期任务的文件内容、不再重要的命令输出以及无关的对话会填满 Claude 的上下文窗口。随着信噪比下降，Claude 难以保持对当前任务的专注。

在不同任务之间使用 `/clear` 来重置上下文窗口。这会清除累积的历史记录，同时保留你的 CLAUDE.md 配置以及 Claude 以全新上下文处理新问题的能力。可以将其视为关闭一个工作会话并打开另一个。

当你完成调试认证并切换到实现新的 API 端点时，请清除上下文。认证细节不再重要，并且会干扰新的工作。

### **为不同阶段使用子代理**

长时间的对话会积累干扰新任务的上下文。你已经调试了一个复杂的认证流程，现在需要对同一段代码进行安全审查。调试细节会影响 Claude 的安全分析，可能导致其忽略问题或关注已解决的疑虑。

告诉 Claude 为工作的不同阶段使用[子代理](https://code.claude.com/docs/en/sub-agents)。子代理保持隔离的上下文，防止早期任务的信息干扰新的分析。在实现支付处理器后，指示 Claude“使用子代理对该代码进行安全审查”，而不是在同一个对话中继续。

子代理最适合多步骤工作流，其中每个阶段需要不同的视角。实现需要架构上下文和功能需求；安全审查需要只专注于漏洞的全新视角。上下文隔离使两种分析都保持敏锐。

### **创建自定义命令**

重复的提示词浪费时间。你发现自己一遍又一遍地输入“审查此代码的安全问题”或“分析此代码的性能问题”。每次你都需要记住能获得良好结果的确切措辞。

自定义斜杠命令将这些内容存储为 `.claude/commands/` 目录中的 Markdown 文件。创建一个名为 `performance-optimization.md` 的文件，其中包含你偏好的性能优化提示词，它就会在任何对话中作为 `/performance-optimization` 可用。命令通过 `$ARGUMENTS` 或编号占位符（如 `$1` 和 `$2`）支持参数，让你可以传递特定文件或参数。

例如，`performance-optimization.md` 可能看起来像这样：

```

# 性能优化

分析所提供的代码中的性能瓶颈和优化机会。进行全面的审查，涵盖：

## 需要分析的领域

### 数据库与数据访问
- N+1 查询问题和缺少预加载
- 频繁查询的列缺少数据库索引
- 低效的连接或子查询
- 大型结果集缺少分页
- 缺少查询结果缓存
- 连接池问题

### 算法效率
- 时间复杂度问题（存在更好的方案时仍使用 O(n²) 或更差）
- 可以优化的嵌套循环
- 冗余计算或重复工作
- 低效的数据结构选择
- 缺少记忆化或动态规划机会

### 内存管理
- 内存泄漏或保留的引用
- 在可以流式处理时加载整个数据集
- 循环中过度实例化对象
- 不必要地在内存中保留大型数据结构
- 缺少垃圾回收机会

### 异步与并发
- 应为异步的阻塞 I/O 操作
- 可以并行运行的顺序操作
- 缺少 Promise.all() 或并发执行模式
- 同步文件操作
- 未优化的工作线程使用

### 网络与 I/O
- 过多的 API 调用（缺少请求批处理）
- 没有响应缓存策略
- 未压缩的大型负载
- 静态资源缺少 CDN 使用
- 缺少连接复用

### 前端性能
- 阻塞渲染的 JavaScript 或 CSS
- 缺少代码分割或懒加载
- 未优化的图片或资源
- 过多的 DOM 操作或回流
- 长列表缺少虚拟化
- 昂贵操作没有防抖/节流

### 缓存
- 缺少 HTTP 缓存头
- 没有应用层缓存层
- 纯函数缺少记忆化
- 静态资源没有缓存破坏

## 输出格式

对于识别出的每个问题：
1. **问题**：描述性能问题
2. **位置**：指定文件/函数/行号
3. **影响**：评级严重程度（严重/高/中/低）并解释预期的性能退化
4. **当前复杂度**：在适用时包括时间/空间复杂度
5. **建议**：提供具体的优化策略
6. **代码示例**：尽可能展示优化后的版本
7. **预期改进**：如果可测量，量化性能提升

如果代码优化良好：
- 确认优化状态
- 列出正确实施的性能最佳实践
- 指出任何可能的次要改进

**需要审查的代码：**
```
$ARGUMENTS
```
