# 使用 CLAUDE.MD 文件：为你的代码库定制 Claude Code

**日期：** 2025-11-25 00:00 UTC
**链接：** https://claude.com/blog/using-claude-md-files

---

如果你使用 AI 编码代理，你会面临同样的挑战：如何在不重复说明的情况下，为它们提供足够的上下文来理解你的架构、约定和工作流程？

随着代码库的增长，这个问题会变得更加复杂。复杂的模块关系、领域特定模式以及团队约定很难自然浮现。你最终不得不在每次对话开始时，重复解释相同的架构决策、测试要求和代码风格偏好。

[CLAUDE.md](https://www.anthropic.com/engineering/claude-code-best-practices) 文件通过为 Claude 提供关于项目的持久上下文来解决这个问题。你可以把它看作一个配置文件，Claude 会自动将其纳入每次对话，确保它始终了解你的项目结构、编码标准和首选工作流程。

在本文中，我们将逐步介绍如何构建你的 [CLAUDE.md](http://claude.md) 文件，分享最佳实践，以及使用它们充分发挥 Claude Code 效能的技巧。

## 什么是 CLAUDE.md 文件？

CLAUDE.md 是一个特殊的配置文件，存在于你的仓库中，为 Claude 提供项目特定的上下文。你可以将其放在仓库根目录下与团队共享，放在父目录中用于单体仓库设置，或者放在你的主文件夹中，以便在所有项目中通用。

以下是一个你可能在仓库中拥有的 CLAUDE.md 示例：

```
# 项目上下文

在处理此代码库时，优先考虑可读性而非巧妙性。在进行架构更改前，先提出澄清性问题。

## 关于本项目

用于用户认证和个人资料的 FastAPI REST API。使用 SQLAlchemy 进行数据库操作，使用 Pydantic 进行验证。

## 关键目录

- `app/models/` - 数据库模型
- `app/api/` - 路由处理器
- `app/core/` - 配置和工具

## 标准

- 所有函数需要类型提示
- 使用 pytest 进行测试（fixtures 在 `tests/conftest.py` 中）
- 遵循 PEP 8，每行 100 个字符

## 常用命令
```bash
uvicorn app.main:app --reload  # 开发服务器
pytest tests/ -v               # 运行测试
```

## 注意事项

所有路由使用 `/api/v1` 前缀。JWT 令牌在 24 小时后过期。
```

一个配置良好的 CLAUDE.md 能改变 Claude 与你的特定项目协作的方式。该文件有多个用途：提供架构上下文、建立工作流程、以及将 Claude 连接到你的开发工具。每次添加都应该解决你遇到的实际问题，而不是理论上的 Claude 可能需要什么。

这个文件可以记录常见的 bash 命令、核心工具、代码风格指南、测试说明、仓库约定、开发者环境设置以及项目特定的警告。没有强制要求的格式。建议保持文件简洁且人类可读，将其视为人类和 Claude 都需要快速理解的文档。

你的 CLAUDE.md 文件会成为 Claude 系统提示的一部分。每次对话都从已加载的上下文开始，无需重复解释基本的项目信息。

## **使用 /init 入门**

从头创建 CLAUDE.md 可能会让人望而生畏，尤其是在不熟悉的代码库中。

`/init` 命令通过分析你的项目并生成一个入门配置来自动化此过程。

在任何 Claude Code 会话中运行 `/init`：

```
cd your-project
claude
/init
```

Claude 会检查你的代码库——读取包文件、现有文档、配置文件和代码结构——然后生成一个针对你的项目定制的 CLAUDE.md。生成的文件通常包括构建命令、测试说明、关键目录以及它检测到的编码约定。

将 `/init` 视为一个起点，而不是最终产品。生成的 CLAUDE.md 能捕捉明显的模式，但可能会遗漏你工作流程中的细微差别。检查 Claude 生成的内容，并根据你团队的实际实践进行优化。

你也可以在已有 CLAUDE.md 的现有项目上使用 `/init`。Claude 会审查当前文件，并根据从探索代码库中学习到的内容提出改进建议。

运行 `/init` 后，考虑以下后续步骤：

* 检查生成内容的准确性
* 添加 Claude 无法推断的工作流程说明（分支命名约定、部署流程、代码审查要求）
* 删除不适用于你项目的通用指南
* 将文件提交到版本控制，以便你的团队受益

`/init` 命令对于快速入门很有效，但真正的价值来自于随着时间的推移对生成的文件进行迭代。当你使用 Claude Code 时，使用 `#` 键添加你发现自己重复说明的指令——这些添加会累积成一个真正反映你团队工作方式的 CLAUDE.md。

## 如何构建你的 CLAUDE.md

以下部分将向你展示如何构建内容以获得最大效果：导航复杂架构、跟踪多步骤任务的进度、集成自定义工具以及通过一致的工作流程防止返工。

### 为 Claude 提供地图

为每个新任务解释你的项目架构、关键库和编码风格会变得很繁琐。你需要 Claude 在无需手动强化的情况下，保持对代码库结构的一致上下文。

在你的 CLAUDE.md 中添加项目摘要和高级目录结构。这能让 Claude 在导航你的代码库时立即获得方向感。

显示关键目录的简单树形输出有助于 Claude 理解不同组件的位置：

```
main.py
├── logs
│   ├── application.log
├── modules
│   ├── cli.py
│   ├── logging_utils.py
│   ├── media_handler.py
│   ├── player.py
```

包含关于你的主要依赖项、架构模式以及任何非标准组织选择的信息。如果你使用领域驱动设计、微服务或特定框架，请记录下来。Claude 使用这张地图来做出更好的决策，知道在哪里查找代码以及在哪里进行更改。

### 将 Claude 连接到你的工具

Claude 继承了你的完整环境，但需要关于使用哪些自定义工具和脚本的指导。你的团队可能拥有用于部署、测试或代码生成的专业工具，Claude 应该了解这些工具。

在你的 CLAUDE.md 中记录自定义工具，并附上使用示例。包括工具名称、基本使用模式以及何时调用它们。如果你的工具通过 `--help` 标志提供帮助文档，请提及这一点，以便 Claude 知道去查看。对于复杂工具，添加你的团队经常使用的常见调用示例。

Claude 作为一个 MCP（模型上下文协议）客户端运行，连接到扩展其能力的 MCP 服务器。通过项目设置、全局配置或检入的 `.mcp.json` 文件来配置这些。`--mcp-debug` 标志有助于在工具未按预期出现时排查连接问题。

例如，如果你为组织配置了 Slack MCP 服务器，并且需要 Claude 理解如何使用它，请在 CLAUDE.md 中包含类似以下内容：

```
### Slack MCP
- 仅发布到 #dev-notifications 频道
- 用于部署通知和构建失败
- 不用于单个 PR 更新（这些通过 GitHub webhooks 处理）
- 速率限制为每小时 10 条消息
```

了解更多关于 MCP 的[基础知识和最佳实践](https://www.anthropic.com/engineering/building-effective-mcp-servers)。

有关设置 Claude Code 权限的更多信息，请参阅 [code.claude.com](https://code.claude.com/docs/en/settings) 上的 settings.json 文档。

### **定义标准工作流程**

让 Claude 直接进入代码更改而不进行规划会导致返工。Claude 可能会实现一个遗漏需求的解决方案，选择错误的架构方法，或者进行破坏现有功能的更改。

你需要 Claude 在行动之前先思考。在你的 CLAUDE.md 中定义标准工作流程，让 Claude 针对不同类型的任务遵循这些流程。一个可靠的默认工作流程在进行更改之前需要回答四个问题：

1. 这是关于当前状态的问题，需要先进行调查吗？
2. 这需要在实施之前制定详细计划吗？
3. 缺少哪些额外信息？
4. 如何测试有效性？

特定的工作流程可能包括：针对功能的探索-计划-编码-提交、针对算法工作的测试驱动开发、或针对 UI 更改的可视化迭代。记录你的测试要求、提交消息格式以及任何审批步骤。当 Claude 提前知道你的工作流程时，它会将工作结构与你团队的实际流程相匹配，而不是猜测。

一个示例工作流程指令可能是：

```
1) 在修改以下位置的代码之前：X, Y, Z
	- 考虑它可能如何影响 A, B, C
	- 构建一个实施计划
	- 制定一个测试计划，用于验证以下功能...
```

## **与 Claude Code 合作的其他技巧**

除了配置你的 CLAUDE.md 文件之外，还有三种额外技巧可以改善你使用 Claude Code 的方式。

### **保持上下文新鲜**

长时间使用 Claude Code 会积累不相关的上下文。来自早期任务的文件内容、不再重要的命令输出以及不相关的对话会填满 Claude 的上下文窗口。随着信噪比下降，Claude 难以保持对当前任务的关注。

在不同任务之间使用 `/clear` 来重置上下文窗口。这会移除累积的历史记录，同时保留你的 CLAUDE.md 配置和 Claude 以新上下文处理新问题的能力。可以把它想象成关闭一个工作会话并打开另一个。

当你完成调试身份验证并切换到实现新的 API 端点时，清除上下文。身份验证细节不再重要，并且会分散新工作的注意力。

### **为不同阶段使用子代理**

长时间的对话会积累干扰新任务的上下文。你刚刚调试了一个复杂的身份验证流程，现在需要对同一段代码进行安全审查。调试细节会影响 Claude 的安全分析，可能导致它忽略问题或专注于已经解决的担忧。

告诉 Claude 为不同的工作阶段使用[子代理](https://code.claude.com/docs/en/sub-agents)。子代理保持隔离的上下文，防止早期任务的信息干扰新的分析。在实现支付处理器后，指示 Claude "使用子代理对该代码进行安全审查"，而不是在同一个对话中继续。

子代理最适合多步骤工作流程，其中每个阶段需要不同的视角。实施需要架构上下文和功能需求；安全审查需要全新的视角，只关注漏洞。上下文分离使两种分析都保持敏锐。

### **创建自定义命令**

重复的提示会浪费时间。你发现自己一遍又一遍地输入"审查此代码的安全问题"或"分析此代码的性能问题"。每次你都需要记住能获得良好结果的确切措辞。

自定义斜杠命令将这些内容作为 markdown 文件存储在你的 `.claude/commands/` 目录中。创建一个名为 `performance-optimization.mm` 的文件，包含你偏好的性能优化提示，它就会在任何对话中作为 `/performance-optimization` 命令可用。命令通过 $ARGUMENTS 或编号占位符（如 `$1` 和 `$2`）支持参数，让你可以传递特定文件或参数。

例如，`performance-optimization.md` 可能如下所示：

```
# 性能优化

分析提供的代码，找出性能瓶颈和优化机会。进行全面的审查，涵盖：

## 分析领域

### 数据库与数据访问
- N+1 查询问题和缺失的预加载
- 频繁查询的列缺少数据库索引
- 低效的连接或子查询
- 大型结果集缺少分页
- 缺少查询结果缓存
- 连接池问题

### 算法效率
- 时间复杂度问题（存在更好的方案时仍使用 O(n²) 或更差）
- 可以优化的嵌套循环
- 冗余计算或重复工作
- 低效的数据结构选择
- 缺少记忆化或动态规划机会

### 内存管理
- 内存泄漏或保留的引用
- 在可以流式处理时加载整个数据集
- 循环中过多的对象实例化
- 不必要地保留在内存中的大型数据结构
- 缺少垃圾回收机会

### 异步与并发
- 应该是异步的阻塞 I/O 操作
- 可以并行运行的顺序操作
- 缺少 Promise.all() 或并发执行模式
- 同步文件操作
- 未优化的工作线程使用

### 网络与 I/O
- 过多的 API 调用（缺少请求批处理）
- 没有响应缓存策略
- 未压缩的大型负载
- 静态资源缺少 CDN 使用
- 缺少连接复用

### 前端性能
- 阻塞渲染的 JavaScript 或 CSS
- 缺少代码拆分或懒加载
- 未优化的图像或资源
- 过多的 DOM 操作或重排
- 长列表缺少虚拟化
- 昂贵操作缺少防抖/节流

### 缓存
- 缺少 HTTP 缓存头
- 没有应用层缓存
- 纯函数缺少记忆化
- 没有缓存破坏的静态资源

## 输出格式

对于识别出的每个问题：
1. **问题**：描述性能问题
2. **位置**：指定文件/函数/行号
3. **影响**：评定严重性（严重/高/中/低）并解释预期的性能下降
4. **当前复杂度**：在适用时包括时间/空间复杂度
5. **建议**：提供具体的优化策略
6. **代码示例**：在可能时展示优化版本
7. **预期改进**：如果可衡量，量化性能提升

如果代码已经优化良好：
- 确认优化状态
- 列出正确实施的性能最佳实践
- 指出任何可能的微小改进

**要审查的代码：**
```
$ARGUMENTS
```
```

你不需要手动编写自定义命令文件。让 Claude 为你创建它们：

```
创建一个名为 /performance-optimization 的自定义斜杠命令，用于分析代码中的数据库查询问题、算法效率、内存管理和缓存机会。
```

Claude 会将 markdown 文件写入 `.claude/commands/performance-optimization.md`，该命令将立即可用。

## **从简单开始，有目的地扩展**

立即创建一个全面的 CLAUDE.md 很诱人。抵制这种冲动。

CLAUDE.md 每次都会被添加到 Claude Code 的上下文中，因此从[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)和[提示工程](https://www.anthropic.com/engineering/prompt-engineering-overview)的角度来看，保持简洁。一种选择：将信息分解成单独的 markdown 文件，并在 CLAUDE.md 文件中引用它们。

不要包含敏感信息、API 密钥、凭据、数据库连接字符串或详细的安全漏洞信息——尤其是当你提交到版本控制时。由于 CLAUDE.md 成为 Claude 系统提示的一部分，请将其视为可能公开共享的文档。

## **让 CLAUDE.md 为你服务**

CLAUDE.md 文件将 Claude Code 从通用助手转变为一个专门为你的代码库配置的工具。从基本的项目结构和构建文档开始，然后根据工作流程中的实际摩擦点进行扩展。

最有效的 CLAUDE.md 文件解决实际问题：它们记录你反复输入的命令，捕捉需要十分钟解释的架构上下文，并建立防止返工的工作流程。你的文件应该反映你的团队实际开发软件的方式——而不是听起来不错但与现实不符的理论最佳实践。

将定制视为一项持续的实践，而不是一次性的设置任务。项目会变化，团队会学到更好的模式，新工具会进入你的工作流程。一个维护良好的 CLAUDE.md 会随着你的代码库一起发展，不断减少在复杂软件上使用 AI 辅助时的摩擦。
