# 如何在 Claude Code 中使用子代理及其适用时机

            **日期：** 2026-04-07 00:00 UTC
            **链接：** https://claude.com/blog/subagents-in-claude-code

            ---

            [Claude Code](https://code.claude.com/docs/en/overview) 能够很好地处理复杂、多步骤的项目，但长时间的会话会累积负担。每次文件读取、每个探索的分支、每个半成品的想法都会保留在上下文窗口中，拖慢响应速度并增加令牌成本。

假设你正在一个大型 TypeScript 单体仓库中构建一个新功能。主要工作是实现，但副任务不断出现：追踪现有服务如何处理认证、查找用于日期格式化的共享工具函数、检查设计系统是否已有接近你需求的组件。这些任务都不需要完整的项目上下文，在主会话中运行它们只会增加噪音。如果能并行运行它们会怎样？

这就是[子代理](https://code.claude.com/docs/en/sub-agents)的用武之地。子代理是一个独立的 Claude 实例，拥有自己的上下文窗口。它接受一个任务，完成工作，然后只返回结果。可以把子代理想象成 Claude Code 会话中的浏览器标签页：一个可以探索分支而不丢失主线程的地方。

在本文中，我们将讨论何时使用子代理是合理的、如何调用它们，以及何时其开销不值得。

## 什么是子代理？

子代理是自包含的代理，拥有自己的上下文窗口。当 Claude 生成一个子代理时，该助手独立工作以读取文件、探索代码或进行更改。当它完成任务后，子代理只将相关结果返回给主对话。

每个子代理从头开始，不受对话历史或已调用技能的影响。多个子代理可以并行运行，每个子代理可以有不同的权限：研究型子代理可能只有只读权限，而实现型子代理则拥有完整的编辑能力。

Claude Code 包含几种内置的子代理类型，包括：

* **通用代理** 用于复杂的多步骤任务
* **计划代理** 在提出实现策略之前研究代码库
* **探索代理** 针对快速、只读的代码搜索进行了优化

Claude Code 通常会自行生成子代理来处理分配的任务。也可以明确指示这种行为，并定义可重用的专家，让 Claude 自动委派给它们。知道何时使用子代理才能让这个功能发挥效用。

## 何时应该使用子代理？

某些类型的工作显然受益于子代理委派。学会识别它们能让这个功能更加有效。

### 研究密集型任务

当理解某事物的工作原理是修改它的前提条件时，子代理可以探索代码库并返回摘要，而不是将数十个文件倾倒到对话中。

**信号：** 收集上下文需要读取大量文件。

**好处：** 主对话保持干净，获得的是综合后的发现而非原始内容。

### 多个独立任务

当需要跨多个文件修复错误、更新多个组件中的模式，或进行互不依赖的更改时，并行子代理能更快完成任务。

**信号：** 子任务之间没有依赖关系。

**好处：** 三个同时工作的子代理通常能在更短时间内完成任务。

### 需要新视角

当目标是对实现进行无偏见的审查时，子代理提供了干净的起点，因为它不会继承主对话中的假设、上下文或盲点。

**信号：** 需要验证，且不希望对话历史影响分析。

**好处：** 更干净、更客观的反馈。

**专业提示：** /clear 命令也能重置上下文和对话历史，提供同样无偏见的起点，但代价是完全丢失历史记录。子代理在保持主对话完整的同时，实现了同样的新视角。

### 提交前的验证

在最终确定更改之前，独立的子代理可以验证实现是否过度拟合测试或遗漏了边缘情况。

**信号：** 在提交代码前需要第二意见。

**好处：** 能发现因对代码过于熟悉而可能忽略的问题。

### 流水线工作流

当任务有不同阶段（即设计、然后实现、然后测试）时，每个阶段都受益于专注的注意力。

**信号：** 具有明确交接点的顺序阶段。

**好处：** 每个子代理专注于自己的阶段，不会因其他阶段的上下文产生噪音。

**专业提示：** 当任务需要探索十个或更多文件，或涉及三个或更多独立的工作项时，这就是一个强烈信号，应引导 Claude 使用子代理。

## 如何引导子代理的使用

有几种调用子代理的方法，从简单的对话到自动化工作流。正确的起点取决于工作流，随着模式的出现，可以逐步增加复杂性。

### 对话式调用

最灵活的方法就是在对话中直接要求 Claude 使用子代理。这适用于所有 Claude Code 界面：终端、VS Code、JetBrains、网页和桌面应用。

能可靠调用子代理的自然语言模式包括：

* "使用子代理探索这个代码库中认证是如何工作的"
* "让一个独立的代理审查这段代码是否存在安全问题"
* "并行研究这个。同时检查 API 路由、数据库模型和前端组件"
* "启动子代理来修复不同包中的这些 TypeScript 错误"

明确具体很重要。指定范围，在任务独立时请求并行执行，并描述期望的输出。

以下是一个有效的提示结构：

```
使用子代理并行探索这个代码库：

1. 查找所有 API 端点并总结它们的用途
2. 识别数据库模式和关系
3. 梳理认证流程

返回每个任务的摘要，而不是完整的文件内容。
```

这个提示之所以有效，是因为它明确定义了三个独立的任务，明确请求并行执行，并指定了输出格式。Claude 理解意图并生成适当的子代理。

有效对话式调用的技巧包括：

* **明确任务范围。** "探索支付如何工作"优于"探索一切"。
* **明确请求并行化。** 说"这些可以并行运行"或"同时处理所有三个"。
* **指定应返回的内容。** 摘要、具体发现或建议。命名输出格式有助于 Claude 交付。
* **在需要无偏见分析时要求新的上下文。** "使用一个看不到我们之前讨论的子代理"确保评估的清洁性。

**专业提示：** 当子代理需要一段时间时，Ctrl+B 将其发送到后台。对话可以继续，结果在完成时自动显示。/tasks 命令显示任何在后台运行的内容。

### 自定义子代理

当反复需要相同类型的子代理时（安全审查员、测试编写者、文档校对者），可以将其定义为一次自定义子代理。

之后，只要任务匹配其描述，Claude 就会自动委派给它，无需提示。

自定义子代理以 markdown 文件形式存在于 `.claude/agents/`（项目级别，与团队共享）或 `~/.claude/agents/`（用户级别，在所有项目中可用）。每个子代理都有自己的系统提示、工具权限，以及可选的自己的模型。

创建自定义子代理最简单的方法是使用 /agents 命令，它会交互式地引导设置，并能从描述中生成初稿。也可以手动编写文件，例如：

```
---
name: security-reviewer
description: 审查代码变更是否存在安全漏洞、
  注入风险、认证问题和敏感数据暴露。
  在涉及认证、支付或用户数据的提交前主动使用。
tools: Read, Grep, Glob
model: sonnet
---

你是一名专注于安全的代码审查员。分析提供的
变更是否存在：
- SQL 注入、XSS 和命令注入风险
- 认证和授权漏洞
- 日志、错误或响应中的敏感数据
- 不安全的依赖或配置

返回按优先级排序的发现列表，附带文件:行号引用
以及每个问题的推荐修复方案。要严格。如果未发现任何问题，
请明确说明，而不是编造问题。
```

有了这个配置，Claude 会自动将匹配的工作路由到子代理。也可以通过名称调用："让 security-reviewer 审查暂存的更改。"

自定义子代理在以下情况下效果最佳：

* 当任务匹配时，需要有一个专家可供 Claude 自动委派
* 工作受益于严格限定范围的系统提示和受限的工具
* 配置需要跨团队共享或跨项目重用

**专业提示：** description 字段是 Claude 用来决定何时委派的依据。要具体说明触发条件，而不仅仅是能力。"在提交前审查代码是否存在安全问题"比"安全专家"路由效果更好。

有关完整的配置参考，包括权限模式以及项目和用户子代理如何交互，请参阅我们的 [Claude Code 子代理文档。](https://code.claude.com/docs/en/sub-agents)

### CLAUDE.md 指令

自定义子代理定义了专家是谁。CLAUDE.md 文件定义了 Claude 何时应该使用它们的规则。如果每次代码审查都应通过只读子代理进行，或者每个架构问题都应先触发研究过程，那么 CLAUDE.md 就是存放该策略的地方。Claude 在每次对话开始时读取它，因此行为在会话和团队成员之间保持一致，无需任何人记住去要求。

CLAUDE.md 适合放置子代理指令的情况包括：

* 代码审查应始终使用只读子代理
* 项目有 Claude 应遵循的特定研究模式
* 需要在团队成员和会话之间保持一致的行为

以下是一个简单的 CLAUDE.md 文件示例，它在特定条件下触发子代理：

```
## 代码审查标准

当被要求审查代码时，始终使用具有只读访问权限的子代理
（仅限 Glob、Grep、Read）。审查应始终检查：
- 安全漏洞
- 性能问题
- 是否符合 /docs/architecture.md 中的项目模式

返回按优先级排序的发现列表，附带文件:行号引用。
```

使用上述 CLAUDE.md 文件，每个代码审查请求都会自动使用定义的模式，无需每次都指定。

有关 CLAUDE.md 文件的更多信息，请参阅[为你的代码库自定义 Claude Code：设置 CLAUDE.md 文件](https://preview.claude.ai/chat/link)和我们的 Claude Code [CLAUDE.md](http://claude.md) [文件文档](https://code.claude.com/docs/en/memory#claude-md-files)。

### 技能

对于重复运行的复杂多步骤工作流，技能提供了可重用的接口。在 .claude/skills/ 中定义一次技能，然后使用 /skill-name 调用它，或让 Claude 在任务匹配其描述时自动加载它。

技能在范围上与 CLAUDE.md 文件不同。CLAUDE.md 文件始终加载并影响每次交互。技能是按需加载的，要么是因为被显式调用，要么是因为 Claude 将当前任务与技能的 description 字段匹配。这使得技能成为存放那些应该可用但不应用于每个提示的工作流的正确位置。

技能在以下情况下适用：

* 某些操作会定期运行
* 不同团队成员需要访问相同的复杂操作
* 需要标准化团队中某些任务的执行方式

以下是一个用于全面代码审查的 deep-review 技能示例：

```
# .claude/skills/deep-review/SKILL.md

---
name: deep-review
description: 并行检查安全性、性能和样式的全面代码审查。
  在提交或拉取请求前审查暂存更改时使用。
---

对暂存更改运行三个并行子代理审查：

1. 安全审查 - 检查漏洞、注入风险、认证问题和敏感数据暴露
2. 性能审查 - 检查 N+1 查询、不必要的迭代、内存泄漏和阻塞操作
3. 样式审查 - 检查与 /docs/style-guide.md 中记录的项目模式的一致性

将发现综合为单一摘要，按优先级排序问题。
每个问题应包括文件、行号和推荐的修复方案。
```

在上面的代码片段中，/deep-review 按需触发三部分子代理分析。由于描述提到了在提交前审查暂存更改，当出现该上下文时，Claude 也可以自动使用这个技能。

技能是一个目录，而不是单个文件。除了 `SKILL.md`，它还可以包含 Claude 填写的模板、显示预期格式的示例输出，或 Claude 作为工作流一部分执行的脚本。传统的 `.claude/commands/` 格式是单个平面文件，因此所有内容都必须放在提示本身中。

有关在 Claude Code 中使用技能的更多信息，请参阅我们的 [Claude Code 技能文档。](https://code.claude.com/docs/en/skills#extend-claude-with-skills)

### 钩子

钩子是用户定义的 shell 命令、HTTP 端点或 LLM 提示，它们在 Claude Code 生命周期的特定点自动执行。[钩子](https://code.claude.com/docs/en/hooks-guide)可以根据事件自动化子代理工作流。钩子在特定操作上触发，并运行子代理任务而无需手动调用。

钩子是正确工具的情况包括：

* 每次提交在创建前都应自动审查
* 安全检查应在无人记得要求的情况下运行
* 类似 CI 的质量门禁应属于本地开发流程

以下是一个 Stop 钩子的示例，它阻止 Claude 结束其轮次，直到测试通过：

```
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/check-tests.sh"
          }
        ]
      }
    ]
  }
}
```

以及 `.claude/hooks/check-tests.sh` 中的脚本：

```
#!/bin/bash
INPUT=$(cat)
STOP_HOOK_ACTIVE=$(echo "$INPUT" | jq -r '.stop_hook_active // false')

# 不要无限循环——如果本轮已经阻止过一次，则放行
if [ "$STOP_HOOK_ACTIVE" = "true" ]; then
  exit 0
fi

if ! npm test --silent > /dev/null 2>&1; then
  jq -n '{
    decision: "block",
    reason: "测试失败。运行 `npm test` 查看失败原因并在完成前修复它们。"
  }'
  exit 0
fi

exit 0
```

当 Claude 完成其轮次时，Stop 事件触发。脚本运行测试套件——如果测试失败，它返回带有 `decision: "block"` 和 `reason` 的 JSON。Claude Code 读取该信息，不允许 Claude 停止，并将原因反馈到对话中作为继续工作的指令。顶部的 `stop_hook_active` 守卫防止无限循环：如果 Claude 已经因为之前的 stop-hook 阻止而继续运行，脚本会允许其退出。

钩子代表了最自动化的子代理编排方法。对话式调用或 CLAUDE.md 指令是更好的起点；钩子则在工作流成熟后使用。

有关完整的钩子配置，请参阅 [Claude Code 高级用户自定义：如何配置钩子](https://claude.com/blog/how-to-configure-hooks)或我们的 [Claude Code 钩子文档](https://code.claude.com/docs/en/hooks)。

## 使用子代理的实用模式

以下模式展示了子代理指导在常见场景中的应用。

### 实现前的研究

当向不熟悉的代码添加功能时，先委派子代理进行研究，使实现讨论更有依据而非探索性，例如：

```
在我实现用户通知之前，使用子代理研究：
- 这个代码库中目前是如何发送邮件的？
- 已经存在哪些通知模式？
- 根据当前架构，新的通知逻辑应该放在哪里？

总结发现，然后我们一起规划实现。
```

综合摘要会到达，而不是二十个文件的原始上下文，实现讨论从坚实的基础开始。

### 并行修改

当需要在多个文件中更新相同模式时，并行子代理完成更快且保持专注，例如：

```
使用并行子代理更新以下文件中的错误处理：
- src/api/users.ts
- src/api/orders.ts
- src/api/products.ts

每个文件应遵循 src/api/auth.ts 中建立的模式。
同时处理所有三个文件。
```

三个并行工作的子代理完成时间大约相当于一个子代理所需的时间。每个子代理专注于自己的文件，不会因其他文件的上下文造成混乱或不一致。

### 独立审查

在实现复杂内容后，使用未受实现过程影响的子代理进行验证，能发现因熟悉而掩盖的问题，例如：

```
使用一个具有只读访问权限的新子代理审查我的支付流程实现。
它不应看到我们之前的讨论。我想要无偏见的审查。

检查：安全漏洞、未处理的边缘情况和错误处理漏洞。要严格。
```

审查子代理评估代码时，不知道考虑了哪些权衡、拒绝了哪些方法或做出了哪些假设。这种外部视角能发现主对话可能遗漏的问题。

### 流水线工作流

对于多阶段任务，链式子代理并在阶段之间进行显式交接，使每个阶段保持专注，例如：

```
让我们以流水线方式构建这个功能：

1. 第一个子代理：设计 API 合同并写入 docs/api-spec.md
2. 第二个子代理：基于该规范实现后端端点
3. 第三个子代理：为实现编写集成测试

每个阶段应在下一个阶段开始前完成。使用输出文件
作为阶段之间的交接机制。
```

使用流水线工作流，任务中的每个阶段都获得专注的上下文。设计子代理不会因实现问题分心，实现子代理基于干净的规范工作，测试子代理独立评估结果。

## 何时不应该使用子代理？

虽然子代理是一个有用的功能，但子代理带有开销。每个子代理都会启动自己的上下文、消耗令牌，并在开发者和工作之间增加一层间接性。当上下文隔离、并行性或新视角确实有帮助时，这种成本是值得的。

对于较小或紧密顺序的任务，坚持使用主对话通常更简单，例如：

* **顺序、依赖性强的工作。** 当第二步需要第一步的全部输出，而第三步需要两者时，单个会话处理链条通常比通过文件传递状态的子代理接力更干净。
* **同一文件编辑。** 两个子代理并行编辑同一文件是冲突的根源。在这种情况下，将紧密耦合的更改保留在一个上下文窗口中。
* **小任务。** 对于快速修复或聚焦的问题，委派的开销超过了收益。只需在主对话中提示或提问。
* **过多的专家代理。** 为每件事定义一个自定义子代理很诱人，但用选项淹没 Claude 会使自动委派变得不可靠。大多数团队会确定少数几个范围明确的代理，而不是一个庞大的名单。
* **需要代理相互协调的工作。** 子代理向主对话报告，但不能相互通信。对于子代理需要通信的任务，请使用[代理团队](https://code.claude.com/docs/en/agent-teams)。使用代理团队时，子代理跨独立会话协调，而不是在一个会话内，这使得它们更重且更昂贵。有关何时使用子代理与代理团队的更多指导，请查看我们的 [Claude Code 代理团队文档](https://code.claude.com/docs/en/agent-teams)。

前面描述的信号（即需要第二意见、子任务之间没有依赖关系、以及广泛的研究）清楚地表明了何时值得委派给子代理。

## 从对话开始，后续再自动化

当有意使用时，子代理才能发挥其全部价值。Claude 提供的自动调用是有帮助的，但知道何时委派研究、并行化工作和请求新视角，能产生比听天由命更好的结果。

使用子代理时，从对话式提示开始。注意哪些请求反复出现，并在这些模式明确后构建自动化。目标是让子代理委派变得毫不费力，这样你的注意力就能保持在重要的工作上。
