# 代理身份：面向自主化、全团队AI的新型访问模型 | Claude by Anthropic

**日期：** 2026-06-24 00:00 UTC  
**链接：** https://claude.com/blog/agent-identity-access-model

---

为了让AI代理在人类-代理团队中发挥最佳作用，它需要能够访问人类所使用的相同工具、文档和上下文。

在“单人”AI体验中（一个人与一个助手聊天），这很简单：你连接你自己的账户，代理代表你行事。但在像 [Claude Tag](http://anthropic.com/news/introducing-claude-tag) 这样的“多人协作”AI体验中，Claude 同时与多人处于一个共享频道中，它使用的是属于*工作空间*（而非任何个人）的工具和上下文。

为了让多人协作体验得以实现，Claude 需要为这些工具拥有自己的账户，由管理员设置并绑定到工作空间。我们将这种访问模型称为***代理身份***。

在这篇文章中，我们将解释代理身份如何工作，它如何将权限从按用户分配转变为按频道分配，以及如何在您自己的工作空间中合理划定其范围。

## **为什么“以用户身份行事”不可行**

当您将AI用作个人助手时，您可以连接 Google Drive、GitHub 和日历等平台，让模型使用*您自己的*访问权限在这些平台中进行读写。

这种模型不适用于 Claude Tag，原因有二：

* **代理自主性不断增强。** AI代理能够独立可靠完成的任务时长[大约每四个月翻一番](https://www.anthropic.com/institute/recursive-self-improvement)。现在，代理可以自行安排未来的任务，并在请求者下线很久之后对事件做出响应。虽然用户可以设置例程，让代理在特定情况下触发行动，但代理在很大程度上是自主工作的。

* **多人协作团队。** Claude Tag 将 Claude 放置在团队已经在协作的共享空间中——例如，一个三位工程师和一位产品经理正在一起调试的频道。但当不止一个人进行引导时，应用谁的权限？永远没有一个单一的合适人选。这使管理员能够独立于相关人类，定义代理在 Slack 中可以做什么，并对 Slack 中完成的操作进行明确追踪。

### Claude 以自身身份行事

在启用了 Claude Tag 的频道中，Claude 并不是代表单个用户行事。它在所接触的每个系统中都有自己的账户：它作为 Claude 应用在 Slack 中发帖，作为 Claude GitHub 应用发起拉取请求，并通过管理员预配的服务账户查询您的数据仓库。

而且由于没有涉及个人用户凭据，共享频道永远不会成为进入某人私人文档的后门。

### 权限继承

在代理身份模型中，管理员在工作空间级别定义一个身份——Claude 在所有地方持有一组基础连接和技能——每个频道默认继承该身份。然后，在合理的情况下，管理员可以在频道级别覆盖它，例如授予工程频道访问 GitHub 和数据仓库的权限，或者将 CRM 连接限制在单个私有频道内。

除了凭据之外，管理员还定义：

* **仓库访问权限：** Claude 可以读写哪些仓库。
* **连接器：** Claude 用来完成工作的工具和 API 密钥。在整个组织中，不同的 API 密钥可以以不同的权限级别连接到同一服务（例如，在通用频道中，Claude 可能被授予数据仓库的只读权限，而在数据团队的私有频道中则被授予写入权限）。
* **技能和插件：** Claude 动态加载的指令、脚本和资源文件夹，以提高在专业任务上的表现。
* **常驻指令：** 每个频道的自定义指令和上下文。

由于这种模型围绕不同的 Claude 身份运作，撤销该身份将终止 Claude 在所有使用该身份的地方的访问权限。相比审计数十个用户账户中单个代理的操作，管理起来要省力得多。

## 代理身份模型如何工作

代理身份将“这个用户能做什么？”的问题替换为“这个代理在这个隔离区内能做什么？”这与按用户的访问控制列表有所不同：这意味着一个没有直接仓库访问权限的频道成员，如果频道的配置文件中授予了 Claude 该权限，可以要求 Claude 读取该仓库。

这非同寻常，但我们认为这是迈向适用于自主化、多人协作代理的访问模型的必要一步。下面，我们概述了如何考虑设置这些边界。

### 身份边界如何工作

Claude Tag 为每个私有频道创建一个独特的身份；工作空间中的公共频道共享一个工作空间级别的身份。Claude 在法律频道的身份无法访问未在该频道授予的代码，其在工程频道的身份也无法读取未在该频道授予的法律文档。记忆和访问都尊重这些边界：Claude 在私有频道中学到的东西永远不会出现在更广泛的工作空间中。

身份属于频道，因此默认情况下频道中的任何人都可以 @提及 Claude，管理员可以将每个频道的配置文件范围限定为权限最低的成员。在企业版计划中，基于角色的访问控制让管理员可以进一步决定哪些成员可以调用 Claude，从而使频道既控制代理可以访问什么，也控制谁可以提出请求。

### 对工具和上下文的广泛默认访问

团队如何在 Claude Tag 中划定 Claude 的工具访问范围：广泛的、低风险的集成在共享频道中以代理身份运行，而个人或团队特定的工具则留在私信中以用户身份运行。

在 Anthropic 内部运行 Claude Tag 时，我们发现其价值随着工具和上下文的访问而倍增。每个连接的系统都让其他系统变得更有用，因为 Claude 可以跨系统组合上下文——从 Slack 中拉取一条线索，从 Drive 中拉取一份文档，从任务追踪系统中拉取一个工单，从数据仓库中拉取一条查询，最终整合成一个单一工具无法提供的答案。

那些从 Claude 中获得最大收益的团队，从一开始就授予其慷慨的访问权限，然后根据组织的管理偏好逐步收回权限。代理身份为 Claude 提供了足够宽泛的范围来做有价值的跨系统工作，同时边界足够严格，使得访问永远不会进入未被授予的地方。我们的建议是：先在几个频道中设置一个基准配置文件，阅读审计记录，然后在工作需要的时逐一有意识地扩展访问权限。

对于需要更细粒度的组织，管理员可以在特定频道中禁用 Claude Tag。管理员还可以应用基于角色的访问控制（RBAC）来限制特定用户对 Claude Tag 的访问。

### 私信

使用 Claude Tag 时，私信的工作方式与共享频道不同。私信在用户个人的 claude.ai 账户上运行——使用他们自己的连接器、凭据和名称。这使得私信成为与 Claude 合作处理那些绝不应该出现在频道中的任务和工具的正确场所，例如电子邮件草稿或只有您拥有许可证的软件。

### 安全与审计

当管理员将连接添加到频道的配置文件时，凭据会被独立存储并映射到该频道的身份，然后在请求时在网络边界注入。任何管理员未允许的主机的出站流量会被直接阻止。在审计方面，使用代理凭据进行的每个例程、每次内存写入和每次网络调用都会被记录，而且由于 Claude 使用自己的服务账户行事，这些操作也会出现在每个连接系统的自身日志中。

## 下一步计划

代理身份是 Claude Tag 访问模型的基础。未来，我们计划加强 Claude Tag 的安全功能，包括即时凭据授予——这样用户可以在当下批准单个敏感操作，而无需永久扩大代理的范围——以及为具有更复杂权限结构的组织提供身份感知覆盖。这将在代理作用域之上增加用户级检查，使得 Claude 仅在频道的配置文件和请求用户自身的权限都允许时才会操作。

从单人到多人协作 AI 的转变（如 Claude Tag 这样的产品）使得长期运行的、基于团队的工作成为可能。代理身份确保 Claude 对工具的访问足够广泛以发挥作用，同时又足够细分以在企业规模下保持安全。
