智能体需要可靠且高效地处理重复性任务。一个初次提示词即便能完成 80% 的任务，也会给用户带来嘈杂而烦人的体验。Warp 正是从这一教训中汲取经验，并将其融入产品战略，为全球近 100 万开发者带来了更优质的体验。

Warp 是一款 AI 驱动的终端和智能体开发环境，构建于 Claude 平台之上。团队最初在内部代码审查智能体上就遭遇了这种"嘈杂体验"问题。工程师们抱怨智能体给出的评论毫无帮助，产出的质量也很低。

团队最初尝试了一些权宜之计，例如根据观察到的代码审查失败案例手动重写提示词。这虽然让输出结果更可用，但无法规模化。改进上下文文件（如 AGENTS.md）也有一定帮助，但远非彻底的解决方案。

最终，团队意识到，真正的问题在于：无论智能体的用途是什么，反馈通常在会话结束时就会消失，从而将关键上下文从智能体闭环中移除。他们的解决方案是：基于 [Agent Skills（智能体技能）](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) 构建一个框架，使智能体能够自我改进——反馈随时间不断积累，持续优化和增强智能体的输出。

继续阅读，了解他们如何在 Claude 平台之上基于技能构建这一系统。

## **基于技能的智能体自我改进闭环**

核心方法是一个使用 [**技能**](https://support.claude.com/en/articles/12512176-what-are-skills) 的自我改进闭环。技能是以文件形式编码的知识，使指令无需直接写入原始提示词中。Warp 演化出一套自我改进的智能体架构，由两个技能组成，中间穿插人工反馈。

**内层/基础技能** 承载功能性领域知识和指令。例如，当一个 PR（合并请求）被提交时，Warp 的代码智能体即依据该基础技能和上下文执行，生成其审查结果。

对智能体输出的**人工反馈**是自我改进闭环的关键组成部分。对于代码审查而言，反馈可以简单到只是一个点赞，但越具体越好。

"用户可以肯定地说'这是一条很好、很有用的评论'，"Warp 创始人 Zach Lloyd 解释道，"但用户也可以详细说明某次代码审查为何不够好。像'你建议重命名这个变量，但我们代码库的规范是这类全局变量应使用这种特定命名方式'这样的具体描述，能告诉智能体下次该怎么做才对。"

**外层/改进技能** 充当一个观察者智能体，按调度运行而非按任务触发。它收集累积的人工反馈，将智能体的建议与人类的实际响应进行对比，然后为基础技能提出一个小型、聚焦的修改。

由于技能本质上是纯文件，智能体非常擅长对其进行更新。这些更新可审查、可审批、可合并，能够走正常的 PR/代码审查流程；一旦合并，下一次内层技能的运行便会继承这一改进。

Warp 如今已将这一模式应用于其整个开源代码仓库，分别设有规范编写、审查和问题分类智能体，每个智能体都拥有各自的自我改进闭环。

"基于文件的技能是一种为智能体编码知识的方式，而无需将知识直接放入提示词中，而是让智能体在执行任务过程中随时查阅，"Zach 说道。"这个框架其实非常简单：有一个基础领域技能，还有一个改进技能来优化该领域技能。这种简洁正是这一方法的美妙之处。"

## **如何为智能体编写自我改进型技能**

以下是 Warp 团队在智能体闭环中编写自我改进型技能时久经验证的建议：

* **写原则，而非规则。** "编写技能时，要像你在指导一个聪明人，而不是在编写程序，"Zach 说。"在技能中加入'寻找重复代码'这样的方向性指引，比列出一大堆变量命名规则更能提供有效指导。"
* **解释原因。** 提供规则背后的理由，能让智能体对问题进行推理，而非机械地遵循僵化指令，从而获得更好的泛化能力。
* **让反馈的给出尽可能轻松。** 在人们已有的工作流中收集反馈，例如直接在 PR 或 Issue 上评论。同时，让这一切自动完成，无需额外的提交步骤。"低摩擦才能让信号持续流动，"Zach 指出。"如果你设置得太复杂，就收不到反馈，也就无法改进技能。"
* **保持技能精简，采用渐进式披露。** [一个好的技能](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) 文件不会很大；它会引用资源文件和脚本，而非将所有内容一次性倾入上下文。
* **反馈质量 > 数量，但数量也有帮助。** 来自资深工程师的一小批详细、领域相关的反馈，可能比大量泛泛而谈的反馈更有价值，因为简单的点赞/点踩无法说明*原因*。"即使样本量较小，如果来自某位人员围绕领域知识的非常详细的反馈，你也能获得高质量的信号，而这些知识智能体本无从获取，"Zach 继续说道。"话虽如此，高质量信号的语料库越大越好。在 Warp，我们使用一个闭环来管理整个开源代码仓库。有数百人参与贡献，我们每周进行数千次代码审查。"
* **在改进技能上投入额外精力。** 在编写改进技能（即观察者智能体）上投入更多精力，其回报远超眼前的智能体闭环本身，因为改进技能在不同使用场景中非常通用。"除了领域知识部分之外，这是一个相当可复用的机制——代码审查智能体的改进技能与其他智能体的改进技能并没有太大区别。"

## **闭环实战：Warp 的 Issue 分类智能体**

[Warp 的 Issue 分类智能体](https://github.com/warpdotdev/warp-agents-demo-github-issue-triage) 展示了自我改进型智能体技能框架的实际应用。每当有人提交一个新的 GitHub Issue 时，该模式即被触发：一个 GitHub Action 会启动一个智能体，分析 Issue 的复杂度和可行性，分配标签，并建议修复方向。该分类智能体依据一个内层技能文件运行，其中包含每个标签含义的领域知识，以及采取行动前如何调研代码库的指引。

在一个示例 Issue 上，第一阶段的内层技能表现不错，但遗漏了一个标签——"ready to spec"（准备编写规范），该标签表示贡献者可以开始针对该 Issue 编写产品和技术规范。Warp 团队的一位维护者发现了这一遗漏，并直接在 Issue 上留下了反馈——正是工作正在进行的地方。关键在于，他不仅说明了预期结果，还解释了为何有此预期：这是一条可操作的反馈，便于智能体日后吸收。

外层改进技能在 [Oz（Warp 的智能体编排平台）](https://docs.warp.dev/) 中运行，作为一个按调度执行的"更新分类"智能体。该智能体先通过身份验证连接 GitHub，运行随技能捆绑的 Python 脚本拉取带有反馈的近期 Issue，将其汇总为一个 JSON 文件，再将该文件读回上下文。捆绑脚本本身即是一种最佳实践：技能可以引用资源文件，而非每次运行时重新编写代码。

在此基础上，智能体识别出维护者评论中的具体反馈信号，并提出了能涵盖这些信号的最小修改。它提交了一个 PR，修改内层技能，使智能体在 Issue 描述了一个真实问题但具体 UI 或 UX 形态尚未确定时，也能应用"ready to spec"标签。

由于整个更新就是一个技能文件，它走的是正常的代码审查流程。该 PR 附带了说明，解释了哪些信号触发了此次变更以及具体改了什么。人工审查、审批、合并后，下一次分类技能的运行即继承了新的知识。最后这一步人工环节闭环了整个流程，确保始终有人掌控实际变更的内容。

Warp 如今已将同一机制在开源代码仓库中大规模运行，其中规范编写智能体、审查智能体和分类智能体各自携带自己的自我改进闭环。

任何智能体，无论其任务是什么，只要从一开始就构建这样一个闭环来捕捉人工反馈信号、将其转化为技能更新，就能随时间不断进化——从一次性的辅助工具成长为能够在整个组织中持续积累能力的系统。

| 你的领域是否可验证？ | 先构建验证测试框架，再让智能体据此调优：生成参考语料，将输出与参考对比，修正，重复。 |
| 如果领域不可验证呢？ | 在存在黄金标准输出的地方，尽量依赖确定性评估。必须使用人工反馈时，将其限定在领域专家范围内——不要广开门路。 |
| 如何判断整个系统在进步？ | 追踪人们已经在关注的全局指标——合并周期、贡献者数量、成本——并将它们反馈给改进智能体。在部署上遵循"爬行-行走-奔跑"的渐进策略。 |

## **闭环实战：Warp 的 Issue 分类智能体**

[Warp 的 Issue 分类智能体](https://github.com/warpdotdev/warp-agents-demo-github-issue-triage) 展示了自我改进型智能体技能框架的实际应用。每当有人提交一个新的 GitHub Issue 时，该模式即被触发：一个 GitHub Action 会启动一个智能体，分析 Issue 的复杂度和可行性，分配标签，并建议修复方向。该分类智能体依据一个内层技能文件运行，其中包含每个标签含义的领域知识，以及采取行动前如何调研代码库的指引。

在一个示例 Issue 上，第一阶段的内层技能表现不错，但遗漏了一个标签——"ready to spec"（准备编写规范），该标签表示贡献者可以开始针对该 Issue 编写产品和技术规范。Warp 团队的一位维护者发现了这一遗漏，并直接在 Issue 上留下了反馈——正是工作正在进行的地方。关键在于，他不仅说明了预期结果，还解释了为何有此预期：这是一条可操作的反馈，便于智能体日后吸收。

外层改进技能在 [Oz（Warp 的智能体编排平台）](https://docs.warp.dev/) 中运行，作为一个按调度执行的"更新分类"智能体。该智能体先通过身份验证连接 GitHub，运行随技能捆绑的 Python 脚本拉取带有反馈的近期 Issue，将其汇总为一个 JSON 文件，再将该文件读回上下文。捆绑脚本本身即是一种最佳实践：技能可以引用资源文件，而非每次运行时重新编写代码。

在此基础上，智能体识别出维护者评论中的具体反馈信号，并提出了能涵盖这些信号的最小修改。它提交了一个 PR，修改内层技能，使智能体在 Issue 描述了一个真实问题但具体 UI 或 UX 形态尚未确定时，也能应用"ready to spec"标签。

由于整个更新就是一个技能文件，它走的是正常的代码审查流程。该 PR 附带了说明，解释了哪些信号触发了此次变更以及具体改了什么。人工审查、审批、合并后，下一次分类技能的运行即继承了新的知识。最后这一步人工环节闭环了整个流程，确保始终有人掌控实际变更的内容。

Warp 如今已将同一机制在开源代码仓库中大规模运行，其中规范编写智能体、审查智能体和分类智能体各自携带自己的自我改进闭环。

任何智能体，无论其任务是什么，只要从一开始就构建这样一个闭环来捕捉人工反馈信号、将其转化为技能更新，就能随时间不断进化——从一次性的辅助工具成长为能够在整个组织中持续积累能力的系统。

| Warp 团队的最佳实践 | |
| --- | --- |
| 你是否将技能与记忆混淆了？ | 技能是程序性的、稳定的——"如何做 X"，与运行无关，经审慎修改。记忆则由智能体在推理时自动写入，且永不停止变化。 |
| 你需要一个改进闭环，还是每个智能体各一个？ | 取折中方案：用一个模板化的基础闭环覆盖各智能体间的共性，再叠加领域特定的权重。少量改进器可各管一个；上百个则应共享。 |
| 当反馈本身有误时怎么办？ | 假设它一定会出错。不要让智能体盲目接受反馈——给它上下文进行合理性校验，过滤哪些人的输入有效，并在过滤阶段或最终审查阶段保留人工介入。 |
| 你的领域是否可验证？ | 先构建验证测试框架，再让智能体据此调优：生成参考语料，将输出与参考对比，修正，重复。 |
| 如果领域不可验证呢？ | 在存在黄金标准输出的地方，尽量依赖确定性评估。必须使用人工反馈时，将其限定在领域专家范围内——不要广开门路。 |
| 如何判断整个系统在进步？ | 追踪人们已经在关注的全局指标——合并周期、贡献者数量、成本——并将它们反馈给改进智能体。在部署上遵循"爬行-行走-奔跑"的渐进策略。 |
