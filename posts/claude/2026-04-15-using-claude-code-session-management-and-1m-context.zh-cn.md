# 使用 Claude Code：会话管理与 100 万上下文

            **日期：** 2026-04-15 00:00 UTC
            **链接：** https://claude.com/blog/using-claude-code-session-management-and-1m-context

            ---

            我们发布了 **`/usage`**，这是一个新的斜杠命令，可帮助您了解 Claude Code 的使用情况。此功能基于与客户的多轮对话而开发。

在这些对话中反复出现的一个问题是，用户管理会话的方式存在很大差异，尤其是在我们为 Claude Code 更新了 100 万上下文之后。

您是只使用一个会话，还是在终端中保持打开两个会话？您是否每次提示都启动一个新会话？您何时使用 [compact](https://platform.claude.com/docs/en/build-with-claude/compaction)、rewind 或 [subagents](https://code.claude.com/docs/en/sub-agents)？是什么导致了不良的 compact 或不良的会话？

这里有大量细节，可以真正塑造您使用 [Claude Code](https://code.claude.com/docs/en/overview) 的体验，而几乎所有细节都源于 [管理您的上下文窗口](https://code.claude.com/docs/en/how-claude-code-works)。

## **关于上下文、上下文压缩和上下文衰退的快速入门**

上下文窗口是模型在生成下一个响应时能够同时"看到"的所有内容。它包括您的系统提示、到目前为止的对话、每次工具调用及其输出，以及每个已读取的文件。Claude Code 拥有 100 万个 token 的上下文窗口。

不幸的是，使用上下文会对性能产生轻微影响，这通常被称为上下文衰退。上下文衰退是指随着上下文增长，模型性能会下降，因为注意力分散到更多 token 上，而较旧、不相关的内容开始干扰当前任务。

上下文窗口是一个硬性截止点，因此当您接近上下文窗口的末尾时，您正在处理的任务会自动被总结为一个更小的描述，模型会在一个新的上下文窗口中继续工作。我们称之为上下文压缩。您也可以自己触发上下文压缩。

## **每一步都是一个分支点**

假设您刚刚让 Claude 做某事并且它已完成——现在您的上下文中已有一些信息（工具调用、工具输出、您的指令），并且对于下一步做什么，您有令人惊讶的多种选择：

* **继续** — 在同一会话中发送另一条消息
* **`/rewind` (esc esc)** — 跳回上一条消息并从那里重试
* **`/clear`** — 开始一个新会话，通常带有一个您从刚学到的内容中提炼出的简报
* **Compact** — 总结到目前为止的会话，并在该总结的基础上继续
* **Subagents** — 将下一部分工作委托给一个拥有自己干净上下文的代理，只将其结果拉回

虽然最自然的做法是继续，但其他四个选项的存在是为了帮助管理您的上下文。

## **何时开始新会话**

何时保持一个长时间运行的会话，何时开始一个新的会话？我们的一般经验法则是：当您开始一个新任务时，您也应该开始一个新会话。

虽然 100 万上下文窗口意味着您现在可以更可靠地完成更长的任务，例如从头构建一个全栈应用，但上下文衰退仍可能发生。

有时您可能会执行相关的任务，其中部分上下文仍然必要，但并非总是如此。例如，为您刚刚实现的功能编写文档。虽然您可以开始一个新会话，但 Claude 必须重新读取您刚刚实现的文件，这会更慢且更昂贵。

## **回退而非纠正**

在 Claude Code 中，双击 Esc（或运行 `/rewind`）可以让您跳回到之前的任何一条消息，并从此处重新提示。该点之后的消息将从上下文中删除。

回退通常是更好的纠正方法。例如，Claude 读取了五个文件，尝试了一种方法，但没有成功。您的本能可能是输入"那没成功，试试 X 代替。"但更好的做法可能是回退到文件读取之后，并用您学到的东西重新提示。"不要使用方法 A，foo 模块没有暴露那个——直接转到 B。"

您也可以使用 *"summarize from here"* 或 `/rewind` 斜杠命令，让 Claude 总结其学习成果并创建一个交接消息，有点像来自尝试过某方法但未成功的未来自我，给前一次迭代的 Claude 的消息。

## **压缩与启动新会话**

一旦会话变长，您有两种方法可以去除无关上下文：`/compact` 或 `/clear`（并重新开始）。它们感觉相似，但行为却大不相同。

**Compact** 要求模型总结到目前为止的对话，然后用该总结替换历史记录。它是有损的，但您不必自己编写任何内容，而且 Claude 可能更全面地包含重要的学习成果或文件。您也可以通过传递指令来引导它（`/compact focus on the auth refactor, drop the test debugging`）。

使用 `/clear`，*您* 写下重要的内容（"我们正在重构 auth 中间件，约束条件是 X，重要的文件是 A 和 B，我们已经排除了方法 Y"）并重新开始。这需要更多工作，但生成的上下文是您认为相关的内容。

## **什么导致不良的自动压缩？**

如果您运行大量长时间运行的会话，您可能已经注意到某些情况下压缩可能特别糟糕。在这种情况下，我们经常发现，当模型无法预测您工作的方向时，可能会发生不良压缩。

在上面的例子中，自动压缩在一次长时间的调试会话后触发，并总结了调查过程，而您的下一条消息是"现在修复我们在 bar.ts 中看到的那个其他警告。"

但由于会话专注于调试，那个其他警告可能已从总结中被删除。

这尤其困难，因为由于上下文衰退，模型在压缩时处于其最不智能的状态。拥有 100 万上下文，您有更多时间主动使用 `/compact`，并附带您想要做什么的描述。

## **子代理和全新的上下文窗口**

[子代理](https://claude.com/blog/subagents-in-claude-code) 在您预先知道某部分工作会产生大量您不再需要的中间输出时，往往效果良好。

当 Claude 通过 Agent 工具生成一个子代理时，该子代理会获得自己全新的上下文窗口。它可以做它需要的任何工作，然后综合其结果，以便只有最终报告返回给父代理。

我们在 Anthropic 使用的思维测试是：*我还会需要这个工具输出吗，还是只需要结论？*

虽然 Claude Code 会自动调用子代理，但您可能希望明确告诉它这样做。例如，您可能希望告诉它：

* "启动一个子代理，根据以下规范文件验证此工作的结果"
* "启动一个子代理，阅读这个其他代码库，总结它如何实现 auth 流程，然后以相同方式自己实现"
* "启动一个子代理，根据我的 git 变更为此功能编写文档"

**综合运用**

为了帮助您选择使用哪个上下文管理功能，我们整理了这张有用的表格，概述了常见情况、应该使用什么工具以及原因。

| 情况 | 考虑使用 | 原因 |
| --- | --- | --- |
| 相同任务，上下文仍然相关 | 继续 | 窗口中的所有内容仍然有用；不要为重建它付出代价。 |
| Claude 走错了路 | Rewind（`双击 Esc`） | 保留有用的文件读取，丢弃失败的尝试，用您学到的东西重新提示。 |
| 任务进行中但会话充满了过时的调试/探索 | `/compact <提示>` | 低工作量；Claude 决定什么重要。必要时用指令引导它。 |
| 开始一个真正的新任务 | `/clear` | 零衰退；您精确控制哪些内容向前传递。 |
| 下一步将产生大量您只需要结论的输出（代码库搜索、验证、文档编写） | 子代理 | 中间工具噪音保留在子代理的上下文中；只有结果返回。 |
