# 将 Claude Opus 4.7 与 Claude Code 结合使用的最佳实践

            **日期：** 2026-04-16 00:00 UTC
            **链接：** https://claude.com/blog/best-practices-for-using-claude-opus-4-7-with-claude-code

            ---

            [Opus 4.7](https://www.anthropic.com/news/claude-opus-4-7) 是我们迄今为止在编码、企业工作流程和长时间运行的代理型任务中最强大的通用模型。它比 Opus 4.6 能更好地处理歧义，在发现错误和审查代码方面能力更强，能更可靠地跨会话携带上下文，并且能在较少指导下推理模糊任务。

在我们的[发布公告](https://www.anthropic.com/news/claude-opus-4-7)中，我们注意到两个变化——更新的分词器以及在更高努力级别下（尤其是在较长会话的后几轮交互中）倾向于更多思考——会影响令牌使用量。因此，当用 Opus 4.7 替换 Opus 4.6 时，需要进行一些调整才能达到最佳性能。对提示词和测试框架进行一些微调可以带来很大的不同。

本文将介绍哪些内容发生了变化，以及如何在 Claude Code 中最有效地使用 Opus 4.7。

## 构建交互式编码会话

Opus 4.7 的令牌使用和行为可能因您是部署具有单次用户轮次的更自主、异步编码代理，还是部署具有多次用户轮次的更交互式、同步编码代理而有所不同。在交互式环境中，它在用户轮次后推理更多：这提高了其在长时间会话中的连贯性、指令遵循和编码质量，但也倾向于使用更多令牌。

为了在 Claude Code 中充分利用 Opus 4.7，我们发现将 Claude 视为一位您委派任务的有能力的工程师，而不是一位您逐行指导的结对编程伙伴，会更有帮助：

* **在第一次轮次中预先指定任务。** 包含意图、约束、验收标准和相关文件位置的明确任务描述，为 Opus 4.7 提供了交付更强大输出所需的上下文。跨多个轮次逐步传达的模糊提示往往会降低令牌效率，有时还会降低整体质量。
* **减少所需的用户交互次数。** 每次用户轮次都会增加推理开销。批量提出您的问题，并为模型提供其继续前进所需的上下文。
* **在适当时使用**[**自动模式**](https://claude.com/blog/auto-mode)**。** 对于您信任模型无需频繁检查即可安全执行的任务，自动模式可以缩短周期时间。它特别适合您已预先提供完整上下文的长时间运行任务。自动模式现已面向 Claude Code Max 用户提供研究预览——您可以使用 Shift+Tab 切换开启。
* **设置任务完成通知。** 让 Claude 在完成任务时播放声音，它可以创建自己的基于钩子的通知。

## Opus 4.7 的推荐努力设置

Opus 4.7 在 Claude Code 中的默认努力级别现在是 `xhigh`。这是一个介于 `high` 和 `max` 之间的新努力级别，让用户能更好地控制困难问题上的推理与延迟之间的权衡。我们推荐在大多数代理型编码工作中使用 xhigh，特别是对于对智能敏感的任务，如设计 API 和模式、迁移遗留代码以及审查大型代码库。

以下是每个努力级别的一些额外指导：

* **`medium` 和 `low`**：适用于对成本敏感、对延迟敏感或范围严格限定的工作。模型在较难任务上的能力会低于更高努力级别，但它仍然优于以相同努力级别运行的 Opus 4.6——有时使用的令牌更少。
* **`high`**：平衡智能和成本。如果您正在运行并发会话或希望在不大幅降低质量的情况下减少支出，请选择 high。
* **`xhigh`（默认，推荐）**：适用于大多数编码和代理型用途的最佳设置。它具有强大的自主性和智能性，而不会产生 max 在长时间代理型运行中可能产生的失控令牌使用量。
* **`max`**：在真正困难的问题上榨取额外性能，但显示出收益递减，并且更容易过度思考。请有目的地使用它，例如在评估中测试模型的最大能力上限，以及用于对智能极度敏感且对成本不敏感的用途。

如果您正在升级到新模型，我们建议尝试不同的努力级别，而不是仅仅移植旧设置。您可以在同一任务期间在不同努力级别之间切换，以更有效地管理令牌使用和推理。

我们将 Opus 4.7 的默认努力级别设置为 xhigh，因为我们相信它是大多数编码任务的最佳设置。如果您是现有的 Claude Code 用户，但尚未手动设置您的努力级别，您将自动升级到 `xhigh`。您仍然可以手动调整您的努力级别。

## 使用自适应思考

**Opus 4.7 不支持具有固定思考预算的扩展思考。** 相反，Opus 4.7 提供自适应思考。这使得思考在每一步都是*可选的*，并允许模型根据上下文决定何时使用更多思考。它可以快速响应简单查询，在某个步骤不会受益时跳过思考，并将其思考令牌投入到最有可能有用的地方。在代理型运行过程中，这可以累积成更快的响应和更好的用户体验。

自适应思考在此版本中有了显著改进——特别是，Opus 4.7 不太容易过度思考。

如果您想对思考速率有更多控制，可以直接在提示中要求：

* **如果您想要更多思考，** 可以尝试类似“在回应前仔细、逐步地思考；这个问题比看起来更难。”的表述。
* **如果您想要更少思考，** 可以尝试类似“优先快速回应，而不是深入思考。有疑问时，直接回应。”的表述。您将节省令牌，但可能会在较难的步骤上损失一些准确性。

## 值得了解的行为变化

Opus 4.6 和 4.7 之间的一些默认行为发生了变化，如果您为旧模型精心调整了提示词或测试框架，这些变化值得了解。

**响应长度根据任务复杂性进行校准。** Opus 4.7 不像 Opus 4.6 那样默认冗长。您可以预期在简单查询上得到较短的答案，在开放式分析上得到较长的答案。如果您的用例依赖于特定的长度或风格，请在提示中明确说明。我们发现，您想要风格的正面示例比负面的“不要这样做”指令效果更好。

**模型调用工具的频率降低，推理更多。** 这在许多情况下会产生更好的结果。如果您想要*更多*工具使用（例如，在代理型工作中更积极的搜索或文件读取），请提供明确描述何时以及为何应使用该工具的指导。

**它默认生成更少的子代理。** Opus 4.7 在决定何时将工作委派给子代理时往往更加审慎。如果您的用例受益于并行子代理（例如，分散到多个文件或独立项目），我们建议明确说明。例如：

不要为可以在单个响应中直接完成的工作生成子代理（例如，重构您已经可以看到的函数）。在分散处理多个项目或读取多个文件时，在同一轮次中生成多个子代理。

## 接下来尝试什么

Opus 4.7 在长时间运行的任务上比以前的模型表现更好。这使得它非常适合那些监督曾经是瓶颈的任务，例如复杂的多文件更改、模糊调试、跨服务的代码审查以及多步骤代理型工作。

我们建议将努力级别保持在 `xhigh`，并看看您的第一次轮次能走多远。
