智能体手动测试
编码智能体的定义性特征在于它能够执行自己编写的代码。正是这一点使得编码智能体比那些仅输出代码却无法验证的LLM有用得多。
切勿假设LLM生成的代码能正常工作，除非该代码已被执行。
编码智能体有能力确认它们生成的代码是否按预期工作，或者进一步迭代修改代码直至其符合要求。
让智能体编写单元测试，尤其是采用测试优先的TDD，是确保它们已实际运行所编写代码的有效方法。
但这并非唯一值得采用的方法。
代码通过测试并不意味着它就能按预期工作。任何使用过自动化测试的人都曾遇到过这种情况：所有测试都通过了，但代码本身却以某种明显的方式失败——它可能在启动时导致服务器崩溃、未能显示关键的UI元素，或者遗漏了测试未覆盖的某些细节。
自动化测试无法替代手动测试。我喜欢在将某个功能纳入发布版本之前，亲眼看到它正常工作。
我发现让智能体手动测试代码同样很有价值，经常能揭示自动化测试未发现的问题。
智能体手动测试的机制
智能体应如何“手动”测试一段代码，取决于该代码的具体内容。
对于Python库，一个有用的模式是 `python -c "... code ..."`。你可以直接将一段（或多行）Python代码字符串传递给Python解释器，包括导入其他模块的代码。
编码智能体都熟悉这个技巧，有时无需提示就会使用它。不过，提醒它们使用 `python -c` 进行测试通常很有效：
使用 `python -c` 在一些边界情况下尝试那个新函数
其他语言可能有类似的机制，如果没有，智能体快速编写一个演示文件然后编译运行它也很方便。我有时会鼓励它使用 `/tmp` 目录，纯粹是为了避免这些文件日后被意外提交到代码库。
在 `/tmp` 中编写代码来测试该函数的边界情况，然后编译并运行它
我的许多项目涉及构建带有JSON API的Web应用程序。对于这些，我告诉智能体使用 `curl` 来测试它们：
运行开发服务器并使用 `curl` 探索那个新的JSON API
告诉智能体“探索”通常会导致它尝试新API的许多不同方面，这可以快速覆盖大量测试场景。
如果智能体在手动测试中发现某些功能无法工作，我喜欢告诉它们用红/绿TDD来修复它。这能确保新的用例最终被永久性的自动化测试所覆盖。
对Web UI使用浏览器自动化
如果项目涉及交互式Web UI，建立手动测试流程会变得更有价值。
历史上，这些很难通过代码进行测试，但过去十年，用于自动化真实浏览器的系统取得了显著改进。在真实环境中，使用真实的Chrome、Firefox或Safari浏览器来测试应用程序，可以发现各种有趣的问题。
编码智能体非常擅长使用这些工具。
目前最强大的是Playwright，这是一个由微软开发的开源库。Playwright提供了功能齐全的API，支持多种流行编程语言的绑定，并且可以自动化任何流行的浏览器引擎。
简单地告诉你的智能体“用Playwright测试那个”可能就足够了。然后智能体可以选择最合适的语言绑定，或者使用Playwright的playwright-cli工具。
编码智能体与专用CLI配合得非常好。Vercel的agent-browser是一个围绕Playwright构建的综合性CLI包装器，专为编码智能体使用而设计。
我自己的项目Rodney也服务于类似的目的，尽管它使用Chrome DevTools协议直接控制Chrome实例。
以下是我用来通过Rodney测试功能的示例提示：
启动开发服务器，然后使用 `uvx rodney --help` 来测试新的主页，查看截图以确认菜单位置正确
这个提示包含了三个技巧：
说“使用 uvx rodney --help”会让智能体通过uvx包管理工具运行rodney --help，这会在首次调用时自动安装Rodney。
`rodney --help` 命令专门设计用于向智能体提供理解和使用该工具所需的一切信息。这是该帮助文本。
说“查看截图”暗示智能体应该使用 `rodney screenshot` 命令，并提醒它可以利用自身的视觉能力来分析生成的图像文件，以评估页面的视觉外观。
这在一个简短的提示中融入了大量的手动测试！
Rodney及类似工具提供了广泛的功能，从在加载的网站上运行JavaScript，到滚动、点击、输入，甚至读取页面的无障碍访问树。
与其他形式的手动测试一样，通过浏览器自动化发现并修复的问题，随后也可以添加到永久性的自动化测试中。
过去，许多开发者避免使用过多的自动化浏览器测试，因为它们以不稳定著称——对页面HTML的微小调整都可能导致令人沮丧的测试失败浪潮。
让编码智能体长期维护这些测试，极大地减少了在面对Web界面设计变更时保持测试更新的阻力。
让它们用Showboat做笔记
让智能体手动测试代码可以发现额外的问题，同时也可以用来创建有助于记录代码并展示其测试过程的工件。
我对让智能体展示其工作过程的挑战很着迷。能够看到演示或记录下来的实验，是确认智能体已全面解决所给挑战的一种非常有用的方式。
我构建了Showboat来促进构建能捕捉智能体手动测试流程的文档。
以下是我经常使用的一个提示：
运行 `uvx showboat --help`，然后创建一个 `notes/api-demo.md` showboat文档，并用它来测试和记录那个新的API。
与上面的Rodney类似，`showboat --help` 命令会教给智能体Showboat是什么以及如何使用它。这是完整的帮助文本。
Showboat的三个关键命令是 `note`、`exec` 和 `image`。
`note` 向Showboat文档追加一条Markdown笔记。`exec` 记录一条命令，然后运行该命令并记录其输出。`image` 向文档添加一张图片——对于使用Rodney截取的Web应用程序截图很有用。
`exec` 命令是其中最重要的，因为它捕获了命令及其产生的输出。这展示了智能体做了什么以及结果是什么，并且旨在阻止智能体作弊，将其期望发生的情况写入文档。
我发现Showboat模式在记录我的智能体会话期间所完成的工作方面效果非常好。我希望能看到类似的模式在更广泛的工具集中被采用。
