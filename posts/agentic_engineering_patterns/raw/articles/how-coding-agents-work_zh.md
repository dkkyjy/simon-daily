编码智能体如何工作
与任何工具一样，了解编码智能体在底层如何工作，可以帮助您就如何应用它们做出更好的决策。
编码智能体是一种软件，它充当大型语言模型（LLM）的“驾驭器”，通过不可见的提示和可调用工具的形式实现的附加功能来扩展该 LLM 的能力。
大型语言模型
任何编码智能体的核心都是一个大型语言模型，即 LLM。这些模型有诸如 GPT-5.4、Claude Opus 4.6、Gemini 3.1 Pro 或 Qwen3.5-35B-A3B 等名称。
LLM 是一种可以补全文本句子的机器学习模型。给模型输入短语“the cat sat on the ”，它（几乎肯定）会建议“mat”作为句子的下一个词。
随着这些模型变得更大，并在越来越多的数据上进行训练，它们可以补全更复杂的句子——例如“a python function to download a file from a URL is def download_file(url): ”。
LLM 实际上并不直接处理单词——它们处理的是标记（token）。一段文本被转换成一个整数标记序列，因此“the cat sat on the ”变成了 [3086, 9059, 10139, 402, 290, 220]。这一点值得理解，因为 LLM 提供商根据处理的标记数量收费，并且一次能考虑的标记数量也有限制。
您可以在 platform.openai.com/tokenizer 上使用 OpenAI 的标记化工具进行实验，看看这是如何工作的。
输入到 LLM 的内容称为提示（prompt）。LLM 返回的文本称为补全（completion），有时也称为响应（response）。
当今许多模型是多模态的，这意味着它们可以接受不仅仅是文本作为输入。视觉 LLM（vLLMs）可以将图像作为输入的一部分，这意味着您可以向它们输入草图、照片或屏幕截图。一个常见的误解是这些图像会经过一个单独的 OCR 或图像分析过程处理，但实际上这些输入也被转换成了更多的整数标记，并以与文本相同的方式进行处理。
聊天模板化提示
最初的 LLM 作为补全引擎工作——用户需要提供一个提示，然后由模型进行补全，如上文所示的两个例子。
这并不特别用户友好，因此模型大多转而使用聊天模板化提示，这种提示将模型通信表示为模拟对话。
这实际上只是一种特殊格式的补全提示，看起来像这样：
user: write a python function to download a file from a URL
assistant:
这个提示的自然补全就是助手（由 LLM 代表）用一些 Python 代码来回答用户的问题。
LLM 是无状态的：每次执行提示时，它们都从同一张白纸开始。
为了维持对话的模拟，与模型对话的软件需要维护自己的状态，并在用户每次输入新的聊天提示时重放整个现有对话：
user: write a python function to download a file from a URL
assistant: def download_url(url):
    return urllib.request.urlopen(url).read()
user: use the requests library instead
assistant:
由于提供商对输入和输出标记都收费，这意味着随着对话变长，每个提示会变得更昂贵，因为输入标记的数量每次都在增加。
标记缓存
大多数模型提供商通过为缓存的输入标记提供更低的费率来部分抵消这一点——在短时间内处理过的常见标记前缀可以按较低费率收费，因为底层基础设施可以缓存并随后重用处理该输入所需的许多昂贵计算。
编码智能体的设计考虑到了这种优化——它们避免修改早期的对话内容，以确保尽可能高效地使用缓存。
调用工具
LLM 智能体的定义性特征是智能体可以调用工具。但什么是工具？
工具是智能体驾驭器提供给 LLM 的一个函数。
在提示本身层面，它看起来像这样：
system: 如果你需要获取天气信息，请在回合结束时使用 <tool>get_weather(city_name)</tool>
user: 旧金山的天气怎么样？
assistant:
这里助手可能会用以下文本回应：
<tool>get_weather("San Francisco")</tool>
然后，模型驾驭软件从响应中提取该函数调用请求——可能使用正则表达式——并执行该工具。
接着，它将结果返回给模型，并构造一个看起来像这样的提示：
system: 如果你需要获取天气信息，请在回合结束时使用 <tool>get_weather(city_name)</tool>
user: 旧金山的天气怎么样？
assistant: <tool>get_weather("San Francisco")</tool>
user: <tool-result>61°，局部多云</tool-result>
assistant:
现在，LLM 可以使用该工具结果来帮助生成用户问题的答案。
大多数编码智能体定义了十几个或更多的工具供智能体调用。其中最强大的工具允许代码执行——例如，用于执行终端命令的 Bash() 工具，或用于运行 Python 代码的 Python() 工具。
系统提示
在前面的例子中，我包含了一条标记为“system”的初始消息，它告知 LLM 可用的工具以及如何调用它。
编码智能体通常以这样的系统提示开始每次对话，该提示不会显示给用户，但会提供指示，告诉模型应该如何行为。

推理
2025 年的重大新进展之一是在前沿模型系列中引入了推理功能。
推理，有时在用户界面中呈现为“思考”，是指模型在向用户呈现回复之前，花费额外时间生成文本，来讨论问题及其潜在解决方案。
这可能看起来类似于一个人大声思考，并具有类似的效果。关键的是，它允许模型花费更多时间（和更多标记）来处理问题，以期获得更好的结果。
推理对于调试代码问题特别有用，因为它为模型提供了一个机会来导航更复杂的代码路径，混合工具调用，并利用推理阶段来追溯函数调用，找到问题的潜在根源。
许多编码智能体包含调整推理努力级别的选项，鼓励模型在更难的问题上花费更多时间“咀嚼”。
LLM + 系统提示 + 工具循环
信不信由你，这就是构建一个编码智能体所需的大部分内容！
如果您想更深入地了解这些东西是如何工作的，一个有用的练习是尝试从头开始构建您自己的智能体。一个简单的工具循环可以在现有 LLM API 的基础上用几十行代码实现。
一个好的工具循环比这需要更多的工作，但其基本机制出奇地简单明了。
