AI 应帮助我们产出更优质的代码
许多开发者担心，将代码外包给 AI 工具会导致质量下降，产生糟糕的代码，这些代码产出速度之快足以让决策者愿意忽视其缺陷。
如果采用编码智能体确实降低了您所产出的代码和功能的质量，您应该直接解决这个问题：找出流程中哪些环节损害了输出质量，并加以修复。
使用智能体产出更差的代码是一种选择。我们可以选择产出更好的代码。

避免承担技术债务
我喜欢从技术债务的角度来思考产出更好的代码。我们承担技术债务是权衡取舍的结果：用"正确的方式"做事耗时太长，因此我们在时间限制内工作，并祈祷我们的项目能存活足够长的时间，以便日后偿还这笔债务。
技术债务的最佳缓解方法是首先避免承担它。
根据我的经验，技术债务修复中常见的一类是简单但耗时的更改。
我们最初的 API 设计未能涵盖后来出现的一个重要情况。修复该 API 需要在几十个不同的地方更改代码，这使得添加一个非常相似但略有不同的新 API 并容忍重复变得更快。
我们早期为一个概念命名时做出了糟糕的选择——例如用了"teams"而不是"groups"——但在代码中到处清理这个命名工作量太大，所以我们只在 UI 中修复它。
随着时间的推移，我们的系统发展出了重复但略有不同的功能，需要合并和重构。
我们的某个文件已经增长到几千行代码，理想情况下我们应将其拆分为单独的模块。
所有这些更改在概念上都很简单，但仍需要投入时间，考虑到更紧迫的问题，这可能很难证明其合理性。

编码智能体可以为我们处理这些任务
像这样的重构任务是编码智能体的理想应用场景。
启动一个智能体，告诉它要更改什么，然后让它在一个分支或工作树中在后台自行处理。
我通常为此使用异步编码智能体，例如 Gemini Jules、OpenAI Codex web 或 Claude Code on the web。这样我就可以运行这些重构任务，而不会中断我在笔记本电脑上的工作流。
在 Pull Request 中评估结果。如果结果良好，就合并它。如果接近完成，就提示它并告诉它需要做哪些不同的调整。如果结果糟糕，就丢弃它。
这些代码改进的成本已降至如此之低，以至于我们可以对轻微的代码异味和不便采取零容忍态度。

AI 工具让我们能考虑更多选项
任何软件开发任务都有大量解决问题的方法。一些最严重的技术债务源于在规划步骤中做出糟糕的选择——错过了一个显而易见的简单解决方案，或者选择了一项后来证明并不完全合适的技术。
LLM 可以帮助确保我们不会错过任何以前可能未曾想到的明显解决方案。它们只会建议其训练数据中常见的解决方案，但这些往往是"无聊的技术"，最有可能奏效。
更重要的是，编码智能体可以帮助进行探索性原型设计。
做出可靠技术选择的最佳方法是通过原型证明它们适合用途。
对于预期有数千并发用户的网站，Redis 是活动信息流的合适选择吗？
确切知道的最佳方法是搭建一个该系统的模拟，并对其运行负载测试，看看哪里会出问题。
编码智能体可以根据一个精心设计的提示构建这种模拟，从而将此类实验的成本降至几乎为零。而且由于成本如此低廉，我们可以同时运行多个实验，测试几种解决方案，以选择最适合我们问题的那一个。

拥抱复合工程循环
智能体遵循指令。我们可以根据以往的经验，随着时间的推移不断改进这些指令，以便在未来运行时获得更好的结果。
Every 公司的 Dan Shipper 和 Kieran Klaassen 将他们公司与编码智能体合作的方法描述为"复合工程"。他们完成的每个编码项目都以回顾结束，他们称之为复合步骤，在此步骤中，他们会总结有效的方法并记录下来，供未来的智能体运行使用。
如果我们希望从智能体获得最佳结果，就应该致力于随着时间的推移不断提高代码库的质量。小的改进会复合增长。过去耗时的质量提升，其成本现已降至没有理由不在交付新功能的同时投资于质量。编码智能体意味着我们终于可以两者兼得。
