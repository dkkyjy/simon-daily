与编码智能体一起使用 Git
Git 是与编码智能体协作的关键工具。将代码置于版本控制之下，可以让我们记录代码随时间的变化，并调查和撤销任何错误。所有编码智能体都熟练掌握了 Git 的基本和高级功能。
这种熟练程度意味着我们在自己使用 Git 时可以更加雄心勃勃。我们不需要记住如何使用 Git 进行操作，但了解其可能性意味着我们可以充分利用 Git 的全部能力。

Git 要点
每个 Git 项目都存在于一个仓库中——磁盘上的一个文件夹，可以跟踪其中文件的更改。这些更改被记录在提交中——即带时间戳的、对一个或多个文件的更改集合，并附有描述这些更改的提交消息以及记录更改者的作者信息。
Git 支持分支，允许你独立地构建和试验新的更改。一旦分支被认为准备就绪，就可以（使用各种方法）将其合并回主分支。
Git 仓库可以被克隆到新的机器上，该克隆包含当前文件及其完整的更改历史记录。
这意味着开发者——或编码智能体——可以在无需额外网络流量的情况下浏览和探索该历史记录，使得深入查看历史记录几乎零成本。
Git 仓库可以仅存在于你自己的机器上，但 Git 的设计初衷是通过将其发布到远程仓库（可以是公开或私有的）来支持协作和备份。GitHub 是这些远程仓库最流行的托管地，但 Git 是开源软件，允许在任何支持 Git 协议的机器或服务上托管这些远程仓库。

核心概念与提示
编码智能体都深刻理解 Git 术语。以下提示应适用于其中任何一个：

在此处启动新的 Git 仓库
将智能体正在工作的文件夹转换为 Git 仓库——智能体可能会运行 `git init` 命令。如果你只说“仓库”，智能体会假定你指的是 Git 仓库。

提交这些更改
创建一个新的 Git 提交来记录智能体所做的更改——通常使用 `git commit -m "提交消息"` 命令。

添加 username/repo 作为 GitHub 远程仓库
这应该为你的仓库配置 GitHub。你需要先使用 github.com/new 创建一个新仓库，并配置你的机器以与 GitHub 通信。

查看今天所做的更改
或“最近的更改”或“最后三次提交”。
这是开始新的编码智能体会话的好方法。告诉智能体查看最近的更改会使其运行 `git log`，这可以立即加载其上下文，包含你最近工作内容的详细信息——包括修改的代码和描述它的提交消息。
以此方式为会话提供背景信息，意味着你可以开始讨论该代码——建议额外的修复、询问其工作原理，或提出基于先前工作的下一个更改。

讨论从主分支集成更改的选项
智能体非常擅长解释不同合并策略的优缺点，并且 Git 中的所有操作总是可以撤销，因此尝试新事物的风险很小。

帮我理清这个 Git 乱局

有很多方式会让你陷入 Git 的混乱，通常是通过以合并冲突结束的拉取或变基命令，或者仅仅是将错误的内容添加到 Git 的暂存区。
理清这些曾经是使用 Git 中最困难、最耗时的部分。现在不再如此！编码智能体可以处理最错综复杂的合并冲突，通过推理新代码的意图，找出要保留的内容以及如何合并冲突的更改。如果你的代码有自动化测试（应该有），智能体可以确保在最终完成合并之前这些测试通过。

查找并恢复我那个实现 ... 功能的代码
如果你丢失了正在处理但之前已提交（或用 `git stash` 保存）的代码，你的智能体很可能可以为你找到它。
Git 有一个称为 reflog 的机制，通常可以捕获未提交到永久分支的代码的详细信息。智能体可以搜索它，也可以搜索其他分支。
只需告诉它们要查找什么，然后看着它们深入挖掘。

使用 git bisect 查找此错误是何时引入的：...
Git bisect 是 Git 武器库中最强大的调试工具之一，但其学习曲线相对陡峭，常常使开发者望而却步。
当你运行 bisect 操作时，你需要向 Git 提供某种测试条件以及一个起始和结束的提交范围。然后 Git 会运行二分搜索，以确定你的测试条件最早在哪次提交中失败。
这可以高效地回答“是什么首次导致了此错误”的问题。唯一的缺点是需要以 Git bisect 可以执行的格式表达错误的测试。
编码智能体可以为你处理这些样板工作。这将 Git bisect 从一个偶尔使用的工具升级为你可以在任何对软件历史行为感到好奇时部署的工具。

重写历史
让我们进入有趣的高级内容。
Git 仓库的提交历史不是固定的。毕竟数据只是磁盘上的文件（隐藏在 `.git/` 目录中），而 Git 本身提供了可用于修改该历史的工具。
不要将 Git 历史视为实际发生事件的永久记录——相反，应将其视为一个精心编写的、描述软件项目进展的故事。
这个故事是辅助未来开发的工具。永久记录错误和已取消的方向有时可能有用，但仓库作者可以做出编辑决策，决定保留什么以及如何最好地记录该历史。
编码智能体非常擅长使用 Git 的高级历史重写功能。

撤销或重写提交
撤销最后一次提交
提交代码后又后悔是很常见的——例如，意识到它包含了一个你本不想包含的文件。对应的 Git 命令是 `git reset --soft HEAD~1`。我从来都记不住这个命令，现在我不需要记了！

从最后一次提交中移除 uv.lock
你也可以对提交进行更精细的操作——例如，重写提交以仅移除单个文件。

用更好的提交消息合并最后三次提交
智能体可以重写提交消息，并可以将多个提交合并为一个单元。
我发现前沿模型通常对提交消息有很好的品味。我曾经坚持自己写这些，但我已经接受它们产生的质量通常足够好，甚至常常比我亲自写的更好。

从旧仓库的碎片中构建新仓库
我发现自己经常使用的一个技巧是，从较大的仓库中提取代码到一个新仓库，同时保留该代码的关键历史记录。
一个常见的例子是库提取。我可能将一些类和函数构建到一个项目中，后来意识到它们更适合作为一个独立的可重用代码库。

在 /tmp/distance-functions 启动一个新仓库，并使用此处的 lib/distance_functions.py 模块在那里构建一个 Python 库——构建类似的提交历史，在新仓库中复制作者和提交日期
这类操作过去通常很复杂，以至于大多数开发者会创建一个脱离旧提交历史的全新副本。现在我们不必再满足于此了！
