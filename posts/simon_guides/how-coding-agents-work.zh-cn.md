# How coding agents work

与任何工具一样，了解编码代理（coding agent）在底层的工作原理，可以帮助你更好地决定如何应用它们。

编码代理是一种软件，它充当大语言模型（LLM）的“框架”（harness），通过由隐形提示（invisible prompts）驱动并作为可调用工具实现的方式，为该LLM扩展额外能力。

## 大语言模型

任何编码代理的核心都是一个大型语言模型，简称LLM。它们有诸如GPT-5.4、Claude Opus 4.6、Gemini 3.1 Pro或Qwen3.5-35B-A3B等名称。

LLM是一种能够补全文本句子的机器学习模型。给模型输入短语“the cat sat on the ”（猫坐在……上），它（几乎肯定会）建议“mat”（垫子）作为句子中的下一个词。

随着这些模型变得越来越大，并在越来越多的数据上进行训练，它们可以补全更复杂的句子——例如“a python function to download a file from a URL is def download_file(url): ”（一个用于从URL下载文件的Python函数是def download_file(url):）。

LLM实际上并不直接处理词语——它们处理的是令牌（tokens）。一段文本被转换成一串整数令牌，因此“the cat sat on the ”变成了[3086, 9059, 10139, 402, 290, 220]。理解这一点很重要，因为LLM提供商根据处理的令牌数量收费，并且它们在一次能考虑的令牌数量上存在限制。

你可以通过platform.openai.com/tokenizer上的OpenAI分词器进行实验，以了解其工作原理。

LLM的输入称为提示（prompt）。LLM返回的文本称为补全（completion），有时也称为响应（response）。

如今许多模型都是多模态的（multimodal），这意味着它们不仅能接受文本作为输入。视觉LLM（vLLMs）可以接受图像作为输入的一部分，这意味着你可以向它们提供草图、照片或屏幕截图。一个常见的误解是，这些图像会通过单独的OCR或图像分析过程进行处理，但实际上，这些输入会被转换成更多的整数令牌，并以与文本相同的方式进行处理。

## 聊天模板化提示

最初的LLM是作为补全引擎工作的——用户需要提供一个提示，然后模型可以对其进行补全，例如上面展示的两个例子。

这并非特别用户友好，因此模型大多转而使用聊天模板化提示（chat templated prompts），这种提示将与模型的通信表示为模拟对话。

实际上，这只是一种具有特殊格式的补全提示形式，看起来像下面这样。

用户：编写一个Python函数，用于从URL下载文件
助手：

```
用户：编写一个Python函数，用于从URL下载文件
助手：

```

这个提示的自然补全结果是，助手（由LLM代表）用一些Python代码来回答用户的问题。

LLM是无状态的：每次执行提示时，它们都从相同的空白状态开始。

为了维持对话的模拟效果，与模型对话的软件需要维护自己的状态，并在用户每次输入新的聊天提示时重放整个现有的对话：

用户：编写一个Python函数，用于从URL下载文件
助手：def download_url(url):
    return urllib.request.urlopen(url).read()
用户：改用requests库
助手：

```
用户：编写一个Python函数，用于从URL下载文件
助手：def download_url(url):
    return urllib.request.urlopen(url).read()
用户：改用requests库
助手：

```

由于提供商对输入和输出令牌都收费，这意味着随着对话变长，每个提示的成本都会增加，因为每次输入令牌的数量都在增长。

## 令牌缓存

大多数模型提供商通过为缓存输入令牌（cached input tokens）提供更低的费率来在一定程度上抵消这一点——在短时间内处理过的常见令牌前缀可以以较低的费率收费，因为底层基础设施可以缓存并重复使用处理该输入所需的大量昂贵计算。

编码代理在设计时就考虑到了这种优化——它们避免修改较早的对话内容，以确保尽可能高效地使用缓存。

## 调用工具

LLM代理（LLM agent）的定义性特征是代理可以调用工具（tools）。但什么是工具呢？

工具是一个函数，代理框架将其提供给LLM使用。

在提示本身层面，这看起来像下面这样：

系统：如果你需要访问天气信息，请以<tool>get_weather(city_name)</tool>结束你的回合
用户：旧金山的天气怎么样？
助手：

```
系统：如果你需要访问天气信息，请以<tool>get_weather(city_name)</tool>结束你的回合
用户：旧金山的天气怎么样？
助手：

```

在这里，助手可能会回复以下文本：

<tool>get_weather("San Francisco")</tool>

```
<tool>get_weather("San Francisco")</tool>

```

然后，模型框架软件从响应中提取该函数调用请求——可能使用正则表达式——并执行该工具。

然后，它将结果返回给模型，并构建一个类似下面这样的提示：

系统：如果你需要访问天气信息，请以<tool>get_weather(city_name)</tool>结束你的回合
用户：旧金山的天气怎么样？
助手：<tool>get_weather("San Francisco")</tool>
用户：<tool-result>61°，局部多云</tool-result>
助手：

```
系统：如果你需要访问天气信息，请以<tool>get_weather(city_name)</tool>结束你的回合
用户：旧金山的天气怎么样？
助手：<tool>get_weather("San Francisco")</tool>
用户：<tool-result>61°，局部多云</tool-result>
助手：

```

LLM现在可以使用该工具结果来帮助生成对用户问题的回答。

大多数编码代理会定义十几个或更多的工具供代理调用。其中最强大的工具允许执行代码——例如，一个Bash()工具用于执行终端命令，或一个Python()工具用于运行Python代码。

## 推理

2025年的一大新进展是将推理（reasoning）引入前沿模型系列。

推理，有时在用户界面中呈现为“思考”（thinking），是指模型花费额外时间生成文本，在向用户呈现回复之前，先讨论问题及其潜在解决方案。

这看起来类似于一个人大声思考，并且具有类似的效果。关键在于，它允许模型花费更多时间（和更多令牌）来解决问题，以期获得更好的结果。

推理对于调试代码中的问题特别有用，因为它让模型有机会导航更复杂的代码路径，混合使用工具调用，并利用推理阶段跟随函数调用回到问题的潜在源头。

许多编码代理都包含调高或调低推理努力程度的选项，鼓励模型在更困难的问题上花费更多时间进行思考。

## LLM + 系统提示 + 循环中的工具

信不信由你，这就是构建编码代理所需的大部分内容！

如果你想更深入地理解这些东西的工作原理，一个有用的练习是尝试从头开始构建你自己的代理。一个简单的工具循环可以通过在现有LLM API之上编写几十行代码来实现。

一个好的工具循环（good tool loop）的工作量远不止于此，但其基本机制却出奇地简单。
