# Using Git with coding agents

Git 是与编码智能体协作的关键工具。将代码纳入版本控制，使我们能够记录代码随时间的变化，并调查和撤销任何错误。所有编码智能体都精通 Git 功能的使用，无论是基础还是高级功能。

这种精通意味着我们在使用 Git 本身时可以更具雄心。我们无需记住如何用 Git 完成操作，但了解其可能性意味着我们可以充分利用 Git 的全部能力。

## Git 基础

每个 Git 项目都存在于一个**仓库**中——这是磁盘上的一个文件夹，可以跟踪其中文件的变化。这些变化记录在**提交**中——即对一个或多个文件的更改的时间戳集合，并附带一条**提交信息**描述这些更改，以及一个**作者**记录谁进行了更改。

Git 支持**分支**，允许你独立地构建和试验新更改。一旦分支被认为准备就绪，就可以（通过多种方法）**合并**回主分支。

Git 仓库可以**克隆**到新机器上，克隆包含当前文件及其完整的更改历史。这意味着开发者——或编码智能体——可以浏览和探索该历史，而无需额外网络流量，从而使历史探索几乎免费。

Git 仓库可以仅存在于你自己的机器上，但 Git 旨在通过将其发布到**远程**（可以是公开或私有的）来支持协作和备份。GitHub 是最流行的远程托管平台，但 Git 是开源软件，可以在任何支持 Git 协议的机器或服务上托管这些远程仓库。

## 核心概念与提示

编码智能体都对 Git 术语有深入理解。以下提示应适用于任何智能体：

**在此处启动一个新的 Git 仓库**\
将智能体正在处理的文件夹转换为 Git 仓库——智能体可能会运行 `git init` 命令。如果你只说“仓库”，智能体将默认指的是 Git 仓库。

**提交这些更改**\
创建一个新的 Git 提交来记录智能体所做的更改——通常使用 `git commit -m "提交信息"` 命令。

**将用户名/仓库添加为 GitHub 远程**\
这应配置你的仓库以连接 GitHub。你需要先使用 `github.com/new` 创建一个新仓库，并配置你的机器与 GitHub 通信。

**查看今天所做的更改**\
或“最近的更改”或“最后三次提交”。这是启动新编码智能体会话的绝佳方式。告诉智能体查看最近的更改会使其运行 `git log`，这可以立即加载你最近工作内容的上下文——包括修改的代码和描述这些更改的提交信息。

以这种方式“播种”会话意味着你可以开始讨论该代码——建议额外的修复、询问其工作原理，或提出基于之前内容的下一步更改。

**集成来自 main 的最新更改**\
在主分支上运行此命令以从远程仓库获取其他贡献，或在分支中运行以集成 main 上的最新更改。

有多种合并更改的方式，包括合并、变基、压缩或快进。如果你记不住这些细节也没关系：**讨论集成来自 main 的更改的选项**。智能体非常擅长解释不同合并策略的优缺点，并且 Git 中的所有操作都可以撤销，因此尝试新事物的风险极小。

**帮我解决这个 Git 混乱问题**

我出人意料地经常使用这个通用提示！这里有一个[最近的例子](https://example.com)，它修复了我因合并冲突而失败的 cherry-pick 操作。

有很多方式会让你陷入 Git 的混乱，通常是通过导致合并冲突的拉取或变基命令，或者仅仅是将错误的内容添加到 Git 的暂存环境。

解开这些曾经是使用 Git 最困难、最耗时的部分。但再也不会了！编码智能体可以导航最复杂的合并冲突，推理新代码的意图，并找出保留什么以及如何合并冲突的更改。如果你的代码有自动化测试（并且**应该**有），智能体可以在最终合并之前确保这些测试通过。

**查找并恢复我的执行……的代码**\
如果你丢失了之前已提交（或通过 `git stash` 保存）的工作代码，你的智能体很可能能为你找到它。

Git 有一种称为 **reflog** 的机制，通常可以捕获尚未提交到永久分支的代码细节。智能体可以搜索它，也可以搜索其他分支。

只需告诉它们要查找什么，然后看它们深入探索。

**使用 git bisect 查找此 bug 是在何时引入的：……**\
Git bisect 是 Git 工具集中最强大的调试工具之一，但它有一个相对陡峭的学习曲线，常常使开发者不愿使用它。

当你运行 bisect 操作时，你向 Git 提供某种测试条件以及开始和结束的提交范围。Git 随后运行二分搜索来识别你的测试条件失败的最早提交。

这可以高效地回答“是什么首先导致了此 bug”的问题。唯一的缺点是需要以 Git bisect 可以执行的格式表达 bug 的测试。

编码智能体可以为你处理这个样板工作。这将 Git bisect 从偶尔使用的工具升级为你可以随时部署的工具，只要你对软件的历史行为感到好奇。

## 重写历史

让我们进入有趣的高级内容。

Git 仓库的提交历史并非固定不变。毕竟数据只是磁盘上的文件（隐藏在 `.git/` 目录中），而 Git 本身提供了可用于修改该历史的工具。

不要将 Git 历史视为实际发生事件的永久记录——相反，应将其视为一个精心创作的**故事**，描述了软件项目的演进过程。

这个故事是辅助未来开发的工具。永久记录错误和取消的方向有时可能有用，但仓库作者可以做出编辑决策，决定保留什么以及如何最好地捕获该历史。

编码智能体非常擅长使用 Git 的高级历史重写功能。

### 撤销或重写提交

**撤销上一次提交**\
提交代码后又后悔是很常见的——例如，意识到其中包含了你本不想包含的文件。Git 的解决方案是 `git reset --soft HEAD~1`。我从来记不住这个命令，但现在我不需要了！

**从上次提交中移除 uv.lock**\
你还可以对提交进行更精细的手术——例如，重写提交以仅移除单个文件。

**合并最后三次提交并附上更好的提交信息**\
智能体可以重写提交信息，并可以将多个提交合并为一个单元。

我发现前沿模型通常在提交信息方面有非常好的品味。我曾经坚持自己编写这些信息，但我已经接受它们产生的质量通常足够好，而且通常比我自己的写得更好。

### 从旧仓库的片段构建新仓库

我发现经常使用的一个技巧是从较大的仓库中提取代码到一个新仓库，同时保留该代码的关键历史。

一个常见的例子是库提取。我可能在一个项目中构建了一些类和函数，后来意识到它们作为独立的可重用代码库更有意义。

**在 /tmp/distance-functions 启动一个新仓库，并在此处用 lib/distance\_functions.py 模块构建一个 Python 库——在新仓库中复制作者和提交日期，构建类似的提交历史**\
这种操作过去非常复杂，以至于大多数开发者会创建一个与旧提交历史无关的全新副本。我们再也不必满足于那样了！
