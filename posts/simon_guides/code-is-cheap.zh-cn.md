# Writing code is cheap now

采用智能体工程实践的最大挑战，在于适应“编写代码如今已变得廉价”这一事实所带来的后果。

代码向来是昂贵的。生成几百行干净、经过测试的代码，大多数软件开发者需要整整一天甚至更长时间。我们许多工程习惯，无论宏观还是微观层面，都围绕这一核心约束而建立。

在宏观层面，我们花费大量时间进行项目设计、评估和规划，以确保昂贵的编码时间能尽可能高效地利用。产品功能创意会根据其能带来多少价值来评估，以换取时间——一个功能需要多次赚回其开发成本才值得投入！

在微观层面，我们每天根据可用时间和预期的权衡做出数百个决策。我是否应该重构那个函数使其更优雅，如果这会多花一小时编码时间？那么编写文档呢？为这个边界情况添加测试值得吗？我能证明为此构建一个调试接口是合理的吗？

编码智能体极大地降低了将代码输入计算机的成本，这颠覆了我们许多个人和组织关于哪些权衡是合理的直觉。

并行运行智能体的能力使这更难评估，因为现在一位人类工程师可以同时在多个地方实现、重构、测试和编写代码文档。

## 优质代码仍有成本

交付新代码的价格已降至几乎免费……但交付优质代码的成本仍然远高于此。

以下是我所说的“优质代码”的含义：

* 代码能运行。它能按预期工作，没有错误。

* 我们知道代码能运行。我们已采取措施向自己和他人确认代码符合预期用途。

* 它解决了正确的问题。

* 它能优雅且可预测地处理错误情况：它不仅仅考虑理想路径。错误应提供足够信息，帮助未来的维护者理解出了什么问题。

* 它简单且精简——它只做必要的事情，以人类和机器现在都能理解且未来能维护的方式。

* 它有测试保护。测试证明它现在能运行，并作为回归套件，避免它在未来悄然失效。

* 它有适当级别的文档，且该文档反映了系统的当前状态——如果代码更改了现有行为，现有文档需要更新以匹配。

* 其设计为未来变更留有余地。保持YAGNI原则很重要——为预判可能永远不会到来的未来变更而增加复杂性的代码通常是糟糕的代码——但同样重要的是，不要编写使未来变更比应有时困难得多的代码。

* 所有其他相关的“性”——可访问性、可测试性、可靠性、安全性、可维护性、可观测性、可扩展性、可用性——即适用于所开发特定软件类别的非功能性质量度量。

编码智能体工具可以帮助完成其中大部分工作，但驱动这些工具的开发者仍承担着重大责任，以确保生成的代码是适合当前项目所需优质子集的优质代码。

## 我们需要建立新习惯

挑战在于培养新的个人和组织习惯，以适应智能体工程的便利性和机遇。

这些最佳实践在我们整个行业中仍在摸索中。我自己也仍在摸索。

目前，我认为我们能做的最好的事情就是自我质疑：每当我们的直觉说“别构建那个，不值得花时间”时，无论如何都发出一个提示，在一个异步智能体会话中，最坏的情况不过是十分钟后检查时发现它不值得消耗令牌。
