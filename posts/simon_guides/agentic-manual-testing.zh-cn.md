# Agentic manual testing

编程代理的显著特征是它能够执行自己编写的代码。这正是编程代理比单纯输出代码却无法验证其正确性的LLM强大得多的原因。

切勿假定LLM生成的代码能够正常工作，除非该代码已被实际执行过。

编程代理有能力确认自己生成的代码是否按预期运行，或者持续迭代代码直至其达到预期效果。

让代理编写单元测试，尤其是采用测试优先的TDD（测试驱动开发）方法，是确保它们充分验证所编写代码的有效途径。

不过，这并非唯一值得采用的方法。

仅仅因为代码通过了测试，并不意味着它能按预期工作。任何使用过自动化测试的人都会遇到这样的情况：所有测试都通过了，但代码本身却在某些明显的地方出了问题——它可能在启动时导致服务器崩溃、无法显示关键的UI元素，或者遗漏了某些测试未能覆盖的细节。

自动化测试无法替代手动测试。在将某个功能发布到版本中之前，我喜欢亲眼看到它正常工作。

我发现让代理进行手动测试也很有价值，这常常能揭示出自动化测试未能发现的问题。

## 代理手动测试的机制

代理应该如何“手动”测试一段代码，取决于这段代码的具体内容。

对于Python库，一个有用的模式是`python -c "... code ..."`。你可以将一段（或多行）Python代码字符串直接传递给Python解释器，其中可以包含导入其他模块的代码。

编程代理都熟悉这个技巧，有时会在没有提示的情况下就使用它。不过，提醒他们使用`python -c`进行测试通常也很有效：

使用 `python -c` 在新函数的边界情况下尝试一下。

其他语言可能也有类似的机制，如果没有，代理编写一个演示文件然后编译并运行它也很快。我有时会鼓励它使用`/tmp`目录，纯粹是为了避免这些文件之后被意外提交到仓库中。

在 `/tmp` 中编写代码来尝试该函数的边界情况，然后编译并运行它。

我的许多项目涉及构建带有JSON API的Web应用程序。对于这些项目，我会告诉代理使用`curl`来测试它们：

启动一个开发服务器，并使用 `curl` 探索那个新的 JSON API。

告诉代理去“探索”，通常会导致它尝试新API的许多不同方面，这能很快覆盖大量场景。

如果代理通过手动测试发现了某些不起作用的地方，我喜欢告诉它们使用红/绿TDD模式来修复它。这能确保新的情况最终被永久性的自动化测试所覆盖。

## 使用浏览器自动化测试Web UI

如果项目涉及交互式Web UI，那么建立手动测试流程就变得更有价值了。

从历史上看，这些UI很难通过代码进行测试，但在过去十年中，用于自动化真实Web浏览器的系统取得了显著进步。针对应用程序运行真实的Chrome、Firefox或Safari浏览器，可以在真实环境中发现各种有趣的问题。

编程代理非常擅长使用这些工具。

目前最强大的工具之一是Playwright，这是一个由微软开发的开源库。Playwright提供了一个功能完备的API，支持多种主流编程语言，并且可以自动化任何主流的浏览器引擎。

只需告诉你的代理“用Playwright测试一下”，可能就足够了。代理可以选择最合适的语言绑定，或者使用Playwright的`playwright-cli`工具。

编程代理与专用的CLI工具配合得非常好。Vercel开发的`agent-browser`是一个围绕Playwright构建的全面CLI封装，专为编程代理设计。

我自己的项目Rodney也服务于类似的目的，不过它是通过Chrome DevTools协议直接控制一个Chrome实例。

以下是我用来使用Rodney测试东西的提示示例：

启动一个开发服务器，然后使用 `uvx rodney --help` 测试新的主页，查看截图以确认菜单位置正确。

这个提示中有三个技巧：

* 说“使用`uvx rodney --help`”会使代理通过`uvx`包管理工具运行`rodney --help`，该工具会在首次调用时自动安装Rodney。

* `rodney --help`命令被专门设计用来为代理提供理解和操作该工具所需的一切信息。这里是该帮助文本。

* 说“查看截图”是提示代理应该使用`rodney screenshot`命令，并提醒它可以使用自己的视觉能力来分析生成的图像文件，以评估页面的视觉外观。

一个简短的提示中包含了如此多的手动测试内容！

Rodney和类似工具提供了广泛的功能，从在加载的网站上运行JavaScript，到滚动、点击、输入，甚至读取页面的无障碍树。

与其他形式的手动测试一样，通过浏览器自动化发现并修复的问题，也可以添加到永久性的自动化测试中。

过去，许多开发者因为浏览器自动化测试有“脆弱”的名声而避免使用它们——对页面HTML的微小改动都可能导致一波令人沮丧的测试失败。

让编程代理随着时间的推移维护这些测试，可以大大减少在Web界面设计发生变化时保持测试更新所带来的摩擦。

## 使用Showboat让代理做笔记

让代理手动测试代码可以捕获额外的问题，但它也可以用来创建有助于记录代码并展示其测试方式的工件。

我对让代理展示其工作成果的挑战非常着迷。能够看到演示或记录在案的实验，是确认代理已经全面解决所给挑战的一种非常有效的方式。

我构建了Showboat来促进创建能够捕获代理手动测试流程的文档。

以下是我经常使用的一个提示：

运行 `uvx showboat --help`，然后创建一个 `notes/api-demo.md` showboat 文档，并用它来测试和记录那个新的 API。

与上面的Rodney类似，`showboat --help`命令教会了代理Showboat是什么以及如何使用它。这里是完整的帮助文本。

Showboat的三个关键命令是`note`、`exec`和`image`。

* `note` 将一条Markdown笔记追加到Showboat文档中。

* `exec` 记录一条命令，然后运行该命令并记录其输出。

* `image` 向文档中添加一张图片——对于使用Rodney拍摄的Web应用程序截图非常有用。

`exec`命令是其中最重要的，因为它捕获了一条命令及其产生的输出。这向你展示了代理做了什么以及结果是什么，并且旨在阻止代理作弊并在文档中写入它*希望*发生的事情。

我发现Showboat模式在记录我的代理会话期间完成的工作方面效果非常好。我希望看到类似的模式在更广泛的工具中被采用。
