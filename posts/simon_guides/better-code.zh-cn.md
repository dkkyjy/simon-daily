# AI should help us produce better code

许多开发者担心将代码外包给AI工具会导致质量下降，产生大量快速生成但质量低劣的代码，而决策者却因速度优势而愿意忽视其缺陷。

如果采用编码代理确实降低了你正在开发的代码和功能的质量，你应该直接解决这个问题：找出流程中哪些环节损害了输出质量，并加以修复。

用代理交付更差的代码是一种选择。我们也可以选择交付更好的代码。

## 避免承担技术债务

我喜欢从技术债务的角度来思考交付更好的代码。技术债务源于权衡取舍：如果"按正确方式"做事耗时过长，我们就会在时间限制下妥协，祈祷项目能存活到未来偿还债务的那一天。

避免技术债务的最佳方式就是一开始就不要承担它。

根据我的经验，常见的技术债务修复类别是那些简单但耗时的变更。

- 我们最初的API设计没有覆盖后来出现的重要场景。修复该API需要修改数十处代码，因此更快捷的做法是添加一个略有差异的新API并容忍重复。
- 我们在早期对某个概念命名不当——例如用"团队"而非"群组"——但清理代码中所有相关术语的工作量太大，因此只在UI中修正。
- 我们的系统随着时间的推移积累了重复但略有差异的功能，需要合并和重构。
- 我们的某个文件已增长到数千行代码，理想情况下应拆分为独立模块。

所有这些变更在概念上都很简单，但仍需要投入时间，在更紧迫的问题面前往往难以证明其合理性。

## 编码代理可以为我们处理这些工作

像这样的重构任务正是编码代理的理想应用场景。

启动一个代理，告诉它需要修改什么，然后让它在你后台的某个分支或工作树中默默运行。

我通常为此使用异步编码代理，例如Gemini Jules、OpenAI Codex网页版或Claude Code网页版。这样我可以在笔记本电脑上运行这些重构任务而不中断自己的工作流程。

在拉取请求中评估结果。如果结果良好，就合并它。如果接近完成，就提示它并告知需要改进的地方。如果结果糟糕，就丢弃它。

这些代码改进的成本已经变得如此之低，以至于我们可以对微小的代码异味和不便之处采取零容忍态度。

## AI工具让我们能够考虑更多选项

任何软件开发任务都面临大量解决问题的方案选择。一些最重大的技术债务源于规划阶段做出的错误选择——错过了显而易见的简单解决方案，或选择了后来发现并不完全合适的技术。

LLM可以帮助确保我们不会错过任何之前可能未注意到的明显解决方案。它们只会提出训练数据中常见的解决方案，但这些往往是"无聊技术"中最可能奏效的方案。

更重要的是，编码代理可以帮助进行探索性原型设计。

做出自信技术选择的最佳方式是通过原型证明其适用性。

对于预期有数千并发用户的网站，Redis是否是活动信息流的良好选择？

最确切的验证方法是搭建该系统的模拟环境并运行负载测试，观察哪些环节会崩溃。

编码代理可以通过一个精心设计的提示词构建此类模拟，从而将这种实验的成本降至几乎为零。而且由于成本如此低廉，我们可以同时运行多个实验，测试多种解决方案，以选出最适合我们问题的方案。

## 拥抱复合工程循环

代理遵循指令。我们可以根据先前学到的经验，随时间推移不断优化这些指令，以便在未来的运行中获得更好的结果。

Every公司的Dan Shipper和Kieran Klaassen将他们使用编码代理的工作方式描述为"复合工程"。他们完成的每个编码项目都以回顾总结告终，他们称之为"复合步骤"——记录有效的方法，供未来的代理运行参考。

如果我们希望从代理那里获得最佳结果，就应该致力于持续提升代码库的质量。微小的改进会不断累积。过去耗时费力的质量提升，如今成本已降至如此之低，以至于在交付新功能的同时投资质量已没有任何借口可言。编码代理意味着我们终于可以两者兼得。
