# Anti-patterns: things to avoid

在我们这个奇怪的新代理工程世界中，有些行为属于反模式。

## 将未经审查的代码强加给协作者

这种反模式很常见，而且非常令人沮丧。

不要提交你自己都没有审查过的代码的拉取请求。

如果你打开一个包含数百行（甚至数千行）由代理为你生成的代码的 PR，并且你自己没有花功夫去确保这些代码是能正常运行的，那么你实际上是在把真正的工作推给别人。

他们自己也可以提示一个代理。你究竟提供了什么价值？

如果你把代码提交审查，你需要有信心它已经准备好让别人花时间在上面。初步的审查是你自己的责任，而不是你应该外包给别人的事情。

一个好的代理工程拉取请求应具备以下特征：

- 代码能运行，并且你确信它能运行。你的工作是交付能运行的代码。
- 变更足够小，能够高效地审查，而不会给审查者带来过多的额外认知负担。几个小的 PR 胜过一个大 PR，而且使用编码代理来处理 Git 的繁琐操作，将代码拆分成单独的提交很容易。
- PR 包含额外的上下文来帮助解释变更。变更服务于什么更高级别的目标？在这里链接相关的问题或规范会很有用。
- 代理会写出看起来很可信的拉取请求描述。你也需要审查这些描述！期望别人阅读你自己都没有阅读和验证过的文本是不礼貌的。

鉴于将未经审查的代码转嫁给别人是多么容易，我建议你包含某种形式的证据，证明你自己已经付出了额外的努力。关于你如何手动测试它的笔记、对特定实现选择的评论，甚至是功能运行时的截图和视频，都能大大证明审查者的时间不会浪费在深究细节上。
