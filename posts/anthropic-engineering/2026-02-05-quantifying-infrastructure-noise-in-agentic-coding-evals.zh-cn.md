# 量化智能体编码评估中的基础设施噪声

**日期：** 2026-02-05 00:00 UTC  
**链接：** https://www.anthropic.com/engineering/infrastructure-noise

---

像 SWE-bench 和 Terminal-Bench 这样的智能体编码基准测试通常用于比较前沿模型的软件工程能力——排行榜上的前几名往往仅相差几个百分点。这些分数常被视为模型相对能力的精确度量，并越来越多地影响着关于部署哪些模型的决策。然而，我们发现仅基础设施配置本身就能产生超出这些差值的差异。在内部实验中，Terminal-Bench 2.0 上资源最充裕与最匮乏的设置之间的差距达到 6 个百分点（p < 0.01）。

静态基准测试直接对模型的输出进行评分——运行时环境不会影响结果。而智能体编码评估则不同：模型被赋予一个完整的环境，在其中编写程序、运行测试、安装依赖包，并在多个回合中迭代。运行时不再是被动的容器，而是问题解决过程中不可或缺的组成部分。两个拥有不同资源预算和时间限制的智能体，所面对的并非同一场测试。

评估开发者已经开始考虑这一点。例如，Terminal-Bench 2.0 在其最新的 2.0 版本中针对每个任务指定了推荐的 CPU 和内存。然而，指定资源与一致地执行资源限制是两回事。此外，我们发现执行方法可能会改变基准测试实际衡量的内容。

## **我们是如何发现这一点的**

我们在 Google Kubernetes Engine 集群上运行 Terminal-Bench 2.0。在校准设置时，我们注意到我们的分数与该基准测试的官方排行榜不符，并且基础设施错误率高得惊人：多达 6% 的任务因 Pod 错误而失败，其中大部分与模型解决问题的能力无关。

分数差异归根结底在于资源限制的执行方式。我们的 Kubernetes 实现将每个任务的资源规格既视为下限（floor）又视为硬上限（hard ceiling）：每个容器保证获得指定的资源，但一旦超出即被终止。容器运行时通过两个独立参数来执行资源限制：一个是保证分配量（即预先保留的资源），另一个是容器被终止的硬限制。当这两个参数设置为相同值时，就没有任何余量来应对瞬时尖峰：一次暂时的内存波动就可能 OOM 杀死一个本来可以成功的容器。为了解决这个问题，Terminal-Bench 的排行榜使用了另一种沙箱提供程序，其实现更为宽松，允许临时超量分配而不终止容器，以优先保证基础设施稳定性。

这一发现引出了更大的问题：资源配置对评估分数的影响究竟有多大？

为了量化脚手架的影响，我们在六种资源配置下运行了 Terminal-Bench 2.0：从严格按任务规格执行（1x，即同时作为下限和上限），到完全不设上限。其他所有条件保持不变：相同的 Claude 模型、相同的 harness、相同的任务集。

在我们的实验中，成功率随着资源余量的增加而提高。这主要归因于基础设施错误率在每个步骤单调下降，从严格执行时的 5.8% 降至无上限时的 0.5%。从严格执行到 3 倍余量（5.8% 降至 2.1%）的下降具有显著性（p < 0.001）。余量越大，因超出分配而被杀死的容器就越少。

从 1x 到 3x，成功分数在噪声范围内波动（p=0.40）。在 1x 时崩溃的大多数任务无论如何都会失败——这是我们在数据中观察到的。智能体尝试探索，碰到资源瓶颈，然后被抢占，但它从来就没有走上正确解决方案的路径。

然而，大约从 3x 开始，这一趋势发生了变化：成功率的提升速度超过了基础设施错误率的下降速度。

从 3x 到无上限，基础设施错误率再下降 1.6 个百分点，而成功率却跃升了近 4 个百分点。额外的资源使智能体能够尝试那些只有在大方分配下才能奏效的方法，例如拉取大型依赖、生成开销大的子进程、以及运行内存密集型的测试套件。在无上限资源下，相对于 1x 的总提升为 +6 个百分点（p < 0.01）。在边缘任务中，如 `rstan-to-pystan` 和 `compile-compcert`，在获得内存余量后成功率显著提升。

## **这对测量有何影响**

大约在 Terminal-Bench 规格的 3 倍以内，额外的资源解决了基础设施可靠性问题，即瞬时资源尖峰。Terminal-Bench 维护者所使用的沙箱提供程序实际上在幕后隐式地做了这件事；评估变得更稳定，但并没有变得更简单。

然而，超过 3 倍这个标志后，额外的资源开始主动帮助智能体解决它之前无法解决的问题，这表明限制实际上会改变评估所衡量的内容。严格的限制会无意中奖励非常高效的策略，而宽松的限制则更为宽容，奖励那些能更好利用所有可用资源的智能体。

一个能快速编写精简高效代码的智能体，在严格限制下会表现良好。一个通过重工具暴力求解的智能体，在宽松限制下会表现良好。两者都是合理的测试目标，但如果不说明资源配置，将它们合并成一个单一的分数，就会使差异——以及真实世界中的可推广性——难以解读。

在 `bn-fit-modify`（一项需要贝叶斯网络拟合的 Terminal-Bench 任务）中，一些模型的第一个动作是安装标准的 Python 数据科学生态系统：`pandas`、`networkx`、`scikit-learn` 以及它们的整个工具链。在宽松限制下，这行得通。在严格限制下，Pod 在安装过程中就会耗尽内存，而此时智能体还没写一行解决方案代码。存在一种更精简的策略（仅使用标准库从头实现数学运算），有些模型确实默认采用这种策略，有些则不会。不同模型有不同的默认方法，而资源配置决定了其中哪些方法恰好会成功。我们在不同的 Anthropic 模型上重复了这一核心发现。效果的方向是一致的，而幅度有所不同。同样的趋势似乎在 Claude 以外的模型上也存在，但我们还没有严格测试过。

我们还在 Terminal-Bench 之外的评估上测试了这一模式是否成立，在 SWE-bench 上进行了交叉实验。我们将总可用内存从 1x 变化到 5x 基线，涉及 227 个问题，每个问题 10 个样本。同样的效果依然存在，但幅度较小：分数再次随着内存增加而单调上升，但 5x 时仅比 1x 高出 1.54 个百分点。SWE-bench 任务对资源的需求较低，因此较小的效果是预期的，但这表明资源分配在那里也并非中立。

## **其他方差来源**

资源分配并非唯一的隐藏变量。在某些配置中，时间限制也开始发挥作用。

原则上，评估设置中的每一个元素都可能影响最终分数，从集群健康状况到硬件规格，从并发水平到出口带宽。智能体评估本质上就是端到端的系统测试，该系统内的任何组件都可能成为混杂变量。例如，我们曾观察到通过率随一天中的不同时间而波动，这可能是因为 API 延迟随流量模式和事件而变化。我们尚未正式量化这一效应，但它说明了一个更大的问题：“模型能力”与“基础设施行为”之间的界限比单个基准分数所显示的要模糊得多。模型提供商可以通过专用硬件来隔离其评估基础设施，但外部评估者则难以做到同样的事。

公开基准测试通常旨在衡量纯粹的模型能力，但在实践中，它们有将模型能力与基础设施特性混为一谈的风险。有时这可能是可取的，因为它允许对整个堆栈进行端到端测试，但更多时候则不然。对于旨在公开共享的编码评估，在多个时间点和多天运行将有助于平均掉噪声。

## **我们的建议**

理想的情况是在完全相同的硬件条件下运行每个评估——无论是运行评估的脚手架还是推理栈——这将确保整个评估的完美可重复性。然而，这并不总是可行的。

考虑到容器运行时实际执行资源的方式（通过保证分配量和单独的硬终止阈值），我们建议评估针对每个任务同时指定这两个参数，而不是单个固定值。单一个精确规格会将保证分配量设置为与终止阈值相等，没有留出任何余量：我们在 1x 时记录到的瞬时内存尖峰足以使评估不稳定。将这两个参数分开，可以给容器足够的喘息空间，以避免虚假的 OOM 杀死，同时仍然强制执行一个硬上限以阻止分数膨胀。

这两个参数之间的区间应进行校准，使得下限和上限处的分数彼此处于噪声范围内。例如，在 Terminal-Bench 2.0 中，将上限设置为任务规格的 3 倍可将基础设施错误率降低大约三分之二（5.8% 降至 2.1%，p < 0.001），同时分数提升幅度很小且完全在噪声范围内（p = 0.40）。这是一个合理的权衡：基础设施混杂因素被基本消除，而又不解除有意义的资源压力。具体的倍数会因基准测试和任务分布而异，因此应当报告，但经验校准原则是通用的。

## **我们为何关注这些发现**

这些发现超出了评估基础设施本身，具有实际后果。基准分数越来越多地被用作决策输入，但这种关注（和依赖）的增加并不总是伴随着在运行或报告方式上的相应严谨性。就目前而言，排行榜上 2 分的领先可能反映了真实的能力差异，也可能反映了某个评估是在更强大的硬件上运行的，甚至是在更幸运的时间段运行的，或者两者兼而有之。如果没有公开（或标准化）的设置配置，外界很难判断，除非感兴趣的各方额外努力，在相同条件下重现客观结果。

对于像 Anthropic 这样的实验室来说，这意味着智能体评估的资源配置应被视作一流的实验变量，以与提示格式或采样温度相同的严谨性进行记录和控制。对于基准维护者来说，发布推荐的资源规格（如 Terminal-Bench 2.0 所做）大有裨益，而进一步指定执行方法将弥补我们发现的差距。对于任何使用基准结果的人，核心结论是：智能体评估上较小的分数差异所包含的不确定性，比报告数字的精度所暗示的要大——尤其是因为某些混杂变量实在难以控制。

在资源方法论标准化之前，我们的数据表明，排行榜上低于 3 个百分点的差异都应受到质疑，直到评估配置被记录并匹配。Terminal-Bench 中中等资源配置范围内观察到的离散度略低于 2 个百分点。简单的二项置信区间已经横跨 1-2 个百分点；我们在此记录的基础设施混杂变量是叠加在这个区间之上，而不是在其内部。在分配范围的极端情况下，离散度达到了 6 个百分点。

几分之差可能标志着真正的能力差距——也可能只是虚拟机更大一点而已。
