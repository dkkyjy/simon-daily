# 针对 AI 智能体的有效上下文工程

**日期：** 2025-09-29 00:00 UTC
**链接：** https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

---

在经历了提示工程成为应用 AI 领域关注焦点的几年之后，一个新的术语开始崭露头角：**上下文工程**。使用语言模型进行构建，正逐渐从为提示找到合适的措辞和短语，转向回答一个更广泛的问题：“什么样的上下文配置最有可能让模型产生我们期望的行为？”

**上下文**指的是在对大语言模型（LLM）进行采样时包含的一组词元。**工程**问题在于优化这些词元的效用，使其既要满足 LLM 固有的约束，又要持续达成预期结果。有效地驾驭 LLM 往往需要*在上下文中思考*——换句话说，就是要考虑 LLM 在任何给定时刻可用的整体状态，以及该状态可能产生哪些潜在行为。

在这篇文章中，我们将探讨新兴的上下文工程艺术，并提供一个精炼的心智模型，用于构建可引导且高效的智能体。

## 上下文工程 vs. 提示工程

在 Anthropic，我们将上下文工程视为提示工程的自然演进。提示工程指的是为了获得最佳结果而编写和组织 LLM 指令的方法（详见[我们的文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)及有用的提示工程策略）。**上下文工程**指的是一套策略，用于策划和维护 LLM 推理过程中的最佳词元（信息）集，其中还包括可能出现在提示之外的其它所有信息。

在 LLM 工程早期，提示是 AI 工程工作中最主要的组成部分，因为除了日常聊天交互之外，大多数用例都需要针对一次性分类或文本生成任务优化提示。顾名思义，提示工程的主要关注点是如何编写有效的提示，尤其是系统提示。然而，随着我们转向构建在多次推理和更长的时间跨度内运行的、能力更强的智能体，我们需要管理整个上下文状态（系统指令、工具、[模型上下文协议](https://modelcontextprotocol.io/docs/getting-started/intro)（MCP）、外部数据、消息历史等）的策略。

一个在循环中运行的智能体会产生越来越多的数据，这些数据*可能*对下一次推理相关，而这些信息必须被循环地精炼。上下文工程是一门[艺术与科学](https://x.com/karpathy/status/1937902205765607626?lang=en)，它从不断演化的可能信息宇宙中策划哪些内容可以被放入有限的上下文窗口。

*与编写提示这一离散任务不同，上下文工程是迭代的，并且每次我们决定向模型传递什么内容时，都需要进行一次策划阶段。*

## 为什么上下文工程对于构建能力强大的智能体很重要

尽管 LLM 速度很快，并且能够管理越来越大的数据量，但我们观察到，LLM 与人一样，在某个时刻会失去焦点或产生困惑。关于“大海捞针”式基准测试的研究揭示了[上下文腐败](https://research.trychroma.com/context-rot)的概念：随着上下文窗口中的词元数量增加，模型从该上下文中准确回忆信息的能力会下降。

虽然有些模型的退化程度较温和，但所有模型都存在这一特性。因此，上下文必须被视为一种边际收益递减的有限资源。就像人类的[工作记忆容量有限](https://journals.sagepub.com/doi/abs/10.1177/0963721409359277)一样，LLM 在解析大量上下文时也有一个“注意力预算”。每引入一个新词元，都会消耗一部分预算，从而增加了精心策划 LLM 可用词元的必要性。

这种注意力稀缺源于 LLM 的架构限制。LLM 基于[Transformer 架构](https://arxiv.org/abs/1706.03762)，该架构允许每个词元[关注整个上下文中的每一个其他词元](https://huggingface.co/blog/Esmail-AGumaan/attention-is-all-you-need)。对于 n 个词元，这会产生 n² 个成对关系。

随着上下文长度的增加，模型捕捉这些成对关系的能力会被削弱，在上下文大小和注意力聚焦之间产生自然张力。此外，模型的注意力模式是从训练数据分布中习得的，而较短的序列通常比较长的序列更常见。这意味着模型在处理全上下文依赖关系方面的经验和专用参数都较少。

像[位置编码插值](https://arxiv.org/pdf/2306.15595)这样的技术允许模型通过适应原始训练时较短的上下文来处理更长的序列，但会在一定程度上损失对词元位置的理解。这些因素造成的是一个性能梯度而非硬性断崖：模型在较长的上下文下仍然具有很强的能力，但与较短上下文下的表现相比，在信息检索和长程推理方面的精度可能会有所降低。

这些现实意味着，深思熟虑的上下文工程对于构建能力强大的智能体至关重要。

## 有效上下文的构成

鉴于 LLM 受限于有限的注意力预算，*好的*上下文工程意味着找到*最小可能的*高信号词元集合，以最大化某个期望结果的可能性。实践这一原则说起来容易做起来难，但在下一节中，我们将概述这一指导原则在上下文的不同组成部分中实际意味着什么。

**系统提示**应当极其清晰，并使用简单直接的语言，以*正确的高度*向智能体呈现想法。正确的高度是两种常见失败模式之间的“金发姑娘区”。一种极端情况是，工程师在提示中硬编码复杂、脆弱的逻辑，以激发精确的智能体行为。这种方法会造成脆弱性，并随着时间的推移增加维护复杂度。另一种极端情况是，工程师有时会提供模糊、高层级的指导，未能向 LLM 提供关于期望输出的具体信号，或者错误地假设了共享的上下文。最佳的高度在于取得平衡：既要足够具体以有效指导行为，又要足够灵活，为模型提供强有力的启发式规则来指导行为。

*在频谱的一端，我们看到脆弱的 if-else 硬编码提示；在另一端，我们看到过于通用或错误假设共享上下文的提示。*

我们建议将提示组织成不同的部分（例如 `<background_information>`、`<instructions>`、`## 工具指导`、`## 输出描述` 等），并使用 XML 标签或 Markdown 标题等技术来区分这些部分，不过随着模型能力的增强，提示的具体格式可能变得不那么重要。

无论你决定如何组织系统提示，都应努力追求能够完整概述你期望行为的最小信息集。（请注意，最小并不一定意味着短；你仍然需要事先给智能体足够的信息，以确保它遵循期望行为。）最好先用最佳模型测试一个最小提示，看看它在你的任务上表现如何，然后根据初始测试中发现的失败模式添加清晰的指令和示例来改进性能。

**工具**允许智能体与其环境交互，并在工作过程中拉取新的、额外的上下文。由于工具定义了智能体与其信息/行为空间之间的契约，因此工具必须促进效率，既要返回词元高效的信息，也要鼓励高效的智能体行为，这一点极其重要。

在[为 AI 智能体编写工具——与 AI 智能体一起](https://www.anthropic.com/engineering/writing-tools-for-agents)一文中，我们讨论了构建能被 LLM 很好理解且功能重叠最小的工具。与设计良好的代码库中的函数类似，工具应当是自包含的、对错误具有鲁棒性，并且对于其预期用途极其清晰。输入参数同样应当具有描述性、无歧义，并且充分利用模型的固有优势。

我们观察到的最常见的失败模式之一是工具集过于臃肿，覆盖了太多功能，或者导致关于使用哪个工具的决策点模糊不清。如果人类工程师在特定情况下都无法明确地说出应该使用哪个工具，那么 AI 智能体也不可能做得更好。正如我们稍后将讨论的，策划一个最小可行的工具集也可以使上下文在长时间交互中得到更可靠的维护和修剪。

提供示例，也就是少样本提示，是一个众所周知的最佳实践，我们继续强烈建议这样做。然而，团队有时会在一段提示中塞入一长串边缘案例，试图阐述 LLM 在特定任务中应遵循的每一条规则。我们不建议这样做。相反，我们建议努力策划一组多样化、典范性的示例，能够有效描绘出智能体的期望行为。对于 LLM 来说，示例就是“一图胜千言”的图画。

我们对上下文不同组成部分（系统提示、工具、示例、消息历史等）的总体指导是：深思熟虑，保持上下文信息丰富且紧凑。现在，让我们深入探讨如何在运行时动态检索上下文。

## 上下文检索与智能体搜索

在[构建有效的 AI 智能体](https://www.anthropic.com/research/building-effective-agents)一文中，我们强调了基于 LLM 的工作流与智能体之间的区别。自从那篇文章发表以来，我们逐渐倾向于一个[简单的定义](https://simonwillison.net/2025/Sep/18/agents/)：智能体就是 LLM 在循环中自主使用工具。

在与客户合作的过程中，我们看到该领域正在趋同于这一简单范式。随着底层模型能力的增强，智能体的自主程度可以扩展：更智能的模型允许智能体自主导航复杂的未知问题空间并从错误中恢复。

我们现在看到工程师在设计智能体上下文时的思维方式正在发生转变。如今，许多 AI 原生应用采用某种形式的基于嵌入的推理前检索，以向智能体提供重要的上下文供其推理。随着该领域向更智能体化的方法过渡，我们越来越多地看到团队用“即时”上下文策略来增强这些检索系统。

采用“即时”方法构建的智能体，不是预先处理所有相关数据，而是维护轻量级的标识符（文件路径、存储查询、网络链接等），并在运行时使用这些引用通过工具动态加载数据到上下文中。Anthropic 的智能体编码解决方案 [Claude Code](https://www.anthropic.com/claude-code) 就是使用这种方法对大型数据库执行复杂数据分析的。模型可以编写有目标的查询、存储结果，并利用 `head` 和 `tail` 等 Bash 命令分析大量数据，而无需将完整的数据对象加载到上下文中。这种方法模仿了人类的认知：我们通常不会记忆整个信息库，而是引入外部的组织和索引系统，如文件系统、收件箱和书签，以便按需检索相关信息。

除了存储效率之外，这些引用的元数据还提供了一种有效精炼行为的机制，无论这些元数据是显式提供的还是隐式的。对于一个在文件系统中运行的智能体而言，位于 `tests` 文件夹中的名为 `test_utils.py` 的文件，与位于 `src/core_logic/` 中的同名文件所暗示的用途是不同的。文件夹层级、命名约定和时间戳都提供了重要信号，帮助人类和智能体理解如何以及何时利用信息。

让智能体自主导航和检索数据，还能实现渐进式披露——换句话说，允许智能体通过探索逐步发现相关的上下文。每一次交互都会产生上下文，为下一个决策提供信息：文件大小暗示复杂度；命名约定暗示用途；时间戳可以作为相关性的代理。智能体可以一层一层地构建理解，只在工作记忆中保留必要的内容，并利用记笔记策略进行额外的持久化。这种自我管理的上下文窗口使智能体专注于相关的子集，而不是淹没在详尽但可能无关的信息中。

当然，这里有一个权衡：运行时探索比检索预计算数据慢。不仅如此，还需要有见地且深思熟虑的工程来确保 LLM 拥有正确的工具和启发式规则，以便有效导航其信息环境。如果没有适当的指导，智能体可能会因误用工具、追逐死胡同或未能识别关键信息而浪费上下文。

在某些情况下，最高效的智能体可能采用混合策略：预先检索一些数据以获得速度，然后根据自己的判断进行进一步的自主探索。决定“正确”自主水平的边界取决于任务。Claude Code 就是一个采用这种混合模型的智能体：[CLAUDE.md](http://claude.md) 文件被预先直接放入上下文，而 `glob` 和 `grep` 等原语则允许它导航其环境并即时检索文件，从而有效避免了索引过时和复杂语法树的问题。

混合策略可能更适合内容动态性较弱的场景，例如法律或金融工作。随着模型能力的提高，智能体设计将趋向于让智能模型智能地行动，并逐步减少人工策划。鉴于该领域的快速发展，“做最简单可行的事”可能仍然是我们给在 Claude 之上构建智能体的团队的最佳建议。

### 长周期任务的上下文工程

长周期任务要求智能体在词元数量超过 LLM 上下文窗口的一系列操作中，保持连贯性、上下文以及目标导向的行为。对于需要持续工作几十分钟到几小时的任务，比如大型代码库迁移或综合性研究项目，智能体需要专门的技术来应对上下文窗口大小的限制。

等待更大的上下文窗口似乎是一种明显的策略。但在可预见的未来，所有大小的上下文窗口都可能受到上下文污染和信息相关性问题的困扰——至少在需要最强智能体性能的情况下是如此。为了使智能体能够在更长的时间跨度内有效工作，我们开发了几种直接解决这些上下文污染问题的技术：压缩、结构化笔记和多智能体架构。

**压缩**

压缩是一种做法，即当对话接近上下文窗口限制时，对其内容进行总结，然后用总结初始化一个新的上下文窗口。压缩通常是上下文工程中用于改善长期连贯性的第一个杠杆。压缩的核心是以高保真度蒸馏上下文窗口的内容，使智能体能够以最小的性能下降继续工作。

例如，在 Claude Code 中，我们通过将消息历史传递给模型来总结和压缩最关键的信息。模型会保留架构决策、未解决的错误和实现细节，同时丢弃冗余的工具输出或消息。然后，智能体可以在这一压缩上下文以及最近访问的五个文件的基础上继续工作。用户可以在不用担心上下文窗口限制的情况下获得连续性。

压缩的艺术在于选择保留什么、丢弃什么，因为过于激进的压缩可能导致丢失微妙但关键的上下文，而这些上下文的重要性可能直到后来才显现出来。对于实现压缩系统的工程师，我们建议在复杂的智能体轨迹上仔细调整你的提示。从最大化召回率开始，确保你的压缩提示能够捕捉到轨迹中的每一段相关信息，然后通过消除多余内容来迭代提高精确度。

一个低垂的果实例子是清除工具调用和结果——一旦某个工具在消息历史深处被调用，智能体为什么还需要再次看到原始结果？最安全、最轻量的压缩形式之一是清除工具结果，最近已作为 [Claude 开发者平台的一项功能](https://www.anthropic.com/news/context-management)推出。

**结构化笔记**

结构化笔记，又称智能体记忆，是一种让智能体定期将笔记持久化保存到上下文窗口之外的技术。这些笔记会在后续被拉回上下文窗口。

这种策略以最小的开销提供持久记忆。就像 Claude Code 创建待办事项列表，或者你的自定义智能体维护一个 `NOTES.md` 文件一样，这种简单的模式允许智能体在复杂任务中跟踪进度，维护那些否则会在数十次工具调用中丢失的关键上下文和依赖关系。

[Claude 玩宝可梦](https://www.twitch.tv/claudeplayspokemon)展示了在非编码领域中记忆如何改变智能体的能力。智能体在数千个游戏步骤中维护精确的计数——跟踪诸如“在过去的 1,234 步中，我一直在 1 号道路训练我的宝可梦，皮卡丘从目标 10 级提升了 8 级”之类的目标。在没有关于记忆结构的任何提示的情况下，它绘制了已探索区域的地图，记住了已解锁的关键成就，并维护了战斗策略的战略笔记，这些笔记帮助它学习哪些攻击对不同对手最有效。

在上下文重置之后，智能体会读取自己的笔记，并继续多小时的训练序列或地下城探索。这种跨总结步骤的连贯性使得长期策略成为可能，而如果仅将所有信息保留在 LLM 的上下文窗口中，这些策略是不可能实现的。

作为我们的 [Sonnet 4.5 发布](https://www.anthropic.com/effective-context-engineering-for-ai-agents)的一部分，我们在 Claude 开发者平台上以公开测试版的形式发布了[一个记忆工具](http://anthropic.com/news/context-management)，通过基于文件的系统使得存储和查询上下文窗口之外的信息更加容易。这使得智能体能够随时间建立知识库，跨会话维护项目状态，并参考之前的工作，而无需将所有内容保留在上下文中。

**子智能体架构**

子智能体架构提供了另一种绕开上下文限制的方法。不是让一个智能体试图在整个项目中维护状态，而是由专门的子智能体用干净的上下文窗口处理聚焦的任务。主智能体通过高层计划进行协调，而子智能体则执行深层技术工作或使用工具查找相关信息。每个子智能体可能会进行大量探索，使用数万甚至更多词元，但只返回其工作的浓缩、蒸馏摘要（通常 1,000-2,000 词元）。

这种方法实现了清晰的关注点分离——详细的搜索上下文保留在子智能体内部，而主导智能体则专注于综合和分析结果。这种模式在[我们如何构建多智能体研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)一文中讨论过，在复杂研究任务上显示了比单智能体系统有显著改进。

在这些方法之间进行选择取决于任务特征。例如：

* 压缩适用于需要大量来回交互的任务，能维持对话流；
* 笔记适用于具有明确里程碑的迭代开发；
* 多智能体架构适用于并行探索能带来巨大收益的复杂研究和分析。

即使模型不断改进，在扩展交互中保持连贯性的挑战仍将是构建更有效智能体的核心。

## 结论

上下文工程代表了我们使用 LLM 构建方式的一个根本性转变。随着模型能力的增强，挑战不仅仅是编写完美的提示——而是在每一步都深思熟虑地策划哪些信息可以进入模型有限的注意力预算。无论你是在为长周期任务实施压缩，设计词元高效的智能体，还是让智能体即时探索其环境，指导原则都是一样的：找到最小可能的高信号词元集合，以最大化期望结果的可能性。

我们概述的这些技术将随着模型的改进而继续演进。我们已经看到，更智能的模型需要更少的规约性工程，允许智能体以更高的自主性运行。但即使能力在扩展，将上下文视为宝贵的有限资源仍将是构建可靠、有效智能体的核心。
