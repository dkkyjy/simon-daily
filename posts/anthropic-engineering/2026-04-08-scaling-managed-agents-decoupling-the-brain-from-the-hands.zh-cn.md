# 扩展托管代理：将大脑与双手解耦

**日期：** 2026-04-08 00:00 UTC
**链接：** https://www.anthropic.com/engineering/managed-agents

---

*通过我们的[文档](https://platform.claude.com/docs/en/managed-agents/overview)开始使用 Claude 托管代理。*  

工程博客上常谈的话题是如何构建[有效的代理](https://www.anthropic.com/engineering/building-effective-agents)并设计[控制器](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)以用于[长时间运行的工作](https://www.anthropic.com/engineering/harness-design-long-running-apps)。这些工作的共同主线是，控制器编码了对 Claude 独自无法完成之事的假设。然而，这些假设需要经常被质疑，因为随着模型改进，它们可能会[过时](http://www.incompleteideas.net/IncIdeas/BitterLesson.html)。

仅举一例，在之前的工作中[我们发现](https://www.anthropic.com/engineering/harness-design-long-running-apps)，Claude Sonnet 4.5 会过早地结束任务，因为它感觉到上下文限制即将达到——这种行为有时被称为“上下文焦虑”。我们通过在控制器中添加上下文重置来解决这个问题。但当我们在 Claude Opus 4.5 上使用相同的控制器时，我们发现这种行为消失了。重置变成了累赘。

我们预计控制器将继续发展。因此，我们构建了托管代理：Claude 平台中的一个托管服务，它通过一组旨在超越任何特定实现（包括我们今天运行的实现）的小型接口，代表您运行长周期代理。

构建托管代理意味着解决计算中的一个老问题：如何设计一个系统来容纳“[尚未想到的程序](http://www.catb.org/esr/writings/taoup/html/ch03s01.html)”。几十年前，操作系统通过将硬件虚拟化为抽象层——*进程*、*文件*——解决了这个问题，这些抽象层足够通用，可以容纳还不存在的程序。这些抽象层比硬件更长久。`read()` 命令不关心它访问的是 1970 年代的磁盘组还是现代 SSD。上层的抽象保持稳定，而底层的实现可以自由更换。

托管代理遵循同样的模式。我们将代理的组件虚拟化：会话（所有发生事件的仅追加日志）、控制器（调用 Claude 并将 Claude 的工具调用路由到相关基础设施的循环）以及沙箱（Claude 可以运行代码和编辑文件的执行环境）。这使得每个组件的实现可以在不干扰其他组件的情况下进行替换。我们对这些接口的形式有明确的意见，但不关心它们背后运行的是什么。

## 不要养宠物

我们最初将所有代理组件放入一个容器中，这意味着会话、代理控制器和沙箱共享一个环境。这种方法有好处，包括文件编辑是直接系统调用，并且无需设计服务边界。

但是，将所有东西耦合到一个容器中，我们遇到了一个老的基础设施问题：我们养了一只[*宠物*](https://cloudscaling.com/blog/cloud-computing/the-history-of-pets-vs-cattle/)。在宠物与牲畜的比喻中，宠物是一个有名有姓、需要亲手照料的个体，你不能失去它；而牲畜是可互换的。在我们的案例中，服务器变成了那只宠物；如果容器失效，会话就丢失了。如果容器无响应，我们必须把它救回来。

救回容器意味着调试无响应的卡住会话。我们唯一的窗口是 WebSocket 事件流，但它无法告诉我们故障发生在*哪里*，这意味着控制器中的错误、事件流中的数据包丢失或容器离线都表现出相同的症状。为了弄清楚出了什么问题，工程师必须在容器内打开一个 shell，但因为这个容器通常也包含用户数据，这种方法实际上意味着我们缺乏调试能力。

第二个问题是，控制器假设 Claude 处理的任何内容都与其共存于同一个容器中。当客户要求我们将 Claude 连接到他们的虚拟私有云时，他们要么必须将他们的网络与我们的网络对等，要么在自己的环境中运行我们的控制器。当我们需要将控制器连接到不同的基础设施时，控制器中的一个假设变成了问题。

## 将大脑与双手解耦

我们得出的解决方案是将我们认为是“大脑”（Claude 及其控制器）的部分与“双手”（执行操作的沙箱和工具）以及“会话”（会话事件日志）解耦。每个部分都成为一个对彼此做出很少假设的接口，并且每个部分都可以独立地失效或被替换。

**控制器离开容器。** 将大脑与双手解耦意味着控制器不再驻留在容器内部。它像调用任何其他工具一样调用容器：`execute(name, input) → string`。容器变成了牲畜。如果容器死亡，控制器会将失败捕获为工具调用错误，并将其传递回 Claude。如果 Claude 决定重试，可以使用标准配方重新初始化一个新容器：`provision({resources})`。我们不再需要救回失败的容器。

**从控制器故障中恢复。** 控制器也变成了牲畜。因为会话日志位于控制器之外，控制器中没有任何东西需要在崩溃后幸存。当一个控制器失效时，可以用 `wake(sessionId)` 重启一个新控制器，使用 `getSession(id)` 取回事件日志，并从最后一个事件开始恢复。在代理循环中，控制器通过 `emitEvent(id, event)` 将会话写入会话日志，以保留事件的持久记录。

**安全边界。** 在耦合设计中，Claude 生成的任何不受信任的代码都在与凭证相同的容器中运行——因此提示注入只需说服 Claude 读取其自身环境即可。一旦攻击者获得了这些令牌，他们就可以创建新的、无限制的会话并将工作委派给它们。窄作用域是一种明显的缓解措施，但这编码了一个关于 Claude 在有限令牌下不能做什么的假设——而 Claude 正变得越来越智能。结构性的修复是确保令牌永远无法从 Claude 生成代码运行的沙箱中访问。

我们使用两种模式来确保这一点。身份验证可以绑定到资源，也可以保存在沙箱外部的保险库中。对于 Git，我们使用每个仓库的访问令牌在沙箱初始化期间克隆仓库，并将其连接到本地 git 远程仓库。Git `push` 和 `pull` 在沙箱内部工作，而代理从未处理过令牌本身。对于自定义工具，我们支持 MCP 并将 OAuth 令牌存储在安全保险库中。Claude 通过专用代理调用 MCP 工具；该代理接收与会话关联的令牌。然后代理可以从保险库中获取相应的凭证，并向外部服务发出调用。控制器永远不会知道任何凭证。

## 会话不是 Claude 的上下文窗口

长周期任务通常超过 Claude 上下文窗口的长度，而解决这个问题的标准方法都涉及关于保留什么内容的不可逆决策。我们在[之前的工作](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)中探讨过这些上下文工程技术。例如，压缩让 Claude 保存其上下文窗口的摘要，而记忆工具让 Claude 将上下文写入文件，从而实现跨会话的学习。这可以与上下文修剪相结合，后者有选择地移除令牌，例如旧的工具结果或思考块。

但是，关于有选择地保留或丢弃上下文的不可逆决策可能导致失败。很难知道未来的轮次需要哪些令牌。如果消息通过压缩步骤被转换，控制器会将压缩后的消息从 Claude 的上下文窗口中移除，这些消息只有被存储后才可恢复。之前的工作[已经探索过](https://arxiv.org/pdf/2512.24601)通过将上下文存储为存在于上下文窗口*之外*的对象来解决这个问题的方法。例如，上下文可以是 REPL 中的一个对象，LLM 通过编写代码来过滤或切片它以编程方式访问它。

在托管代理中，会话提供了同样的好处，充当存在于 Claude 上下文窗口之外的上下文对象。但上下文并非存储在沙箱或 REPL 中，而是持久存储在会话日志中。接口 `getEvents()` 允许大脑通过选择事件流的位置片段来查询上下文。该接口可以灵活使用，允许大脑从上次停止读取的地方继续，在特定时刻之前回退几个事件以查看前因，或者在特定操作之前重新读取上下文。

任何获取的事件也可以在传递给 Claude 的上下文窗口之前，在控制器中进行转换。这些转换可以是控制器编码的任何内容，包括上下文组织以实现高提示缓存命中率以及上下文工程。我们将可恢复的上下文存储（在会话中）与任意的上下文管理（在控制器中）分离，因为我们无法预测未来模型需要什么样的特定上下文工程。这些接口将上下文管理推入控制器，并且仅保证会话是持久的并且可供查询。

## 多个大脑，多双双手

**多个大脑。** 将大脑与双手解耦解决了我们最早的客户投诉之一。当团队希望 Claude 在他们自己的 VPC 中处理资源时，唯一的途径是将他们的网络与我们的网络对等，因为容纳控制器的容器假设所有资源都紧邻它。一旦控制器不再位于容器中，这个假设就消失了。同样的改变带来了性能上的回报。当我们最初将大脑放在容器中时，这意味着多个大脑需要同样多的容器。对于每个大脑，在容器配置好之前无法进行推理；每个会话都预先支付了完整的容器设置成本。每个会话，即使是那些永远不会接触沙箱的会话，都必须克隆仓库、启动进程、从我们的服务器获取待处理事件。

这段死时间体现在首字节时间（TTFT）上，它衡量会话在接受工作与产生第一个响应令牌之间的等待时间。TTFT 是用户最*能感受到*的延迟。

将大脑与双手解耦意味着容器仅在大脑通过工具调用 `(execute(name, input) → string)` 需要时才配置。因此，不需要立即使用容器的会话无需等待容器。推理可以在编排层从会话日志中拉取待处理事件后立即开始。使用这种架构，我们的 p50 TTFT 大约下降了 60%，p95 下降了超过 90%。扩展到多个大脑仅仅意味着启动多个无状态控制器，并且仅在需要时才连接到双手。

**多双双手。** 我们还希望将每个大脑连接到多双双手。在实践中，这意味着 Claude 必须推理多个执行环境并决定将工作发送到哪里——这是一项比在单个 shell 中操作更困难的认知任务。我们最初将大脑放在单个容器中，因为早期的模型不具备这种能力。随着智能的提升，单个容器反而变成了限制：当那个容器失效时，我们丢失了大脑正在触及的每个手的状态。

将大脑与双手解耦使得每个手成为一个工具：`execute(name, input) → string`：输入名称和输入，返回一个字符串。这个接口支持任何自定义工具、任何 MCP 服务器以及我们自己的工具。控制器不知道沙箱是一个容器、一部手机还是一个宝可梦模拟器。而且由于没有手与任何大脑耦合，大脑之间可以互相传递双手。

## 结论

我们面临的挑战是一个老问题：如何设计一个系统来容纳“尚未想到的程序”。操作系统通过将硬件虚拟化为足够通用的抽象层，以容纳还不存在的程序，从而持续了几十年。通过托管代理，我们旨在设计一个能够容纳未来控制器、沙箱或其他围绕 Claude 组件的系统。

托管代理是一种元控制器，秉承同样的精神，它对 Claude 未来需要的*具体*控制器没有偏见。相反，它是一个具有通用接口的系统，允许存在许多不同的控制器。例如，Claude Code 是一个优秀的控制器，我们广泛用于各种任务。我们还表明，特定任务的代理控制器在狭窄领域表现出色。托管代理可以容纳其中任何一种，随时间的推移匹配 Claude 的智能。

元控制器设计意味着对围绕 Claude 的接口有明确的意见：我们期望 Claude 将需要操纵状态（会话）和执行计算（沙箱）的能力。我们还期望 Claude 需要能够扩展到多个大脑和多双双手。我们设计这些接口的目的是让它们能够在长时间跨度的可靠和安全运行。但我们不对 Claude 需要的大脑或双手的数量或位置做出任何假设。
