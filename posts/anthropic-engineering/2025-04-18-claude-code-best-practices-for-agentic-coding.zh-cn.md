# Claude Code：代理编码的最佳实践

**日期：** 2025-04-18 00:00 UTC  
**链接：** https://www.anthropic.com/engineering/claude-code-best-practices

---

Claude Code 是一个代理式编码环境。与回答问题并等待的聊天机器人不同，Claude Code 可以读取你的文件、运行命令、进行更改，并在你观看、重定向或完全离开时自主解决问题。  
这改变了你的工作方式。你不再需要自己编写代码然后请 Claude 审查，而是描述你想要的功能，Claude 会找出构建它的方法。Claude 会探索、规划并实现。  
但这种自主性仍然有一个学习曲线。Claude 在你需要理解的某些约束下工作。  
本指南涵盖了在 Anthropic 内部团队以及在不同代码库、语言和环境中使用 Claude Code 的工程师中已被证明有效的模式。有关代理循环在底层如何工作的更多信息，请参阅 [Claude Code 的工作原理](/docs/en/how-claude-code-works)。

---

大多数最佳实践都基于一个约束：Claude 的上下文窗口很快就会填满，并且性能会随之下降。  
Claude 的上下文窗口包含你的整个对话，包括每条消息、Claude 读取的每个文件以及每个命令输出。然而，这可能会很快填满。一次调试会话或代码库探索可能生成并消耗数万个词元。  
这很重要，因为 LLM 的性能会随着上下文的填充而下降。当上下文窗口即将填满时，Claude 可能会开始“忘记”较早的指令或犯更多错误。上下文窗口是需要管理的最重要资源。要了解会话在实践中的填充方式，请 [观看交互式演练](/docs/en/context-window)，了解启动时加载了什么以及每次文件读取的成本。通过 [自定义状态行](/docs/en/statusline) 持续跟踪上下文使用情况，并查看 [减少词元使用](/docs/en/costs#reduce-token-usage) 以获取减少词元使用的策略。

## [​](#give-claude-a-way-to-verify-its-work) 给 Claude 一种验证其工作的方法

给 Claude 一个可以运行的检查：测试、构建、用于比较的截图。这是你观看的会话与你离开的会话之间的区别。

当工作看起来完成时，Claude 就会停止。如果没有可以运行的检查，“看起来完成”是唯一可用的信号，而你就成为了验证循环：每个错误都在等待你发现它。给 Claude 一些能产生通过或失败结果的东西，循环就会自行闭合。Claude 执行工作，运行检查，读取结果，并迭代直到检查通过。  
检查可以是任何能返回 Claude 可以在对话中读取的信号的东西：测试套件、构建退出代码、代码检查工具、将输出与基准进行比较的脚本，或者与设计进行比较的 [浏览器截图](/docs/en/chrome)。

| 策略 | 之前 | 之后 |
| --- | --- | --- |
| **提供验证标准** | *”实现一个验证电子邮件地址的函数”* | *”编写一个 validateEmail 函数。示例测试用例：[user@example.com](mailto:user@example.com) 为 true，invalid 为 false，[user@.com](mailto:user@.com) 为 false。实现后运行测试”* |
| **视觉验证 UI 更改** | *”让仪表盘看起来更好看”* | *”[粘贴截图] 实现此设计。截取结果截图并与原图进行比较。列出差异并修复它们”* |
| **解决根本原因，而非症状** | *”构建失败”* | *”构建失败并出现此错误：[粘贴错误]。修复它并验证构建成功。解决根本原因，不要抑制错误”* |

检查存在后，决定它如何严格地控制停止：

* **在一条提示中**：要求 Claude 运行检查并在同一条消息中迭代，如上表所示。
* **跨会话**：将检查设置为 [`/goal` 条件](/docs/en/goal)。一个独立的评估器会在每次操作后重新检查，Claude 会一直工作直到满足条件。
* **作为确定性门控**：[Stop 钩子](/docs/en/hooks#stop) 将你的检查作为脚本运行，并阻止操作结束，直到检查通过。Claude Code 会覆盖该钩子，并在连续 8 次阻塞后结束该操作。
* **通过第二意见**：一个 [验证子代理](/docs/en/sub-agents) 或一个 [动态工作流](/docs/en/workflows) 会检查其自己的发现，让一个全新的模型尝试反驳结果，这样执行工作的代理就不会是自己评分。

每一步都在设置和注意力之间进行权衡。提示版本适用于今天的任何任务。`/goal` 和 Stop 钩子版本可以让无人值守的运行在没有你的情况下正确完成。  
让 Claude 展示证据，而不是断言成功：测试输出、它运行的命令及其返回结果，或结果的截图。查看证据比自己重新运行验证更快，并且适用于你没有观看的会话。

## [​](#explore-first-then-plan-then-code) 先探索，再规划，后编码

将调研和规划与实现分开，以避免解决错误的问题。

让 Claude 直接跳转到编码可能会产生解决错误问题的代码。使用 [规划模式](/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode) 将探索与执行分开。  
推荐的工作流有四个阶段：

1

探索

进入规划模式。Claude 读取文件并回答问题，不进行任何更改。

claude (规划模式)

```
读取 /src/auth，了解我们如何处理会话和登录。
同时查看我们如何管理包含机密的环境变量。
```

2

规划

要求 Claude 创建详细的实现计划。

claude (规划模式)

```
我想添加 Google OAuth。需要更改哪些文件？
会话流程是什么？创建一个计划。
```

按 `Ctrl+G` 在文本编辑器中打开计划，以便在 Claude 继续之前直接编辑。

3

实现

退出规划模式，让 Claude 编码，并根据其计划进行验证。

claude (默认模式)

```
根据你的计划实现 OAuth 流程。为回调处理程序编写测试，
运行测试套件并修复任何失败。
```

4

提交

要求 Claude 使用描述性消息提交并创建 PR。

claude (默认模式)

```
使用描述性消息提交并打开一个 PR
```

规划模式很有用，但也会增加开销。对于范围明确且修复很小的任务（例如修复拼写错误、添加日志行或重命名变量），直接要求 Claude 执行。当你对方法不确定时、更改涉及多个文件时，或者你正在修改的代码不熟悉时，规划最为有用。如果你能用一句话描述差异，请跳过计划。

## [​](#provide-specific-context-in-your-prompts) 在提示中提供具体的上下文

你的指令越精确，需要的修正就越少。

Claude 可以推断意图，但它无法读心。引用特定文件、提及约束、指出示例模式。

| 策略 | 之前 | 之后 |
| --- | --- | --- |
| **限定任务范围。** 指定哪个文件、什么场景以及测试偏好。 | *”为 foo.py 添加测试”* | *”为 foo.py 编写一个测试，涵盖用户已退出的边缘情况。避免使用模拟。”* |
| **指向源。** 引导 Claude 到可以回答问题的源。 | *”为什么 ExecutionFactory 有如此奇怪的 API？”* | *”查看 ExecutionFactory 的 git 历史，并总结其 API 是如何形成的”* |
| **引用现有模式。** 指向代码库中的模式给 Claude。 | *”添加一个日历小部件”* | *”查看主页上现有小部件是如何实现的，以了解模式。HotDogWidget.php 是一个很好的例子。遵循该模式实现一个新的日历小部件，让用户选择一个月份并前后翻页选择年份。从头开始构建，不要使用代码库中已使用的库之外的库。”* |
| **描述症状。** 提供症状、可能的位置以及“已修复”的样子。 | *”修复登录错误”* | *”用户报告会话超时后登录失败。检查 src/auth/ 中的身份验证流程，特别是令牌刷新。编写一个失败的测试来重现该问题，然后修复它”* |

模糊的提示在探索时并且可以承受纠正的情况下可能很有用。像“你会改进这个文件中的什么？”这样的提示可能会发现你没有想到的问题。

### [​](#provide-rich-content) 提供丰富的内容

使用 `@` 引用文件，粘贴屏幕截图/图片，或直接通过管道传输数据。

你可以通过多种方式向 Claude 提供丰富的数据：

* **使用 `@` 引用文件**，而不是描述代码所在位置。Claude 会在响应之前读取文件。
* **直接粘贴图片**。复制/粘贴或拖放图片到提示中。
* **提供文档和 API 参考的 URL**。使用 `/permissions` 将常用域名列入允许列表。
* **通过管道传输数据**，运行 `cat error.log | claude` 直接发送文件内容。
* **让 Claude 获取它需要的内容**。告诉 Claude 使用 Bash 命令、MCP 工具或通过读取文件自行拉取上下文。

## [​](#configure-your-environment) 配置你的环境

一些设置步骤可以使 Claude Code 在所有会话中显著提高效率。有关扩展功能及何时使用每个功能的完整概述，请参阅 [扩展 Claude Code](/docs/en/features-overview)。

### [​](#write-an-effective-claude-md) 编写有效的 CLAUDE.md

运行 `/init` 根据你当前的项目结构生成一个起始 CLAUDE.md 文件，然后随时间进行完善。

CLAUDE.md 是一个特殊文件，Claude 会在每次对话开始时读取它。包含 Bash 命令、代码风格和工作流规则。这为 Claude 提供了无法仅从代码推断出的持久上下文。  
`/init` 命令分析你的代码库以检测构建系统、测试框架和代码模式，为你提供一个坚实的完善基础。  
CLAUDE.md 文件没有要求的格式，但保持简短易读。例如：

CLAUDE.md

```
# 代码风格
- 使用 ES 模块 (import/export) 语法，不要使用 CommonJS (require)
- 尽量解构导入（例如 import { foo } from 'bar'）

# 工作流
- 完成一系列代码更改后一定要进行类型检查
- 为了提高性能，优先运行单个测试，而不是整个测试套件
```

CLAUDE.md 在每个会话中都会加载，因此只包含广泛适用的内容。对于仅在某些时候相关的领域知识或工作流，请改用 [技能](/docs/en/skills)。Claude 会在需要时按需加载它们，而不会使每个对话变得臃肿。  
保持简洁。对于每一行，问自己：“删除这一行会导致 Claude 犯错吗？”如果不是，就删掉。臃肿的 CLAUDE.md 文件会导致 Claude 忽略你的实际指令！

| ✅ 包含 | ❌ 排除 |
| --- | --- |
| Claude 无法猜测的 Bash 命令 | Claude 可以通过阅读代码弄清楚的内容 |
| 与默认值不同的代码风格规则 | Claude 已知的标准语言约定 |
| 测试指令和首选测试运行器 | 详细的 API 文档（改为链接到文档） |
| 仓库规范（分支命名、PR 约定） | 频繁变化的信息 |
| 项目特定的架构决策 | 长篇幅的解释或教程 |
| 开发者环境特性（所需的环境变量） | 代码库的逐文件描述 |
| 常见的陷阱或非明显行为 | 不言自明的实践，如“编写整洁的代码” |

如果尽管有禁止规则，Claude 仍然不断做你不希望它做的事情，那么该文件可能太长，规则被忽略了。如果 Claude 问你在 CLAUDE.md 中已经回答过的问题，那么措辞可能含糊不清。像对待代码一样对待 CLAUDE.md：在出现问题时进行审查，定期精简，并通过观察 Claude 的行为是否真正改变来测试更改。  
你可以通过添加强调（例如“重要”或“你必须”）来调整指令，以提高遵守程度。将 CLAUDE.md 检入 git，以便你的团队可以贡献。该文件的价值会随着时间的推移而累积。  
CLAUDE.md 文件可以使用 `@path/to/import` 语法导入其他文件：

CLAUDE.md

```
参见 @README.md 了解项目概述，参见 @package.json 了解可用的 npm 命令。

# 附加说明
- Git 工作流：@docs/git-instructions.md
- 个人覆盖：@~/.claude/my-project-instructions.md
```

你可以将 CLAUDE.md 文件放在多个位置：

* **主文件夹 (`~/.claude/CLAUDE.md`)**：适用于所有 Claude 会话
* **项目根目录 (`./CLAUDE.md`)**：检入 git 以与团队共享
* **项目根目录 (`./CLAUDE.local.md`)**：个人项目特定笔记；将此文件添加到 `.gitignore` 中，以便不与团队共享
* **父目录**：在 `root/CLAUDE.md` 和 `root/foo/CLAUDE.md` 都会自动拉取的 monorepo 中很有用
* **子目录**：当 Claude 读取这些目录中的文件时，会按需拉入子目录的 CLAUDE.md

### [​](#configure-permissions) 配置权限

使用 [自动模式](/docs/en/permission-modes#eliminate-prompts-with-auto-mode) 让分类器处理审批，使用 `/permissions` 将特定命令列入允许列表，或使用 `/sandbox` 实现操作系统级隔离。每种方法都在减少中断的同时让你保持控制。

默认情况下，Claude Code 会请求对可能修改系统的操作的权限：文件写入、Bash 命令、MCP 工具等。这很安全但很繁琐。在第十次批准后，你不再真正审查，只是点击通过。有三种方法可以减少这些中断：

* **自动模式**：一个独立的分类器模型审查命令，仅阻止看起来有风险的操作：范围升级、未知基础设施或由恶意内容驱动的操作。当您信任任务的大致方向但不想点击每一步时，这是最佳选择
* **权限允许列表**：允许你认为安全的特定工具，例如 `npm run lint` 或 `git commit`
* **沙箱**：启用操作系统级隔离，限制文件系统和网络访问，允许 Claude 在定义的边界内更自由地工作

了解更多关于 [权限模式](/docs/en/permission-modes)、[权限规则](/docs/en/permissions) 和 [沙箱](/docs/en/sandboxing) 的信息。

### [​](#use-cli-tools) 使用 CLI 工具

告诉 Claude Code 在与外部服务交互时使用 CLI 工具，如 `gh`、`aws`、`gcloud` 和 `sentry-cli`。

CLI 工具是与外部服务交互的最上下文高效的方式。如果你使用 GitHub，请安装 `gh` CLI。Claude 知道如何使用它来创建问题、打开拉取请求和阅读评论。没有 `gh`，Claude 仍然可以使用 GitHub API，但未经身份验证的请求经常会遇到速率限制。  
Claude 也能有效地学习它尚不熟悉的 CLI 工具。尝试这样的提示：`使用 'foo-cli-tool --help' 了解 foo 工具，然后使用它来解决 A、B、C。`

### [​](#connect-mcp-servers) 连接 MCP 服务器

运行 `claude mcp add` 连接外部工具，如 Notion、Figma 或你的数据库。

借助 [MCP 服务器](/docs/en/mcp)，你可以要求 Claude 从问题跟踪器实现功能、查询数据库、分析监控数据、集成 Figma 的设计以及自动化工作流。

### [​](#set-up-hooks) 设置钩子

使用钩子来执行每次都必须执行且零例外的情况。

[钩子](/docs/en/hooks-guide) 会在 Claude 工作流的特定点自动运行脚本。与提供建议的 CLAUDE.md 指令不同，钩子是确定性的，保证动作发生。  
Claude 可以为你编写钩子。尝试这样的提示：*“编写一个钩子，在每次文件编辑后运行 eslint”* 或 *“编写一个阻止写入 migrations 文件夹的钩子。”* 直接编辑 `.claude/settings.json` 以手动配置钩子，然后运行 `/hooks` 浏览已配置的内容。

### [​](#create-skills) 创建技能

在 `.claude/skills/` 中创建 `SKILL.md` 文件，为 Claude 提供领域知识和可重用工作流。

[技能](/docs/en/skills) 用特定于你的项目、团队或领域的信息扩展 Claude 的知识。Claude 在相关时会自动应用它们，或者你可以直接使用 `/skill-name` 调用它们。  
通过在 `.claude/skills/` 中添加一个包含 `SKILL.md` 的目录来创建技能：

.claude/skills/api-conventions/SKILL.md

```
---
name: api-conventions
description: 我们服务的 REST API 设计约定
---
# API 约定
- URL 路径使用 kebab-case
- JSON 属性使用 camelCase
- 列表端点始终包含分页
- 在 URL 路径中对 API 进行版本控制 (/v1/, /v2/)
```

技能还可以定义你直接调用的可重复工作流：

.claude/skills/fix-issue/SKILL.md

```
---
name: fix-issue
description: 修复 GitHub 问题
disable-model-invocation: true
---
分析并修复 GitHub 问题：$ARGUMENTS。

1. 使用 `gh issue view` 获取问题详情
2. 理解问题中描述的问题
3. 在代码库中搜索相关文件
4. 实现修复问题所需的更改
5. 编写并运行测试以验证修复
6. 确保代码通过代码检查和类型检查
7. 创建描述性提交消息
8. 推送并创建一个 PR
```

运行 `/fix-issue 1234` 来调用它。对于具有副作用且你希望手动触发的流程，请使用 `disable-model-invocation: true`。

### [​](#create-custom-subagents) 创建自定义子代理

在 `.claude/agents/` 中定义专门的助手，Claude 可以委托它们执行独立的任务。

[子代理](/docs/en/sub-agents) 在自己的上下文中运行，并拥有自己允许的工具集。它们对于读取大量文件或需要专门关注而不弄乱主对话的任务非常有用。

.claude/agents/security-reviewer.md

```
---
name: security-reviewer
description: 审查代码是否存在安全漏洞
tools: Read, Grep, Glob, Bash
model: opus
---
你是一名高级安全工程师。审查以下代码：
- 注入漏洞 (SQL、XSS、命令注入)
- 身份验证和授权缺陷
- 代码中的机密或凭证
- 不安全的处理数据

提供具体的行引用和建议修复。
```

明确告诉 Claude 使用子代理：*“使用子代理审查此代码是否存在安全问题。”*

### [​](#install-plugins) 安装插件

运行 `/plugin` 浏览市场。插件无需配置即可添加技能、工具和集成。

[插件](/docs/en/plugins) 将技能、钩子、子代理和 MCP 服务器捆绑到一个可安装的单元中，来自社区和 Anthropic。如果你使用类型化语言，请安装 [代码智能插件](/docs/en/discover-plugins#code-intelligence)，为 Claude 提供精确的符号导航和编辑后的自动错误检测。  
有关选择技能、子代理、钩子和 MCP 的指导，请参阅 [扩展 Claude Code](/docs/en/features-overview#match-features-to-your-goal)。

## [​](#communicate-effectively) 有效沟通

你与 Claude Code 沟通的方式会显著影响结果的质量。

### [​](#ask-codebase-questions) 提出代码库问题

向 Claude 提出你会问高级工程师的问题。

在接入新代码库时，使用 Claude Code 进行学习和探索。你可以向 Claude 提出你会向另一位工程师提出的同类问题：

* 日志记录是如何工作的？
* 如何创建新的 API 端点？
* `foo.rs` 第 134 行的 `async move { ... }` 是做什么的？
* `CustomerOnboardingFlowImpl` 处理哪些边缘情况？
* 为什么第 333 行的代码调用 `foo()` 而不是 `bar()`？

以这种方式使用 Claude Code 是一种有效的入职工作流，可以加快上手速度并减少其他工程师的负担。不需要特殊的提示技巧：直接提问即可。

### [​](#let-claude-interview-you) 让 Claude 采访你

对于较大的功能，先让 Claude 采访你。从一个最小提示开始，要求 Claude 使用 `AskUserQuestion` 工具采访你。

Claude 会询问你可能尚未考虑的事情，包括技术实现、UI/UX、边缘情况和权衡。

```
我想构建 [简要描述]。请使用 AskUserQuestion 工具详细采访我。

询问关于技术实现、UI/UX、边缘情况、关注点和权衡。不要问显而易见的问题，深入挖掘我可能未考虑到的难点。

继续采访直到我们涵盖所有内容，然后将完整规范写入 SPEC.md。
```

规范完成后，启动一个新的会话来执行它。新会话拥有干净的上下文，完全专注于实现，并且你有一个书面的规范可供参考。  
最有用的规范是自包含的：它们命名了涉及的文件和接口，说明了哪些内容不在范围内，并以一个端到端的验证步骤结束，证明该功能有效。花在使规范精确上的时间比花在观看实现上的时间更有价值。

## [​](#manage-your-session) 管理你的会话

对话是持久且可逆的。利用这一点！

### [​](#course-correct-early-and-often) 尽早且经常纠正

一旦注意到 Claude 偏离轨道，立即纠正它。

最佳结果来自紧密的反馈循环。尽管 Claude 偶尔会在第一次尝试时就完美解决问题，但快速纠正通常会更快地产生更好的解决方案。

* **`Esc`**：使用 `Esc` 键中途停止 Claude。上下文会被保留，因此你可以重定向。
* **`Esc + Esc` 或 `/rewind`**：按两次 `Esc` 或运行 `/rewind` 打开回退菜单，恢复之前的对话和代码状态，或从选定的消息进行总结。
* **`"撤销那一步"`**：让 Claude 还原其更改。
* **`/clear`**：在不相关的任务之间重置上下文。包含无关上下文的长时间会话可能会降低性能。

如果你在一个会话中对同一个问题纠正了 Claude 两次以上，则上下文已被失败的方法所污染。运行 `/clear` 并使用更具体的提示（包含你学到的内容）重新开始。一个带有更好提示的干净会话几乎总是优于一个带有累积纠正的长时间会话。

### [​](#manage-context-aggressively) 积极管理上下文

在不相关的任务之间运行 `/clear` 以重置上下文。

当接近上下文限制时，Claude Code 会自动压缩对话历史，这有助于保留重要的代码和决策，同时释放空间。  
在长时间会话中，Claude 的上下文窗口可能会被不相关的对话、文件内容和命令填满。这会降低性能，有时会分散 Claude 的注意力。

* 在任务之间频繁使用 `/clear`，以完全重置上下文窗口
* 当自动压缩触发时，Claude 会总结最重要的内容，包括代码模式、文件状态和关键决策
* 为了获得更多控制，运行 `/compact <指令>`，例如 `/compact 专注于 API 更改`
* 要只压缩部分对话，请使用 `Esc + Esc` 或 `/rewind`，选择一个消息检查点，然后选择 **从此处总结** 或 **总结到此为止**。前者压缩从该点开始的消息，同时保留早期上下文；后者压缩早期消息，同时保留最近的消息完整。请参阅 [恢复与总结](/docs/en/checkpointing#restore-vs-summarize)。
* 在 CLAUDE.md 中使用指令自定义压缩行为，例如 `"压缩时，始终保留已修改文件的完整列表和所有测试命令"`，以确保关键上下文在总结中幸存
* 对于不需要保留在上下文中的快速问题，请使用 [`/btw`](/docs/en/interactive-mode#side-questions-with-%2Fbtw)。答案会出现在一个可关闭的覆盖层中，并且从不进入对话历史，因此你可以检查细节而不增加上下文。

### [​](#use-subagents-for-investigation) 使用子代理进行调查

使用“使用子代理调查 X”来委托调研。它们会在单独的上下文中探索，保持你的主对话清洁以实现实现。

由于上下文是你的基本约束，子代理是可用的最强大工具之一。当 Claude 研究代码库时，它会读取大量文件，所有这些文件都会消耗你的上下文。子代理在单独的上下文窗口中运行，并返回摘要：

```
使用子代理调查我们的身份验证系统如何处理令牌
刷新，以及我们是否有任何现有的 OAuth 实用程序可以重用。
```

子代理探索代码库，读取相关文件，并返回发现，而不会弄乱你的主对话。  
你也可以在 Claude 实现某些内容后使用子代理进行验证：

```
使用子代理审查此代码是否存在边缘情况
```

### [​](#rewind-with-checkpoints) 使用检查点回退

你发送的每个提示都会创建一个检查点。你可以将对话、代码或两者都恢复到任何以前的检查点。

Claude 会在每次更改前自动快照文件，以便检查点可以恢复它们。双击 `Escape` 或运行 `/rewind` 打开回退菜单。你可以仅恢复对话、仅恢复代码、两者都恢复，或从选定的消息进行总结。有关详细信息，请参阅 [检查点](/docs/en/checkpointing)。  
你可以告诉 Claude 尝试一些有风险的操作，而不是仔细规划每一步。如果不起作用，请回退并尝试不同的方法。检查点会跨会话持续存在，因此你可以关闭终端并在之后仍然回退。

检查点只跟踪 *由 Claude 进行的* 更改，而不是外部进程。这不能替代 git。

### [​](#resume-conversations) 恢复对话

使用 `/rename` 命名会话，并将其视为分支：每个工作流都有自己的持久上下文。

Claude Code 会在本地保存对话，因此当任务跨越多个时段时，你无需重新解释上下文。运行 `claude --continue` 继续最近的会话，或运行 `claude --resume` 从列表中选择一个。为会话提供描述性名称，如 `oauth-migration`，以便稍后可以找到它们。有关恢复、分支和命名控制的完整内容，请参阅 [管理会话](/docs/en/sessions)。

## [​](#automate-and-scale) 自动化和扩展

一旦你熟练使用一个 Claude，就可以通过并行会话、非交互式模式和扇出模式来成倍增加你的输出。  
到目前为止，所有内容都假设一个人、一个 Claude 和一个对话。但 Claude Code 可以水平扩展。本节中的技术展示了如何完成更多工作。

### [​](#run-non-interactive-mode) 运行非交互模式

在 CI、预提交钩子或脚本中使用 `claude -p "提示"`。添加 `--output-format stream-json --verbose` 以获取流式 JSON 输出。

使用 `claude -p "你的提示"`，你可以在没有会话的情况下非交互式地运行 Claude。[非交互模式](/docs/en/headless) 是将 Claude 集成到 CI 管道、预提交钩子或任何自动化工作流的方式。输出格式允许你以编程方式解析结果：纯文本、JSON 或流式 JSON。

```
# 一次性查询
claude -p "解释这个项目是做什么的"

# 用于脚本的结构化输出
claude -p "列出所有 API 端点" --output-format json

# 用于实时处理的流式
claude -p "分析这个日志文件" --output-format stream-json --verbose
```

### [​](#run-multiple-claude-sessions) 运行多个 Claude 会话

并行运行多个 Claude 会话以加快开发速度、运行隔离的实验或启动复杂的工作流。

选择适合你需要多少协调的并行方法：

* [工作树](/docs/en/worktrees)：在隔离的 git 检出中运行单独的 CLI 会话，使编辑不会冲突
* [桌面应用](/docs/en/desktop#work-in-parallel-with-sessions)：以可视方式管理多个本地会话，每个会话在自己的工作树中
* [Web 上的 Claude Code](/docs/en/claude-code-on-the-web)：在 Anthropic 管理的云基础设施上运行会话，位于隔离的虚拟机中
* [代理团队](/docs/en/agent-teams)：多个会话的自动协调，具有共享任务、消息传递和团队负责人

除了并行化工作之外，多个会话还可以实现专注于质量的工作流。全新的上下文可以改进代码审查，因为 Claude 不会偏向于它刚刚编写的代码。  
例如，使用编写者/审查者模式：

| 会话 A（编写者） | 会话 B（审查者） |
| --- | --- |
| `为我们的 API 端点实现一个速率限制器` |  |
|  | `审查 @src/middleware/rateLimiter.ts 中的速率限制器实现。查找边缘情况、竞争条件和与我们现有中间件模式的一致性。` |
| `这是审查反馈：[会话 B 输出]。解决这些问题。` |  |

你可以对测试做类似的事情：让一个 Claude 编写测试，然后让另一个 Claude 编写代码以使测试通过。

### [​](#fan-out-across-files) 跨文件扇出

循环遍历任务，为每个任务调用 `claude -p`。使用 `--allowedTools` 为批处理操作限定权限范围。

对于大型迁移或分析，你可以将工作分布到许多并行的 Claude 调用中：

1

生成任务列表

让 Claude 列出所有需要迁移的文件（例如，`列出所有需要迁移的 2,000 个 Python 文件`）

2

编写脚本循环遍历列表

```
for file in $(cat files.txt); do
  claude -p "将 $file 从 React 迁移到 Vue。返回 OK 或 FAIL。" \
    --allowedTools "Edit,Bash(git commit *)"
done
```

3

先在几个文件上测试，然后大规模运行

根据前 2-3 个文件的问题优化提示，然后在完整集合上运行。`--allowedTools` 标志限制了 Claude 可以做什么，这在无人值守运行时非常重要。

你也可以将 Claude 集成到现有的数据/处理管道中：

```
claude -p "<你的提示>" --output-format json | your_command
```

在开发期间使用 `--verbose` 进行调试，并在生产环境中关闭它。

### [​](#run-autonomously-with-auto-mode) 使用自动模式自主运行

对于具有后台安全检查的不间断执行，请使用 [自动模式](/docs/en/permission-modes#eliminate-prompts-with-auto-mode)。一个分类器模型会在命令运行前对其进行审查，阻止范围升级、未知基础设施和由恶意内容驱动的操作，同时允许常规工作在没有提示的情况下进行。

```
claude --permission-mode auto -p "修复所有 lint 错误"
```

对于使用 `-p` 标志的非交互式运行，如果分类器反复阻止操作，自动模式会中止，因为没有可以回退的用户。有关阈值，请参见 [当自动模式回退时](/docs/en/permission-modes#when-auto-mode-falls-back)。

### [​](#add-an-adversarial-review-step) 添加对抗性审查步骤

在将任务视为完成之前，让一个子代理在全新的上下文中审查差异并报告差距。

Claude 无人值守运行的时间越长，在你认为工作完成之前进行独立检查就越重要。在全新的 [子代理](/docs/en/sub-agents) 上下文中运行的审查者只看到差异和你给出的标准，而不是产生更改的推理，因此它会根据自己的条件评估结果。  
对于正确性检查，运行捆绑的 [`/code-review` 技能](/docs/en/commands)，该技能会在新的子代理中审查当前差异的错误，并将发现返回给会话。要根据你的计划检查差异，请自己编写审查提示。指明要检查的工作、要对照的计划以及什么算作发现：

```
使用子代理根据 PLAN.md 审查速率限制器的差异。检查
是否所有要求都已实现，列出的边缘情况是否有测试，并且
任务范围之外的部分没有更改。报告差距，而不是风格偏好。
```

由于审查者作为子代理运行，实现会话会直接收到差距，并可以修复它们并重新审查，而无需你在窗口之间复制发现。对于较长的自主运行，[代理团队](/docs/en/agent-teams) 可以在许多任务中保持这个循环，同时你可以抽查记录的发现。

被要求发现差距的审查者通常都会报告一些差距，即使工作是无懈可击的，因为这是它被要求做的。追求每一个发现会导致过度工程：额外的抽象层、防御性代码和针对不可能发生的情况的测试。告诉审查者只标记影响正确性或既定要求的差距，并将其余视为可选。

## [​](#avoid-common-failure-patterns) 避免常见的失败模式

这些是常见的错误。尽早识别它们可以节省时间：

* **厨房水槽式会话。** 你从一个任务开始，然后要求 Claude 做一些不相关的事情，然后又回到第一个任务。上下文中充满了无关信息。  
  > **修复**：在不相关的任务之间使用 `/clear`。
* **反复纠正。** Claude 做错了，你纠正它，它仍然错了，你又纠正。上下文中充满了失败的方法。  
  > **修复**：经过两次失败的纠正后，使用 `/clear` 并编写一个更好的初始提示，包含你学到的内容。
* **过于详细的 CLAUDE.md。** 如果你的 CLAUDE.md 太长，Claude 会忽略其中一半，因为重要的规则在噪音中丢失了。  
  > **修复**：无情地精简。如果 Claude 在没有指令的情况下已经正确执行了某个操作，请删除它或将其转换为钩子。
* **信任然后验证的差距。** Claude 生成了一个看似合理的实现，但没有处理边缘情况。  
  > **修复**：始终提供验证（测试、脚本、屏幕截图）。如果你无法验证它，就不要发布它。
* **无限探索。** 你要求 Claude “调查”某事而没有限定范围。Claude 读取了数百个文件，填满了上下文。  
  > **修复**：缩小调查范围或使用子代理，以便探索不会消耗你的主上下文。

## [​](#develop-your-intuition) 培养你的直觉

本指南中的模式并非一成不变。它们是在一般情况下效果不错的起点，但可能并非在所有情况下都是最优的。  
有时你 *应该* 让上下文累积，因为你正在深入一个复杂的问题，历史记录很有价值。有时你应该跳过规划并让 Claude 自己弄清楚，因为任务是探索性的。有时一个模糊的提示完全正确，因为你希望在约束之前看到 Claude 如何解释问题。  
关注哪些有效。当 Claude 产生出色的输出时，注意你做了什么：提示结构、你提供的上下文、你所在的模式。当 Claude 挣扎时，问为什么。是上下文太嘈杂？提示太模糊？任务对一次传递来说太大了？  
随着时间的推移，你将培养出任何指南都无法捕捉的直觉。你会知道何时具体、何时开放，何时规划、何时探索，何时清除上下文、何时让它累积。
