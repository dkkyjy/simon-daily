# 近期关于 Claude Code 质量报告的更新

**日期：** 2026-04-23 00:00 UTC
**链接：** https://www.anthropic.com/engineering/april-23-postmortem

---

在过去一个月里，我们一直在调查部分用户反映 Claude 回复质量下降的问题。我们将这些反馈追溯至三项分别影响 Claude Code、Claude Agent SDK 和 Claude Cowork 的变更。API 未受影响。

截至 4 月 20 日（v2.1.116），这三个问题均已解决。

在这篇文章中，我们将说明我们的发现、修复的内容，以及我们将采取哪些不同的措施，以确保类似问题再次发生的可能性大幅降低。

我们非常重视有关性能下降的报告。我们从未有意降低模型性能，并且能够立即确认我们的 API 和推理层未受影响。

经过调查，我们发现了三个不同的问题：

1. 在 3 月 4 日，我们将 Claude Code 的默认推理努力从 `高` 改为 `中`，以减少 `高` 模式下一些用户遇到的极长延迟（足以让 UI 看起来卡死）。这是一个错误的权衡。我们在 4 月 7 日回滚了此更改，因为用户告诉我们他们更倾向于默认使用更高智能，而在简单任务中选择较低的推理努力。此变更影响了 Sonnet 4.6 和 Opus 4.6。
2. 在 3 月 26 日，我们发布了一项更改，以清除空闲超过一小时的会话中 Claude 的旧思考内容，从而降低用户恢复这些会话时的延迟。一个 bug 导致该操作在会话的后续每一轮中持续发生，而不是仅发生一次，这使得 Claude 显得健忘且重复。我们在 4 月 10 日修复了此问题。此变更影响了 Sonnet 4.6 和 Opus 4.6。
3. 在 4 月 16 日，我们添加了一条系统提示指令以减少冗长。与其他提示变更结合后，它损害了代码质量，并于 4 月 20 日被回滚。此变更影响了 Sonnet 4.6、Opus 4.6 和 Opus 4.7。

由于每项变更影响的是不同时间表下的不同流量片段，整体效果看起来像是广泛而不一致的性能下降。虽然我们在 3 月初就开始调查这些反馈，但起初很难将其与用户反馈中的正常波动区分开来，并且我们的内部使用和评估最初都无法复现所识别出的问题。

这不是用户应该从 Claude Code 获得的体验。自 4 月 23 日起，我们将重置所有订阅用户的使用限制。

## 对 Claude Code 默认推理努力的更改

当我们在 2 月份于 Claude Code 中发布 Opus 4.6 时，我们将默认推理努力设置为 `高`。

不久之后，我们收到用户反馈，称 Claude Opus 4.6 在高努力模式下有时会思考时间过长，导致 UI 看起来卡死，并为这些用户带来不成比例的延迟和 token 消耗。

一般来说，模型思考时间越长，输出越好。努力等级是 Claude Code 让用户设定这种权衡的方式——更多思考 vs 更低延迟和更少的使用限制命中。在我们为模型校准努力等级时，我们会考虑这种权衡，以便在测试时计算曲线上选择能为人们提供最佳选项范围的点。在产品层面，我们随后选择曲线上的哪个点作为默认值，并将该值作为努力参数发送到 Messages API；然后通过 `/effort` 提供其他选项。

在我们的内部评估和测试中，中等努力在绝大多数任务中实现了略低的智能，但延迟显著降低。它也没有遇到高努力模式中偶尔出现的极长尾思考延迟问题，并且有助于最大化用户的使用限制。因此，我们推出了一项更改，将中等努力设为默认值，并通过产品内对话框解释了原因。

推出后不久，用户开始报告 Claude Code 感觉不太智能。我们发布了一系列设计迭代，使当前的努力设置更清晰，以提醒用户可以更改默认值（启动时的通知、内联努力选择器，以及恢复 ultrathink），但大多数用户仍保留了中等努力默认值。

在听取更多客户的反馈后，我们于 4 月 7 日撤销了这一决定。所有用户现在默认使用 `极高` 努力（Opus 4.7）和 `高` 努力（所有其他模型）。

## 一项导致先前推理丢失的缓存优化

当 Claude 推理一个任务时，该推理通常保留在对话历史中，以便在后续每一轮中，Claude 能够看到它为何做出之前的编辑和工具调用。

在 3 月 26 日，我们发布了本意是对此功能进行效率改进的变更。我们使用提示缓存来使用户的连续 API 调用更便宜、更快。Claude 在发出 API 请求时将输入 token 写入缓存，然后在一段时间不活动后，提示从缓存中被逐出，为其他提示腾出空间。缓存利用率是我们精心管理的内容（更多信息请参阅我们的[方法](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)）。

设计本应很简单：如果会话空闲超过一小时，我们可以通过清除旧的思考部分来降低用户恢复该会话的成本。由于请求无论如何都会是缓存未命中，我们可以从请求中修剪不必要的消息，以减少发送到 API 的未缓存 token 数量。然后我们会恢复发送完整的推理历史。为此，我们使用了 `clear_thinking_20251015` API 头部以及 `keep:1`。

实现中存在一个 bug。它没有只清除一次思考历史，而是在会话的后续每一轮中都进行了清除。一旦会话跨过空闲阈值，该进程的每个后续请求都告诉 API 只保留最近的一个思考块，并丢弃之前的所有内容。这种情况会累积：如果你在 Claude 正在使用工具的过程中发送了一条后续消息，那么在该错误标志下会开始新的一轮，因此即使是当前轮的推理也会被丢弃。Claude 会继续执行，但越来越不记得它为什么选择做它正在做的事情。这表现为用户报告的健忘、重复和奇怪的工具选择。

由于这会导致后续请求持续丢弃思考块，这些请求也会导致缓存未命中。我们认为这正是导致用户报告使用限制消耗比预期更快的另一个原因。

最初，两个不相关的实验使我们难以复现此问题：一个仅内部的服务器端实验（涉及消息队列）；以及另一个正交的变更（改变了我们显示思考的方式），该变更在大多数 CLI 会话中抑制了这个 bug，因此即使我们在测试外部构建时也没有发现它。

这个 bug 位于 Claude Code 的上下文管理、Anthropic API 和扩展思考的交汇处。它所引入的变更通过了多次人工和自动化代码审查，以及单元测试、端到端测试、自动化验证和内部试用。再加上该问题仅在一个边缘情况（陈旧会话）下发生，并且难以复现，我们花了一周多的时间才发现并确认了根本原因。

作为调查的一部分，我们使用 Opus 4.7 对引发问题的拉取请求进行了回溯性[代码审查](https://code.claude.com/docs/en/code-review)。当提供了收集完整上下文所需的代码仓库时，Opus 4.7 发现了这个 bug，而 Opus 4.6 没有。为了防止此类问题再次发生，我们现在正在支持将更多仓库作为代码审查的上下文。

我们在 4 月 10 日的 v2.1.101 版本中修复了这个 bug。

## 一项旨在减少冗长的系统提示变更

我们最新的模型 Claude Opus 4.7 相对于其前身有一个显著的行为特点：正如我们在发布时[写到的那样](https://www.anthropic.com/news/claude-opus-4-7)，它倾向于相当冗长。这使得它在处理难题时更聪明，但也会产生更多的输出 token。

在发布 Opus 4.7 之前的几周，我们开始调整 Claude Code 以做准备。每个模型的行为略有不同，我们会在每个版本发布前花时间优化相应的框架和产品。

我们有许多工具来减少冗长：模型训练、提示改进，以及改进产品中的思考用户体验。最终我们使用了所有这些工具，但系统提示中的一项添加对 Claude Code 的智能产生了过大的影响：

> *“长度限制：工具调用之间的文本保持在 ≤25 词以内。最终回复保持在 ≤100 词以内，除非任务需要更多细节。”*

经过数周的内部测试，并且在我们运行的一组评估中没有发现回归后，我们确信这一变更没有问题，并于 4 月 16 日与 Opus 4.7 一起发布。

作为此次调查的一部分，我们使用更广泛的评估集进行了更多的消融实验（从系统提示中移除各行以了解每行的影响）。其中一项评估显示 Opus 4.6 和 4.7 均下降了 3%。我们立即在 4 月 20 日的发布中回滚了该提示。

## 未来改进

我们将采取多项不同的措施来避免这些问题：我们将确保更大比例的内部员工使用与公众完全相同的 Claude Code 构建版本（而不是我们用于测试新功能的版本）；并且我们将对我们内部使用的[代码审查](https://code.claude.com/docs/en/code-review)工具进行改进，并将这一改进版本交付给客户。

我们还增加了对系统提示变更的更严格管控。对于 Claude Code 的每一次系统提示变更，我们都会运行一套广泛的按模型评估，继续进行消融实验以了解每行的影响，并且我们已经构建了新的工具来使提示变更更易于审查和审计。我们还为我们的 CLAUDE.md 添加了指导，以确保特定于模型的变更加门控，仅针对目标模型。对于任何可能以智能为代价的变更，我们将增加浸泡期、更广泛的评估套件以及逐步推出，以便更早地发现问题。

我们最近在 X 上创建了 @ClaudeDevs，以便有更多空间深入解释产品决策及其背后的推理。我们将在 GitHub 上的集中式线程中分享相同的更新。

最后，我们要感谢我们的用户：那些使用 `/feedback` 命令与我们分享问题（或在网上发布具体、可复现示例）的用户，正是他们最终使我们能够识别并修复这些问题。今天，我们将重置所有订阅用户的使用限制。

我们非常感谢你们的反馈和耐心。
