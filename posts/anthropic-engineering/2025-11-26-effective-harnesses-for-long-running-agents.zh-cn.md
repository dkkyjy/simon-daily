# 长期运行代理的有效框架

**日期：** 2025-11-26 00:00 UTC
**链接：** https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

---

随着AI代理能力的增强，开发者越来越多地让它们承担需要数小时甚至数天工作的复杂任务。然而，让代理在多个上下文窗口间保持一致的进展仍然是一个未解决的问题。

长期运行代理的核心挑战在于它们必须在离散的会话中工作，而每个新会话开始时都没有之前会话的记忆。想象一个由轮班工程师组成的软件项目，每个新工程师到达时对上一个班次发生的事情毫无记忆。由于上下文窗口有限，且大多数复杂项目无法在单个窗口内完成，代理需要一种方式来弥合编码会话之间的鸿沟。

我们开发了一个双管齐下的解决方案，使[Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)能够在多个上下文窗口中有效工作：一个**初始化代理**，负责在首次运行时设置环境；以及一个**编码代理**，其任务是在每个会话中逐步取得进展，同时为下一个会话留下清晰的工件。你可以在随附的[快速入门](https://github.com/anthropics/claude-quickstarts/tree/main/autonomous-coding)中找到代码示例。

## 长期运行代理的问题

Claude Agent SDK 是一个强大、通用的代理框架，擅长编码以及其他需要模型使用工具收集上下文、规划和执行的任务。它具有上下文管理功能，例如压缩，这使得代理能够在耗尽上下文窗口之前完成一项任务。理论上，有了这样的设置，代理应该能够无限期地继续执行有用的工作。

然而，压缩还不够。即使像 Opus 4.5 这样的前沿编码模型，如果只给一个高级提示（例如“构建一个 [claude.ai](http://claude.ai/redirect/website.v1.a23c2e9e-ccfe-4a56-aed3-c4cdbd962cc4) 的克隆版”），在 Claude Agent SDK 上以循环方式跨越多个上下文窗口运行，也无法构建出一个生产质量的 Web 应用。

Claude 的失败表现在两种模式中。首先，代理往往试图一次做太多事情——基本上就是尝试一次性完成整个应用。这常常导致模型在实现中途耗尽上下文，使得下一个会话从一个功能只实现了一半且缺乏文档的状态开始。然后代理不得不猜测发生了什么，并花费大量时间尝试让基础应用重新工作起来。即使在有压缩的情况下也会发生这种情况，因为压缩并不总能向下一个代理传递完全清晰的指令。

第二种失败模式通常出现在项目后期。在一些功能已经构建完成后，后续的代理实例环顾四周，看到已经取得了进展，然后宣布任务完成。

这便将问题分解为两个部分。首先，我们需要建立一个初始环境，为给定提示所要求的*所有*功能奠定基础，从而使代理能够按步骤、按功能地工作。其次，我们应该提示每个代理朝着目标逐步取得进展，同时在会话结束时将环境保持在一个干净的状态。所谓“干净状态”，我们指的是适合合并到主分支的代码：没有重大错误，代码有序且文档齐全，总的来说，开发者可以轻松地开始一个新功能，而不必先清理一个不相关的烂摊子。

在内部实验时，我们使用双管齐下的解决方案解决了这些问题：

1. 初始化代理：第一个代理会话使用专门的提示，要求模型设置初始环境：一个 `init.sh` 脚本、一个 `claude-progress.txt` 文件（用于记录代理所做的工作），以及一个显示添加了哪些文件的初始 git 提交。
2. 编码代理：后续每个会话都要求模型逐步取得进展，然后留下结构化更新。¹

这里的关键洞察是找到一种方法，让代理在从全新的上下文窗口开始时能够快速理解工作状态，这通过 `claude-progress.txt` 文件以及 git 历史记录来实现。这些实践灵感来自于对高效软件工程师日常工作的了解。

## 环境管理

在更新的 [Claude 4 提示指南](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/claude-4-best-practices#multi-context-window-workflows)中，我们分享了一些多上下文窗口工作流的最佳实践，包括一个使用“第一个上下文窗口的专用提示”的框架结构。这个“专用提示”要求初始化代理设置环境，包含未来编码代理有效工作所需的所有必要上下文。在此，我们深入探讨此类环境的一些关键组成部分。

### 功能列表

为了解决代理一次性完成应用或过早认为项目已完成的问题，我们提示初始化代理编写一份全面的功能需求文件，扩展用户的初始提示。在 [claude.ai](http://claude.ai/redirect/website.v1.a23c2e9e-ccfe-4a56-aed3-c4cdbd962cc4) 克隆示例中，这意味着超过 200 个功能，例如“用户可以打开一个新的聊天，输入查询，按回车，看到 AI 响应”。这些功能最初都被标记为“失败”，以便后续的编码代理能够清楚地了解完整功能是什么样的。

```
{
    "category": "functional",
    "description": "新聊天按钮创建新的对话",
    "steps": [
      "导航到主界面",
      "点击'新聊天'按钮",
      "验证新对话已创建",
      "检查聊天区域是否显示欢迎状态",
      "验证对话出现在侧边栏中"
    ],
    "passes": false
  }
```

复制

我们提示编码代理只通过更改 `passes` 字段的状态来编辑此文件，并使用措辞强硬的指令，例如“删除或编辑测试是不可接受的，因为这可能导致功能缺失或存在错误”。经过一些实验，我们决定使用 JSON 格式，因为与 Markdown 文件相比，模型不太可能不当更改或覆盖 JSON 文件。

### 逐步进展

有了这样的初始环境脚手架，下一个迭代的编码代理就被要求一次只处理一个功能。事实证明，这种逐步方法是解决代理倾向于一次做太多事情的关键。

一旦开始逐步工作，模型在做出代码更改后保持环境处于干净状态仍然至关重要。在我们的实验中，我们发现引发这种行为的最佳方式是要求模型将其进展提交到 git，并附上描述性提交消息，同时在进度文件中编写其进展摘要。这允许模型使用 git 来回滚错误的代码更改并恢复代码库的正常工作状态。

这些方法还提高了效率，因为它们消除了代理猜测之前发生了什么并花费时间尝试让基本应用重新工作的需要。

### 测试

我们观察到的最后一个主要失败模式是 Claude 倾向于在没有适当测试的情况下将功能标记为完成。如果没有明确的提示，Claude 往往会进行代码更改，甚至使用单元测试或针对开发服务器的 `curl` 命令进行测试，但无法识别功能在端到端层面是否有效。

在构建 Web 应用的情况下，一旦明确提示 Claude 使用浏览器自动化工具并像人类用户一样进行所有测试，它在端到端验证功能方面表现得相当好。

Claude 通过 Puppeteer MCP 服务器在测试 claude.ai 克隆时截取的屏幕截图。

为 Claude 提供这类测试工具显著提升了性能，因为代理能够识别并修复仅从代码角度不明显的错误。

仍然存在一些问题，例如 Claude 视觉能力的限制以及浏览器自动化工具难以识别所有类型的错误。例如，Claude 无法通过 Puppeteer MCP 看到浏览器原生的警报模态框，依赖这些模态框的功能因此往往更容易出错。

## 迅速进入状态

有了上述所有机制，每个编码代理都会被提示经过一系列步骤来熟悉情况，其中一些步骤虽基本但仍有所帮助：

1. 运行 `pwd` 查看你当前的工作目录。你只能编辑此目录中的文件。
2. 阅读 git 日志和进度文件，了解最近的工作进展。
3. 阅读功能列表文件，选择一个尚未完成且优先级最高的功能开始工作。

这种方法在每个会话中为 Claude 节省了一些 token，因为它不必再费心去搞清楚如何测试代码。同时，这也得益于让初始化代理编写一个 `init.sh` 脚本，该脚本可以启动开发服务器，并在实现新功能之前运行一个基本的端到端测试。

在 claude.ai 克隆的案例中，这意味着代理总是启动本地开发服务器，并使用 Puppeteer MCP 开始一个新的聊天、发送一条消息并接收响应。这确保了 Claude 能够快速识别应用是否处于损坏状态，并立即修复任何现有错误。如果代理转而开始实现一个新功能，它很可能会使问题更加恶化。

综合以上，一个典型的会话会以以下助手消息开始：

```
[助手] 我将先熟悉一下情况，了解项目的当前状态。
[工具使用] <bash - pwd>
[工具使用] <read - claude-progress.txt>
[工具使用] <read - feature_list.json>
[助手] 让我检查一下 git 日志，看看最近的工作。
[工具使用] <bash - git log --oneline -20>
[助手] 现在让我检查是否有 init.sh 脚本来重启服务器。
<启动开发服务器>
[助手] 很好！现在让我导航到应用程序，验证一些基本功能是否仍然有效。
<测试基本功能>
[助手] 根据我的验证测试，可以看出基本功能运行良好。核心聊天功能、主题切换、对话加载和错误处理都正常工作。现在让我更全面地审查 tests.json 文件，了解接下来需要实现什么。
<开始处理一个新功能>
```

代理失败模式及解决方案

| **问题** | **初始化代理行为** | **编码代理行为** |
| --- | --- | --- |
| Claude 过早地宣布整个项目已完成。 | 设置一个功能列表文件：根据输入规范，创建一个结构化的 JSON 文件，包含一系列端到端功能描述。 | 在会话开始时读取功能列表文件。选择一个单一功能开始处理。 |
| Claude 在环境中留下带有错误或未记录进展的状态。 | 写入初始 git 仓库和进度记录文件。 | 通过读取进度记录文件和 git 提交日志开始会话，并对开发服务器运行一个基本测试以捕获任何未记录的错误。通过写入 git 提交和进度更新结束会话。 |
| Claude 过早地将功能标记为完成。 | 设置一个功能列表文件。 | 自行验证所有功能。只有在仔细测试后才将功能标记为“通过”。 |
| Claude 必须花时间搞清楚如何运行应用。 | 编写一个 `init.sh` 脚本来启动开发服务器。 | 通过读取 `init.sh` 开始会话。 |

总结了长期运行 AI 代理中的四种常见失败模式及解决方案。

## 未来工作

这项研究展示了长期运行代理框架中可能的一组解决方案，以使模型能够在多个上下文窗口之间逐步取得进展。然而，仍有一些开放性问题。

最值得注意的是，目前仍不清楚一个单一的通用编码代理是否能在不同上下文中表现最佳，还是通过多代理架构能够获得更好的性能。似乎合理的想法是，专门的代理（如测试代理、质量保证代理或代码清理代理）能够在软件开发生命周期的子任务中表现得更好。

此外，此演示针对全栈 Web 应用开发进行了优化。未来的方向是将这些发现推广到其他领域。很可能部分或全部这些经验教训可以应用于长期运行代理任务所需的领域，例如科学研究或金融建模。
