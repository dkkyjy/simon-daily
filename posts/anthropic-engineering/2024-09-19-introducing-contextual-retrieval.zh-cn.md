# 引入情境化检索

**日期：** 2024-09-19 00:00 UTC
**链接：** https://www.anthropic.com/engineering/contextual-retrieval

---

要使AI模型在特定情境中有用，它通常需要获取背景知识。例如，客户支持聊天机器人需要了解其服务的具体业务，而法律分析机器人则需要了解大量过往案例。

开发者通常使用检索增强生成（RAG）来增强AI模型的知识。RAG是一种从知识库中检索相关信息并将其附加到用户提示中的方法，从而显著提升模型的响应质量。问题在于，传统的RAG解决方案在编码信息时会移除上下文，这常常导致系统无法从知识库中检索到相关信息。

在这篇文章中，我们概述了一种能够显著改进RAG中检索步骤的方法。该方法称为“情境化检索”，并使用了两种子技术：情境化嵌入和情境化BM25。该方法可将检索失败次数减少49%，若结合重排序，则可减少67%。这些是检索准确率的显著提升，直接转化为下游任务更好的性能。

您可以使用我们的[食谱](https://platform.claude.com/cookbook/capabilities-contextual-embeddings-guide)轻松部署自己的情境化检索解决方案与Claude。

### 关于直接使用更长提示的说明

有时最简单的解决方案就是最好的。如果您的知识库小于200,000个令牌（约500页材料），您可以直接将整个知识库包含在给模型的提示中，无需使用RAG或类似方法。

几周前，我们为Claude发布了[提示缓存](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)，这使这种方法更快且更具成本效益。开发者现在可以在API调用之间缓存常用提示，将延迟降低超过2倍，并将成本降低高达90%（您可以通过阅读我们的[提示缓存食谱](https://platform.claude.com/cookbook/misc-prompt-caching)了解其工作原理）。

然而，随着知识库的增长，您将需要更可扩展的解决方案。这时候情境化检索就派上用场了。

## RAG入门：扩展到更大的知识库

对于无法放入上下文窗口的较大知识库，RAG是典型的解决方案。RAG通过预处理知识库来工作，步骤如下：

1. 将知识库（文档的“语料库”）分解成较小的文本块，通常不超过几百个令牌；
2. 使用嵌入模型将这些块转换为编码语义的向量嵌入；
3. 将这些嵌入存储在允许按语义相似性搜索的向量数据库中。

在运行时，当用户向模型输入查询时，向量数据库用于根据与查询的语义相似性找到最相关的块。然后，将最相关的块添加到发送给生成模型的提示中。

虽然嵌入模型擅长捕捉语义关系，但它们可能会遗漏关键的确切匹配。幸运的是，有一种较老的技术可以在这些情况下提供帮助。BM25（最佳匹配25）是一种使用词汇匹配来查找精确词或短语匹配的排序函数。它对于包含唯一标识符或技术术语的查询特别有效。

BM25通过建立在TF-IDF（词频-逆文档频率）概念之上来工作。TF-IDF衡量一个词在文档集合中的重要性。BM25通过考虑文档长度并将饱和函数应用于词频来改进这一点，这有助于防止常见词主导结果。

以下是BM25在语义嵌入失败时如何成功的示例：假设用户在技术支持数据库中查询“错误代码 TS-999”。嵌入模型可能会找到关于一般错误代码的内容，但可能错过精确的“TS-999”匹配。BM25会查找这个特定的文本字符串以识别相关文档。

RAG解决方案可以通过结合嵌入和BM25技术，使用以下步骤更准确地检索最适用的块：

1. 将知识库（文档的“语料库”）分解成较小的文本块，通常不超过几百个令牌；
2. 为这些块创建TF-IDF编码和语义嵌入；
3. 使用BM25基于精确匹配找到最佳块；
4. 使用嵌入基于语义相似性找到最佳块；
5. 使用排名融合技术对(3)和(4)的结果进行合并和去重；
6. 将前K个块添加到提示中以生成响应。

通过利用BM25和嵌入模型，传统RAG系统可以提供更全面和准确的结果，平衡精确的术语匹配与更广泛的语义理解。

一个标准的检索增强生成（RAG）系统，同时使用嵌入和最佳匹配25（BM25）来检索信息。TF-IDF（词频-逆文档频率）衡量词的重要性，并构成BM25的基础。

这种方法使您能够成本有效地扩展到巨大的知识库，远远超出单个提示所能容纳的范围。但这些传统的RAG系统有一个显著的局限性：它们常常破坏上下文。

### 传统RAG中的上下文难题

在传统RAG中，文档通常被拆分成较小的块以实现高效检索。虽然这种方法对许多应用效果不错，但当单个块缺乏足够的上下文时，可能会导致问题。

例如，假设您的知识库中嵌入了一批财务信息（比如美国SEC申报文件），并且您收到以下问题：*“ACME公司在2023年第二季度的收入增长率是多少？”*

一个相关的块可能包含文本：*“公司收入较上一季度增长了3%。”* 然而，这个块本身并没有指明它指的是哪家公司或相关的时间段，这使得检索到正确的信息或有效使用信息变得困难。

## 引入情境化检索

情境化检索通过在嵌入之前（“情境化嵌入”）和创建BM25索引之前（“情境化BM25”）向每个块前置该块特有的解释性上下文来解决这个问题。

让我们回到SEC申报文件集合的例子。以下是一个块如何被转换的示例：

```
original_chunk = "公司收入较上一季度增长了3%。"

contextualized_chunk = "此块来自ACME公司2023年第二季度业绩的SEC申报文件；上一季度的收入为3.14亿美元。公司收入较上一季度增长了3%。"
```

复制

值得注意的是，过去已经提出了其他使用上下文改进检索的方法。其他提议包括：向块添加通用文档摘要（我们实验了，但发现收益非常有限）、假设文档嵌入和基于摘要的索引（我们评估了，但性能较低）。这些方法与本文提出的方法不同。

### 实现情境化检索

当然，手动为知识库中成千上万甚至数百万个块添加注释工作量太大。为了实现情境化检索，我们求助于Claude。我们编写了一个提示，指示模型使用整个文档的上下文提供简洁、块特有的上下文，以解释该块。我们使用了以下Claude 3 Haiku提示为每个块生成上下文：

```
<document> 
{{WHOLE_DOCUMENT}} 
</document> 
这是我们要在整个文档中定位的块 
<chunk> 
{{CHUNK_CONTENT}} 
</chunk> 
请给出一个简短简洁的上下文，以将此块定位在整个文档中，以改进该块的搜索检索。仅用简洁的上下文回答，不要其他内容。
```

复制

生成的上下文文本（通常为50-100个令牌）在嵌入之前以及在创建BM25索引之前被前置到该块。

以下是预处理流程的实际样子：

*情境化检索是一种提高检索准确率的预处理技术。*

### 使用提示缓存降低情境化检索的成本

由于我们上面提到的特殊提示缓存功能，情境化检索在Claude上可以低成本地实现。通过提示缓存，您无需为每个块传入参考文档。您只需将文档加载到缓存中一次，然后引用之前缓存的内容即可。假设800个令牌的块，8k个令牌的文档，50个令牌的上下文指令，以及每个块100个令牌的上下文，**生成情境化块的一次性成本为每百万文档令牌1.02美元**。

#### 方法

我们在各种知识领域（代码库、小说、ArXiv论文、科学论文）、嵌入模型、检索策略和评估指标上进行了实验。我们在[附录II](https://assets.anthropic.com/m/1632cded0a125333/original/Contextual-Retrieval-Appendix-2.pdf)中包含了每个领域使用的问题和答案示例。

下图显示了在所有知识领域中使用表现最佳的嵌入配置（Gemini Text 004）并检索前20个块的平均性能。我们使用1减去recall@20作为评估指标，该指标衡量在前20个块中未能检索到的相关文档的百分比。您可以在附录中看到完整结果——情境化在我们评估的每个嵌入-来源组合中都提高了性能。

#### 性能提升

我们的实验表明：

* **情境化嵌入将前20个块检索失败率降低了35%**（5.7% → 3.7%）。
* **结合情境化嵌入和情境化BM25将前20个块检索失败率降低了49%**（5.7% → 2.9%）。

*结合情境化嵌入和情境化BM25可将前20个块检索失败率降低49%。*

#### 实现注意事项

在实现情境化检索时，需要牢记以下几点：

1. **块边界：** 考虑如何将文档拆分成块。块大小、块边界和块重叠的选择会影响检索性能¹。
2. **嵌入模型：** 虽然情境化检索在我们测试的所有嵌入模型上都提升了性能，但某些模型可能受益更多。我们发现[Gemini](https://ai.google.dev/gemini-api/docs/embeddings)和[Voyage](https://www.voyageai.com/)嵌入特别有效。
3. **自定义情境化提示：** 虽然我们提供的通用提示效果不错，但针对您的特定领域或用例定制的提示可能会取得更好的结果（例如，包含一个关键术语词汇表，这些术语可能只在知识库中的其他文档中定义）。
4. **块数量：** 在上下文窗口中添加更多块会增加包含相关信息的可能性。然而，过多信息可能会分散模型的注意力，因此存在一个限度。我们尝试了提供5、10和20个块，发现使用20个块在这些选项中性能最佳（见附录中的比较），但值得根据您的用例进行实验。

**始终运行评估：** 通过传递情境化块并区分上下文和块本身，可能会改进响应生成。

## 使用重排序进一步提升性能

在最后一步，我们可以将情境化检索与另一种技术结合，以获得更多性能提升。在传统RAG中，AI系统搜索其知识库以找到可能相关的信息块。对于大型知识库，这种初始检索通常会返回大量块——有时数百个——相关性和重要性各不相同。

重排序是一种常用的过滤技术，用于确保只将最相关的块传递给模型。重排序能提供更好的响应，并降低成本和延迟，因为模型处理的信息更少。关键步骤如下：

1. 执行初始检索以获取前N个可能相关的块（我们使用了前150个）；
2. 将前N个块与用户查询一起传递给重排序模型；
3. 使用重排序模型，根据每个块与提示的相关性和重要性为其打分，然后选择前K个块（我们使用了前20个）；
4. 将前K个块作为上下文传递给模型以生成最终结果。

*结合情境化检索和重排序以最大化检索准确率。*

### 性能提升

市场上有几种重排序模型。我们使用[Cohere重排序器](https://cohere.com/rerank)进行了测试。Voyage[也提供重排序器](https://docs.voyageai.com/docs/reranker)，但我们没有时间进行测试。我们的实验表明，在各种领域中，添加重排序步骤进一步优化了检索。

具体来说，我们发现重排序后的情境化嵌入和情境化BM25将前20个块检索失败率降低了67%（5.7% → 1.9%）。

*重排序后的情境化嵌入和情境化BM25将前20个块检索失败率降低67%。*

#### 成本和延迟考虑

重排序的一个重要考虑因素是对延迟和成本的影响，尤其是在重排序大量块时。由于重排序在运行时增加了一个额外步骤，它不可避免地会增加少量延迟，即使重排序器可以并行对所有块进行评分。在重排序更多块以获得更好性能与重排序更少块以降低延迟和成本之间存在固有的权衡。我们建议根据您的具体用例尝试不同设置，以找到合适的平衡。

## 结论

我们进行了大量测试，比较了上述所有技术的不同组合（嵌入模型、是否使用BM25、是否使用情境化检索、是否使用重排序以及检索的总前K个结果数量），涵盖了各种不同的数据集类型。以下是我们发现的总结：

1. 嵌入+BM25优于单独使用嵌入；
2. 在我们测试的模型中，Voyage和Gemini的嵌入效果最佳；
3. 将前20个块传递给模型比仅传递前10或前5个块更有效；
4. 向块添加上下文能显著提高检索准确率；
5. 重排序优于不重排序；
6. **所有这些优势都是叠加的：** 为了最大化性能提升，我们可以将情境化嵌入（来自Voyage或Gemini）与情境化BM25结合，再加上重排序步骤，并将20个块添加到提示中。
