# skill-forge：从零开始构建你自己的 Claude Code 技能

**日期：** 2026-03-25 00:00 UTC  
**链接：** https://agricidaniel.com/blog/skill-forge-build-claude-code-skills

---

当你构建大量 Claude Code 技能时，会有这样的体验：你会发现 70% 的工作是结构性的。目录布局、清单文件、钩子配置、README 样板——这些在所有技能中都一样。实际的逻辑可能只占 30% 的工作量。

**skill-forge 的存在是因为我一直在仓库之间复制粘贴文件夹结构，就好像还在 2003 年。** 一定会有更好的方法。于是我构建了一个。

## skill-forge 是什么？

skill-forge 是一个用来构建其他 Claude Code 技能的 Claude Code 技能。是的，它是递归的。是的，我觉得这挺有意思。

更具体地说，它是一个引导式工作流，能带你从“我有一个技能的灵感”到“我有一个可运行、可发布的技能”，根据复杂度不同，耗时 5 到 15 分钟。它处理了脚手架搭建、结构、配置和样板代码。**你只需要专注于逻辑——真正关键的部分。**

它通过斜杠命令运行：`/skill-forge`。然后，它会引导你完成结构化的设计流程，生成技能文件，并可选地发布到你的 GitHub 仓库。

## 我为什么构建它

在构建了 claude-seo、claude-ads 和 claude-blog 之后——每个都是相当复杂的多文件技能——我意识到自己在脚手架搭建上花的时间比花在逻辑上的还多。每个技能都需要：

*   Claude Code 期望的特定目录结构
*   具有正确模式（schema）的清单文件
*   带有适当参数解析的斜杠命令定义
*   用于生命周期事件的钩子配置
*   解释安装和用法的 README
*   能在 Claude 执行模型中正常工作的错误处理模式

我第一次构建技能时，花了 3 个小时才把结构弄对。第二次花了 2 个小时。等到第四次，我把它自动化了。**skill-forge 就是那个自动化工具，打包起来让任何人都能使用。**

还有一个不那么明显的原因：一致性。当你手动构建技能时，每个技能最终都会略有不同。不同的目录命名、不同的清单约定、不同的错误处理模式。当你要维护 21 个仓库时，这种不一致就会累积起来。一个技能的错误处理修正在其他技能上无法通用，因为模式都是定制的。skill-forge 强制执行标准结构，这意味着整个技能组合的维护工作变得可预测。

## 它是如何工作的：5 步流程

### 第一步：设计

skill-forge 会询问你的技能应该做什么、为谁设计、需要哪些命令。它会利用这些信息生成一份设计文档——可以把它想象成一份蓝图。你可以在编写任何代码之前审查并完善它。这一步大约需要 2 分钟，并且能防止最常见的失败模式：还没想清楚命令接口就开始写代码。

### 第二步：脚手架搭建

基于设计，skill-forge 会创建完整的文件结构。目录布局、清单文件、命令存根、配置文件。所有内容都位于正确的位置，使用正确的命名约定。脚手架包含占位注释，解释每个部分的作用，这样即使你是新手，也能在不查看文档的情况下浏览生成的代码。

skill-forge 在几秒钟内就能搭建出完整的技能结构。

### 第三步：构建

这一步是你（以及 Claude）编写实际逻辑的地方。skill-forge 提供骨架；你填充血肉。它会根据你的设计为每个命令生成起始代码，这样你就不用从空白文件开始了。对于 API 集成技能，它还会生成带有恰当错误处理、重试逻辑和响应解析的 HTTP 客户端样板代码。

### 第四步：审查

skill-forge 会验证技能结构，检查常见错误（缺失的清单字段、错误的钩子语法、孤立的文件），并运行一次干测试。它能捕获那些当你尝试安装技能时本会坑你的错误。我见过有人花好几个小时调试一个无法加载的技能，最后发现只是清单里少了一个逗号。审查步骤几秒钟内就能发现这类问题。

### 第五步：发布

创建一个 Git 仓库（或添加到已有仓库），编写带有安装说明的合适 README，并可选择推送到 GitHub。你的技能已经准备好让其他人安装和使用。生成的 README 包含徽章区域、特性列表、命令参考和配置文档——全部根据你的设计文档填充。**再也不需要为每个项目从头编写文档了。**

## 4 个复杂度层级

并非每个技能都是像 claude-seo 那样拥有 2,974 颗星的大型单体。skill-forge 支持 4 个复杂度层级：

1.  **单文件技能** - 一个命令，一个文件，简单逻辑。比如：一个快速实用工具，如 URL 验证器或文本格式化工具。5 分钟内即可构建完成。这些是你在想“要是有个斜杠命令就好了”时构建的技能。大多数开发者都有 10-20 个这样的个人工具。

2.  **多命令技能** - 多个斜杠命令，共享实用工具，一些配置。比如：一个内容工具，包含 `/draft`、`/optimize` 和 `/publish` 命令。10-15 分钟内构建完成。这是大多数实用技能所在的层级。

3.  **集成技能** - 连接外部 API、处理认证、管理状态。比如：集成 Google Ads API 的 claude-ads。涉及更多内容，但 skill-forge 会处理 API 客户端脚手架、令牌刷新流程和速率限制处理。生成的代码包含带有指数退避的重试逻辑——这种你总是想实现但一直没空做的东西。

4.  **多技能编排** - 一个协调其他技能的技能。比如：一个项目管理技能，按顺序触发 claude-seo、claude-blog 和 claude-ads。**这是 skill-forge 节省最多时间的地方**，因为技能间通信模式手动实现起来很棘手。在技能之间正确处理数据流、优雅地处理失败、跨技能边界维护状态，都需要精心的架构设计，而 skill-forge 以模板形式提供了这些。

## 示例：5 分钟内构建一个审计技能

让我展示一下这有多快。假设你想要一个审计网站元标签的技能。

你运行 `/skill-forge` 并回答提示：

*   **名称：** meta-audit
*   **描述：** 审计整个网站的元标签
*   **命令：** /meta-audit（接受 URL，检查标题、描述、OG 标签、canonical）
*   **层级：** 单文件
*   **外部 API：** 无（使用 fetch）

skill-forge 会生成整个技能。目录、清单、带有参数解析的命令、fetch 逻辑、输出格式化。**你审查生成的代码，按喜好调整验证规则，然后你就拥有了一个可用的技能。**

使用标准的 Claude Code 技能安装流程进行安装，然后 `/meta-audit https://example.com` 立即生效。

以下是生成的技能开箱即用实际检查的内容：标题标签是否存在及其长度（50-60 个字符）、元描述是否存在及其长度（150-160 个字符）、Open Graph 标签（og:title、og:description、og:image、og:url）、Twitter Card 标签、canonical URL、robots 指令以及 viewport 元标签。这是一个坚实的基础。你可以通过编辑生成的检查函数来添加自定义检查（如 hreflang 验证或结构化数据存在性）。

（生成的代码并非完美——它只是一个起点。但这是一个已经处理了边界情况、错误和输出格式化的起点。而这正是从零开始编写最耗费时间的部分。）

## 我的其他技能是如何构建的

自从构建了 skill-forge 以来，我发布的每个技能都是用它的脚手架搭建的：

*   **claude-blog**（300 颗星） - 多命令技能，第 2 层。skill-forge 生成了 `/blog` 命令结构、内容流水线阶段以及 CMS 集成脚手架。从搭建到第一个可用版本的总构建时间：大约 4 小时。如果没有 skill-forge，根据我在 claude-seo 上的经验，估计要 12 小时以上。

*   **claude-ads**（1,171 颗星） - 集成技能，第 3 层。skill-forge 生成了 Google Ads API 客户端、认证流程和广告系列管理命令。仅 OAuth2 流程从零实现就需要一天时间。skill-forge 在脚手架中提供了一个可用的认证流程。

*   **banana-claude**（41 颗星） - 集成技能，第 3 层。skill-forge 生成了 Gemini API 集成和创意总监提示架构。多步骤生成流水线（意图分析、风格映射、提示工程、质量检查）在设计阶段就已结构化，这节省了大量架构返工工作。

claude-seo 早于 skill-forge（正是这个项目让我意识到我需要它），但我后来将其结构调整为符合 skill-forge 的约定。**在所有 21 个仓库中保持一致的结构使维护工作大大简化。** 当我在一个技能的错误处理模式中修复一个 bug 时，我可以在所有技能中机械地应用同样的修复。
