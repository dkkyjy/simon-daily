# AI 如何改变 Anthropic 的工作方式

**日期：** 2025-12-02 00:00 UTC  
**链接：** https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic  
**标签：** 社会影响

---

AI 如何改变我们的工作方式？我们[之前的研究](https://www.anthropic.com/economic-index) 关于 AI 的经济影响着眼于整个劳动力市场，涵盖了各种不同的工作岗位。但如果我们更详细地研究一些 AI 技术的早期采用者——也就是我们自己——会怎样呢？

将目光转向内部，2025 年 8 月，我们对 132 名 Anthropic 工程师和研究人员进行了调查，进行了 53 次深入定性访谈，并研究了内部 [Claude Code](https://www.anthropic.com/claude-code) 的使用数据，以了解 AI 的使用如何改变 Anthropic 的现状。我们发现，AI 的使用正在从根本上改变软件开发人员的工作性质，既带来了希望，也引发了担忧。

我们的研究揭示了一个正在经历重大变革的工作场所：工程师完成的工作量大增，变得更“全栈”（能够成功完成超出其正常专业领域的任务），学习和迭代速度加快，并着手处理之前被忽视的任务。这种广度上的扩展也让人们开始思考其中的权衡——一些人担心这可能导致更深层次技术能力的丧失，或者更难以有效监督 Claude 的输出，而另一些人则欣然接受更广泛、更高层次思考的机会。一些人发现，与 AI 的合作越多，与同事的合作就越少；有些人甚至想知道，他们最终是否会自动化自己的工作，从而被淘汰。

我们认识到，在一家构建 AI 的公司研究 AI 的影响意味着我们处于一种特权地位——我们的工程师能够早期接触尖端工具，工作在一个相对稳定的领域，并且他们本身也在为影响其他行业的 AI 转型做出贡献。尽管如此，我们仍认为研究和发布这些发现总体上是有用的，因为在 Anthropic 内部工程师身上发生的事情，可能仍然是更广泛社会转型的指示性前兆。我们的发现暗示了一些可能需要跨部门尽早关注的挑战和考量（不过，关于局限性，请参见[附录](https://anthropic.com/research/how-ai-is-transforming-work-at-anthropic#appendix) 中的说明）。在收集这些数据时，Claude Sonnet 4 和 Claude Opus 4 是最强大的可用模型，并且能力还在持续提升。

更强大的 AI 带来了生产力提升，但也引发了关于保持技术专长、维护有意义的协作，以及为不确定的未来做好准备等问题——这个未来可能需要我们在 AI 增强的工作场所中采用新的学习方法、指导方式和职业发展路径。我们在下面的“展望未来”部分讨论了我们内部正在探索这些问题的一些初步步骤。我们还在最近关于 [AI 相关经济政策想法](https://www.anthropic.com/research/economic-policy-responses) 的博客文章中探讨了潜在的政策应对措施。

## 主要发现

在本节中，我们简要总结来自调查、访谈和 Claude Code 数据的发现。我们在后续章节中提供详细的发现、方法和注意事项。

**调查数据**

1. **Anthropic 工程师和研究人员最常使用 Claude 来修复代码错误和学习代码库。** 调试和代码理解是最常见的用途（图 1）。
2. **人们报告 Claude 的使用率和生产力提升均在增加。** 员工自我报告在工作中的 60% 使用 Claude，并实现了 50% 的生产力提升，比去年同一时间增加了 2-3 倍。这种生产力看起来是每个任务类别花费的时间略有减少，但产出量却大幅增加（图 2）。
3. **27% 的 Claude 辅助工作原本是不会完成的**，例如扩展项目、制作锦上添花的工具（如交互式数据仪表板），以及手动操作不划算的探索性工作。
4. **大多数员工经常使用 Claude，但同时报告只能将 0-20% 的工作“完全委托”给它。** Claude 是一个持续的协作者，但使用它通常需要主动监督和验证，尤其是在高风险工作中——而不是直接移交任务无需任何验证。

**定性访谈**

1. **员工正在培养 AI 委托的直觉。** 工程师倾向于委托那些易于验证的任务，他们“可以相对轻松地抽查正确性”、低风险（例如“一次性调试或研究代码”）或枯燥的任务（“我对做某事的兴奋程度越高，我越不可能使用 Claude”）。许多人描述了一个信任递进的过程：从简单任务开始，逐渐委托更复杂的工作——尽管他们目前保留大部分设计或“品味”任务，但随着模型改进，这个边界正在被重新协商。
2. **技能集正在扩展到更多领域，但有些领域实践变少。** Claude 使人们能够将技能扩展到更多软件工程领域（“我能很有能力地处理前端、事务性数据库……以前我会害怕碰这些东西”），但也有一些员工矛盾地担心更深层技能集的萎缩——这些技能对于编写和审查代码都是必需的：“当产出如此容易和快速时，要真正花时间去学习某样东西变得越来越困难。”
3. **与编码手艺的关系正在改变。** 一些工程师欢迎 AI 辅助并关注结果（“我曾以为我真的很喜欢写代码，但我发现我实际上只是喜欢写代码带给我的东西”）；另一些人则表示“（编写代码的）某些部分确实让我怀念。”
4. **工作场所的社会动态可能正在改变。** Claude 现在成为过去向同事提问的首选——一些人报告说，因此指导和合作的机会减少了。（“我喜欢与人合作，现在不那么‘需要’他们，这有点难过……资历较浅的人来找我提问题的频率也降低了。”）
5. **职业演变与不确定性。** 工程师报告工作转向更高层次的管理 AI 系统，并报告生产力显著提升。然而，这些变化也引发了关于软件工程作为职业的长期轨迹的问题。一些人对未来表达了矛盾的感受：“短期内我感到乐观，但长期来看我认为 AI 会做所有事情，让我和许多其他人变得无关紧要。” 其他人则强调真正的不确定性，仅仅表示“很难说”几年后他们角色的样子。

**Claude Code 使用趋势**

1. **Claude 正在越来越自主地处理更复杂的任务。** 六个月前，Claude Code 在需要人类输入之前平均完成约 10 个操作。现在，它通常能处理大约 20 个操作，需要较少的人类指挥即可完成更复杂的工作流程（图 3）。工程师越来越多地使用 Claude 处理复杂任务，如代码设计/规划（从 1% 到 10%）和实现新功能（从 14% 到 37%）（图 4）。
2. **Claude 修复了很多“小麻烦”。** 8.6% 的 Claude Code 任务涉及修复改善生活质量的小问题，比如重构代码以提高可维护性（即“修复小麻烦”），而人们说这些小问题通常会被推迟处理。这些小修复可以累积成更大的生产力和效率提升。
3. **每个人都在变得更“全栈”。** 不同团队以不同方式使用 Claude，通常是为了增强其核心专长——安全团队用它分析不熟悉的代码，对齐与安全团队用它构建数据的前端可视化，等等（图 5）。

## 调查数据

我们对来自组织各处的 132 名 Anthropic 工程师和研究人员进行了关于 Claude 使用情况的调查，以更准确地了解他们日常如何使用它。我们通过内部沟通渠道以及直接联系代表研究和产品职能的不同团队的员工来分发调查问卷。我们在附录中包含了局限性部分，其中包含更多方法细节，并且我们分享了[我们的调查问题](https://assets.anthropic.com/m/6cd21f7d4f82afcb/original/Claude-at-Work-Survey.pdf)，以便其他人可以评估我们的方法并适应他们自己的研究。

### 人们使用 Claude 完成哪些编码任务？

我们让接受调查的工程师和研究人员评估他们在各种编码任务中使用 Claude 的频率，例如“调试”（使用 Claude 帮助修复代码中的错误）、“代码理解”（让 Claude 解释现有代码以帮助人类用户理解代码库）、“重构”（使用 Claude 帮助重构现有代码）和“数据科学”（例如让 Claude 分析数据集并制作条形图）。

以下是常见的日常任务。大多数员工（55%）每天使用 Claude 进行调试。42% 的人每天使用 Claude 进行代码理解，37% 的人每天使用 Claude 实现新功能。频率较低的任务是高级设计/规划（可能是因为这些任务人们倾向于保留给人类处理），以及数据科学和前端开发（可能是因为它们总体上是较不常见的任务）。这与下面“Claude Code 使用趋势”部分报告的 Claude Code 使用数据分布大致一致。

### 使用率和生产力

员工自我报告称，12 个月前，他们在日常工作中使用 Claude 的比例为 28%，从中获得了 +20% 的生产力提升；而现在，他们在 59% 的工作中使用 Claude，平均获得 +50% 的生产力提升。（这大致证实了我们在整个工程组织采用 Claude Code 后，每个工程师每天的合并拉取请求增加了 67%。）同比比较相当惊人——这表明一年内两项指标都增加了超过 2 倍。使用率和生产力也高度相关，在分布的极端情况下，14% 的受访者通过使用 Claude 将生产力提高了 100% 以上——这些是我们的内部“超级用户”。

对于这一发现（以及下面其他自我报告的生产力发现），需要说明的是，生产力难以精确衡量（更多局限性请参见[附录](https://anthropic.com/research/how-ai-is-transforming-work-at-anthropic#appendix)）。AI 研究非营利组织 METR 的[近期工作](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)表明，在非常熟悉的代码库上与 AI 合作的经验丰富的开发者会高估 AI 带来的生产力提升。尽管如此，METR 认为导致生产力低于预期的因素（例如 AI 在大型复杂环境或需要大量隐性知识/背景的环境中表现较差）与我们的员工表示他们*不*委托给 Claude 的任务类型密切相关（参见下面的 [AI 委托方法](https://anthropic.com/research/how-ai-is-transforming-work-at-anthropic#ai-delegation-approaches)）。我们的生产力提升是*跨任务*自我报告的，这可能反映了员工正在发展战略性 AI 委托技能——这是 METR 研究未考虑到的。

当我们询问员工，在他们当前使用 Claude 的任务类别中，Claude 如何影响他们在该任务类别上的总体时间花费和工作产出量时，一个有趣的生产力模式出现了。几乎在所有任务类别中，我们观察到时间花费净减少，而产出量净增加更大：

*图 2：按任务（y 轴）划分的时间花费（左图）和产出量（右图）的影响。每张图的 x 轴对应与不使用 Claude 相比，在 Claude 辅助任务类别中自我报告的时间花费或产出量的减少（负值）、增加（正值）或不变（垂直虚线）。误差线显示 95% 置信区间。圆面积与每个评分点的回答数量成正比。仅包括报告在每个任务类别中使用 Claude 的受访者。*

然而，当我们深入查看原始数据时，发现时间节省的回答聚集在相反的两端——有些人在有 Claude 辅助的任务上花费的时间*明显更多*。

为什么呢？人们通常解释说，他们必须花更多时间调试和清理 Claude 的代码（例如“当我乱写代码把自己逼入绝境时”），并且由于代码不是他们自己写的，理解 Claude 的代码需要更多认知开销。一些人提到在“赋能”意义上花费了更多时间——一个人说使用 Claude 帮助他们“坚持完成以前会立刻放弃的任务”；另一个人说这帮助他们进行更彻底的测试，以及在新的代码库中进行更多学习和探索。似乎总体而言，经历时间节省的工程师可能是那些为 Claude 快速界定可验证任务的人，而花费更多时间的人可能在调试 AI 生成的代码，或在 Claude 需要更多指导的领域工作。

从我们的数据中也不清楚报告的时间节省被重新投入到哪里——是投入到额外的工程任务、非工程任务、与 Claude 互动或审查其输出，还是工作之外的活动。我们的任务分类框架并不能捕捉工程师分配时间的所有方式。此外，时间节省可能反映了自我报告中的感知偏差。需要进一步研究来厘清这些效应。

产出量的增加则更直接和显著；所有任务类别都有更大的净增加。这种模式合理，因为人们报告的是任务类别（比如总体上的“调试”），而不是单个任务——即人们可以在调试类别上花费略少的时间，同时总体上产生更多的调试产出。生产力很难直接衡量，但自我报告的数据表明，在 Anthropic，AI 主要通过更大的产出量来推动生产力提升。

### Claude 赋能新工作

我们好奇的一点是：Claude 是否在赋能质上新型的工作？或者说，Claude 辅助的工作是否最终会被员工完成（尽管速度可能较慢）？

员工估计他们 27% 的 Claude 辅助工作如果没有 Claude 就不会完成。工程师们提到使用 AI 来扩展项目、锦上添花的工具（例如交互式数据仪表板）、有用但乏味的工作（如文档和测试），以及手动操作不划算的探索性工作。正如一个人解释的那样，他们现在可以修复更多之前损害生活质量的“小麻烦”，比如重构结构不良的代码，或构建“小工具以帮助更快完成其他任务”。我们也在使用数据分析中寻找了这一点，并[发现](https://anthropic.com/research/how-ai-is-transforming-work-at-anthropic#fixing-papercuts) 8.6% 的 Claude Code 任务涉及“小麻烦修复”。

另一位研究人员解释说，他们同时运行了多个 Claude 实例，全部在探索不同的问题解决方法：

> 人们倾向于将超级能力的模型视为单个实例，就像获得一辆更快的汽车。但是拥有百万匹马……可以让你测试大量不同的想法……当你拥有这种额外的探索广度时，会感到兴奋且更有创造力。

正如我们将在以下部分看到的那样，这种新工作通常涉及工程师处理其核心专长之外的任务。

### 有多少工作可以完全委托给 Claude？

尽管工程师经常使用 Claude，但超过一半的人表示，他们只能将 0-20% 的工作“完全委托”给 Claude。（值得注意的是，受访者对“完全委托”的理解可能存在差异——从完全不需要验证的任务，到足够可靠只需要轻微监督的任务。）当解释原因时，工程师描述了与 Claude 积极迭代合作并验证其输出的过程——尤其是对于复杂任务或代码质量标准至关重要的高风险领域。这表明工程师倾向于与 Claude 紧密合作并检查其工作，而不是不加验证地移交任务，并且他们对什么算作“完全委托”设定了很高的标准。

## 定性访谈

虽然这些调查结果揭示了显著的生产力提升和工作模式变化，但它们引发了关于工程师日常如何经历这些变化的问题。为了理解这些指标背后的人性维度，我们对 53 名参与调查的 Anthropic 工程师和研究人员进行了深入访谈，以更深入地了解他们对工作场所这些变化的感受和想法。

### AI 委托方法

工程师和研究人员正在开发各种策略，以高效地利用 Claude 在他们的工作流程中。人们通常委托以下任务：

| |
| --- |
| **在用户背景之外 *且* 低复杂度**：“我会在低背景但认为总体复杂度也低的事情上使用 Claude。” “我遇到的大部分基础设施问题并不难，Claude 可以处理……我不太懂 Git 或 Linux……Claude 很好地弥补了我在这些领域经验的不足。” |
| **易于验证**：“对于验证工作量相对于创造工作量不大的所有事情，它绝对*棒极了*。” |
| **定义明确或自成一体**：“如果项目的某个子组件与其余部分充分解耦，我会让 Claude 试一下。” |
| **代码质量不重要**：“如果是可丢弃的调试或研究代码，直接交给 Claude。如果是概念上困难或需要某种特定调试注入，或者是设计问题，我会自己做。” |
| **重复或枯燥**：“我对做某事的兴奋程度越高，我越不可能使用 Claude。而如果我对某件事感到很抗拒……我经常发现更容易的是与 Claude 开始关于该任务的对话。” 在我们的调查中，平均而言，人们说 44% 的 Claude 辅助工作是他们自己不会喜欢做的任务。 |
| **提示比执行更快**：“对于我预期花费不到 10 分钟的任务……我可能不会费心使用 Claude。” “冷启动问题现在可能是最大的障碍。冷启动是指我有很多关于我的团队代码库的内置信息，而 Claude 默认不会拥有这些信息……我可能花时间尝试追求完美的提示……但我就直接自己去做了。” |

我们的员工在委托决策中提到的这些因素，与外部 METR [研究](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/) 中发现的导致 AI 相关生产力放缓的因素（例如开发者对代码库熟悉度高、大型复杂仓库）相似。在我们的访谈中，这些委托标准的一致性表明，适当的任务选择是 AI 生产力提升的一个重要因素（在未来的生产力研究中应仔细控制）。

#### 信任但验证

许多用户描述了他们使用 Claude 的进展，涉及随着时间的推移委托越来越复杂的任务：“起初我使用 AI 工具询问关于 Rust 编程语言的基本问题……最近，我一直在使用 Claude Code 进行所有编码。”

一位工程师将信任的进展比作采用其他技术，如谷歌地图：

> 一开始我只会在我不知道的路线上使用谷歌地图……这就像我使用 Claude 写我不知道的 SQL，但不会让它写我知道的 Python。然后我开始在大部分知道的路线上使用谷歌地图，但可能不知道最后一段……今天我一直在使用谷歌地图，即使是日常通勤。如果它建议走另一条路，我会照做，只是相信它考虑了所有选择……今天我也以类似方式使用 Claude Code。

工程师对于是在自己的专长领域内还是专长领域外使用 Claude 存在分歧。有些人在“外围”领域使用它来节省实施时间；其他人更喜欢熟悉的领域，在那里他们可以验证输出（“我使用 Claude 的方式是，我仍然完全理解它在做什么”）。一位安全工程师强调了经验的重要性，当时 Claude 提出了一个“在危险方面非常聪明，就像一位非常有才华的初级工程师可能提出的方案”。也就是说，只有具备判断力和经验的用户才能认识到它有问题。

其他工程师对两种类型的任务都使用 Claude，要么以实验方式（“我基本上总是让 Claude 先尝试任何编码问题”），要么根据他们在任务中的专长水平调整方法：

> 我既用它处理我的核心专长任务（作为加速器，我知道期望什么并能有效引导代理）也处理稍微超出我专长领域的任务，在那里我大致知道期望什么，但 Claude 能填补我记忆或对特定定义熟悉程度上的空白。

> 如果是我特别精通的事情，我会更果断地告诉 Claude 需要追踪什么。如果是我没有把握的事情，我通常请它做专家，给我选项以及我应考虑和研究的见解。

#### 人们为自己保留哪些任务？

人们一致表示，他们不使用 Claude 处理需要高层次或战略性思考的任务，或需要组织背景或“品味”的设计决策。一位工程师解释说：“我通常保留高层次思考和设计。我可以委托从新功能开发到调试的任何事情。” 这在我们的调查数据中得到反映，该数据显示设计和规划任务的生产力提升最小（图 2）。不过，许多人将委托边界描述为一个“移动的目标”，随着模型改进而不断重新协商（下面 Claude Code 使用数据显示，现在与六个月前相比，编码设计/规划的使用相对更多）。

### 技能转变

#### 新能力……

调查发现 27% 的 Claude 辅助工作原本不会完成，这反映了一个更广泛的模式：工程师利用 AI 在其核心专长之外工作。许多员工报告完成了以前超出其专长的工作——后端工程师构建用户界面；研究人员创建可视化。一位后端工程师描述了通过 Claude 迭代构建复杂用户界面的过程：“它做得比我曾经能做到的好得多。我根本做不到，肯定不能按时……（设计师们）说‘等等，这是你做的？’我说‘不，这是 Claude 做的——我只是提示了它。’”

工程师报告“变得更全栈了……我能很有能力地处理前端、事务性数据库或 API 代码，而以前我会害怕碰我不太擅长的东西。” 这种能力扩展实现了更紧密的反馈循环和更快的学习——一位工程师说，原本“几周的过程”——构建、安排会议、迭代——可以变成“几小时的协作会议”，同事在场提供实时反馈。

总体而言，人们对快速原型设计、并行工作、减少苦差事以及总体提升野心的新能力感到兴奋。一位高级工程师告诉我们：“这些工具肯定让初级工程师更有生产力，也更敢于承担他们原本不会参与的项目类型。” 有些人还说，使用 Claude 降低了“激活能量”，使他们更容易战胜拖延，“大大减少了我想开始解决问题所需的能量，因此我愿意处理更多额外的事情。”

#### …以及更少的动手实践

与此同时，一些人担心“随着委托更多工作，技能会萎缩”，以及在手动解决问题过程中发生的附带（或“间接”）学习会丢失：

> 如果你自己去调试一个难题，你会花时间阅读文档和代码，这些并不直接有助于解决问题——但在这整个过程中，你在构建系统如何工作的模型。现在这种情况少了很多，因为 Claude 可以直接带你到问题所在。

> 我过去会探索每个配置以理解工具能做什么，但现在我依赖 AI 告诉我如何使用新工具，因此我缺乏专业知识。在与队友交谈时，我能立即回忆起某些事情，而现在我不得不问 AI。

> 使用 Claude 有可能跳过我通过解决简单实例来学习如何完成任务的部分，然后后来难以解决更复杂的实例。

一位高级工程师说，如果自己更初级的话，会更担心自己的技能：

> 我主要是在我知道答案应该是什么样子的情况下使用 AI。我通过‘硬方式’做软件工程培养出了那种能力……但如果我处于职业生涯早期，我认为需要付出很多刻意的努力才能继续培养自己的能力，而不是盲目接受模型输出。

编码技能萎缩之所以令人担忧，原因之一是“监督悖论”——如上所述，有效使用 Claude 需要监督，而监督 Claude 需要可能因过度使用 AI 而萎缩的编码技能。一个人说：

> 老实说，我更担心的是监督和监管问题，而不是我的具体技能……我的技能萎缩或未能发展，主要会在我在意的事情上影响我安全使用 AI 的能力，而不是我独立完成这些任务的能力。

为了对抗这一点，一些工程师刻意在不使用 AI 的情况下练习：“偶尔，即使我知道 Claude 能完美解决一个问题，我也不会让它做。这有助于我保持敏锐。”

#### 我们还需要这些动手编码技能吗？

也许软件工程正在向更高的抽象层次发展，这在过去已经发生过。早期的程序员更贴近机器——手动管理内存，用汇编语言编写，甚至拨动物理开关来输入指令。随着时间的推移，出现了更高级、更易读的语言，自动处理复杂的底层操作。也许，特别是在“氛围编码”兴起的情况下，我们现在正在转向英语作为编程语言。我们的一位员工建议有抱负的工程师“擅长让 AI 编写代码，并专注于学习更高层次的概念和模式。”

少数员工说，他们感觉这种转变使他们能够更高层次地思考——“关于最终产品和最终用户”，而不仅仅是代码。一个人将当前的转变比喻为以前在计算机科学中必须学习链表——更高级编程语言现在自动处理的基本结构。“我很高兴我知道如何做……但执行那些底层操作在情感上并不特别重要。我更关心代码能让我做什么。” 另一位工程师做了类似的比较，但指出抽象是有代价的——随着迁移到更高级语言，大多数工程师失去了对内存处理的深入理解。

继续在某个领域发展技能可以导致更好地监督 Claude 和更高效的工作（“我注意到对于我熟悉的事情，我通常做起来更快”）。但工程师们对于这是否重要存在分歧。一些人保持乐观：

> 我不太担心技能侵蚀。AI 仍然让我仔细思考问题，并帮助我学习新方法。如果说有什么不同的话，能更快地探索和测试想法，加速了我在某些领域的学习。

另一个人则更务实：“我肯定在萎缩作为软件工程师的技能……但如果需要，这些技能可以恢复，我只是不再需要它们了！” 一个人指出，他只失去了不太重要的技能，比如制作图表，而“关键类型的代码我仍然能写得很好。”

也许最有趣的是，一位工程师对前提提出了质疑：“‘变生疏’的框架依赖于一个假设，即编码总有一天会回到 Claude 3.5 之前的样子。而我认为不会。”

#### 软件工程的技艺与意义

工程师们在是否怀念动手编码方面存在明显分歧。一些人感到真正的失落——“对我来说这是一个时代的结束——我已经编程 25 年了，那种对技能的自信是我职业满足感的核心。” 另一些人担心不喜欢工作的新性质：“整天提示 Claude 并不有趣或充实。放点音乐，进入状态，自己实现东西要有趣和充实得多。”

一些人直接处理了这种权衡并接受了它：“（编写代码）的某些部分我确实怀念——重构代码时那种禅意的流畅状态，但总体而言我现在生产力高得多，我很乐意放弃。”

一个人说，与 Claude 迭代变得*更有趣*了，因为与人相比，他们可以对反馈更挑剔。另一些人则更关注结果。一位工程师说：

> 我曾预期到现在会感到害怕或无聊……但我并没有这两种感觉。相反，我为能做得更多而感到兴奋。我曾以为我真的很喜欢写代码，但实际上我只是喜欢写代码带给我的东西。

人们是拥抱 AI 辅助还是哀悼动手编码的缺失，似乎取决于他们认为软件工程最意义的方面。

### 工作场所中不断变化的社会动态

一个更突出的主题是，Claude 已经成为过去向同事提问的首选。“我现在问的问题（比以前）多得多，但大约 80-90% 都给了 Claude，” 一位员工指出。这创造了一个过滤机制，Claude 处理日常查询，同事则处理更复杂、战略性或背景密集的 AI 能力不足以解决的问题（“我对团队的依赖减少了 80%，但剩下的 20% 至关重要，我会去找他们讨论”）。人们也会与 Claude“ brainstorm”，类似于与人类合作者的互动。

大约一半的人报告团队协作模式没有变化。一位工程师说，他仍然与人们会面，分享背景，选择方向，并认为在不久的将来仍会有很多协作，但“不是做标准的专注工作，而是与许多 Claude 对话。”

然而，其他人描述与同事的互动减少了（“我与 Claude 的合作远多于与任何同事。”）一些人欣赏这种社会摩擦的减少（“我不会因为占用同事时间而感到内疚”）。另一些人抗拒这种变化（“我真的不喜欢‘你问过 Claude 了吗？’这种常见回应。我非常喜欢与人们面对面工作，并且高度珍视这一点”）或者怀念以前的工作方式：“我喜欢与人合作，现在不那么‘需要’他们，这有点难过。” 几个人指出了对传统师徒关系的影响，因为“Claude 可以为初级员工提供很多指导”，而不是由高级工程师指导。一位高级工程师说：

> 令人难过的是，资历较浅的人来找我提问题的频率降低了，尽管他们的问题确实得到了更有效的回答，并且学习得更快。

### 职业不确定性及适应

许多工程师描述他们的角色从编写代码转向管理 AI。工程师越来越将自己视为“AI 代理的管理者”——有些人已经“经常同时运行几个 Claude 实例。” 一个人估计他们的工作已经“70% 以上变成了代码审查员/修改者，而不是全新的代码编写者”，另一个人认为“为 1 个、5 个或 100 个 Claude 承担责任”是他们未来角色的一部分。

从长远来看，职业不确定性普遍存在。工程师们将这些变化视为更广泛行业变革的先兆，许多人表示“很难说”几年后他们的职业生涯会是什么样子。一些人在短期乐观和长期不确定性之间表达了矛盾。“短期内我感到乐观，但长期来看我认为 AI 会做所有事情，让我和许多其他人变得无关紧要，” 一个人说道。其他人则更尖锐地指出：“感觉就像我每天来上班就是为了让自己失业。”

一些工程师更为乐观。一个人说：“我为初级开发者担心，但我也欣赏初级开发者可能是对新技术最渴望的。我总体对这个职业的轨迹感到非常乐观。” 他们争辩说，虽然存在经验不足的工程师发布有问题的代码的风险，但更好的 AI 护栏、更多内置教育资源以及从错误中自然学习，将帮助该领域随着时间的推移适应。

我们询问人们如何设想他们未来的角色，以及是否有任何适应策略。一些人提到计划进一步专业化（“培养有意义地审查 AI 工作的技能将需要更长时间和更多专业化”），一些人预期未来专注于更人际和战略性的工作（“我们将花更多时间达成共识，让 AI 花更多时间在实施上”）。一个人说他们专门使用 Claude 进行职业发展，从中获得关于工作和领导技能的反馈（“我学习东西的速度，或者即使没有完全学习也能变得高效的速度，彻底改变了。我几乎感觉天花板为我碎裂了。”）

总体而言，许多人承认深深的不确定性：“我对未来哪些具体技能会有用信心很低。” 一位团队领导说：“没人知道会发生什么……重要的是要非常适应变化。”

## Claude Code 使用趋势

调查和访谈数据表明，增加 Claude 使用率正在帮助人们更快工作并承担新型工作，尽管这也伴随着 AI 委托和技能发展方面的紧张。尽管如此，自我报告的数据只讲述了一部分故事。为了补充这一点，我们还分析了 Anthropic 团队中的实际 Claude 使用数据。由于调查受访者报告 Claude Code 是其使用的大部分，我们使用[隐私保护分析工具](https://www.anthropic.com/research/clio)分析了 2025 年 2 月和 8 月的 200,000 份内部 Claude Code 记录。

### 以更少监督应对更难的问题

在过去的六个月里，Claude Code 的使用已转向更困难、更自主的编码任务（图 3）：

* **员工使用 Claude Code 处理越来越复杂的任务。** 我们将每个记录的任务复杂度按 1-5 等级进行评估，其中 1 对应“基本编辑”，5 对应“需要人类专家数周/月工作的高水平任务”。任务复杂度从平均 3.2 增加到 3.8。为了说明分数之间的差异：平均 3.2 的任务包括“排除 Python 模块导入错误”，而平均 3.8 的任务包括“实现并优化缓存系统”。
* **每个记录中 Claude Code 连续工具调用的最大数量增加了 116%。** 工具调用对应 Claude 使用外部工具采取的动作，如编辑文件或运行命令。Claude 现在平均连续进行 21.2 次独立工具调用而无需人类干预，而六个月前是 9.8 次。
* **人类交互轮次减少了 33%。** 每个记录的平均人类交互轮次从 6.2 减少到 4.1，表明与六个月前相比，现在完成给定任务所需的人类输入更少。

*图 3：2025 年 8 月与 2025 年 2 月之间 Claude Code 使用情况的变化（x 轴）。平均任务复杂度随时间增加（左图），每个记录的平均最大连续工具调用数随时间增加（中图），人类交互轮次随时间减少（右图）。误差线显示 95% 置信区间。数据表明，随着时间的推移，人们越来越多地向 Claude 授予更多自主权。*

这些使用数据证实了调查数据：工程师将越来越复杂的工作委托给 Claude，Claude 需要的监督越来越少。这似乎很可能推动了观察到的生产力提升。

### 任务分布

我们将 Claude Code 记录分类为一种或多种编码任务类型，研究不同任务的使用在过去六个月中如何演变：

*图 4：各种编码任务（y 轴）在总记录数（x 轴）中的百分比分布。我们将六个月前的分布（粉色）与当前分布（紫色）进行比较。y 轴按 2025 年 2 月的频率排序。*

从使用数据估计的总体任务频率分布与自我报告的任务频率分布大致一致。2025 年 2 月到 8 月之间最显著的变化是，现在使用 Claude 实现新功能（14.3% → 36.9%）和进行代码设计或规划（1.0% → 9.9%）的记录比例大幅增加。Claude Code 任务相对分布的这种变化可能表明 Claude 在这些更复杂任务上变得更好，但也可能反映团队如何为不同工作流程采用 Claude Code 的变化，而不是绝对工作量的增加（参见附录中的更多局限性）。

#### 修复小麻烦

我们从调查中发现，工程师现在花更多时间进行小的生活质量改进；与此一致，目前 8.6% 的 Claude Code 任务被归类为“小麻烦修复”。这些包括更大的任务，如创建性能可视化工具和重构代码以提高可维护性，以及更小的任务，如创建终端快捷方式。这可能有助于工程师报告的生产力提升（处理之前被忽视的生活质量改进可能随着时间的推移带来更多效率），并可能减少日常工作摩擦和挫败感。

#### 跨团队的任务差异

为了研究任务目前在团队间的差异，我们改进了分类方法，将 8 月的每条记录分配单一主要编码任务，并按内部团队（y 轴）分割数据。堆积条形图显示了每个团队的编码任务细分：

*图 5：每个水平条代表一个团队（y 轴），分段显示该团队在不同编码任务（x 轴）上 Claude Code 使用比例，按编码任务（图例）着色。顶部条（“所有团队”）代表总体分布。*

“所有团队”条显示总体分布，最常见的任务是构建新功能、调试和代码理解。这为团队特定比较提供了基线。

显著的团队特定模式：

1. **预训练**团队（帮助训练 Claude）经常使用 Claude Code 构建新功能（54.6%），其中很大一部分是运行额外实验。
2. **对齐与安全**和**后训练**团队使用 Claude Code 进行前端开发最多（分别为 7.5% 和 7.4%），通常用于创建数据可视化。
3. **安全**团队经常使用 Claude Code 进行代码理解（48.9%），特别是分析和理解代码库中不同部分的安全影响。
4. **非技术**员工经常使用 Claude Code 进行调试（51.5%），例如排除网络问题或 Git 操作，以及数据科学（12.7%）；Claude 似乎在弥补技术知识差距方面很有价值。

这些团队特定模式中的许多都展示了我们在调查和访谈中观察到的相同能力扩展：使团队中的人能够承担他们否则没有时间或技能去做的新型工作。例如，预训练团队运行了大量额外实验，非技术员工能够修复代码中的错误。而数据表明，团队确实使用 Claude 完成其核心任务（例如，基础设施团队最常使用 Claude Code 进行基础设施和 DevOps 工作），Claude 也常常增强他们的核心任务（例如，研究人员使用 Claude 进行前端开发以更好地可视化数据）。这表明 Claude 正在使每个人在工作中变得更全栈。

## 展望未来

在过去一年中，Anthropic 员工大大增加了对 Claude 的使用，不仅用它加速现有工作，还学习新的代码库、减少苦差事、扩展到新领域，以及处理之前被忽略的改进。随着 Claude 变得更加自主和强大，工程师们正在发现利用 AI 委托的新方法，同时也在思考未来需要哪些技能。这些转变带来了明显的生产力和学习优势，同时也伴随着对软件工程工作长期轨迹的真正不确定性。AI 会像过去的软件工程转型——从低级到高级编程语言，或者从个人贡献者到管理者那样（正如几位工程师所建议的）？还是会更深入？

现在还为时过早——Anthropic 内部有很多早期采用者，情况正在迅速变化，我们的发现可能目前不适用于其他组织或环境（参见附录中的更多局限性）。这项研究反映了这种不确定性：结果是微妙的，没有单一共识或明确的指令出现。但它确实提出了如何深思熟虑且有效地应对这些变化的问题。

为了跟进这项初步工作，我们正在采取几个步骤。我们正在与 Anthropic 工程师、研究人员和领导层讨论，以应对提出的机遇和挑战。这包括研究如何让团队团结起来并相互协作，如何支持专业发展，以及/或如何建立 AI 增强工作的最佳实践（例如，以我们的 [AI 流利度框架](https://www.anthropic.com/learn/claude-for-you)为指导）。我们还在将这项研究扩展到工程师之外，以了解 AI 转型如何影响整个组织中的角色，并支持 CodePath 等外部组织调整计算机科学课程以适应 AI 辅助的未来。展望未来，我们也在考虑结构性方法，随着 AI 能力的进步，这些方法可能变得越来越重要，例如组织内角色演变或技能重塑的新途径。

我们预计在 2026 年随着思考的成熟分享更具体的计划。Anthropic 是一个负责任工作转型的实验室；我们不仅想研究 AI 如何改变工作，还想尝试如何深思熟虑地应对这种转型，首先从我们自己开始。

## 附录

### 局限性

我们的调查结果受到一些方法学限制。我们通过便利抽样和目的性抽样（以确保广泛的组织代表性）选择了受访者。我们在多个内部 Slack 频道发布了调查问卷，获得了 68 份回复，我们还从组织架构图中选择了 20 个不同团队（研究和产品职能），并直接向每个团队 5-10 人发送消息（总共联系 207 人），最后 64 份回复的回复率为 31%。我们采访了前 53 位回复的人。这里可能存在一些选择偏差，因为特别参与 Claude 或有强烈意见（正面或负面）的人更可能回复，而体验更中性的人可能代表性不足。

此外，回复可能受到社会期望偏差的影响（因为回复不是匿名的，所有参与者都是 Anthropic 员工，受访者可能夸大了对 Claude 影响的正面评价）以及近期偏差（要求参与者回忆 12 个月前的生产力和使用模式容易受到记忆扭曲的影响）。此外，如前所述，生产力通常很难估算，因此这些自我报告应谨慎对待。这些自我报告的感知应与我们更客观的 Claude Code 使用数据一起解读，未来的研究将受益于匿名数据收集和更稳健验证的测量工具。

我们的 Claude Code 分析在不同时间段使用了比例抽样，这意味着我们只能衡量任务分布的相对变化，而不是工作量的绝对变化。例如，当我们报告功能实现从 14% 增加到 Claude Code 使用的 37% 时，这并不一定意味着正在完成更多的总功能工作。

最后，这项研究是在 2025 年 8 月进行的，当时 Claude Sonnet 4 和 Claude Opus 4 是我们的最先进模型。鉴于 AI 发展的快速步伐，随着新模型的可用，我们观察到的模式可能已经发生了变化。
