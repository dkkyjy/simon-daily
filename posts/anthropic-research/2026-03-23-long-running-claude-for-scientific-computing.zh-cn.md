# 面向科学计算的长期运行Claude

**日期：** 2026年3月23日 00:00 UTC
**链接：** https://www.anthropic.com/research/long-running-Claude
**标签：** 科学

---

*在这篇文章中，Discovery团队的成员Siddharth Mishra-Sharma解释了如何将多日智能体编码工作流——测试预言机、持久化记忆以及编排模式——应用于科学计算任务，即使这些任务不在自己的专业领域内。*

### **前提**

目前大多数使用AI智能体的科学家都处于对话循环的工作模式中，紧密地管理着每一步流程。随着模型在过去一年左右的时间里在[长周期任务](https://metr.org/time-horizons/)上取得显著进步，一种新的工作方式出现了：我们不必介入每一个细节，而是指定高层次目标，然后让一组智能体自主工作。这使得原本可能需要数天、数周甚至数月才能完成的项目，在短短几个小时内就能完成。某些类型的科学任务非常适合这种模式，例如：重新实现一个数值求解器、将用旧版Fortran方言编写的遗留科学软件转换为现代语言、以及根据参考实现对大型代码库进行调试。这些任务范围明确、成功标准清晰，人类监督可以是间歇性的，而非持续性的。

Anthropic的[C编译器项目](https://www.anthropic.com/engineering/building-c-compiler)展示了这一模式的一个版本，其中Claude在大约2000个会话中工作，构建了一个能够编译Linux内核的C编译器。本文描述了如何利用Claude Code为科学计算任务设置类似的模式，并考虑到了典型学术实验室的环境。作为一个具体例子，我将演示如何使用Claude Opus 4.6[实现一个可微分的宇宙学玻尔兹曼求解器](https://github.com/smsharma/clax)。这是一种数值代码，用于预测大爆炸余辉——宇宙微波背景（CMB）——的统计特性。它通过演化光子、重子、中微子和暗物质在早期宇宙中的耦合方程来实现这一目标。

像[CLASS](http://class-code.net/)和[CAMB](https://camb.info/)这样的玻尔兹曼求解器是宇宙学中的核心科学基础设施，使我们能够利用像*Planck*和*Simons Observatory*这样的巡天数据来约束宇宙学模型。一个可微分的版本——能够通过整个求解器传播梯度——使得基于梯度的推断方法成为可能，从而极大地加速参数估计。用JAX编写这是一个自然的选择，因为它本质上免费提供了自动微分和与加速器（例如GPU）的兼容性。

值得注意的是，这个任务并不属于我的核心科学领域——我对这些工具和科学有较高层次的了解，但并没有足够的专业知识在合理的时间内自行完成它。真正拥有专业知识的研究团队已经在JAX中构建了[可微分](https://arxiv.org/abs/2311.03291)[求解器](https://arxiv.org/abs/2602.15104)，具备CLASS中存在的部分功能。这些工作通常需要数月到数年的研究人员时间。这里的要点是看看一个智能体能否在非领域专家的最小引导下走得更远。

这类任务在结构上与C编译器项目不同，后者可以分派给大量并行智能体。而玻尔兹曼求解器则是一个深度耦合的流水线——在模拟早期宇宙如何复合时，一个小小的数值误差或不精确的近似都会微妙地影响下游的所有结果。因此，它需要一套不同的智能体技能。调试需要因果地追溯整个链条，并利用领域知识，这可能更适合单个智能体按顺序工作，在需要时产生子智能体，并使用参考实现来二分定位差异。

我们将使用一个运行SLURM作业调度器的HPC集群作为我们的计算环境，但核心思路——进度文件、测试预言机、带有明确规则的智能体提示——无论您在何处运行Claude Code都适用。

### **起草计划并本地迭代**

在这种向管理自主研究智能体团队转变的过程中，您应该花大部分时间（与Claude协商）精心制定一套指令，清晰阐明项目的交付成果和相关背景信息。这些指令应放在位于根目录的CLAUDE.md文件中。Claude会特殊对待该文件，将其保持在上下文中，并引用它以获取整体计划。至关重要的是，Claude可以在工作中编辑这些指令，在解决问题时为未来的工作更新它们。

[这里](https://github.com/smsharma/clax/blob/6a6b2330cf25edded1bb31ec57a0091aa794a5d3/CLAUDE.md)是宇宙学玻尔兹曼求解器项目的早期CLAUDE.md，显示了在初次尝试编写求解器后的整体计划和设计决策。为了达到这一点，我指定了项目的高层目标——实现与参考CLASS实现完全的功能等价性，同时完全可微分，并在主要科学交付成果上达到0.1%的精度目标——然后与Claude反复迭代，直到计划看起来令人满意。由于0.1%是两种经典玻尔兹曼代码CLASS和CAMB之间典型的吻合水平，这看起来是一个合理的科学目标。

### **会话间的记忆**

进度文件（按照惯例我们称之为CHANGELOG.md）是智能体的便携式长期记忆，充当一种实验笔记。在CLAUDE.md中，Claude被指示在该文件中跟踪进度。

一个好的进度文件可能会跟踪当前状态、已完成的任务、失败的方法及其原因、关键检查点处的精度表以及已知的限制。失败的方法很重要——没有它们，后续会话会重新尝试同样的死胡同。一条记录可能看起来像：“尝试使用Tsit5求解扰动ODE，系统过于刚性。切换到Kvaerno5。”[这里](https://github.com/smsharma/clax/blob/main/CHANGELOG.md)是运行示例的变更日志，展示了这些要素。

### **测试预言机**

虽然通过智能体进行更开放式的科学发现肯定即将到来，但今天长期运行的自主科学工作关键在于智能体需要一种方法来了解自己是否在取得进展。对于科学代码，这可以是参考实现、一个可量化的明确目标，或现有的测试套件。指示智能体在工作中扩展测试套件并运行测试也有助于防止回归。在我的示例任务中，Claude被指示以[CLASS C源代码](https://github.com/lesgourg/class_public)为参考实现，构建并持续运行单元测试。

### **Git作为协调工具**

Git可以是监控和协调智能体进度的一种不错方式，无需亲力亲为。智能体应在每个有意义的单元工作后提交并推送。这为您提供了可恢复的历史记录，以防出现差错，使进度在本地可见，并防止工作丢失（例如，如果您的计算配额在会话中途用完）。

在实践中，这可以是CLAUDE.md中的一组指令，例如：“在每个有意义的单元工作后提交并推送。在每次提交前运行`pytest tests/ -x -q`。永远不要提交导致现有测试失败的代码。”

要引导智能体，您可以随时通过SSH进入集群并手动重新提示和/或更新其指令。通常更方便的做法是直接让本地Claude Code实例通过SSH进入并为您运行命令；这同样适用于下面描述的所有内容。

### **执行循环**

如上所述，通常先在本地迭代计划，直到您拥有一个看起来合理的计划并已编码到CLAUDE.md中。然后，在计算节点上的终端复用器（如tmux）中启动一个Claude Code会话，告诉智能体您的代码库在哪里，然后让它自行运转。由于会话在tmux内运行，您可以分离、合上笔记本电脑，并偶尔检查进度（对于玻尔兹曼求解器，我会在手机上看GitHub，例如在排队买咖啡的时候）。

在HPC集群上，您可能会通过SLURM调度器请求一个节点，一个启动Claude Code在tmux会话中运行的示例作业脚本可能如下所示：

```
#!/bin/bash
#SBATCH --job-name=claude-agent
#SBATCH --partition=GPU-shared
#SBATCH --gres=gpu:h100-32:1
#SBATCH --time=48:00:00
#SBATCH --output=agent_%j.log
cd $PROJECT/my-solver
source .venv/bin/activate
export TERM=xterm-256color
tmux new-session -d -s claude "claude; exec bash"
tmux wait-for claude
```

复制

作业启动后，您连接到tmux会话，给Claude Code一个方向（例如，“读取CHANGELOG.md并接手下一个任务”），当您满意它走上正轨后就可以分离。您可以随时重新连接以检查进度、引导或启动新任务，使用类似这样的命令：

```
srun --jobid=JOBID --overlap --pty tmux attach -t claude
```

复制

**Ralph循环：** 随着模型能力的增强，它们需要的定制编排（如提示工程、RAG或上下文填充）越来越少。但在某个时间点上，提供一定程度的脚手架作为能力提升仍然是有用的。例如，当前模型可能会遭受*智能体懒惰*——当被要求完成一个复杂、多部分的任务时，它们有时会找到借口在完成整个任务之前停止（“天色已晚，我们明天再继续吧？”）。

为了规避这一点，一个有用的编排模式是[*Ralph循环*](https://ghuntley.com/loop/)，它本质上是一个*for*循环，当智能体声称完成时将其踢回上下文，并询问它是否*真的*完成了。这对于长期运行的任务很有用，因为智能体会承认任务不符合要求，然后继续工作直到符合要求。其他类似模式包括[GSD](https://github.com/gsd-build/get-shit-done)（以及[领域特定变体](https://arxiv.org/abs/2603.20179)[^1]）以及Claude Code原生的/loop命令。

Ralph可以通过/plugin安装。Claude Code中的一个典型调用提示可能如下所示：

```
/ralph-loop:ralph-loop “请继续工作，直到在整个参数范围内达到0.1%精度的成功标准。” --max-iterations 20 --completion-promise “DONE”
```

复制

这里，Claude将迭代最多20次，直到它用“DONE”咒语保证任务完成。

### **结果**

Claude从零开始在[该项目](https://github.com/smsharma/clax)上工作了几天，在其各个输出上达到了与参考CLASS实现低于百分之一的吻合。我要求Claude在项目过程中重建代码主要输出（各种CMB角功率谱）的精度，并标定开发过程中的里程碑。它生成了下面的图，展示了达到百分之一以下精度的路径。

随着智能体在代码库上工作，达到百分之一以下精度的路径随时间变化。

智能体的开发轨迹有些笨拙。例如，其测试覆盖存在明显漏洞——有一段时间它只在一个（基准）参数点上测试代码，大大降低了其捕捉错误的表面积。它也可能犯一些低级错误，比如在规范约定上出错，或者花费数小时追逐宇宙学家一眼就能发现的错误，但它一直在朝着规定的百分之一以下精度目标持续取得进展。

该项目的一个副作用是，通过观看git提交历史，我对玻尔兹曼求解器及其建模的物理有了惊人的了解。该项目并非源自我的核心科学领域，但跟随Claude的渐进进展并查阅我不认识的内容，结果证明是一种有效渗透科学知识的方式。[提交日志](https://github.com/smsharma/clax/commits/main/)读起来就像一个快速、超级字面的博士后实验笔记。

虽然最终的求解器尚未达到生产级别（例如，它在所有条件下都无法与参考CLASS实现达到可接受的精度吻合），但它展示了智能体驱动开发可以将数月甚至数年的研究人员工作压缩为数天。

这种压缩改变了什么算空闲时间。AI研究中一个普遍的经历是晚上启动一个实验（例如训练运行），然后第二天早上满意地看到结果。不运行实验会带来机会成本。如今，不运行智能体似乎也会带来成本。如果你有计算资源和成功标准明确的项目，那么每一个*没有*智能体为你工作的夜晚，都是可能被搁置的潜在进展。
