## 引言

确保程序没有 bug 是软件工程中最具挑战性的方面之一。尽管开发者付出了最大努力，bug 仍然经常潜伏。最常见的测试代码方法是 *基于示例的测试*：开发者写出一个具体的示例用例，然后验证实际输出是否与预期输出匹配。例如，开发者可能会验证一个对列表 [2, 10, 5, 4] 调用的排序函数是否返回输出 [2, 4, 5, 10]。然而，用这样的测试来彻底覆盖一个程序很具挑战性：bug 常常停留在开发者未测试的边界情况中。毕竟，如果开发者没有想到测试某个边界情况，那么开发者在实现中也很可能没有考虑该情况！

相比之下，*基于属性的测试* 是一种软件测试范式，旨在测试代码的一般属性是否对所有（或大多数）输入成立。开发者指定一个关于程序的属性或不变量——例如，JSON 反序列化是序列化的逆操作——以及该属性接受何种输入（例如，任何可 JSON 序列化的对象）。基于属性的测试框架随后通过使用类似模糊测试的技术生成有效输入作为测试用例，自动搜索该属性的反例。由于开发者指定的是一般输入域，而不是单个测试用例，基于属性的测试使开发者免于思考每个边界情况，并允许他们在更高级别的抽象上操作。

在我们于 2025 年 NeurIPS [*Deep Learning for Code*](https://dl4c.github.io/) 研讨会上展示的论文中（该论文是一个 [MATS](https://www.matsprogram.org/) 项目的成果），我们开发了一个能够自主为现有代码编写基于属性测试的 AI 智能体。我们引导智能体通过阅读类型注解、文档字符串、函数名称和注释来发现属性。然后，智能体使用 Hypothesis 编写相应的基于属性测试。

在这项工作中，我们专注于识别一般 bug 的问题，而不仅仅是安全漏洞。许多导致安全漏洞的逻辑错误类都适合进行基于属性的测试。例如，在最近的一篇[博客文章](https://red.anthropic.com/2025/smart-contracts/)中，我们专注于识别*智能合约*中的 bug；几乎所有那些漏洞都是逻辑错误的结果。在未来，我们设想也许可以将我们在此描述的技术应用于在部署之前主动识别 bug。

我们使用我们的智能体并在流行的开源 Python 仓库（如 NumPy、SciPy 和 Pandas）中发现了数百个潜在 bug。为了负责任地披露这些 bug，并确保我们不会不必要地给维护者增加负担，我们仔细审查了每个 bug。

我们使用的审查过程比我们为自己代码审查所实施的过程更为费力，但我们强烈倾向于减少误报数量。我们的过程如下：首先，我们只选择最高优先级的 bug 进行审查。我们将这些潜在 bug 发送给三位专家人工审查（每个 bug 平均审查一小时）。然后，我们丢弃了任何三位人工审查员中有一位对其有效性不确定的 bug。最后，我们（这篇博客的作者）手动审查了每个候选 bug。只有当我们对其正确性也确信时，我们才手动向仓库维护者提交 issue。我们已经提交了其中一些 bug 报告，并且正在提交更多。

我们已经公开了所有数据，包括尚未验证的 bug，以及为了完整起见，甚至包括我们确定为无效的 bug，以便维护者可以在[这个网站](https://mmaaz-git.github.io/agentic-pbt-site/)上查看它们。在未来几周内，我们打算提交许多剩余 bug（经过额外验证后），并将我们的项目扩展到其他 PyPI 项目。

```
# 基于示例的测试
def test_sort():
    assert my_sort([1,3,2]) == [1,2,3]
    assert my_sort([1,0,-5]) == [-5,0,1]

# Hypothesis 中的基于属性测试
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_sort(lst):
    result = my_sort(lst)
    for i in range(len(result)-1):
        assert result[i] <= result[i+1]
```

**图 1.** 测试代码的两种方式。基于示例的单元测试验证特定的人工指定的输入。相比之下，基于属性的测试指定一个一般属性（例如，排序列表的定义），并依赖框架自动构造可能使该属性失败的输入。

## 我们的基于属性测试智能体

我们的基于属性测试智能体构建为一个自定义的 Claude Code 命令。该智能体接受一个参数，指向一个特定的目标，可以是单个 Python 文件（例如 normalizers.py）、一个模块（例如 numpy、scipy.signal）或一个函数（例如 requests.get、json.loads）。然后，智能体按照以下过程识别潜在 bug：

1. 通过阅读代码、提取相关文档以及探索目标与代码库其余部分的关系，来阅读并理解目标。
2. 基于这些发现提出属性。
3. 在 Hypothesis 中编写相应的基于属性测试。
4. 运行测试并反思：如果测试失败，测试是否真正发现了 bug，还是测试需要调整？如果测试成功，测试是否测试了任何有价值的东西，或者仅仅是空洞的？
5. 如果智能体确信找到了真正的 bug，它会写出格式化的 bug 报告。

**图 2.** 智能体的工作流程。

为了帮助智能体进行长期的多步骤推理，我们引导它使用待办事项列表来跟踪进度。

设计智能体时的一个优先事项是减少误报——根据我们的个人经验，有用的开发者工具应该尽量减少向开发者呈现的错误报告数量。自我反思循环有助于减少误报的数量，同样，将任何属性建立在目标的显式用法和文档基础上也有帮助。例如，在一次智能体运行中，智能体编写了一个首先通过的属性。然而，经过自我反思，智能体意识到它将整个测试包裹在 try-catch 块中。移除这个后，测试失败，智能体发现了一个 bug。我们还观察到，与 Sonnet 4 相比，Opus 4.1 和 Sonnet 4.5 在自我反思方面有显著改进。

## 在真实的 PyPI 包中搜索 bug

为了在现实世界中测试我们智能体的能力，我们策划了超过 100 个流行的 Python 包，涵盖从数值计算到解析再到数据库等多个领域。我们在每个包上调用我们的智能体，并收集所有生成的 bug 报告。

### 评估智能体

对于评估的第一阶段（在我们的论文中有所涵盖），我们在每个包上使用 Claude Opus 4.1 运行智能体，并收集所有生成的 bug 报告。为了评估这些 bug 报告，我们确定了两个标准：第一，“这是一个有效的 bug 吗？”，第二，“这既是一个有效的 bug，又是我们合理应该向库维护者报告的吗？”第二个标准比第一个更严格，因为例如，一个 bug 可能是有效的，但过于微小而不值得提交报告。

在 984 份 bug 报告中，我们手动选择了 50 份进行审查。我们发现其中 56% 的报告是有效的 bug，32% 是既是有效又值得我们报告的 bug。

基于这个手动审查，我们开发了一个评分系统，将 bug 按 15 分评分，目的是找出最可能有效且值得开发者修复的 bug。我们使用 Opus 4.1 根据此评分系统对所有 bug 报告进行评分。我们发现这个排序步骤相当有效：在高分 bug 报告中，86% 是有效的，81% 既是有效又可报告。

在评估的第二阶段，我们在 10 个重要包的子集上使用 Sonnet 4.5 运行智能体，在每个包上运行多次。我们还开发了一个使用 Sonnet 4.5 阅读代码和 bug 报告以检查 bug 正确性和严重性的评估智能体，这比第一阶段的评分系统更复杂。最后，我们支付了 3 位专家人工审查员来评估高严重性 bug 的正确性。

要阅读我们智能体发现的所有 bug 报告，请访问 <https://mmaaz-git.github.io/agentic-pbt-site/>。

### 维护者验证

评估任何发现代码中 bug 的工具的有效性都很困难。虽然我们尽力验证 bug 报告的正确性，但包维护者是最终的仲裁者。为了验证我们的智能体能够找到维护者认为有效且值得修复的 bug，我们选择了五个特别有趣的 bug，并手动将它们及其建议的补丁报告到各自的 GitHub 仓库。在未来几周内，我们计划在验证后继续报告其他 bug。

### numpy

numpy.random.wald 有时返回负数，这是一个 bug，因为 Wald 分布的样本应该只返回正数。这是我们在上面的示例运行中演示的 bug。Claude 知道这是 Wald 分布的一个属性，并编写了一个直接的 PBT 来检查所有生成的样本是否为正。我们将错误追溯到代码中发生的灾难性抵消，并在提交拉取请求时开发了一个数值更稳定的公式。正如 NumPy 维护者在拉取请求中所示，我们的重构公式的相对误差比之前的算法低了近十个数量级。

*补丁已合并：<https://github.com/numpy/numpy/pull/29609>*

### aws-lambda-powertools

slice\_dictionary() 由于没有递增迭代器而重复返回第一个块。我们的智能体通过识别切片然后重建字典应该返回原始字典来捕获了这个 bug。

*补丁已合并：<https://github.com/aws-powertools/powertools-lambda-python/pull/7246>*

### cloudformation-cli-java-plugin

item\_hash() 由于使用了原地 .sort() 方法（返回 None），导致所有列表都产生相同的 hash(None) 值。智能体通过测试不同输入应该有不同的哈希值来捕获了这个 bug。

*补丁已提交：<https://github.com/aws-cloudformation/cloudformation-cli/pull/1106>*

### tokenizers

EncodingVisualizer.calculate\_label\_colors() 缺少闭合括号，返回无效的 HSL CSS。我们的智能体通过测试输出应与 HSL 颜色代码的正则表达式匹配来识别了这个 bug。

*补丁已合并：<https://github.com/huggingface/tokenizers/pull/1853>*

### python-dateutil

easter() 在使用儒略历的某些年份返回非星期日的日期。维护者将这种行为视为由不同的历法系统导致的预期行为，并承认其语义微妙。

*该 issue 无效：<https://github.com/dateutil/dateutil/issues/1437>*

对 python-dateutil 的报告显示了智能体的一个重要局限性：从具有微妙或复杂语义的代码中推导属性仍然困难。如果代码做出了隐式假设，只有库维护者才能决定要测试的正确属性是什么。

## 结论

随着语言模型的不断改进，我们认为智能体化的基于属性测试可能成为人工编写测试的越来越有价值的补充。基于属性测试的高级语义保证使其在开发过程中自然适合配对使用。我们发现，LLM 特别擅长从上下文（函数名称、文档字符串、其他函数如何调用它等）中识别给定代码块*应该*成立的属性。这使得 LLM 能够有效地编写高质量的基于属性测试。

展望未来，我们相信将 LLM 应用于测试和 bug 发现是一个重要的研究方向。尤其是随着 LLM 在利用漏洞方面的能力提升，有必要在使用 LLM 进行利用的攻击者之前保持领先。

虽然在这项工作中我们没有专注于补丁的自动生成，但这显然是未来的一个方向。如果能够（几乎）完全指定一段代码的正确性属性，那么纠正 bug 就会变得容易得多，我们相信在不久的将来，LLM 将能够有效地提出值得维护者考虑的高质量补丁。
