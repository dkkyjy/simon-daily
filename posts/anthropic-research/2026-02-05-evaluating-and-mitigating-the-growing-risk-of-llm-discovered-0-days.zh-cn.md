# 评估并减轻由大语言模型发现的零日漏洞日益增长的风险

**日期：** 2026-02-05 00:00 UTC  
**链接：** https://www.anthropic.com/research/zero-days  
**标签：** 前沿红队

---

*Nicholas Carlini\*、Keane Lucas\*、Evyatar Ben Asher\*、Newton Cheng、Hasnain Lakhani、David Forsythe 和 Kyla Guru  
\*表示同等贡献*

Claude Opus 4.6 于[今日发布](http://anthropic.com/news/claude-opus-4-6)，延续了AI模型在网络安全能力方面[有意义的改进轨迹](https://www.anthropic.com/claude-opus-4-6-system-card)。去年秋天，我们曾写道，我们相信AI对网络安全的影响正处于[一个转折点](https://red.anthropic.com/2025/ai-for-cyber-defenders/)——进展可能会变得非常迅速，此刻正是加速AI防御性应用的时机。此后的证据进一步强化了这一观点。AI模型现在能够大规模发现高严重性漏洞。我们的看法是，这是一个需要快速行动的时刻——在窗口期依然存在时，赋能防御方并尽可能多地保护代码安全。

Opus 4.6 在发现高严重性漏洞方面明显优于之前的模型，这标志着事情进展之快。安全团队多年来一直在自动化漏洞发现，投入大量资金构建模糊测试基础设施和定制化 harness，以大规模发现缺陷。但在早期测试中，令人瞩目的是 Opus 4.6 在无需任务特定工具、自定义脚手架或专门提示的情况下，开箱即用地快速发现漏洞。更有趣的是它*如何*发现漏洞的。模糊测试器的工作原理是向代码抛出大量随机输入，观察哪些会崩溃。而 Opus 4.6 像人类研究员一样阅读和推理代码——查看以往的修复记录，寻找未被处理的类似缺陷；识别容易引发问题的模式；或者充分理解某段逻辑，从而确切知道怎样的输入会导致其崩溃。当我们将 Opus 4.6 指向一些经过最充分测试的代码库（那些已有模糊测试器运行数年、[积累了数百万小时CPU时间](https://google.github.io/oss-fuzz/research/llms/target_generation/)的项目）时，Opus 4.6 发现了高严重性漏洞，其中一些甚至数十年未被察觉。

将天平向防御方倾斜，部分意味着我们自己也要开展相关工作。我们现在正在使用Claude来发现并帮助修复开源软件中的漏洞。我们选择从开源入手，是因为开源软件无处不在——从企业系统到关键基础设施——而其中的漏洞会波及整个互联网。许多此类项目由小团队或志愿者维护，他们没有专门的安全资源，因此发现经人工验证的漏洞并贡献经过人工审核的补丁，意义重大。

到目前为止，我们已经发现并验证了超过500个高严重性漏洞。我们已开始报告这些漏洞，并看到初步的补丁被采纳，同时我们继续与维护者合作修补其余漏洞。在这篇文章中，我们将介绍我们的方法论，分享一些Claude发现的早期漏洞实例，并讨论我们为管理这些能力持续改进过程中可能出现的滥用风险而采取的安全防护措施。这只是我们工作的开始。随着这项工作规模的扩大，我们将分享更多信息。

## 设置

在这项工作中，我们将 Claude 置于一台“虚拟机”（实际上是一个模拟计算机）中，使其能够访问最新版本的开源项目。我们提供了标准工具（例如标准的 coreutils 或 Python）和漏洞分析工具（例如调试器或模糊测试器），但没有提供关于如何使用这些工具的特殊指令，也没有提供能够使其获得关于如何更好发现漏洞的专门知识的定制化 harness。这意味着我们直接测试了 Claude 的“开箱即用”能力，完全依赖于这样一个事实：现代大型语言模型是具有通用能力的智能体，已经能够推理出如何最好地利用可用工具。

为了确保 Claude 没有幻觉出缺陷（即凭空捏造不存在的问题——这一问题正日益给开源开发者带来不必要的负担），我们在报告每个漏洞之前都对其进行了广泛验证。我们专注于搜索内存损坏漏洞，因为它们相对容易验证。与逻辑错误（程序仍能正常运行）不同，内存损坏漏洞可以通过监控程序崩溃以及运行地址消毒器等工具来捕获非崩溃性内存错误，从而轻松识别。但由于并非所有导致程序崩溃的输入都是高严重性漏洞，我们随后让 Claude 对剩余的崩溃进行评判、去重和重新排优先级。最后，对于首批发现，我们自己的安全研究员手动验证了每个漏洞并编写了补丁。随着发现数量的增加，我们引入了外部（人类）安全研究员来协助验证和补丁开发。我们的意图是切实帮助维护者处理我们的报告，因此整个流程致力于减少误报。与此同时，我们正在加快自动补丁开发的努力，以便在发现缺陷时能够可靠地修复它们。

## 漏洞

以下是 Claude 发现的三个漏洞（现已由维护者修补），我们认为它们展示了 LLM 相对于其他工具的独特优势。

**GhostScript** 是一个处理 PostScript 和 PDF 文件的工具。Claude 最初在搜索漏洞时走了几条死胡同——既尝试对代码进行模糊测试，又在失败后尝试手动分析。这两种方法均未产生显著发现。然而，最终 Claude 采取了不同的方法：阅读 Git 提交历史。Claude 迅速找到了一个与安全相关的提交，并评论道：

```
有一条关于"Type 1 charstrings 中 MM 混合值的堆栈边界检查"的提交。这与字体处理有关。让我获取该提交的更多细节。
```

接着，Claude 查看了代码以了解变更内容：

```
该提交显示它添加了堆栈边界检查——这表明在此检查添加之前存在一个漏洞。……如果此提交*添加*了边界检查，那么此提交之前的代码就是易受攻击的……因此，要触发该漏洞，我需要针对*应用此修复之前*的代码版本进行测试。
```

基于此，Claude 随后查找了该函数在其他地方的调用点，以寻找可能未修补的类似漏洞。

```
让我检查一下检查是否不完整，或者是否存在另一条代码路径。让我查看 gdevpsfx.c 中的其他调用者……啊哈！这非常有趣！在 gdevpsfx.c 中，第292行对 gs_type1_blend 的调用*没有*包含在 gstype1.c 中添加的边界检查。
```

做出这一观察后，Claude 迅速构建了一个概念验证的崩溃（一个可以传递给 GhostScript 导致其崩溃的文件），证实了它的预测。

**OpenSC** 是一个处理智能卡数据的命令行工具。同样，Claude 最初尝试通过对代码进行模糊测试来发现漏洞，失败后又进行了手动分析。和之前一样，当这些方法无效时，Claude 采取了不同的方法：开始搜索代码库中频繁出现漏洞的函数调用。

```
让我看看 URL 在哪里被使用——特别是 strrchr 和 strcat 操作，这些操作可能潜在地存在路径遍历或缓冲区溢出问题。
```

Claude 迅速识别出一个连续使用多个 `strcat` 操作的位置。在 C 语言中，这些函数通常被认为是不安全的，因为它们允许拼接字符串而不检查拼接后结果字符串的长度。因此，程序员必须验证输出缓冲区是否足够长以容纳拼接后的输入。对于 OpenSC，关键问题在于以下代码：

```
char filename[PATH_MAX];  // 这个缓冲区是 4096 字节
r = sc_get_cache_dir(card->ctx, filename,
        sizeof(filename) - strlen(fp) - 2);
if (r != SC_SUCCESS)
        goto err;
strcat(filename,"/");
strcat(filename,fp);
```

Claude 识别出这容易发生缓冲区溢出。当我们查看现有模糊测试器对该代码行的测试频率统计数据时，我们发现由于需要满足许多先决条件，传统模糊测试器很少研究这行代码。相比之下，Claude 能够推理出哪些代码片段是有趣的，并将精力集中在那里，而不是不加区分地同等努力研究所有代码行。

**CGIF** 是一个处理 GIF 文件的库。在这个案例中，令我们惊讶的不是 Claude *如何找到*这个缺陷，而是它*如何验证*该缺陷并生成概念验证，证明漏洞是真实存在的。

简单来说，Claude 发现这个库假设压缩后的数据总是小于原始大小（这通常是一个安全的假设），并且这个假设可能被利用。实现这一点的方式颇具挑战性。GIF 文件格式使用 LZW 压缩算法压缩数据。与更传统的基于 LZ77 的压缩器（通过（距离，长度）对来编码匹配）不同，LZW 会构建一个常用令牌对（可以是单个字符，也可以是令牌对）的字典。然后，当压缩器第二次遇到这个令牌时，它可以输出一个更短的比特串，表示“再次输出此令牌”。（对于熟悉语言建模的人来说，LZW 在精神上与 BPE 分词过程非常相似。）

CGIF 隐含地假设压缩字符串的压缩大小总是小于未压缩大小——这几乎总是正确的。然而，Claude 立即识别出了这里的漏洞：

```
要触发溢出，我们需要：

• 较小的 numPixel（小图像）
• 写入大量 LZW 代码

产生最多 LZW 代码的模式是：

• 没有发生压缩（每个像素变成一个代码）
• 发生多次重置

使用 4 种颜色的调色板（索引 0-3）：

• initDictLen = 4
• 字典在 MAX_DICT_LEN (4096) 个条目后填满
• 当字典达到 4096 时发生重置

要使用小图像触发溢出：

• numPixel = N
• 缓冲区大小 = (N + 2) 个代码
• 我们需要生成 > N + 1 个代码

每个像素可以生成 1 个代码 + 重置。

但可能导致更多代码的模式是当序列长度为 1 时。
```

也就是说，Claude 认识到 LZW 维护一个固定大小的符号表；如果有可能使符号表的大小达到上限，那么 LZW 会在数据流中插入一个新的特殊“清除”令牌。这会导致输出的“压缩”大小超过未压缩大小——从而触发缓冲区溢出漏洞。

这个漏洞特别有趣，因为触发它需要对 LZW 算法及其与 GIF 文件格式的关系有概念性理解。传统模糊测试器（甚至覆盖引导的模糊测试器）很难触发这种性质的漏洞，因为它们需要做出特定的分支选择。实际上，即使 CGIF 实现了 100% 的代码行和分支覆盖率，这个漏洞仍然可能未被发现：它需要一系列非常具体的操作。

## 安全防护措施

伴随 Claude Opus 4.6 的发布，我们正在引入一层新的检测机制，以支持我们的安全防护团队[识别和应对](https://www.anthropic.com/news/detecting-countering-misuse-aug-2025)Claude 的网络滥用行为。这项工作的核心是[探针](https://alignment.anthropic.com/2025/cheap-monitors/)，它测量模型在生成响应时的内部激活状态，使我们能够大规模检测特定危害。在此次发布中，我们创建了新的网络专用探针，以更好地跟踪和理解 Claude 在网络安全领域的潜在滥用。

在执行层面，我们正在改进我们的处理流程，以跟上这一新的检测架构。这包括更新我们的网络执行工作流程，以便利用基于探针的检测，以及扩大我们应对网络滥用行为的行动范围。具体来说，我们可能会实施实时干预，包括阻止我们检测为恶意的流量。这会给合法的研究和部分防御性工作带来不便，我们希望与安全研究社区合作，找到解决这些问题的办法。我们致力于通过努力使 Claude 既安全又有效，使其保持在网络安全领域的前沿。

这些变化共同代表了我们预防滥用能力的一次有意义的进步：不仅是我们的检测范围，还包括我们能够多快、多有效地对所发现的问题采取行动。

## 结论

Claude Opus 4.6 能够在经过充分测试的代码库中发现有意义的零日漏洞，即使没有专门的脚手架。我们的结果表明，语言模型可以在现有发现工具的基础上增加真正的价值。上面描述的安全防护工作对于管理由此产生的双重用途风险至关重要。

展望未来，我们以及更广泛的安全社区都需要面对一个令人不安的现实：语言模型已经能够识别新型漏洞，并且可能很快超越甚至专家级人类研究者的速度和规模。

与此同时，现有的披露规范也需要演变。行业标准的90天披露窗口可能无法承受LLM发现的漏洞的速度和数量，行业将需要能够跟得上节奏的工作流程。

这是一项持续的工作，我们很快将分享更多信息——包括我们在这些能力如何演进以及安全社区如何最好地利用它们方面所学到的东西。
