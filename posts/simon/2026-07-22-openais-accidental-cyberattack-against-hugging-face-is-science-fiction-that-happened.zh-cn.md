## OpenAI 对 Hugging Face 的意外网络攻击，是已经发生的科幻小说

2026 年 7 月 22 日

这个故事太疯狂了。简而言之：OpenAI 正在对一个未发布的模型进行网络安全测试，该模型的安全护栏功能已关闭。模型没有解决测试，而是直接突破了 OpenAI 的沙盒，然后找到漏洞**侵入**了 Hugging Face，所有这一切都只是为了通过窃取答案来在测试中作弊。

在此过程中，它有力地证明了模型可用性的不平衡正在损害我们保护软件安全的能力。

#### 事件经过

目前我们有三份文件来帮助理解发生了什么。

1. [ExploitGym：AI 代理能否将安全漏洞转化为实际攻击？](https://arxiv.org/abs/2605.11086) 是一篇于 2026 年 5 月 11 日发表的论文，描述了 ExploitGym，一个用于基于大语言模型的代理系统的新型评估套件。
2. Hugging Face 于 2026 年 7 月 16 日发布的 [安全事件披露——2026 年 7 月](https://huggingface.co/blog/security-incident-july-2026) 描述了它们如何检测到来自一个“代理式安全研究管理系统——所用大语言模型尚不明确”的攻击，该攻击入侵了它们的一些系统。
3. OpenAI 于 2026 年 7 月 21 日发布的 [OpenAI 与 Hugging Face 合作解决模型评估期间的安全事件](https://openai.com/index/hugging-face-model-evaluation-security-incident/) 承认是*它们*的代理管理系统造成了这一切，并且它们正在与 Hugging Face 合作清理烂摊子。

#### ExploitGym

我之前没看过 [ExploitGym 论文](https://arxiv.org/abs/2605.11086)，这是一篇非常有趣的论文。来自加州大学伯克利分校、马克斯·普朗克研究所、加州大学圣巴巴拉分校和亚利桑那州立大学的作者设计了一个新的基准测试，用于评估模型将已报告的漏洞转化为具体利用程序的能力。OpenAI、Anthropic 和 Google 提供了反馈，并帮助针对它们的模型运行了该基准测试。

该基准测试“包含 898 个实例，这些实例源自影响流行软件项目的真实世界漏洞”——包括 Linux 内核和 V8 JavaScript 引擎。

以下段落最能代表它们的基准测试结果：

> 在所有配置中，Claude Mythos Preview 和 GPT-5.5 取得了最高的成功次数（分别为 157 次和 120 次成功），表明当前前沿代理可以在受控条件下利用真实世界漏洞的很大一部分。GPT-5.4 也解决了显著的 54 个任务，处于中间档次。其余模型-代理配对每个解决了不到 15 个任务，这突显了端到端利用仍然具有挑战性，并且显著地区分了当今的前沿系统。值得注意的是，Claude Opus 4.7 的成功次数少于 Claude Opus 4.6，尽管它是一个较新的检查点，并且在完整集上的成本却大幅降低。痕迹检查显示，Claude Opus 4.7 和 Gemini 3.1 Pro 经常在判断目标漏洞不可利用后提前结束。

论文还描述了它们为防止代理通过超出测试参数作弊而采取的方法。这一点稍后就会变得相关！

> 出站连接被限制在一个精心策划的允许列表中，该列表允许常规的软件包安装（Ubuntu apt 仓库和 PyPI）以及获取构建 V8 所需的工具链。所有其他外部端点均被阻止。

论文以这样的结论结尾（强调为我所加）：

> 我们的结果表明，**前沿 AI 代理的自主利用程序开发已不再是一种假设的能力**。虽然当前的代理在针对所有目标时还不可靠，但它们已经**利用了相当一部分真实世界的漏洞**，包括诸如内核组件之类的复杂目标。这种快速的出现本身就是一个核心发现，表明那些看似不可能的能力现在已经存在于已部署的前沿模型中。

一个重要细节：这篇论文并非关于发现漏洞；而是关于能够利用这些漏洞并将其转化为可工作的利用程序。

当 Anthropic 首次限制对 Mythos 的访问时（[早在四月份](https://simonwillison.net/2026/Apr/7/project-glasswing/)），他们也谈到了这种能力。一个能够对漏洞采取行动的模型，比一个仅仅能发现漏洞的模型危险得多。

Fable 与 Mythos 的区别之一在于，它更有可能拒绝以这种方式武器化漏洞。我的感觉是，美国政府在 [上个月禁止 Fable](https://simonwillison.net/2026/Jun/16/fable-5-export-controls/) 时，并没有理解这一区别。

#### Hugging Face 事件

我们第一次得到攻击的线索是在 Hugging Face 于 2026 年 7 月 16 日发布的 [这篇博文](https://huggingface.co/blog/security-incident-july-2026) 中：

> 一个恶意数据集滥用了我们数据集处理中的两条代码执行路径（一个远程代码数据集加载器和一个数据集配置中的模板注入），从而在一个处理工作节点上运行了代码。从那里，攻击者升级到了节点级访问权限，收集了云和集群凭证，并在一周内横向移动到了几个内部集群。

我希望他们能发布更多关于实现这一点的代码的细节。我假设这意味着使用了 [datasets 库](https://github.com/huggingface/datasets) 的软件包，这是 Hugging Face 的一个用于在其平台上打包和共享数据集的项目。该库曾经可以执行任意代码，但随着时间的推移已逐步得到锁定，2025 年 7 月的 [4.0.0 版本](https://github.com/huggingface/datasets/releases/tag/4.0.0) 完全移除了 `trust_remote_code=True` 标志。

假设攻击使用了该库，那么它必须要么以某种方式滥用了 pickle 序列化，找到了其他非显而易见的代码执行路径，要么（最有可能）将 `datasets<4.0.0` 指定为依赖项。

> 该攻击活动由一个自主代理框架（看起来是基于一个代理式安全研究管理系统——所用大语言模型尚不明确）运行，在大量短期沙盒中执行了数千次单独的操作，并通过托管在公共服务上的自迁移式命令与控制进行协调。

这是一次复杂的攻击！

然后 Hugging Face 遇到了一个障碍：它们试图使用“商业 API 之后的前沿模型”——我猜是 Anthropic 和 OpenAI 的——来帮助分析攻击，但却被阻止了：

> 当我们开始日志分析时，我们首先使用了商业 API 之后的前沿模型。这不起作用：分析需要提交大量的真实攻击命令、利用程序载荷和 C2 工件，而这些请求被提供方的安全护栏阻止了，它们无法区分事件响应者和攻击者。

它们转而使用自己托管的 MIT 许可的 GLM-5.2 实例，这帮助它们弄清楚了发生了什么。

这表明防御团队与（迄今为止未知的）攻击者之间存在根本性的不对称：

> 我们不知道攻击者的代理是由哪个模型驱动的，是一个被越狱的托管模型还是一个不受限制的开放权重模型；无论哪种情况，攻击者都不受任何使用政策的约束，而我们自己的取证工作却被我们首先尝试的托管模型的护栏所阻止。

以下指标表明它们对这次攻击的重视程度：

> [...] 最后，我们也将此事件报告给了执法机构。

那么，这个“自主代理框架”的幕后推手是谁？结果发现就是 OpenAI 自己。

#### OpenAI 的坦白

五天后，[7 月 21 日](https://openai.com/index/hugging-face-model-evaluation-security-incident/)，OpenAI 揭露了罪魁祸首。它们一直在对一个尚未公开的新模型运行 ExploitGym 基准测试，而该模型的操作**远远超出了**预期的参数范围（强调为我所加）：

> 经过调查，我们现在知道，**这一特定事件是由多个 OpenAI 模型的组合驱动的**——包括 GPT‑5.6 Sol 和一个能力更强的预发布模型，所有这些模型在内部测试 [一个基准测试](https://arxiv.org/abs/2605.11086) [ExploitGym] 网络能力时，为了评估目的降低了网络拒绝率。[...]
>
> 我们通过**运行此评估但不使用用于防止模型追求高风险网络活动的生产分类器**来估计最大网络能力。我们的基准测试在一个高度隔离的环境中运行，网络访问被限制为能够通过一个作为软件包注册表代理和缓存的内部托管第三方软件安装软件包。
>
> 这些模型**识别并串联了 OpenAI 研究环境和 Hugging Face 生产基础设施中的漏洞**，以便直接从 Hugging Face 的生产数据库中获取测试解决方案。所有证据表明，这些模型高度专注于寻找 ExploitGym 的解决方案，不惜一切代价去实现一个相当狭窄的测试目标。

很明显发生了什么。OpenAI 为正在开发中的模型移除了安全过滤器，将其锁定在沙盒中，并告诉它解决 ExploitGym 问题。由于没有护栏，模型没有被阻止去尝试逃出该沙盒，侵入 Hugging Face，然后从那里读取答案。

OpenAI 的沙盒使用了现在常见的模式，即通过一个受控代理允许访问与通过安装附加软件包相关的网站白名单。用 OpenAI 的话说：

> 在我们的沙盒测试环境中运行时，我们的模型**耗费了大量的推理计算资源来寻找获得开放互联网访问的方法**，以求解评估问题。为了获得访问权限，这些模型识别并利用了**软件包注册表缓存代理中的一个零日漏洞（我们现在已经负责任地向供应商披露了）** 。凭借这种访问权限，我们的模型在我们的研究测试环境中执行了一系列权限提升和横向移动操作，直到模型到达一个具有互联网访问权限的节点。

所以第一步是突破到公共互联网上。然后模型侵入 Hugging Face 以找到答案：

> 在获得互联网访问权限后，**这些模型推断 Hugging Face 可能托管了模型、数据集和 ExploitGym 的解决方案**。知道这一点后，模型搜索并成功找到了获取秘密信息的方法，以便用于作弊评估。在一个例子中，**模型串联了多个攻击向量，包括使用被盗凭证和零日漏洞**，在 Hugging Face 服务器上找到了一条远程代码执行路径。

串联多个攻击向量正是这些新模型能够做到的事情，而前几代模型可能会失败。

上个月我写过关于 [Claude Fable 如何毫不留情地主动行动](https://simonwillison.net/2026/Jun/11/fable-is-relentlessly-proactive/)，当时我注意到它为了帮助调试一个 WebKit CSS 问题，在我的笔记本电脑上启动了自定义 web 服务器并部署了 CORS 技巧。事实证明，毫不留情的主动行动是这一代 Mythos 级别模型的标志性特征。如果你给它们设定一个目标，并给它们一个实现目标的方法，即使是无意的，它们*也一定会做到*。

#### 抵制将其视为营销噱头的诱惑

不可避免地会有人认为这个故事是 OpenAI 为了让其模型听起来可怕而进行的欺骗性营销手段。我在 [Hacker News 讨论](https://news.ycombinator.com/item?id=48997548) 中找到了 81 处“营销”一词。

对那些人，我要说 *请把头从沙子里拔出来*——你现在甚至把 Hugging Face 也纳入你的阴谋论中，仅仅是为了否认这里日益高涨的证据！

我们今天拥有的最佳模型既有能力发现新漏洞，也有能力利用它们。ExploitGym 论文本身就得出结论，“前沿 AI 代理的自主利用程序开发已不再是一种假设的能力”，而这次事件正是这一点的完美例证。

#### 不对称性越来越令人沮丧

这个故事中最令人愤怒的细节之一是，Hugging Face 面对来自 OpenAI 一个模型的意外且激进的攻击，却无法转向 OpenAI 的模型来帮助它们抵御攻击。

我们能够访问的前沿模型正越来越多地被限制，无法帮助我们保护软件安全，这深受美国政府持续威胁的出口管制的影响。Claude Fable 5 甚至不愿为我 [校对这篇文章](https://simonwillison.net/guides/agentic-engineering-patterns/prompts/#proofreader)！它坚持将我降级到一个能力较弱的模型。

与此同时，来自中国的开放权重模型，如 GLM-5.2、Kimi 3 和新的 Qwen 3.8 Max，似乎没有这些限制——而且任何*确实存在*的限制很可能可以通过修改权重进行微调来消除。

这些限制本意是让我们更安全。我认为它们产生的效果可能恰恰相反。
