**[用 Rust 重写 Bun](https://bun.com/blog/bun-in-rust)**（[来源](https://news.ycombinator.com/item?id=48837877 "Hacker News")）Jarred Sumner 一直在承诺这篇博客文章（[自 5 月 9 日起](https://x.com/jarredsumner/status/2053063524826620129)），内容是关于他将 Bun 从 Zig 重写为 Rust，而他承诺的时间远超完成重写所需的时间。

老实说，等待是值得的。这是一篇对极其复杂的代理工程（agentic engineering）的详细描述，涉及动态工作流、试运行、对抗性审查以及各种其他有趣的技巧。

Jarred 用前半篇文章赞扬 Zig 让 Bun 走到了今天这一步。然后我们进入一个核心思想，重点由我标出：

> 我们的错误修复列表让人感觉糟糕，我厌倦了带着对 Bun 崩溃的担忧入睡。我不怪 Zig —— 其他 Zig 用户没有我们遇到的那些 bug，而且将垃圾回收与手动管理内存混合使用是一种足够少见的需求，以至于没有任何语言真正为此设计。如果没有 Zig，我们不可能走到这一步，我将永远心存感激。**直到最近，对于像 Bun 这样的项目，编程语言的选择还是一条单行道。**

每个人都知道你不应该停下来从头重写一个大型软件。Joel Spolsky 早在 2000 年 4 月就在《你永远不该做的事，第一部分》中强调了这一点。

由当今前沿模型驱动的编码代理改变了这一等式。

为什么选择 Rust？全都归结于那些内存管理方面的挑战：

> 那个 bug 列表中的很大一部分是释放后使用、双重释放以及错误路径中的“忘记释放”。在安全的 Rust 中，这些是编译器错误，并且通过 `Drop` 实现类似 RAII 的自动清理。

重写的一个关键促成因素是 Bun 的测试套件是用 TypeScript 编写的，这意味着它可以作为一个一致性套件。这使得一个代理框架能够自动化从 Bun 到 Rust 的初始移植工作，最初只是作为一个实验，尝试我们现在称之为 Mythos/Fable 的模型的早期版本。

> 起初，我没指望它能成功。几天后，测试套件的高比例开始通过，我看到新的 Rust 代码与原始的 Zig 代码库非常匹配。我的看法从“这值得一试”变成了“我要合并这个”。……
>
> 在那些天的大部分时间里（以及之后），我监控工作流 —— 手动阅读输出以检查问题和错误，并提示 Claude 编辑循环以修复问题。
>
> 如何审查一个增加了超过 100 万行代码的 PR？如何开始建立必要的信心，以负责任地合并大量 LLM 编写的代码？
>
> 一个包含百万条断言的语言无关测试套件、对抗性代码审查，以及当出现问题时，修复生成代码的流程而不是手动修复代码。

Bun 的新实现已经在 Claude Code 中上线近一个月了：

> Claude Code v2.1.181（于 6 月 17 日发布）及后续版本使用了 Rust 移植版的 Bun。启动速度在 Linux 上快了 10%，但除此之外，几乎没人注意到。无聊是好事。

在 Anthropic 工作的一个好处是不需要为 token 付费 —— 当估算成本高达 165,000 美元时，这很方便。

> 合并前，这消耗了 59 亿未缓存输入 token、6.9 亿输出 token 以及 720 亿缓存输入 token 读取 —— 按 API 定价约为 165,000 美元。

整件事是一个引人入胜的案例研究，展示了如何借助协调的并行代理承担极其雄心勃勃的项目。
