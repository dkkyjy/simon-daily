# 智能体编码的未来：从指挥者到编排者

**日期：** 2026-01-02 00:00 UTC
**链接：** https://addyosmani.com/blog/future-agentic-coding/

---

**AI编码助手**已迅速从新奇事物转变为必需品，如今高达90%的软件工程师都在使用某种AI进行编码。但软件开发领域正在涌现一种新范式——工程师利用**自主编码智能体集群**。在这个智能体驱动的未来，软件工程师的角色正从**实施者**演变为**管理者**，换言之，从*编码者*转变为**指挥者**，并最终成为[**编排者**](https://www.youtube.com/watch?v=sQFIiB6xtIs)。

随着时间的推移，开发者将越来越多地**引导AI智能体构建正确的代码**，并协调多个智能体协同工作。本文探讨了AI辅助编码中**指挥者**与**编排者**之间的区别，定义了这些角色，并审视了当今前沿工具如何体现每种方法。资深工程师可能已开始看到端倪：我们的工作正从*“我该如何编码这个？”*转变为*“我该如何让正确的代码被构建出来？”*——这是一个微妙但深刻的转变。

编排工具的核心要点是什么？它支持多智能体工作流，你可以并行运行多个智能体而不会相互干扰。但让我们先谈谈术语。

## **指挥者：引导单个AI智能体**

在AI编码的背景下，扮演**指挥者**意味着在特定任务上与单个AI智能体密切合作，就像指挥家引导独奏者完成一场表演。

工程师在每个步骤中都保持参与，动态引导智能体的行为，调整提示，在需要时进行干预，并实时迭代。这是许多开发者已经熟悉的“AI结对编程”模型的逻辑延伸。通过指挥式工作流，**编码发生在人类与AI之间的同步、交互式会话中**，通常在你的IDE或命令行界面中进行。

**关键特征：** 指挥者与一个智能体保持紧密的反馈循环，验证或修改每个建议，就像驾驶员使用GPS导航一样。AI帮助编写代码，但开发者仍执行许多手动步骤——创建分支、运行测试、编写提交信息等，并最终决定接受哪些建议。

至关重要的是，**这种交互大多是短暂的**：一旦代码编写完成且会话结束，AI的角色就结束了，任何未在代码中捕获的上下文或决策可能会丢失。这种模式对于聚焦任务非常有效，允许精细控制，但并未充分利用多个AI并行工作的潜力。

**作为指挥者的现代工具：** 当前几种AI编码工具体现了指挥者模式：

* **Claude Code (Anthropic)：** Anthropic的Claude模型提供了一种编码助手模式（可通过CLI工具或编辑器集成访问），开发者与Claude对话以生成或修改代码。例如，使用**Claude Code CLI**，你在shell中导航项目，要求Claude实现一个函数或重构代码，它会打印差异或文件更新供你批准。你仍然是指挥者：你触发每个操作并立即审查输出。虽然Claude Code具有处理长时间运行任务和工具的功能，但在基本使用中，它本质上是一个在人类指导下逐步工作的智能协作者。
* **Gemini CLI (Google)：** 一个由Google的Gemini模型驱动的命令行助手，用于规划和编码，具有非常大的上下文窗口。工程师可以提示Gemini CLI分析代码库或起草解决方案计划，然后交互式地迭代结果。人类指导每一步，Gemini在CLI会话中响应。它是一个一次一个的协作者，不会自行进行代码更改（至少在这种指挥者模式下）。
* **Cursor (编辑器AI助手)：** Cursor编辑器（一个专门的AI增强型IDE）可以以内联或聊天模式运行，你可以向它提问或要求编写代码片段，它会立即在你的编码会话中执行这些编辑或给出答案。同样，你一次一个请求地引导它。Cursor作为指挥者的优势在于其深度上下文集成——它会索引你的整个代码库，以便AI可以回答关于任何部分的问题。但其标志是**你，开发者，实时发起并监督每个更改**。
* **VSCode, Cline, Roo Code (IDE内聊天)：** 类似于上述工具，其他编码智能体也属于这一类别。它们建议代码甚至多步修复，但始终在持续的人类指导下进行。

这种指挥式AI辅助已经显著提高了生产力。感觉就像身边始终有一个初级工程师或结对程序员。然而，它本质上是**一次一个智能体且同步的**。要真正大规模利用AI，我们需要超越单一智能体指挥者的角色。这就是**编排者**角色登场的地方。

## **编排者：管理智能体集群**

如果说指挥者与一个AI“音乐家”合作，那么**编排者**则监督整个交响乐团——多个AI智能体并行工作于项目的不同部分。编排者设定高层目标，定义任务，并让一队自主编码智能体独立执行实现细节。

人类不是微观管理每个函数或错误修复，而是专注于**协调、质量控制和集成**智能体的输出。在实际操作中，这通常意味着工程师可以**将任务分配给AI智能体（例如通过问题或提示），并让这些智能体异步生成代码更改——通常以可直接审查的拉取请求形式**。工程师的工作变成了审查、提供反馈和合并结果，而不是亲自编写所有代码。

这种异步、并行的工作流是一个根本性的转变。它将AI辅助从前景移到了背景。**当你专注于更高层次的设计或其他工作时，你的“AI团队”正在后台编码。** 当他们完成后，他们会将完成的工作（包括测试、文档等）交给你审查。这类似于作为项目技术负责人将任务委派给多个开发者，然后审查他们的拉取请求，只不过这里的“开发者”是AI智能体。

**关键特征：** 编排者处理的是**自主智能体**，它们可以规划和执行多步编码任务，只需最少的干预。这些智能体拥有更多的自主权：它们可以克隆你的仓库，创建新的git分支，编辑多个文件，编译/运行测试，并在提交解决方案前迭代优化。

编排者不会看到每个中间步骤（除非他们选择查看）；他们主要确保最终结果符合要求。重要的是，这一切都发生在**可追踪、持久的工作流**中（通常利用版本控制和CI管道），而不是短暂的建议。例如，GitHub的编码智能体完全通过GitHub上的拉取请求运作，因此每个更改都被记录并可审查。另一个标志是并发性：编排者可以启动多个智能体同时处理不同的任务，极大地并行化开发过程。

**作为编排者的现代工具：** 仅在过去一年中，就出现了几种体现编排者范式的工具：

* **GitHub Copilot *编码智能体*** (Microsoft)：Copilot的这次升级将其从编辑器内助手转变为**自主的后台开发者**（我在[这个视频](https://www.youtube.com/watch?v=sQFIiB6xtIs)中介绍了它）。你可以将GitHub问题分配给Copilot的智能体，或通过VS Code智能体面板调用它，告诉它（例如）“实现功能X”或“修复错误Y”。Copilot然后**通过GitHub Actions启动一个临时开发环境，检出你的仓库，创建一个新分支，并开始编码**。它可以运行测试、linter，甚至在需要时启动应用，无需人工看管。完成后，它会打开一个包含更改的拉取请求，附带描述和有意义的提交信息。然后它请求你的审查。你，人类编排者，审查PR（也许使用Copilot的AI辅助**代码审查**获取初步分析）。如果需要更改，你可以留下评论，如@copilot请为边缘情况Z更新单元测试，智能体将迭代PR。**这就是异步、自主的代码生成的实际应用。** 值得注意的是，Copilot自动化了繁琐的簿记工作：创建分支、提交、打开PR等，这些过去会耗费开发者的时间。所有围绕编写代码的琐碎工作（除了设计本身）都被处理了，使开发者能够专注于高层级的审查和指导。GitHub的智能体有效地让一个工程师监督许多“AI初级开发者”并行处理不同的问题（你甚至可以创建多个专门针对不同任务类型的智能体）。

* **Jules, Google的编码智能体：** **Jules** 是一个自主编码智能体。Jules **“不是副驾驶，不是代码补全助手，而是一个自主智能体，它读取你的代码，理解你的意图，然后开始工作。”** 与Google Cloud和GitHub集成，Jules让你连接一个仓库，然后要求它执行任务，就像对待你团队中的开发者一样。在幕后，Jules **将你的整个代码库克隆到一个安全的云虚拟机中**，并用强大的模型进行分析。你可以告诉Jules：“为我们的应用添加用户认证”或“将此项目升级到最新的Node.js并修复任何兼容性问题”。它会制定一个计划，提交给你批准，一旦你批准，就异步执行更改。它在新分支上提交，甚至可以打开一个拉取请求供你合并。Jules处理编写新代码、更新测试、更新依赖等，而你可以做其他事情。至关重要的是，Jules提供了**透明度和控制**：它在进行更改前向你展示其提议的计划和推理，并允许你在任何时候干预或修改指令（Google称之为“用户可操控性”）。这类似于给AI实习生一个规范，并较少频繁地监督他们——你相信他们能基本做对，但你仍然验证最终的差异。Jules还拥有独特的功能，如**音频变更日志**（它生成代码更改的口头摘要）以及在云中并发运行多个任务的能力。简而言之，Google的Jules展示了编排者模型：你定义任务，Jules异步完成繁重的工作，你监督结果。

* **OpenAI Codex (云智能体)：** OpenAI推出了一种新的基于云的**Codex智能体**，以补充ChatGPT。这个演进的Codex（不同于2021年的Codex模型）被描述为**“一个基于云的软件工程智能体，可以并行处理许多任务”**。它作为ChatGPT Plus/Pro的一部分提供，名称为*OpenAI Codex*，并通过npm CLI（npm i -g @openai/codex）提供。使用Codex CLI或其VS Code/Cursor扩展，你可以将任务委派给OpenAI的智能体，类似于Copilot或Jules。例如，从终端你可以说：*“嘿Codex，为设置页面实现暗黑模式”*。然后Codex启动进入你的仓库，编辑必要的文件，可能运行你的测试套件，完成后呈现差异供你合并。它在隔离的沙箱中运行以确保安全，在容器中运行每个任务，包含你的仓库和环境。与其他工具一样，OpenAI的Codex智能体与开发者工作流集成：你甚至可以从手机上的**ChatGPT移动应用**启动任务，并在智能体完成时收到通知。OpenAI强调Codex可以无缝切换**“在实时协作和异步委派之间”**。在实践中，这意味着你可以灵活地以指挥者模式（在IDE中结对编程）或编排者模式（将后台任务交给云智能体）使用它。Codex还可以被邀请到你的Slack频道中——团队成员可以在Slack中向@Codex分配任务，它将从对话和你的仓库中提取上下文来执行它们。这是一个无处不在的AI辅助愿景，编码任务可以从任何地方委派。早期用户报告说，Codex可以自主识别和修复错误，或在给定良好范围提示的情况下生成重要功能。所有这些再次与编排者工作流一致：人类定义目标，AI智能体自主交付解决方案。

* **Anthropic Claude Code (用于Web)：** Anthropic已经提供Claude作为AI聊天机器人一段时间了，他们的Claude Code CLI一直是交互式编码的最爱。Anthropic迈出了下一步，推出了**Claude Code for Web**，实际上是其编码智能体的托管版本。使用Claude Code for Web，你将其指向你的GitHub仓库（具有可配置的沙箱权限）并给它一个任务。然后智能体在Anthropic管理的容器中运行，就像CLI版本一样，但现在你可以从Web界面甚至移动应用触发它。它排队多个提示和步骤，执行它们，完成后，将分支推送到你的仓库（并可以打开PR）。本质上，Anthropic将其单一智能体Claude Code变成了云中可编排的服务。他们甚至提供了一个“传送”功能，如果你想手动接管，可以将会话传输到你的本地环境。这个Web版本的理由与编排者的好处一致：便利性和规模。你不需要在机器上运行长时间的任务；Anthropic的云处理繁重的工作，具有**文件系统和网络隔离**以确保安全。Claude Code for Web承认*自主性与安全性*是关键——通过沙箱化智能体，他们减少了对持续权限提示的需求，让智能体更自由地运作（减少用户的看管）。实际上，Anthropic使Claude更容易作为按需启动的自主编码工作者使用。

* **Cursor后台智能体：** 简而言之——Cursor 2.0有一个更聚焦的[多智能体界面](https://cursor.com/blog/2-0#the-multi-agent-interface)，更侧重于智能体而非文件。Cursor 2将其[后台智能体](https://cursor.com/docs/cloud-agent)功能扩展为开发者的完整编排层。除了作为交互式助手，Cursor 2让你生成自主后台智能体，它们在托管的云工作区中异步运行。当你委派任务时，Cursor 2的智能体现在克隆你的GitHub仓库，启动一个临时环境，并检出一个隔离的分支，在那里端到端执行工作。这些智能体可以处理整个开发循环——从编辑和运行代码，到安装依赖、执行测试、运行构建，甚至搜索网络或参考文档来解决问题。完成后，它们推送提交并打开一个详细的拉取请求，总结它们的工作。Cursor 2引入了多智能体编排，允许多个后台智能体在不同任务上并发运行——例如，一个优化UI组件，另一个优化后端性能或修复测试。每个智能体的活动通过一个实时仪表板可见，可以从桌面或移动设备访问，使你能够监控进度、发出后续指令或在需要时手动干预。这个新系统有效地将每个智能体视为按需AI劳动力的一部分，通过开发者的高层意图进行协调。Cursor 2对并行、异步执行的关注极大地放大了单个工程师的吞吐量——完全实现了编排者模型，即人类监督一队协作的AI开发者，而不是一个单一的助手。

* **智能体编排平台：** 除了单个产品，还出现了旨在编排多个智能体的**平台和开源项目**。例如，Melty Labs的[**Conductor**](https://conductor.build/)（尽管名字如此！）实际上是一个编排工具，让你在自己的机器上并行部署和管理多个Claude Code智能体。使用Conductor，每个智能体获得自己隔离的Git工作树以避免冲突，你可以看到所有智能体的仪表板（“谁在做什么”），并在它们进行时审查它们的代码。其理念是让运行一小群编码智能体变得像运行一个一样容易。类似地，[**Claude Squad**](https://smtg-ai.github.io/claude-squad/)是一个流行的开源终端应用，它基本上多路复用Anthropic的Claude——它可以生成几个Claude Code实例，在单独的tmux窗格中并发工作，允许你给每个实例不同的任务，从而通过并行化实现“10倍速”编码。这些编排工具强调了这一趋势：开发者希望协调*多个*AI编码智能体，并让它们协作或分工。甚至Microsoft的Azure AI服务也在实现这一点——在Build 2025上，他们宣布了工具，让开发者**“编排多个专门智能体来处理复杂任务”**，支持智能体间通信的SDK，以便你的智能体集群可以相互交谈和共享上下文。所有这些基础设施都在构建中，以支持**编排者工程师**，他们可能最终监督数十个AI进程处理软件开发生命周期的不同部分。

## **指挥者与编排者——差异**

**许多工程师将继续参与指挥式工作流（单一智能体、交互式），即使编排者模式日趋成熟。这两种模式将共存。**

很明显，“指挥者”和“编排者”不仅仅是花哨的术语，它们描述了我们在与AI合作方式上的真正转变：

* **控制范围：** 指挥者在微观层面运作，引导一个智能体完成单个任务或狭窄问题。编排者在宏观层面运作，为多个智能体或一个能够处理多步骤项目的强大单一智能体定义更广泛的任务和目标。指挥者问：“我如何借助AI解决这个函数或错误？”编排者问：“我今天可以委派哪些任务给AI智能体来推动这个项目前进？”
* **自主程度：** 在指挥者模式下，AI的自主性很低——它在每一步都等待用户提示。在编排者模式下，我们给予AI高自主性——它可能内部规划和执行数十个步骤（编写代码、运行测试、调整方法），然后才需要人类反馈。GitHub Copilot智能体或Jules一旦被分配，会尝试从头到尾完成一个功能，而Copilot的IDE建议仅在你输入时逐行提供。
* **同步与异步：** 指挥者交互通常是同步的——你提示，AI在几秒内响应，你立即集成或迭代。这是一个实时循环。编排者交互是异步的——你可能派遣一个智能体，然后在几分钟或几小时后回来检查它是否完成（有点像启动一个长时间的CI任务）。这意味着编排者必须处理等待、上下文切换，并可能同时管理多个事情，这对开发者来说是一种不同的工作流节奏。
* **产物和可追溯性：** 一个微妙但重要的区别：编排者工作流产生持久的产物，如分支、提交和拉取请求，这些保存在版本控制中。智能体的工作被完全记录（并且通常链接到问题/工单），这提高了可追溯性和协作性。对于指挥者风格（IDE聊天等），除非开发者手动提交中间更改，否则AI的许多参与没有被明确记录。本质上，编排者留下了纸质痕迹（或者更确切地说是git痕迹），团队中的其他人可以看到甚至自己触发。这有助于更自然地将AI带入团队流程。
* **人力投入模式：** 对于指挥者，人类在AI工作时几乎100%的时间都积极参与——审查每个输出，优化提示等。这是交互式工作。对于编排者，人类的投入是前置的（为智能体编写良好的任务描述或规范，设置正确的上下文）和后置的（审查最终代码并测试），但中间不需要太多。这意味着一个编排者可以并行管理比一次与一个AI合作时可能完成的更多总工作量。本质上，编排者利用**大规模自动化**，以牺牲精细控制为代价换取吞吐量的广度。

为了说明，考虑一个常见场景：添加一个涉及前端、后端并需要新测试的新功能。作为指挥者，你可能会打开AI聊天，在AI的帮助下实现后端逻辑，然后分别实现前端，然后要求它生成一些测试——每一步都顺序进行，你全程参与。作为编排者，你可以将后端实现分配给一个智能体（智能体A），前端UI更改分配给另一个（智能体B），测试创建分配给第三个（智能体C）。你给每个智能体一个提示或问题描述，然后退后一步，让它们并发工作。

短暂时间后，你可能会得到三个PR：一个用于后端，一个用于前端，一个用于测试。你的工作就是审查和集成它们（如果智能体A/B的代码在集成过程中发生变化，也许让智能体C调整测试）。实际上，你管理了一个迷你“AI团队”来交付这个功能。这个例子突出了编排者如何思考**任务分配和集成**，而指挥者则专注于**逐步实施**。

值得注意的是，**这些角色是流动的，而不是僵化的类别**。一个开发者可能在一个时刻扮演指挥者，在下一个时刻扮演编排者。例如，你可能启动一个异步智能体来处理一个任务（编排者模式），同时你亲自与另一个AI合作处理一个棘手的算法（指挥者模式）。工具也在模糊界限：正如OpenAI的Codex营销所暗示的，你可以在实时协作和异步委派任务之间无缝切换。所以，将“指挥者”与“编排者”视为AI辅助开发光谱的两端，中间有许多混合工作流。

## **为什么编排者很重要**

专家们认为，向编排的转变可能是我们见过的编程生产力最大的飞跃之一。考虑历史趋势：我们从编写汇编语言到使用高级语言，然后到使用框架和库，最近到利用AI进行自动补全。每一步都抽象掉了更多低层工作。**自主编码智能体是下一个抽象层**——你不是手动编写每一段代码，而是在更高层次描述你需要什么，然后让多个智能体构建它。

随着编排者风格智能体的发展，我们可以想象更大比例的代码由AI起草。当AI智能体生成，比如说，80%或90%的代码，而人类提供10%的关键指导和监督时，软件团队会是什么样子？许多人认为这并不意味着取代开发者——而是意味着**增强开发者以构建更好的软件**。我们可能会见证生产力的爆炸式增长，一个小型工程师团队，有效管理数十个智能体进程，可以完成曾经需要一队程序员数月才能完成的工作。（注意：我仍然相信，如果所有这些代码不变成垃圾，我们将继续专注于人类技能的代码审查循环需要改进。）

一个有趣的可能性是，**每个工程师在某种程度上都成为AI开发者的*管理者***。这有点像每个人都拥有一个由实习生或初级工程师组成的个人团队。你的效率将取决于你如何很好地分解任务、向AI传达需求以及验证结果。人类的判断力仍然至关重要：决定构建什么、确保正确性、处理歧义以及在AI可能不足的地方注入创造力或领域知识。换句话说，编排者的技能——良好的规划、[提示工程](/agentic-engineering/prompt-engineering/)、验证和监督——将会非常抢手。这些智能体远非使工程师过时，而是可以将**工程师提升到更具战略性、监督性的角色**。

## **走向专业的“AI团队”**

今天的编码智能体主要处理实现：编写代码、修复代码、编写测试等。但愿景不止于此。想象一个完整的软件开发管道，其中**多个专门的AI智能体处理生命周期的不同阶段，由人类编排者协调**。这已经在望。研究人员和公司已经提出了架构，例如，你可以拥有：

* **规划智能体**，分析功能请求或错误报告，并将其分解为具体任务
* **编码智能体**（或多个）实现代码中的任务
* **测试智能体**生成并运行测试以验证更改
* **代码审查智能体**检查拉取请求的质量和标准合规性
* **文档智能体**更新README或文档以反映更改
* 可能还有**部署/监控智能体**，可以推出更改并监控生产中的问题。

在这种情况下，人类工程师的角色变成了**对整个流程的监督和编排**：你可以通过一个高层目标启动流程（例如，“在我们的应用中添加通过加密货币支付的支持”），规划智能体将其转化为子任务，编码智能体异步实现每个子任务，测试智能体和审查智能体捕捉问题或打磨代码，最后一切在监控智能体的监督下合并和部署。

人类将介入批准计划，解决智能体提出的任何冲突或问题，并给予最终部署批准。这本质上是一个**“AI蜂群”**端到端地处理软件开发，工程师作为乐队的指挥者。

虽然这听起来未来主义，但我们看到了早期迹象。Microsoft的Azure AI Foundry现在为多智能体工作流和企业环境中的智能体编排提供了构建块，隐含地支持了多个智能体将在复杂、多步骤任务上协作的想法。科技公司的内部实验让智能体创建拉取请求，其他智能体审查者自动批评这些请求，形成AI/AI交互，人类最终参与。在开源社区中，人们将Claude Squad（并行编码器）等工具与集成其输出的附加脚本链接起来。并且关于诸如**[模型上下文协议（MCP）](/agentic-engineering/mcp/)** 等标准的讨论已经开始，以便智能体共享状态并相互通信结果。

我之前指出过，“*专门用于设计、实现、测试和监控的智能体可以协同工作，在复杂环境中开发、启动和落地功能*”——开发者将这些AI智能体加入他们的团队，并指导/监督他们的执行。在这样的设置中，智能体将*“自主与其他智能体协调，在关键点请求人类反馈、审查和批准”*，并在彼此之间处理琐碎工作。目标是**一个中央平台，我们可以在工作流中部署专门的智能体，而无需人类微观管理每个单独步骤**——相反，人类在完全上下文中监督整个操作。

这可能会改变软件项目的管理方式：更像运行一个自动化装配线，工程师确保质量和方向，而不是在线上手工制作每个组件。

## **编排中的挑战和人类角色**

这是否意味着编程变成了一个按钮活动，你坐下来让AI工厂运行？不完全是——而且可能永远不会完全如此。编排者模式存在重大挑战和未解决的问题：

* **质量控制与信任：** 编排多个智能体意味着你无法亲眼看到每一个更改。错误或设计缺陷可能会在仅依赖AI的情况下漏过。[人类监督](/agentic-engineering/human-in-the-loop/)作为最终安全网仍然**至关重要**。实际上，当前工具明确要求人类在合并前审查AI的拉取请求。这种关系通常被比作管理一个初级开发者团队：他们可以完成很多工作，但你不能不审查就发布他们的代码。编排者工程师必须警惕检查AI的工作，编写良好的测试用例，并设置监控。AI智能体可能犯错或产生逻辑正确但不可取的解决方案（例如，以复杂的方式实现功能）。编排技能的一部分是知道**何时干预**与何时信任智能体的计划。正如Stack Overflow的CTO所写，*“开发者保持评估AI输出的专业知识”*，并且需要新的**“信任模型”**来进行这种协作。
* **协调与冲突：** 当多个智能体在共享代码库上工作时，会出现协调问题——就像多个开发者如果触及相同文件可能发生冲突一样。我们需要策略来防止合并冲突或重复工作。当前的解决方案使用*工作区隔离*（每个智能体在自己的git分支或独立环境中工作）和明确的任务分离。例如，每个任务一个智能体，任务设计为最小化重叠。一些编排工具甚至可以自动合并更改或变基智能体分支，但通常由人类来集成。确保智能体不互相干扰是一个活跃的开发领域。可以想象，在未来，智能体可能通过某种智能体间通信协议相互协商以避免冲突，但今天，编排者设定边界。
* **上下文、共享状态和交接：** 编码工作流状态丰富：仓库结构、依赖、构建系统、测试套件、风格指南、团队实践、遗留代码、分支策略等。多智能体编排需要共享上下文、记忆和顺畅的过渡。但在企业环境中：跨智能体的上下文共享并非易事。没有统一的“工作流编排层”，每个智能体可能成为孤岛，在其领域内工作良好但无法融合。在编码工程团队中，这可能转化为：一个智能体创建功能分支，另一个运行单元测试，另一个合并到主分支——如果第一个智能体没有标记第二个智能体期望的元数据，就会出现故障。
* **提示与规范：** 讽刺的是，随着AI处理更多编码，**人类的“编码”上升到编写规范和提示的层面**。智能体输出的质量高度依赖于你如何很好地指定任务。模糊的指令导致结果不佳或智能体走偏。已经出现的最佳实践包括为智能体编写迷你设计文档或验收标准——本质上像对待需要明确完成定义的承包商一样对待它们。这就是为什么我们看到像*规范驱动开发*这样的想法用于AI：你给智能体一个详细的构建规范，以便它可以可预测地执行。工程师需要磨练他们无歧义地描述问题和所需解决方案的能力。矛盾的是，这是一项非常古老的技能（编写良好的规范和测试），在AI时代重新变得重要。随着智能体的改进，提示可能会变得更简单（“为我编写一个具有X和Y功能的移动应用，具有这些功能”），但产生更复杂的结果，我们还没有达到AI能直觉理解所有未言明之事的程度。目前，编排者必须对其数字劳动力成为优秀的沟通者。
* **工具与调试：** 对于人类开发者，如果出现问题，他们可以实时调试。对于自主智能体，如果出现问题（例如智能体卡在问题上或产生失败的PR），编排者必须调试情况：是糟糕的提示吗？智能体误解了规范吗？我们回滚并重试，还是介入并手动修复？正在添加新工具来帮助解决这个问题：例如，**检查点和回滚**命令让你撤销智能体如果走错路的更改。监控仪表板可以显示智能体是否花费太长时间或有错误。但实际上，编排者有时可能不得不降级到指挥者模式来修复问题，然后回到编排。随着智能体变得更健壮，这种相互作用将得到改善，但它突出了编排不仅仅是“发射后不管”——它需要主动监控。AI可观测性工具（跟踪成本、性能、智能体准确性）可能成为开发者工具包的一部分。
* **伦理与责任：** 另一个角度——如果AI智能体编写了大部分代码，谁对许可证合规性、安全漏洞或该代码中的偏见负责？最终，人类编排者（或其组织）承担责任。这意味着编排者应该纳入实践，如对AI生成的代码进行安全扫描和验证依赖。有趣的是，像Copilot和Jules这样的智能体包括内置的安全保障（例如，它们不会引入已知易受攻击的库版本，并且可以被指示运行安全审计）。但归根结底，*“信任，但验证”*是座右铭。人类对发布的内容负责，因此编排者需要确保AI贡献符合团队的质量和伦理标准。

总之，编排者风格开发的兴起并没有将人类从循环中移除——它**改变了人类在循环中的位置**。我们从转动扳手的人转变为设计和监督转动扳手的机器的人。这是一个更高杠杆的位置，但也要求更广泛的意识。

适应成为有效的AI指挥者和编排者的开发者可能会在这个新格局中**更有价值**。

## **结论：每个工程师都是指挥大师？**

每个工程师都会成为多个编码智能体的编排者吗？这是一个挑衅性的问题，但趋势表明我们正朝着这个方向前进，对于一大类编程任务来说。2020年代末软件工程师的日常现实可能包括更少的埋头编码和更多对主要由AI编写的代码的高层监督。

今天我们已经看到早期采用者将AI智能体视为队友——例如，一些开发者报告每天向AI委派10多个拉取请求，有效地**将智能体视为独立的队友而不是智能自动补全**。这些开发者解放了自己，专注于系统设计、棘手的算法，或者只是协调更多的工作。

也就是说，对每个人来说，转变不会一夜之间发生。初级开发者可能从“AI指挥者”开始，熟悉与单个智能体合作，然后才承担编排多个智能体的任务。经验丰富的工程师更有可能早期采用编排者工作流，因为他们有经验来架构任务和评估结果。在许多方面，这反映了职业成长：初级工程师实现（现在有AI帮助），高级工程师设计和集成（很快有AI智能体团队）。

我们讨论的工具——从GitHub的编码智能体到Google的Jules到OpenAI的Codex——正在迅速降低尝试这种方法门槛，所以预计它会很快成为主流。抛开夸张不谈，这些能力可以极大地放大单个开发者所能做的事情，这是事实。

那么，我们都会成为编排者吗？可能在某种程度上——是的。我们仍然会编写代码，特别是对于新颖或复杂的、难以简单规范化的部分。但大部分样板代码、常规模式，甚至许多复杂的胶水代码都可以卸载给AI。“软件工程师”的角色可能会演变，强调产品思维、架构和验证，而实际的编码在很大程度上成为自动化行为。在这个设想的未来中，要求工程师手动编写数千行平凡代码会感觉像要求现代会计师用铅笔和纸计算账目一样低效。相反，工程师会将那部分委派给他们的AI智能体，并专注于围绕它的创造性和批判性思维方面。

顺便说一句，是的，有很多需要谨慎的地方。我们需要确保这些智能体不会引入比它们解决的更多的问题。编排多个智能体的开发者体验仍在成熟中——有时可能很笨拙。但轨迹是清晰的。就像持续集成和自动化测试成为标准实践一样，**持续向AI委派**可能成为开发过程的正常部分。掌握这两种模式的工程师——知道何时作为精确的指挥者，何时扩展为编排者——将处于最佳位置来利用这个“智能体驱动”的世界。

有一件事是确定的：我们在未来5-10年内构建软件的方式将与过去10年大不相同。**我想强调，并非所有或大多数代码会在未来一两年内由智能体驱动，但这是我们前进的方向。** 键盘不会消失，但伴随着我们的敲击，我们将向智能助手集群发出高层指令。最终，人类元素仍然不可替代：是我们的判断力、创造力以及对现实世界需求的理解，引导这些AI智能体朝着有意义的结果前进。

**编码的未来不是AI或人类，而是AI*和*人类——人类作为指挥者和编排者掌舵，指挥一个强大的合奏来实现我们的软件抱负。**
