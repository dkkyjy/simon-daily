# 循环工程

**日期：** 2026-06-07 00:00 UTC
**链接：** https://addyosmani.com/blog/loop-engineering/

**来源：** [Addy Osmani](https://addyosmani.com/blog/)

---

> *摘要：你不再需要擅长提示词了。真正需要擅长的是设计替你做提示的循环系统。它由五个构建块加上一个记笔记的地方组成，Codex 和 Claude Code 现在都具备这五个要素。*

**循环工程是用你自己设计系统来替代你亲自向智能体发提示的过程。** 这里的循环可以理解为一个递归目标：你定义一个目的，AI 不断迭代直到完成。我相信这可能是我们使用编码智能体的未来方式。不过，现在还为时过早，我持怀疑态度，并且你绝对要小心 token 成本（如果你 token 充裕或匮乏，使用模式会截然不同），所以我想详细解释一下它是什么以及意味着什么。

---

Peter Steinberger 最近说：“你不应该再亲自给编码智能体发提示了。你应该设计循环来替你做提示。” 同样，Anthropic 的 Claude Code 负责人 Boris Cherny 也说：“我不再亲自给 Claude 发提示了。我有运行的循环来替我做提示并决定下一步做什么。我的工作就是写循环。”

好吧，这到底是什么意思？

大约两年来，你从编码智能体那里得到结果的方式是写一个好的提示并分享足够的上下文。你输入内容，阅读返回结果，再输入下一个内容。智能体是一个工具，你全程握着它，一个回合接一个回合。这部分已经结束了，或者至少有人认为它即将结束。

现在，你构建一个小型系统，它负责发现任务、分配任务、检查结果、记录完成情况，然后决定下一步做什么。你让这个系统去驱动智能体，而不是你自己。我之前写过与此相关的概念：[智能体框架工程](https://addyosmani.com/blog/agent-harness-engineering/)，即构建单个智能体运行的环境；以及[工厂模型](https://addyosmani.com/blog/factory-model/)，即构建软件的系统。循环工程位于框架之上一个层级。框架加上定时器，它生成小助手，并自我驱动。

让我惊讶的是，这不再是一个工具问题了。一年前，如果你想要一个循环，你得写一大堆 bash 脚本，然后永远维护它，它只属于你一个人。现在，这些组件直接内置于产品中。Steinberger 列出的清单几乎完全对应 Codex 应用，也几乎同样对应 Claude Code。一旦你注意到它们的结构相同，你就不会再争论该用哪个工具，而是直接设计一个无论你使用哪个工具都能正常工作的循环。

## 五个要素，加上笔记

一个循环需要五样东西，外加一个记录状态的地方。我先列出它们，然后再进行映射。

1.  **自动化任务**：按计划自动运行，自行完成发现和分类。
2.  **工作树**：确保两个并行工作的智能体不会互相干扰。
3.  **技能**：记录项目知识，智能体原本只能靠猜测。
4.  **插件和连接器**：将智能体与你已有的工具连接起来。
5.  **子智能体**：一个负责产生想法，另一个负责检查验证。

然后是第六样东西：**记忆**。一个 Markdown 文件，或者一个 Linear 看板，任何存在于单次对话之外、能记录已完成和下一步任务的东西。听起来简单得不值一提。但这是每个长期运行的智能体都依赖的相同技巧，我在[长期运行智能体](https://addyosmani.com/blog/long-running-agents/)中探讨过：模型在每次运行之间会遗忘，所以记忆必须存储在磁盘上，而不是上下文中。智能体会忘记，但仓库不会。

现在，这两个产品都具备了所有五个要素。

| 基本要素 | 在循环中的职责 | Codex 应用 | Claude Code |
| --- | --- | --- | --- |
| **自动化任务** | 按计划发现和分类 | [自动化标签页](https://developers.openai.com/codex/app/automations)：选择项目、提示、频率、环境；结果进入分类收件箱；`/goal` 用于运行直到完成 | 定时任务和 cron，`/loop`，`/goal`，钩子，GitHub Actions |
| **工作树** | 隔离并行功能 | 每个线程内置工作树 | `git worktree`，`--worktree`，子智能体的 `isolation: worktree` |
| **技能** | 将项目知识代码化 | [Agent Skills](https://developers.openai.com/codex/skills) (`SKILL.md`)，通过 `$name` 或隐式调用 | [Agent Skills](https://addyosmani.com/blog/agent-skills/) (`SKILL.md`) |
| **插件 / 连接器** | 连接你的工具 | 连接器 (MCP) 加上用于分发的插件 | MCP 服务器加上插件 |
| **子智能体** | 构思和验证 | [子智能体](https://developers.openai.com/codex/subagents) 在 `.codex/agents/` 中定义为 TOML | 任务子智能体在 `.claude/agents/` 中，智能体团队 |
| **状态** | 追踪已完成事项 | 通过连接器的 Markdown 或 Linear | 通过 MCP 的 Markdown (`AGENTS.md`, 进度文件) 或 Linear |

名称上有些许差异，但功能是相同的。让我逐一解释，因为说实话，细节决定了循环是稳定运行还是悄然崩溃。

## 自动化任务，这是心跳

自动化任务是让循环成为真正循环的关键，而不仅仅是一次性的运行。在 Codex 应用中，你可以在自动化标签页中创建一个任务，选择项目、要运行的提示、运行频率，以及是在本地代码库运行还是在后台工作树中运行。发现问题的运行结果会进入分类收件箱，没发现问题的运行结果会自动归档，这很贴心。OpenAI 内部用它来做一些枯燥的事情，比如每日问题分类、总结 CI 失败、编写提交简报、追踪上周添加的 bug。自动化任务可以调用技能，这样你就可以保持重复性任务的可维护性，使用 `$skill-name` 而不是粘贴一大段没人会更新的指令到计划任务中。

Claude Code 通过调度和钩子达到同样的效果。你可以使用 `/loop` 按间隔运行提示或命令，可以调度 cron 任务，可以通过钩子在智能体生命周期的特定点触发 shell 命令，或者将整个流程推到 GitHub Actions 上，这样即使你合上笔记本电脑，它也能继续运行。想法完全一样：你定义一个自主任务，给它一个节奏，结果会呈现给你，这样你就不需要亲自去检查了。

还有一个会话内的基本要素值得一提，它更接近本文的核心。`/loop` 按节奏重复运行。`/goal` 持续运行，直到你编写的条件真正成立，并且每次迭代后，会有一个独立的小模型检查你是否完成，这样编写代码的智能体就不会给自己打分。你给它类似“test/auth 中的所有测试通过且 lint 干净”的指令，然后就可以离开了。Codex 也有同样的功能，也叫 `/goal`，它会跨回合持续工作，直到一个可验证的停止条件成立，并支持暂停、恢复和清除。相同的功能，两个工具都有，这基本上是本文的模式。

所以，这部分是发现任务的环节。循环的其余部分则是对任务采取行动。

## 工作树，让并行不会变成混乱

一旦你运行多个智能体，文件就会开始冲突，这将成为失败点。两个智能体写入同一个文件，就像两个工程师在没有事先沟通的情况下提交到同一行代码一样令人头疼。Git 工作树解决了这个问题：它是一个独立的、共享相同仓库历史的工作目录，位于自己的分支上，这样智能体 A 的编辑根本不会影响到智能体 B 的代码库。

Codex 内置了工作树支持，因此多个线程可以同时处理同一个仓库而不会互相干扰。Claude Code 通过 `git worktree`、`--worktree` 标志（用于在独立代码库中打开会话）以及子智能体上的 `isolation: worktree` 设置（让每个助手获得一个自动清理的独立代码库）提供了相同的隔离能力。我在[编排税](https://addyosmani.com/blog/orchestration-tax/)中写过这方面的人为因素：工作树消除了机械冲突，但你自己仍然是瓶颈，你的审查带宽决定了你能实际运行多少个，而不是工具本身。

## 技能，让你不必每次都解释你的项目

技能让你不必像金鱼一样每次会话都重新解释相同的项目上下文。两个工具使用相同的格式：一个包含 `SKILL.md` 的文件夹，里面存放指令和元数据，以及可选的脚本、参考资料、资产。当你用 `$` 或 `/skills` 调用技能时，或者当你的任务与技能描述匹配时，Codex 就会运行该技能——这就是为什么一个紧凑、无聊的描述胜过聪明描述的原因。Claude Code 以相同的方式运作，我在[智能体技能](https://addyosmani.com/blog/agent-skills/)中写过这个模式。

技能也是意图不再需要你反复付费的地方。我在[意图债务](https://addyosmani.com/blog/intent-debt/)中论证过，智能体每次会话开始时都是“冷启动”的，它会用自信的猜测来填补你意图中的任何漏洞。技能就是写在外部的意图：约定、构建步骤、“我们因为那次事故不这样做”——只写一次，智能体每次运行都会读取。没有技能，循环每次都会从零开始重新推导你的整个项目；有了技能，它就能产生复利效应。

有一点要弄清楚：技能是创作格式，插件是你分发它的方式。当你想要在仓库之间共享技能或打包几个技能时，你可以将它们打包成插件。这在 Codex 和 Claude Code 中都是如此。

## 插件和连接器，循环触及你的真实工具

一个只能看到文件系统的循环是一个微小的循环。连接器，基于 MCP 构建，让智能体读取你的问题追踪器、查询数据库、访问测试 API、在 Slack 中发送消息。Codex 和 Claude Code 都支持 MCP，所以你为一个工具编写的连接器通常也能在另一个工具中使用。插件将连接器和技能打包在一起，这样你的队友可以一次性安装你的设置，而不必从记忆中重建整个系统。

这就是一个说“这是修复方案”的智能体，与一个能自动打开 PR、关联 Linear 工单并在 CI 通过后自动通知频道的循环之间的区别。连接器是循环能够在你实际环境中行动的原因，而不是仅仅告诉你它能做什么。

## 子智能体，让创造者远离检查者

循环中最有用的结构性元素，毫无疑问，是将编写者与检查者分开。编写代码的模型在给自己的作业打分时太过宽容了。第二个具有不同指令（有时是不同模型）的智能体能够捕捉到第一个智能体自我说服时产生的错误。

Codex 只在你要求时生成子智能体，同时运行它们，然后将结果整合到一个答案中。你可以在 `.codex/agents/` 中将你自己的智能体定义为 TOML 文件，每个文件包含名称、描述、指令以及可选的模型和推理努力程度，这样你的安全审查员可以是一个高努力度的强模型，而你的探索者可以是一个快速只读的东西。Claude Code 通过 `.claude/agents/` 中的子智能体和在它们之间传递工作的智能体团队来实现同样的功能。两者中常见的分工是一个探索，一个实现，一个根据规范进行验证。

我之前两次提出过这个观点，一次是[代码智能体管弦乐队](https://addyosmani.com/blog/code-agent-orchestra/)，一次是[对抗性代码审查](https://addyosmani.com/blog/adversarial-code-review/)。它在循环内部特别重要的原因是，循环在你没有监视的情况下运行，因此一个你真正信任的验证者是你能够放心离开的唯一理由。子智能体确实会消耗更多 token，因为每个子智能体都有自己的模型和工具工作，所以要把 token 花在那些值得获得第二意见的地方。这基本上也是 Claude Code 的 `/goal` 在底层做的事情：一个全新的模型决定循环是否完成，而不是执行工作的那个模型——将创造者与检查者的分离应用于停止条件本身。

## 一个循环的样子

将所有这些组合起来，一个单一的线程就变成了一个小控制面板。这是我经常使用的一个模式。

一个自动化任务每天早上在仓库上运行。它的提示调用一个分类技能，读取昨天的 CI 失败、未解决的问题、最近的提交，并将结果写入一个 Markdown 文件或 Linear 看板。对于每个值得做的发现，线程会打开一个隔离的工作树，并派一个子智能体去起草修复方案，然后第二个子智能体根据项目技能和现有测试审查该草案。

连接器让循环可以打开 PR 并更新工单。任何循环无法处理的事情都会进入我的分类收件箱。状态文件是整个循环的支柱，它记录了尝试过什么、通过了什么、还有什么未完成，这样第二天早上运行时就能从今天停止的地方继续。

看看你实际做了什么。你只设计了一次。你没有亲自提示任何一个步骤。这就是 Steinberger 观点的现实体现，而且在 Codex 或 Claude Code 中都是相同的循环，因为组件是相同的。

## 循环仍然不能为你做什么

循环改变了工作方式，但它并没有把你从工作中删除。而且，随着循环变得更好，三个问题实际上会变得更尖锐，而不是更容易。

**验证仍然在于你。** 一个无人值守运行的循环也是一个无人值守犯错的循环。你将验证子智能体与创造者分开的全部原因，就是为了让循环的“完成”声明有意义。即便如此，“完成”也只是一个声明，而不是一个证明。我一直在重复[AI 时代的代码审查](https://addyosmani.com/blog/code-review-ai/)中的同一句话：你的工作是交付你确认过的代码。

**如果你允许，你的理解仍然会退化。** 循环交付你没有编写的代码越快，现有代码与你实际理解之间的差距就越大。这就是[理解债务](https://addyosmani.com/blog/comprehension-debt/)，一个顺畅的循环只会让它增长得更快，除非你阅读循环产生的内容。

**最舒适的姿态是最危险的。** 当循环自我运行时，你很容易停止拥有自己的观点，只是接受它返回的任何东西。我称之为[认知投降](https://addyosmani.com/blog/cognitive-surrender/)。当你带着判断力去设计循环时，它是解药；当你用它来避免思考时，它是催化剂——相同的行动，相反的结果。

## 构建循环。保持工程师身份。

我认为这是我们工作方式演变的预览。话虽如此，如果我不亲自审查代码，或者如果我完全依赖自动化循环来修复问题，我的产品质量将会受到影响。我很可能最终陷入一个向下的螺旋，不断地把自己挖进更深的坑里。

也就是说，去设置你的循环吧，但不要忘记直接给智能体发提示也同样有效。关键在于找到正确的平衡。

循环也可能根据你的不同产生不同的结果。两个人可以构建完全相同的循环，却得到完全相反的结果。一个人用它来在自己深刻理解的工作上加速前进。另一个人用它来避免理解工作本身。循环不知道其中的区别。你知道。

这就是为什么循环设计比提示工程更难，而不是更容易。Cherny 的观点不是工作变得更容易了。而是杠杆点转移了。

构建循环。但要像打算保持工程师身份的人那样去构建它，而不仅仅是按下“开始”按钮的人。
