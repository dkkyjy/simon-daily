# 如何为AI智能体编写优秀的规范文档

**日期：** 2026-01-13 00:00 UTC  
**链接：** https://addyosmani.com/blog/good-spec/

---

**太长不看版：目标是用清晰的规范涵盖恰到好处的细节（可能包括结构、风格、测试、边界），既能引导AI又不至于让它不堪重负。将大型任务分解为多个小任务，而不是把所有内容塞进一个大型提示中。先以只读模式进行规划，然后执行并持续迭代。**

*“我听过很多关于为AI智能体编写优秀规范的说法，但一直没找到可靠的框架。我能写出堪比RFC的规范，但到了某个点，上下文太大，模型就崩溃了。”*

许多开发者都有这种挫败感。简单地把一份庞大的规范扔给AI智能体是行不通的——[上下文窗口](/agentic-engineering/context-window/)限制和模型的“注意力预算”会成为障碍。关键在于编写智能规范：能够清晰引导智能体、保持在实用的上下文大小范围内、并随项目演进的文档。本指南将我从使用Claude Code和Gemini CLI等编码智能体的实践中提炼出的最佳实践，整合成一个能让AI智能体保持专注且高效的规范编写框架。

我们将涵盖优秀AI智能体规范的五个原则，每个原则都以加粗的要点开头。

## **1. 从高层愿景开始，让AI起草细节**

**以简洁的高层规范启动项目，然后让AI将其扩展为详细的计划。**

与其前期过度设计，不如从清晰的目标陈述和几个核心需求开始。将其视为“产品简报”，让智能体据此生成更详尽的规范。这利用了AI在细节展开方面的优势，同时你保持对方向的掌控。除非你从一开始就有非常具体的技术要求必须满足，否则这种方法效果很好。

**为什么有效：** 基于LLM的智能体在获得扎实的高层指令时，非常擅长充实细节，但它们需要清晰的任务方向以避免偏离轨道。通过提供简短的提纲或目标描述，并要求AI生成完整的规范（例如spec.md），你为智能体创建了一个持久的参考。提前规划在使用智能体时更为重要——你可以先迭代计划，然后将其交给智能体来编写代码。规范成为你和AI共同构建的第一个产物。

**实用方法：** 开始新的编码会话时，提示：“你是一名AI软件工程师。为[项目X]起草一份详细规范，涵盖目标、功能、约束条件和分步计划。”保持初始提示的高层性——例如“构建一个用户可以跟踪任务的Web应用（待办事项列表），包含用户账户、数据库和简单UI”。智能体可能会回应一份结构化的规范草案：概述、功能列表、技术栈建议、数据模型等。这份规范随后成为你和智能体都可以参考的“真相来源”。GitHub的AI团队推广[规范驱动开发](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)，其中“规范成为共享的真相来源……是随项目演进的活的可执行产物”。在编写任何代码之前，审查并完善AI的规范。确保它与你的愿景一致，并纠正任何幻觉或偏离目标的细节。

**使用规划模式强制执行规划优先：** 像Claude Code这样的工具提供[规划模式](https://code.claude.com/docs/en/common-workflows)，将智能体限制为只读操作——它可以分析你的代码库并创建详细计划，但在你准备好之前不会编写任何代码。这非常适合规划阶段：以规划模式启动（在Claude Code中按Shift+Tab），描述你想要构建的内容，让智能体在探索你现有代码的同时起草规范。让它通过向你提问关于计划的问题来澄清模糊之处。让它审查计划的架构、最佳实践、安全风险和测试策略。目标是完善计划，直到没有误解的余地。只有那时你才退出规划模式，让智能体执行。这种工作流防止了常见的陷阱：在规范尚未稳固之前就跳入代码生成。

**将规范用作上下文：** 一旦批准，保存此规范（例如作为SPEC.md），并根据需要将相关部分提供给智能体。许多使用强大模型的开发者正是这样做的——规范文件在会话之间持续存在，每当项目恢复工作时为AI提供锚点。这减轻了当对话历史过长或需要重启智能体时可能发生的遗忘问题。这类似于团队中使用产品需求文档（PRD）的方式：每个人（人类或AI）都可以参考的文档，以保持正轨。有经验的开发者经常“先编写好的文档，模型可能仅凭该输入就能构建匹配的实现”，正如一位工程师所观察到的。规范就是那份文档。

**保持目标导向：** 为AI智能体编写的高层规范应侧重于“什么”和“为什么”，而不是“如何做”的细枝末节（至少在初期如此）。把它想象成用户故事和验收标准：用户是谁？他们需要什么？成功是什么样的？（例如“用户可以添加、编辑、完成任务；数据持久保存；应用响应迅速且安全”）。这使AI的详细规范扎根于用户需求和成果，而不仅仅是技术待办事项。正如[GitHub Spec Kit文档](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)所述，提供你正在构建什么以及为什么的高层描述，让编码智能体生成侧重于用户体验和成功标准的详细规范。从这种大局观开始，可以防止智能体在后续进入编码阶段时只见树木不见森林。

## **2. 像专业的PRD（或SRS）一样结构化规范**

**将你的AI规范视为结构化文档（PRD），包含清晰的章节，而不是一堆松散的笔记。**

许多开发者对待智能体的规范就像传统的产品需求文档（PRD）或系统设计文档一样——全面、组织良好、易于“字面理解”的AI解析。这种正式的方法为智能体提供了可遵循的蓝图，并减少了歧义。

**六个核心领域：** GitHub对[超过2,500个智能体配置文件](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/)的分析揭示了一个清晰的模式：最有效的规范涵盖六个领域。将其用作完整性的检查清单：

**1. 命令：** 尽早放置可执行的命令——不仅是工具名称，而是完整的命令及其标志：`npm test`、`pytest -v`、`npm run build`。智能体会不断引用这些命令。

**2. 测试：** 如何运行测试、使用什么框架、测试文件存放在哪里、以及有什么覆盖率期望。

**3. 项目结构：** 源代码放在哪里、测试放在哪里、文档属于哪里。要明确：“`src/`用于应用代码，`tests/`用于单元测试，`docs/`用于文档。”

**4. 代码风格：** 一个展示你风格的真实代码片段胜过三段描述文字。包括命名约定、格式化规则以及良好输出的示例。

**5. Git工作流：** 分支命名、提交消息格式、PR要求。如果你明确说明，智能体可以遵循这些规则。

**6. 边界：** 智能体绝不应触碰的内容——密钥、供应商目录、生产配置、特定文件夹。“绝不提交密钥”是GitHub研究中最常见的有效约束。

**明确你的技术栈：** 说“React 18搭配TypeScript、Vite和Tailwind CSS”，而不是“React项目”。包括版本和关键依赖。模糊的规范产生模糊的代码。

**使用一致的格式：** 清晰为王。许多开发者使用Markdown标题甚至类似XML的标签来划分章节，因为AI模型处理结构良好的文本比处理自由形式的散文更好。例如，你可以将规范结构化为：

```
# 项目规范：我的团队任务应用

## 目标
- 为小团队构建一个管理任务的Web应用……

## 技术栈
- React 18+、TypeScript、Vite、Tailwind CSS
- Node.js/Express后端、PostgreSQL、Prisma ORM

## 命令
- 构建：`npm run build`（编译TypeScript，输出到dist/）
- 测试：`npm test`（运行Jest，提交前必须通过）
- 代码检查：`npm run lint --fix`（自动修复ESLint错误）

## 项目结构
- `src/` – 应用源代码
- `tests/` – 单元测试和集成测试
- `docs/` – 文档

## 边界
- ✅ 始终：提交前运行测试，遵循命名约定
- ⚠️ 先询问：数据库架构变更，添加依赖
- 🚫 绝不：提交密钥，编辑node_modules/，修改CI配置
```

这种组织层次不仅帮助你清晰思考，也帮助AI找到信息。Anthropic的工程师建议[将提示组织成不同的部分](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)（如<background>、<instructions>、<tools>、<output_format>等），正是出于这个原因——它给模型提供了关于哪些信息属于哪里的强烈信号。请记住，“简洁不一定意味着简短”——如果规范中的细节很重要，不要回避，但要保持重点突出。

**将规范集成到你的工具链中：** 将规范视为与版本控制和CI/CD绑定的“可执行产物”。[GitHub Spec Kit](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)使用一个四阶段、有门控的工作流，使你的规范成为工程过程的核心。不是编写规范然后放在一边，而是规范驱动实现、检查清单和任务分解。你的主要角色是引导；编码智能体完成大部分编写工作。每个阶段都有特定的工作，在当前任务完全验证之前，你不会进入下一个阶段：

**1. 规范：** 你提供你正在构建什么以及为什么的高层描述，编码智能体生成详细的规范。这不是关于技术栈或应用设计——而是关于用户旅程、体验以及成功是什么样的。谁将使用这个？它解决什么问题？他们将如何与之交互？把它想象成映射你想要创建的用户体验，让编码智能体充实细节。这成为一个活的产物，随着你了解更多而演进。

**2. 计划：** 现在你进入技术层面。你提供你期望的技术栈、架构和约束，编码智能体生成全面的技术计划。如果你的公司标准化了某些技术，这就是你说明的地方。如果你正在与遗留系统集成或有合规要求，所有这些都放在这里。你可以要求多个计划变体来比较方法。如果你提供内部文档，智能体可以直接将你的架构模式整合到计划中。

**3. 任务：** 编码智能体获取规范和计划，并将其分解为实际工作——小的、可审查的块，每个解决拼图的一个特定部分。每个任务应该是你可以独立实现和测试的东西，几乎就像为你的AI智能体进行测试驱动开发。不是“构建认证”，而是获得具体的任务，如“创建一个验证电子邮件格式的用户注册端点。”

**4. 实现：** 你的编码智能体逐个（或并行）处理任务。不是审查数千行的代码转储，而是审查解决特定问题的重点变更。智能体知道要构建什么（规范）、如何构建（计划）以及要处理什么（任务）。关键的是，你的角色是在每个阶段进行验证：规范是否捕捉到你想要的？计划是否考虑了约束？是否有AI遗漏的边缘情况？这个过程内置了检查点，供你在前进之前进行批评、发现差距和纠正方向。

这种有门控的工作流防止了Willison所说的“纸牌屋代码”——经不起推敲的脆弱AI输出。Anthropic的Skills系统提供了类似的模式，允许你定义可重用的基于Markdown的行为，智能体可以调用这些行为。通过将你的规范嵌入这些工作流，你确保智能体在规范得到验证之前无法继续，并且更改会自动传播到任务分解和测试中。

**考虑使用agents.md创建专业角色：** 对于像GitHub Copilot这样的工具，你可以创建[agents.md文件](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/)，定义专门的智能体角色——@docs-agent用于技术写作，@test-agent用于QA，@security-agent用于代码审查。每个文件作为该角色行为、命令和边界的重点规范。当你想为不同任务使用不同智能体而不是一个通用助手时，这特别有用。

**为智能体体验（AX）设计：** 正如我们为开发者体验（DX）设计API一样，考虑为“智能体体验”设计规范。这意味着干净、可解析的格式：智能体将使用的任何API的OpenAPI模式、总结文档供LLM消费的llms.txt文件，以及显式的类型定义。Agentic AI Foundation（AAIF）正在标准化像[MCP（模型上下文协议）](/agentic-engineering/mcp/)这样的协议用于工具集成——遵循这些模式的规范更容易被智能体消费并可靠地执行。

**PRD与SRS思维模式：** 借用既定的文档实践会有所帮助。对于AI智能体规范，你通常会将两者融合到一个文档中（如上所示），但涵盖两个角度对你有利。像PRD一样编写它，确保你包含以用户为中心的上下文（“每个功能背后的原因”），这样AI就不会为错误的事情进行优化。像SRS一样扩展它，确保你确定AI实际生成正确代码所需的具体细节（比如使用什么数据库或API）。开发者发现，这种额外的前期投入通过大幅减少后来与智能体的沟通失误而获得了回报。

**使规范成为“活文档”：** 不要写完就忘了。随着你和智能体做出决定或发现新信息，更新规范。如果AI不得不更改数据模型，或者你决定削减一个功能，在规范中反映出来，使其保持为事实依据。将其视为版本控制的文档。在[规范驱动的工作流](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)中，规范驱动实现、测试和任务分解，在规范得到验证之前你不会进入编码阶段。这个习惯使项目保持连贯，特别是如果你或智能体离开后稍后再回来。记住，规范不仅是为了AI——它帮助你作为开发者保持监督，并确保AI的工作满足实际需求。

## **3. 将任务分解为模块化提示和上下文，而不是一个大的提示**

**分而治之：一次给AI一个专注的任务，而不是一个包含所有内容的一体化提示。**

有经验的AI工程师已经学会，试图将整个项目（所有需求、所有代码、所有指令）塞进一个提示或智能体消息中是导致混乱的秘诀。你不仅可能触及令牌限制，还可能因为“[指令的诅咒](https://maxpool.dev/research-papers/curse_of_instructions_report.html)”而导致模型失去焦点——太多指令导致它无法很好地遵循任何一个。解决方案是以模块化的方式设计你的规范和工作流，一次处理一个部分，只拉取该部分所需的上下文。

**过多上下文/指令的诅咒：** 研究已经证实了许多开发者凭经验观察到的情况：当你向提示中堆积更多指令或数据时，模型遵循每一条指令的性能会[显著下降](https://openreview.net/pdf/848f1332e941771aa491f036f6350af2effe0513.pdf)。一项研究将此称为“指令的诅咒”，显示即使是GPT-4和Claude在被要求同时满足许多需求时也会挣扎。实际上，如果你提出10条详细规则的要点，AI可能遵循前几条并开始忽略其他规则。更好的策略是迭代式聚焦。[行业指南](https://maxpool.dev/research-papers/curse_of_instructions_report.html)建议将复杂需求分解为顺序的、简单的指令作为最佳实践。一次让AI专注于一个子问题，完成它，然后继续。这保持了高质量并控制了错误。

**将规范划分为阶段或组件：** 如果你的规范文档非常长或涵盖了很多内容，考虑将其分成部分（要么是物理上分离的文件，要么是清晰分离的章节）。例如，你可能有一个“后端API规范”部分和另一个“前端UI规范”部分。当AI在处理后端时，你不需要总是将前端规范喂给它，反之亦然。许多使用多智能体设置的开发者甚至为每个部分创建单独的智能体或子进程——例如，一个智能体处理数据库/模式，另一个处理API逻辑，另一个处理前端——每个都有规范的相关切片。即使你使用单个智能体，你也可以通过只将相关规范部分复制到该任务的提示中来模拟这一点。避免上下文过载：不要在一次操作中将认证任务与数据库架构变更混在一起，正如[DigitalOcean AI指南](https://docs.digitalocean.com/products/gradient-ai-platform/concepts/context-management/)所警告的那样。保持每个提示紧密围绕当前目标。

**大型规范的扩展目录/摘要：** 一个巧妙的技术是让智能体为规范构建一个带有摘要的扩展目录。这本质上是一个“规范摘要”，将每个部分浓缩为几个关键点或关键词，并引用可以找到细节的地方。例如，如果你的完整规范有一个“安全需求”部分，长达500字，你可以让智能体将其总结为：“安全：使用HTTPS，保护API密钥，实现输入验证（见完整规范§4.2）”。通过在规划阶段创建层次化摘要，你获得了一个可以留在提示中的鸟瞰视图，而精细细节则被卸载，除非需要。这个扩展目录充当索引：智能体可以查阅它并说“啊哈，有一个安全部分我应该看看”，然后你可以按需提供该部分。这类似于人类开发者浏览大纲，然后在处理特定部分时翻到规范文档的相关页面。

要实现这一点，你可以在编写规范后提示智能体：“将上述规范总结成一个非常简洁的大纲，包含每个部分的关键点和参考标签。”结果可能是一个包含每个部分一两句话摘要的列表。该摘要可以保留在系统或助手消息中，以引导智能体的焦点，而不会消耗太多令牌。这种[层次化摘要方法](https://addyo.substack.com/p/context-engineering-bringing-engineering)已知有助于LLM通过关注高层结构来维护长期上下文。智能体携带一个规范的“心理地图”。

**利用子智能体或“技能”处理不同规范部分：** 另一种高级方法是使用多个专门的智能体（Anthropic称之为子智能体，或者你可以称之为“技能”）。每个子智能体针对特定专业领域进行配置，并被给予与该领域相关的规范部分。例如，你可能有一个数据库设计子智能体，只知道规范的数据模型部分，以及一个API编码子智能体，知道API端点规范。主智能体（或编排器）可以自动将任务路由到适当的子智能体。好处是每个智能体处理更小的上下文窗口和更专注的角色，这可以[提高准确性并允许在独立任务上并行工作](https://10xdevelopers.dev/structured/claude-code-with-subagents/)。Anthropic的Claude Code通过允许你定义具有自己系统提示和工具的子智能体来支持这一点。“每个子智能体都有特定的目的和专业领域，使用自己与主对话分开的上下文窗口，并有一个自定义系统提示指导其行为，”正如他们的文档所述。当出现与子智能体领域匹配的任务时，Claude可以将该任务委托给它，子智能体独立返回结果。

**用于吞吐量的并行智能体：** 同时运行多个智能体正在成为开发者生产力的“下一个大事件”。不是等待一个智能体完成后再开始另一个任务，你可以为非重叠的工作启动并行智能体。Willison将此描述为“[拥抱并行编码智能体](https://simonwillison.net/2025/Oct/7/vibe-engineering/)”，并指出它“出奇地有效，尽管精神上令人疲惫”。关键在于划定任务范围，使智能体不会互相干扰——一个智能体编写功能代码，而另一个编写测试，或者同时构建独立的组件。像LangGraph或OpenAI Swarm这样的编排框架可以帮助协调这些智能体，通过向量数据库（如Chroma）的共享内存让它们访问公共上下文，而无需重复提示。

**单智能体与多智能体：何时使用每种**

| 方面 | 单智能体 | 并行/多智能体 |
| --- | --- | --- |
| **优势** | 设置更简单；开销更低；更容易调试和跟踪 | 更高的吞吐量；处理复杂的相互依赖关系；每个领域有专家 |
| **挑战** | 大型项目上下文过载；迭代较慢；单点故障 | 协调开销；潜在冲突；需要共享内存（如向量数据库） |
| **最佳适用** | 独立模块；中小型项目；早期原型开发 | 大型代码库；一个编码+一个测试+一个审查；独立功能 |
| **提示** | 使用规范摘要；每任务刷新上下文；经常开始新会话 | 初始限制在2-3个智能体；使用MCP共享工具；定义清晰边界 |

实际上，使用子智能体或技能特定提示可能看起来像：你维护多个规范文件（或提示模板）——例如SPEC_backend.md、SPEC_frontend.md——然后告诉AI，“对于后端任务，参考SPEC_backend；对于前端任务，参考SPEC_frontend。”或者在像Cursor/Claude这样的工具中，你实际上为每个启动一个子智能体。这当然比单智能体循环设置更复杂，但它模仿了人类开发者的做法——我们在心理上将大型规范划分为相关块（你不会同时记住整个50页的规范；你回忆当前任务所需的部分，并对整体架构有一个大致了解）。正如所指出的，挑战在于管理相互依赖关系：子智能体仍然需要协调（前端需要知道后端规范中的API契约等）。中央概述（或“架构师”智能体）可以通过引用子规范并确保一致性来提供帮助。

**将每个提示聚焦于一个任务/部分：** 即使没有花哨的多智能体设置，你也可以手动强制执行模块化。例如，在规范编写完成后，你的下一步可能是：“步骤1：实现数据库模式。”你只给智能体提供规范的数据库部分，加上规范中的任何全局约束（如技术栈）。智能体处理这个。然后对于步骤2，“现在实现认证功能”，你提供规范的认证部分，以及可能相关的模式部分。通过为每个主要任务刷新上下文，你确保模型没有携带大量可能分散注意力的过时或不相关信息。正如一个指南所建议的：“[开始新的会话](https://docs.digitalocean.com/products/gradient-ai-platform/concepts/context-management/)以在切换主要功能时清除上下文”。你可以每次提醒智能体关键的全局规则（来自规范的约束部分），但如果不需要，不要塞入整个规范。

**使用内联指令和代码TODO：** 另一个模块化技巧是使用你的代码或规范作为对话的活动部分。例如，用// TODO注释搭建你的代码，描述需要做什么，让智能体逐个填充它们。每个TODO本质上充当一个小任务的迷你规范。这使AI保持激光聚焦（“根据这个规范片段实现这个特定函数”），你可以紧密循环迭代。这类似于一次给AI一个检查清单项，而不是整个清单。

底线：小的、聚焦的上下文胜过一个大提示。这提高了质量，并防止AI因一次性处理太多而“不堪重负”。正如一套最佳实践所总结的，给模型提供“一个任务焦点”和“仅相关信息的”，避免到处倾倒所有内容。通过将工作结构化为模块——并使用规范摘要或子规范智能体等策略——你将绕过上下文大小限制和AI的短期记忆上限。记住，一个喂养良好的AI就像一个喂养良好的函数：只给它[当前工作所需的输入](https://addyo.substack.com/p/context-engineering-bringing-engineering)。

## **4. 内置自我检查、约束和人类专业知识**

**让你的规范不仅仅是智能体的待办事项清单，也是质量控制的指南——并且不要害怕注入你自己的专业知识。**

一个好的AI智能体规范会预见AI可能出错的地方，并设置[护栏](/agentic-engineering/guardrails/)。它还利用你所知道的（领域知识、边缘情况、“陷阱”），这样AI就不会在真空中运行。把规范想象成AI的教练和裁判：它应该鼓励正确的方法并指出犯规。

**使用三层边界：** [GitHub对2,500多个智能体文件的分析](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/)发现，最有效的规范使用三层边界系统，而不是简单的禁止列表。这给智能体提供了更清晰的指导，说明何时继续、何时暂停、何时停止：

**✅ 始终做：** 智能体无需询问即可采取的行动。“始终在提交前运行测试。”“始终遵循风格指南中的命名约定。”“始终将错误记录到监控服务。”

**⚠️ 先询问：** 需要人类批准的行动。“在修改数据库模式前询问。”“在添加新依赖前询问。”“在更改CI/CD配置前询问。”这一层捕获可能没问题但值得人工检查的高影响变更。

**🚫 绝不做：** 硬性停止。“绝不提交密钥或API密钥。”“绝不编辑node_modules/或vendor/。”“未经明确批准，绝不删除失败的测试。”“绝不提交密钥”是研究中单个最有用的约束。

这种三层方法比扁平的规则列表更细致。它承认某些行动总是安全的，某些需要监督，某些是绝对禁止的。智能体可以自信地执行“始终”项目，标记“先询问”项目供审查，并在“绝不做”项目上硬性停止。

**鼓励自我验证：** 一个强大的模式是让智能体自动对照规范验证其工作。如果你的工具允许，你可以集成诸如单元测试或代码检查之类的检查，AI可以在生成代码后运行这些检查。但即使在规范/提示级别，你也可以指示AI进行双重检查：例如，“实现后，将结果与规范进行比较，并确认所有需求都已满足。列出任何未解决的规范项目。”这促使LLM反思其输出与规范的关系，捕捉遗漏。这是一种内置到过程中的自我审计形式。

例如，你可以在提示后附加：“（在编写函数后，审查上述需求列表，确保每个都已满足，标记任何缺失的）。”然后模型将（理想情况下）输出代码，后跟一个简短的检查清单，指示它是否满足了每个需求。这在你甚至运行测试之前就减少了它忘记某些东西的机会。这不是万无一失的，但它有帮助。

**LLM作为裁判进行主观检查：** 对于难以自动测试的标准——代码风格、可读性、遵循架构模式——考虑使用“LLM作为裁判”。这意味着让第二个智能体（或单独的提示）根据你规范的质量指南审查第一个智能体的输出。Anthropic和其他公司发现这对主观评估很有效。你可以提示：“审查此代码是否遵循我们的风格指南。标记任何违规。”裁判智能体返回反馈，要么被采纳，要么触发修订。这在语法检查之外增加了一层语义评估。

**一致性测试：** Willison倡导构建一致性套件——语言无关的测试（通常是基于YAML的），任何实现都必须通过。这些充当契约：如果你正在构建一个API，一致性套件指定了预期的输入/输出，智能体的代码必须满足所有情况。这比临时单元测试更严格，因为它直接源自规范，并且可以在实现之间重用。在你的规范的成功部分中包含一致性标准（例如，“必须通过conformance/api-tests.yaml中的所有案例”）。

**在规范中利用测试：** 如果可能，将测试计划甚至实际测试纳入你的规范和提示流程。在传统开发中，我们使用TDD或编写测试用例来澄清需求——你可以对AI做同样的事情。例如，在规范的成功标准中，你可能会说“这些样本输入应产生这些输出……”或“以下单元测试应通过。”可以提示智能体在脑海中运行这些案例，或者如果它有这个能力，实际执行它们。Simon Willison指出，拥有[健壮的测试套件](https://simonwillison.net/2025/Oct/7/vibe-engineering/)就像给智能体超能力——当测试失败时，它们可以快速验证和迭代。在AI编码上下文中，在规范中编写一些测试的伪代码或预期结果可以指导智能体的实现。此外，你可以在子智能体设置中使用专门的“[测试智能体](https://10xdevelopers.dev/structured/claude-code-with-subagents/)”，它获取规范的标准并持续验证“代码智能体”的输出。

**带入你的领域知识：** 你的规范应反映只有经验丰富的开发者或了解上下文的人才知道的见解。例如，如果你正在构建一个电子商务智能体，并且你知道“产品”和“类别”具有多对多关系，请明确说明（不要假设AI会推断出来——它可能不会）。如果某个库出了名的棘手，提及要避免的陷阱。本质上，将你的指导注入规范。规范可以包含诸如“如果使用库X，注意Y版本中的内存泄漏问题（应用变通方案Z）”之类的建议。这种细节水平将平均水平的AI输出转变为真正健壮的解决方案，因为你已经引导AI远离了常见陷阱。

此外，如果你有偏好或风格指南（比如“在React中使用函数组件而不是类组件”），将其编码到规范中。AI将模仿你的风格。许多工程师甚至在规范中包含小例子，例如“所有API响应应为JSON。例如，错误时返回{“error”: “message”}。”通过给出一个快速示例，你将AI锚定到你想要的确切格式。

**简单任务的极简主义：** 虽然我们倡导详尽的规范，但专业知识的一部分是知道何时保持简单。对于相对简单、独立的任务，过于繁琐的规范实际上可能造成混乱而非帮助。如果你要求智能体做直接的事情（比如“在页面上居中一个div”），你可能只需要说，“确保保持解决方案简洁，不要添加多余的标记或样式。”那里不需要完整的PRD。相反，对于复杂任务（比如“实现带有令牌刷新和错误处理的OAuth流程”），那是你拿出详细规范的时候。一个好的经验法则：根据任务复杂性调整规范细节。不要对难题规范不足（智能体会挣扎或偏离轨道），但也不要对琐碎任务规范过度（智能体可能会被缠住或在不必要的指令上消耗上下文）。

**如果需要，维护AI的“角色”：** 有时，你的规范的一部分是定义智能体应如何表现或回应，特别是如果智能体与用户交互。例如，如果构建客户支持智能体，你的规范可能包括诸如“使用友好和专业的语气”、“如果你不知道答案，要求澄清或提供后续跟进，而不是猜测”之类的指南。这类规则（通常包含在系统提示中）有助于保持AI的输出与期望一致。它们本质上是AI行为的规范项目。保持它们一致，并在长时间会话中必要时提醒模型（LLM如果不加约束，可能会随着时间的推移在风格上“漂移”）。

**你仍然是执行循环中的主管：** 规范赋予智能体权力，但你仍然是最终的质量过滤器。如果智能体产生了技术上满足规范但感觉不对的东西，相信你的判断。要么完善规范，要么直接调整输出。AI智能体的伟大之处在于它们不会生气——如果它们交付了偏离的设计，你可以说，“实际上，那不是我的意图，让我们澄清规范并重做。”规范是与AI协作中的活产物，而不是你不能更改的一次性合同。

Simon Willison幽默地将与AI智能体合作比作“一种非常奇怪的管理形式”，甚至“从编码智能体获得良好结果感觉[不舒服地接近于管理人类实习生](https://simonwillison.net/2025/Oct/7/vibe-engineering/)”。你需要提供清晰的指令（规范），确保它们有必要的上下文（规范和相关的数据），并给出可操作的反馈。规范设定了舞台，但执行期间的监控和反馈是关键。如果AI是一个“奇怪的数字实习生，如果给他们机会绝对会作弊”，你编写的规范和约束就是防止作弊并让他们保持任务的方法。

这是回报：一个好的规范不仅告诉AI要构建什么，还帮助它自我纠正并保持在安全边界内。通过内置验证步骤、约束和你来之不易的知识，你大大增加了智能体的输出在第一次尝试时就正确的几率（或至少更接近正确）。这减少了迭代次数和那些“它到底为什么这样做？”的时刻。

## **5. 测试、迭代和演进规范（并使用正确的工具）**

**将规范编写和智能体构建视为一个迭代循环：尽早测试、收集反馈、完善规范，并利用工具自动化检查。**

初始规范不是终点——它是循环的开始。最好的结果来自于你持续验证智能体的工作与规范的一致性并相应调整。此外，现代AI开发者使用各种工具来支持这个过程（从CI管道到上下文管理工具）。

**持续测试：** 不要等到最后才看智能体是否满足规范。在每个主要里程碑之后，甚至每个函数之后，运行测试或至少进行快速手动检查。如果某些东西失败，在继续之前更新规范或提示。例如，如果规范说“密码必须用bcrypt哈希”，而你看到智能体的代码存储明文——停下来纠正它（并提醒规范或提示关于该规则）。自动化测试在这里大放异彩：如果你提供了测试（或者边进行边编写），让智能体运行它们。在许多编码智能体设置中，你可以在完成任务后让智能体运行npm test或类似命令。结果（失败）然后可以反馈到下一个提示，有效地告诉智能体“你的输出在X、Y、Z上不符合规范——修复它。”这种智能体循环（编码 -> 测试 -> 修复 -> 重复）非常强大，是像Claude Code或Copilot Labs这样的工具处理更大任务的发展方向。始终定义“完成”意味着什么（通过测试或标准）并检查它。

**迭代规范本身：** 如果你发现规范不完整或不清晰（也许智能体误解了某些东西，或者你意识到你错过了一个需求），更新规范文档。然后明确地将智能体与新规范重新同步：“我已按如下方式更新了规范……根据更新的规范，相应调整计划或重构代码。”这样规范保持为单一事实来源。这类似于我们在正常开发中处理需求变更的方式——但在这里，你也是AI智能体的产品经理。如果可能，保持版本历史（即使只是通过提交消息或笔记），这样你知道什么变了以及为什么。

**利用上下文管理和记忆工具：** 有一个不断增长的工具生态系统来帮助管理AI智能体上下文和知识。例如，[检索增强生成（RAG）](/agentic-engineering/rag/)是一种模式，智能体可以从知识库（如向量数据库）中即时拉取相关数据块。如果你的规范很大，你可以嵌入其部分内容，让智能体在需要时检索最相关的部分，而不是总是提供整个内容。还有实现模型上下文协议（MCP）的框架，根据当前任务自动向模型提供正确的上下文。一个例子是[Context7](https://docs.digitalocean.com/products/gradient-ai-platform/concepts/context-management/)（context7.com），它可以根据你正在处理的内容自动从文档中获取相关的上下文片段。实际上，这可能意味着智能体注意到你在处理“支付处理”，并将你的规范或文档的“支付”部分拉入提示。考虑利用这样的工具或设置一个基本版本（即使是在你的规范文档中进行简单搜索）。

**小心并行化：** 一些开发者同时运行多个智能体实例处理不同任务（如前所述使用子智能体）。这可以加速开发——例如，一个智能体生成代码，而另一个同时编写测试，或者两个功能并行构建。如果你走这条路，确保任务真正独立或清晰分离以避免冲突（规范应注明任何依赖关系）。例如，不要让两个智能体同时写入同一个文件。一种工作流是让一个智能体生成代码，另一个并行审查，或者构建独立的组件，稍后再集成。这是高级用法，管理起来可能精神上很累（正如Willison承认的，运行多个智能体[出奇地有效，尽管精神上令人疲惫](https://simonwillison.net/2025/Oct/7/vibe-engineering/)！）。从最多2-3个智能体开始，以保持可管理性。

**版本控制和规范锁定：** 使用Git或你选择的版本控制系统来跟踪智能体做了什么。[良好的版本控制习惯](https://simonwillison.net/2025/Oct/7/vibe-engineering/)在AI辅助下甚至更重要。将规范文件本身提交到仓库。这不仅保留了历史，而且智能体甚至可以使用git diff或blame来理解变化（LLM在阅读差异方面相当有能力）。一些高级智能体设置让智能体查询VCS历史以查看某些内容何时被引入——令人惊讶的是，模型可以“在Git方面非常能干”。通过将规范保存在仓库中，你允许你和AI都跟踪演进。有工具（如前面提到的GitHub Spec Kit）将规范驱动开发集成到git工作流中——例如，在更新规范时门控合并，或从规范项生成检查清单。虽然你不需要这些工具就能成功，但要点是将规范像代码一样对待——勤奋地维护它。

**成本和速度考虑：** 使用大型模型和长上下文可能很慢且昂贵。一个实用技巧是明智地使用模型选择和批处理。也许使用更便宜/更快的模型进行初始草稿或重复工作，将最有能力（且最昂贵）的模型保留用于最终输出或复杂推理。一些开发者使用GPT-4或Claude进行规划和关键步骤，但将更简单的扩展或重构卸载到本地模型或更小的API模型。如果使用多个智能体，也许不是所有都需要顶级模型；一个运行测试的智能体或代码检查智能体可以是较小的模型。还要考虑限制上下文大小：如果5k令牌足够，不要喂20k令牌。正如我们讨论的，[更多令牌可能意味着收益递减](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

**监控并记录一切：** 在复杂的智能体工作流中，记录智能体的行动和输出至关重要。检查日志以查看智能体是否偏离或遇到错误。许多框架提供跟踪日志或允许打印智能体的思维链（特别是如果你提示它逐步思考）。审查这些日志可以突出显示规范或指令可能被误解的地方。这类似于调试程序——除了“程序”是对话/提示链。如果发生奇怪的事情，回到规范/指令，看看是否有歧义。

**学习并改进：** 最后，将每个项目视为完善你规范编写技能的学习机会。也许你会发现某种措辞持续混淆AI，或者以某种方式组织规范部分能产生更好的遵循度。将这些教训纳入下一个规范。AI智能体领域正在快速发展，因此新的最佳实践（和工具）不断涌现。通过博客（如Simon Willison、Andrej Karpathy等人的博客）保持更新，并不要害怕实验。
