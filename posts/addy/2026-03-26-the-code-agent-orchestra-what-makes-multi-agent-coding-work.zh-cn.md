## 我们所处的时刻

**你曾经与一个AI结对编程。现在你管理一个智能体团队。**

六个月前，大多数开发者在紧密的同步循环中与单个AI助手协作。你输入提示词，等待，审查输出，提供反馈，重复。你的上限就是单个上下文窗口能容纳的一切。对话线程就是你的工作空间。

那种模式已被取代。如今，最高效的开发者正在协调多个异步运行的智能体——每个智能体都有自己的上下文窗口、自己的文件范围、自己的职责领域——而开发者从上方进行编排。代码库成为你的画布，而非对话线程。这是从指挥家（一名乐手，实时指导）到管弦乐团指挥（整个乐团，异步协调）的转变。我在[《智能体编码的未来》](https://addyosmani.com/blog/future-agentic-coding/)中写过这种转变的早期迹象。

本次演讲涵盖了如何实际实现这一转变：模式、工具、质量门以及做好这件事所需的纪律。

## AI辅助编码的8个层级

**大多数开发者停留在第3-4级。编排层级从第6级开始，它需要一套与让你达到第5级完全不同的技能。**

Steve Yegge最近概述了开发者随AI工具演进的八个层级，这是一个有用的框架，用于理解你当前所处位置以及前进方向。

本次演讲涵盖了第5到第8级。你在这个阶梯上处于什么位置？

## 转变：从指挥家到管弦乐团指挥

**指挥家模式给你一个智能体，同步运行，你的上下文窗口是硬性上限。管弦乐团指挥模式给你多个智能体，各自拥有自己的上下文窗口，异步工作，而你负责规划和检查。**

核心心智模型的转变是结对编程与管理团队之间的区别。在指挥家模式中，你实时指导单个AI智能体。它是同步的、顺序的，你的上下文窗口是硬性上限。这种模式的工具包括Claude Code CLI和Cursor编辑器内智能体模式。

在管弦乐团指挥模式中，你协调整个乐团。多个智能体，每个都有自己的上下文窗口，异步工作。你规划工作、分配任务，并定期检查进度。这种模式的工具包括Agent Teams、Conductor、Codex和Copilot Coding Agent。

就像[管理一个真实团队](https://addyosmani.com/blog/coding-agents-manager/)一样，你现在需要不同的技能：[清晰的规格说明](https://addyosmani.com/blog/good-spec/)、工作分解和输出验证，而不是自己编写代码。

## 单智能体的天花板

**每个开发者最终都会在使用单个智能体时遇到三堵墙：上下文过载、缺乏专业化、缺乏协调。子智能体解决了前两个问题。Agent Teams解决了所有三个问题。**

为什么一个智能体不能包揽一切？三个限制因素。

**上下文过载。** 一个智能体只能容纳有限的信息。大型代码库会压垮单个上下文窗口。随着对话变长，你会丢失重要细节。

**缺乏专业化。** 一个智能体做所有事情——数据层、API、UI、测试——是万金油，样样通样样松。一个只处理数据层的专注智能体，比一个同时处理整个代码库的通才智能体，能写出好得多的数据库代码。

**缺乏协调。** 即使你生成了助手，它们也无法相互通信、共享任务列表或解决依赖关系。在没有协调原语的情况下添加的智能体越多，情况就越难。

## 为什么采用多智能体？

**并行性、专业化、隔离性和复合学习不仅仅是相加——它们是相乘的。三个专注的智能体始终优于一个工作三倍时间的通才智能体。**

采用多智能体的四个复合原因：

* **并行性（3倍吞吐量）**——三个智能体同时构建前端、后端和测试。
* **专业化（聚焦的上下文）**——每个智能体只看到它拥有的文件。一个只知道`db.js`的智能体，比一个同时处理整个代码库的智能体，能写出更好的数据库代码。
* **隔离性（安全执行）**——Git工作树为每个智能体提供自己的工作目录。工作时没有合并冲突。
* **复合学习**——一个[`AGENTS.md`](https://addyosmani.com/blog/agents-md/)文件跨会话积累模式和陷阱，因此每次会话都会让下一次变得更好。

## 模式1：子智能体——聚焦的委派

**子智能体是最简单的多智能体模式，也是你应该首先尝试的模式。**

子智能体使用Task工具从父编排器生成专门的子智能体。父智能体将任务分解成碎片，为每个碎片生成子智能体，并手动管理依赖关系图。

这是一个具体示例。你给Claude Code一个提示词："使用Express和SQLite构建一个名为Link Shelf的书签管理器。"父编排器将其分解为三个子智能体简报：

1. **数据层子智能体**——构建包含模式和CRUD操作的`db.js`，完成后编写`DATA.md`报告
2. **业务逻辑子智能体**——构建包含输入规则的`validation.js`，完成后编写`LOGIC.md`报告
3. **API路由子智能体**——读取`DATA.md`和`LOGIC.md`，构建包含Express路由的`server.js`

前两个子智能体是独立的——它们并行运行。第三个依赖于两者，因此在开始之前等待它们的报告文件。父智能体手动管理这个依赖关系图。

### 演示1：子智能体构建Link Shelf

观看父智能体分解提示词，并行生成数据和验证子智能体，然后在两个报告都准备好后启动API路由子智能体。测试最终通过。

**子智能体解决的问题：** 每个智能体的上下文隔离、专业化、独立任务的并行执行，并且在大约22万个令牌的总成本下是成本中性的。

**仍然缺失的东西：** 父智能体必须手动管理依赖关系图。智能体之间没有对等消息传递。没有共享任务列表。如果你在文件范围上马虎，两个智能体可能写入同一个文件。

底线：子智能体给你并行执行，但需要手动协调。这对于简单的分解来说很好。但当协调成为瓶颈时，你需要Agent Teams。

## 专业提示：分层子智能体——团队的团队

**不要止步于一层委派。生成功能主管，它们再生成自己的专家。这给你3倍更深的分解，而不会撑爆任何人的上下文窗口。**

与其让你的编排器生成六个子智能体——这会碎片化它的上下文——不如生成两个功能主管。每个功能主管再生成自己的两到三个专家。

父编排器只与两个智能体对话，保持其上下文清晰。功能主管A得到一个像"构建搜索功能"这样的简报，并自行将其分解为数据、逻辑和API子智能体。父智能体永远看不到那些细节。

这模仿了真实工程组织的运作方式。你不会让工程副总裁给各个工程师分配任务。你通过技术主管的层级来运作。

## 模式2：Agent Teams——真正的并行执行

**Agent Teams添加了子智能体所缺乏的协调原语：带有依赖跟踪的共享任务列表、队友之间的对等消息传递，以及防止冲突的文件锁定。**

Agent Teams是Claude Code用于真正并行执行的实验性功能。启用它：

```
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
```

架构有三层：

1. **团队主管**在最顶层——分解工作，创建任务列表，综合结果
2. **共享任务列表**在中间——带有状态（待处理、进行中、已完成、已阻塞）的任务、依赖跟踪和文件锁定
3. **队友**在最底层——每个都是独立的Claude Code实例，拥有自己的上下文窗口，在tmux分屏窗格中运行

队友从共享列表中自行认领任务。它们直接相互发送消息——对等通信，不通过主管。当一个队友完成并标记任务为已完成时，任何依赖于它的已阻塞任务会自动解除阻塞。随时按`Ctrl+T`切换任务列表的视觉覆盖层。

### 演示2：Agent Teams并行构建搜索

这是主角演示。我们从可用的Link Shelf应用开始，给Claude Code一个提示词："创建一个三人智能体团队来添加搜索功能。"主管生成后端、前端和测试队友。后端队友开始搜索API端点。前端队友开始搜索UI。测试队友最初被阻塞——等待API。当后端完成并将API合约发送给前端时，测试任务自动解除阻塞。三者同时工作。

### 演示3：Agent Team通信特写

这个较短的演示聚焦于通信机制。观看`Ctrl+T`任务列表覆盖层、后端标记API端点完成时的依赖自动解除阻塞，以及后端智能体直接向前端智能体发送API合约的对等消息，无需经过主管。

## Agent Teams：机制如何运作

**两种机制使Agent Teams工作：带有自动依赖解析的共享任务列表，以及防止主管成为瓶颈的对等消息传递。**

**共享任务列表**为每个任务赋予一个状态：待处理、进行中、已完成或已阻塞。已阻塞的任务有显式依赖。当后端队友标记搜索API为已完成时，已阻塞的测试编写任务自动翻转为待处理，某个队友会接手。文件锁定防止两个队友同时编辑同一个文件。

**对等消息传递**是另一个关键部分。后端智能体直接告诉前端智能体API合约："GET /search?q= 返回 [{id,title,url}]。"这不经过主管。当一个队友空闲时，主管会自动收到通知。这种对等方法防止主管成为协调瓶颈。

## Agent Teams：关键要点

**三到五个队友是理想数量。令牌成本线性扩展，三个专注的队友始终优于五个分散的队友。**

* **带协调的真正并行性**——不仅仅是同时运行东西。带有依赖跟踪的共享任务列表确保工作按正确顺序进行。
* **对等消息传递防止瓶颈**——队友直接通信。后端告诉前端API合约，无需主管作为中介。
* **风险任务的计划审批**——要求队友在实现之前编写计划。主管审查并批准或拒绝，在代码存在之前捕捉架构问题。
* **合理调整团队规模**——3-5个队友是理想数量。令牌成本随团队规模线性增长。

## Agent Teams专业提示：可靠性

**带有强制反思的循环护栏显著减少卡住的智能体。一个专用的@reviewer队友在每个任务完成时自动触发，意味着主管只看到通过审查的代码。**

**循环护栏 + 反思步骤。** 每个队友获得一个硬性的`MAX_ITERATIONS=8`。在每次重试之前，强制进行反思提示：

> "什么失败了？什么具体改变能修复它？我是否在重复同样的方法？"

这一单一改变显著减少了卡住的智能体。没有它，智能体会无限循环尝试同样的失败方法。有了它，它们会自我纠正。

**专用@reviewer队友。** 生成一个永久审查者，具有以下约束：

* **模型：** Claude Opus 4.6（只读）
* **工具：** 仅限lint、测试、安全扫描
* **触发：** 在每个TaskCompleted事件上自动触发
* **比例：** 每3-4个构建者配1个审查者

主管只看到通过审查的代码。这就像在团队内部内置了一个永久的CI质量门。

## 模式3：规模化编排

**当你需要管理跨多个仓库和功能的5、10或20个以上的智能体时，你需要专门构建的编排工具。2026年的每个工具都适合三个层级之一——为工作选择正确的层级。**

2026年的工具格局分为三个层级：

### 第1层：进程内子智能体和团队

Claude Code子智能体和Agent Teams。单个终端会话，无需额外工具。从这里开始。

### 第2层：本地编排器

你的机器在隔离的工作树中生成多个智能体。你通过仪表板、差异审查和合并控制保持参与。最适合3-10个智能体在已知代码库上工作。工具包括Conductor、Vibe Kanban、Gastown、OpenClaw + Antfarm、Claude Squad、Antigravity和Cursor Background Agents。

### 第3层：云端异步智能体

分配一个任务，合上笔记本电脑，回来时看到一个拉取请求。智能体在云端虚拟机中运行。无需终端，无需本地设置。工具包括Claude Code Web、GitHub Copilot Coding Agent、Google的Jules和OpenAI的Codex Web。

2026年的大多数开发者将使用所有三个层级——第1层用于交互式工作，第2层用于并行冲刺，第3层用于在一夜之间清理积压任务。

## 工具聚焦

### Conductor by Melty Labs

Conductor是在Mac上开始多智能体编排的最快方式。它并行运行多个Claude Code和Codex智能体，每个在自己的git工作树中，带有可视化仪表板和差异优先的审查UI。它是免费的——你只需支付你的API成本。目前仅限macOS（Apple Silicon和Intel）。理想使用场景是3-8个并行功能在同一个仓库上，并带有视觉监督。

### Claude Code Web

位于`claude.ai/code`的Claude Code Web是Claude Code的第3层版本——完全基于浏览器，无需终端。连接你的GitHub仓库，描述任务，它们在Anthropic管理的云端虚拟机中运行。你可以在运行中进行引导，获得自动PR创建，并从iOS应用访问它。关键心智模型：Teams（终端）用于与智能体并肩工作；Web（浏览器）用于委派任务然后离开。

### GitHub Copilot Coding Agent

一个重要区别：IDE中的Copilot智能体模式是同步和交互式的。GitHub上的Copilot Coding Agent是完全异步的。将任何GitHub问题分配给`@copilot`或使用Agents面板，它会在GitHub Actions环境中创建一个草稿PR。现在它在标记你之前运行一个自我审查循环。包括Claude Code和Codex在内的第三方智能体也可以通过相同的Agents面板访问，你可以从Slack、Jira、Linear和Azure Boards触发它。

### Jules by Google

Jules是Google的异步云端编码智能体，由Gemini驱动。工作流程：连接一个GitHub仓库，描述一个任务，Jules生成一个计划，你在任何代码写入之前批准它，然后在云端虚拟机中运行并返回一个带有完整推理和终端日志的PR。独特功能包括音频变更日志、任务中中断，以及用于直接管道传输GitHub问题的Jules Tools CLI。它自动读取你仓库的`AGENTS.md`，无需额外配置。

### OpenAI Codex Web

Codex Web是这个领域最广泛使用的工具之一。每个任务在预加载了你GitHub仓库的独立沙盒容器中运行。表面生态系统涵盖Web、CLI（开源）、macOS应用、IDE扩展和GitHub集成——全部通过你的ChatGPT账户连接。可验证证据功能为每个任务返回终端日志和测试输出的引用，因此你可以审计确切发生了什么。

### Cursor Cloud Agents + Glass

相同的智能体基础，但在隔离的云端虚拟机中运行。从Web、桌面应用、Slack、Linear、GitHub、API启动智能体，甚至将cursor.com/agents作为PWA安装到手机上。Glass是Cursor的新界面，使智能体管理成为主要表面，传统编辑器在你需要时才使用。这反映了整个生态系统中更广泛的模式：控制平面正在成为主要体验，而编辑器是它下面的一个工具。

### Vibe Kanban

Vibe Kanban解决了"末日滚动间隙"——智能体工作时你无事可做的2-5分钟。创建带有详细提示词的任务卡片，拖到"进行中"，每个都有自己的工作树和分支。在面板内审查差异，向正在运行的智能体发送反馈。支持Claude Code、Codex、Gemini CLI、Amp、Cursor Agent CLI等。跨平台（Mac、Windows、Linux），免费，自带密钥。

## 规模化专业提示

**多模型路由在不牺牲质量的情况下降低成本。人工策划的AGENTS.md在任何长度上都比机器生成的更有价值——研究表明AI编写的规则没有好处，甚至可能略微降低成功率。**

### 多模型路由

并非每个任务都需要你最昂贵的模型。将规划和架构任务路由到较便宜的Gemini/Claude/OpenAI模型之一。将实现路由到Sonnet、Opus或Codex。将审查路由到专用的安全模型。创建一个`MODEL_ROUTING.md`文件：

```

规划          -> Gemini 
实现          -> Claude Opus或Sonnet 
审查          -> 等等。
测试          -> 等等。
```

### 工作树生命周期脚本

三个shell别名自动化了繁琐工作：

```
agent-spin <feature>   # 创建工作树 + 分支 + 启动智能体
agent-merge <feature>  # 变基 + 审查 + 打开PR
agent-clean            # 移除已完成的工作树
```

大约12行bash代码。Conductor为你可视化地完成这些操作。

### 仅限人工策划的AGENTS.md

这是重要的一点。[研究表明](https://addyosmani.com/blog/agents-md/)（Gloaguen等人，苏黎世联邦理工学院），LLM生成的AGENTS.md文件没有好处，甚至可能略微降低成功率（平均约3%），同时将推理成本增加超过20%。相比之下，开发者编写的上下文文件提供了约4%的适度改进。绝不让智能体直接写入`AGENTS.md`。主管必须批准每一行。保持简短，带有清晰的部分：

```
## 风格
- 使用带钩子的函数组件
- 优先使用具名导出

## 陷阱
- SQLite需要WAL模式才能并发读取
- Express中间件顺序对认证很重要

## 架构决策
- 所有状态在SQLite中，没有内存缓存
- 每个功能模块一个Express路由器

## 测试策略
- API路由的集成测试优先于单元测试
- 使用supertest进行HTTP断言
```

## 质量门：信任但要验证

**三个质量门使智能体输出值得信赖：计划审批在代码存在之前捕获糟糕的架构，钩子在每个生命周期事件上强制执行自动化检查，AGENTS.md跨会话复合学习。**

**计划审批。** 要求队友在开始编码之前编写计划。主管审查方法并批准或拒绝。修复糟糕计划比修复糟糕代码便宜得多。流程如下：

```
队友 >>> 编写计划 >>> 主管审查 >>> 批准/拒绝 >>> 实现
```

**钩子。** 生命周期事件上的自动化检查。一个`TeammateIdle`钩子在允许智能体停止工作之前验证所有测试通过。一个`TaskCompleted`钩子在标记任务完成之前运行lint和测试。如果钩子失败，智能体继续工作直到通过：

```
任务完成 >>> 钩子运行 npm test >>> 通过？允许  |  失败？继续工作
```

**AGENTS.md用于复合学习。** 这个文件捕获发现的模式、陷阱和风格偏好。每个智能体在会话开始时读取它，每次会话更新它。会话一了解了一个测试模式，AGENTS.md被更新，会话二避免了同样的错误。

## 瓶颈已经转移

**瓶颈不再是生成。而是[验证](https://addyosmani.com/blog/code-review-ai/)。智能体能够以惊人的速度产生令人印象深刻的输出。自信地知道该输出是否正确才是困难的部分。**

在变更之前通过的测试并不能保证它们能捕获来自该变更的回归。智能体可以编写技术上有效但遗漏了重要案例的测试。上下文窗口限制意味着在大型代码库上工作的智能体可能错过其当前视图之外的重要约束。而一个单一开发者遇到的不稳定环境作为恼人的边缘情况，当四十个智能体同时遇到同一个不稳定测试时，就变成了系统性阻塞。

直到[验证基础设施](https://addyosmani.com/blog/code-review-ai/)赶上生成能力，人工审查不是可选的额外负担。它是安全系统。对令人印象深刻的智能体输出的适当反应不是因为它看起来好就信任它。而是拥有架构理解和测试纪律来严格评估它。

## 演示4：质量门和自我改进的智能体

这个演示将所有内容联系在一起。观看三件事。首先，计划审批流程——一个队友提议添加收藏功能，主管发现计划缺少数据库迁移步骤并拒绝它，队友修改。其次，任务完成时钩子触发——`TaskCompleted`钩子捕获了一个被遗忘的`console.log`语句，智能体在任务标记完成之前修复它。第三，`AGENTS.md`在最后更新，添加了一个新条目："在向现有表添加列时，始终包含ALTER TABLE迁移。"该学习成果会延续到每个未来会话。

## Ralph循环和自我改进的智能体

**Ralph循环模式将开发分解为小的原子任务，并在无状态但迭代的循环中运行智能体。每次迭代：选择任务，实现，验证，如果通过则提交，重置上下文并重复。这避免了上下文溢出，同时通过外部内存保持连续性。**

由Geoffrey Huntley和Ryan Carson推广，Ralph循环是"睡觉时发货"模式背后的原理。Carson的独立`ralph`工具（snarktank/ralph）实现了核心循环，而他的Antfarm项目使用相同模式在OpenClaw之上添加了多智能体编排。核心思想可跨工具推广。

五步循环：

1. **选择**——从`tasks.json`中选择下一个任务
2. **实现**——进行更改
3. **验证**——运行测试、类型检查、lint
4. **提交**——如果检查通过，提交并更新任务状态
5. **重置**——清除智能体上下文，用下一个任务重新开始

关键洞察是无状态但迭代。通过每次迭代重置，智能体避免了积累混乱。小范围有界的任务比一个巨大的提示词产生更干净的代码，幻觉更少。

使其可靠的保障措施：将错误反馈用于自动重试，但在3次以上卡住的迭代后终止并重新分配。始终在功能分支上工作。设置迭代次数、时间和令牌的硬性限制。智能体打开一个PR——你在合并前审查。

四种内存通道跨重置持续存在：git提交历史、进度日志、任务状态文件（`tasks.json`）和作为长期语义内存的`AGENTS.md`。从一个循环过夜开始。逐步升级到十个分支上的十个循环。

### 让智能体随时间变得更聪明

**使用REFLECTION.md提案进行自我反思。** 在每个任务之后，强制智能体编写一个REFLECTION.md：什么让我惊讶，一个要添加到AGENTS.md的模式，一个提示词改进。主管审查并合并已批准的学习成果。这就是[复合学习如何实际复合](https://addyosmani.com/blog/self-improving-agents/)——系统性地，而非临时性地。

**令牌预算和终止标准。** 为每个智能体设置硬性预算：前端18万个令牌，后端28万个令牌。在预算的85%时，自动暂停并通知主管。如果在同一个错误上卡住3次以上迭代，终止并重新分配给一个新的智能体。

**Beads / 持久内存。** Gastown的"beads"模式：不可变的、由git支持的每个决策和结果的记录，具有完整来源。智能体通过任务图和可SQL寻址的数据平面查询过去的beads——不是传统的基于向量的RAG，而是结构化、可查询的制度性记忆，远远超出平面markdown文件。

## 纪律：什么让这一切奏效

**人工瓶颈是一个特性，而非缺陷。以人类速度，错误缓慢累积，痛苦迫使早期纠正。有了智能体大军，小错误以超出你捕捉能力的速度复合。**

当人类缓慢编写代码时，你早期就感受到痛苦。测试失败，代码审查发现问题，你注意到重复。痛苦是即时的，所以你边做边修。

有了编排好的智能体大军，没有自然的瓶颈。小的无害错误——这里一个代码异味，那里一个重复，一个不必要的抽象——以不可持续的速度复合。你已将自己从循环中移除，所以直到为时已晚你才感受到痛苦。然后有一天你试图添加一个功能，架构不允许。你的测试同样不可信，因为智能体也写了那些测试。

这就是为什么每个质量门都很重要。计划审批、钩子、令牌预算、人工审查——它们存在不是因为它们很好拥有，而是因为没有它们，你会智能体式地把自己编码进一个角落。

### 委派任务，而非判断

**让智能体处理范围明确、有清晰通过/失败标准的任务、样板代码、迁移和测试脚手架。为自己保留：架构、决定不构建什么、在完整上下文中审查、以及产生好系统的品味。**

智能体擅长任何具有严格评估函数的事情——智能体可以衡量自己的工作。它们确实擅长样板代码、迁移、测试脚手架，以及探索你永远没有时间手动尝试的方法。

为自己保留：架构和API设计（智能体在其训练数据中见过大量糟糕的架构，会很乐意将企业模式照搬到你的初创公司），决定不构建什么（说不是一个智能体不具备的特性），以及在完整系统上下文中审查智能体输出（智能体只有局部视图）。

构建更少的功能，但构建正确的功能。代码生成的速度是海妖之歌。放慢速度以保持理解。因为如果你[失去对自己系统的理解](https://addyosmani.com/blog/comprehension-debt/)，你就失去了修复它、扩展它，甚至知道它何时损坏的能力。

### 你的规格说明是杠杆

**当你并行编排五十个智能体时，模糊的思考不仅减慢你的速度——它会倍增。模糊的需求通过几十个并行运行传播，每个都以略微不同的方式稍微出错。强大的工程师从智能体中获得更多杠杆，而非更少。**

平庸输出与卓越输出之间的差异几乎完全取决于你规格说明的质量。模糊的规格说明在整个舰队中倍增错误。精确的规格说明——带有清晰的架构、集成边界、边缘情况和不变量——在各地倍增为精确的实现。

[规格说明](https://addyosmani.com/blog/good-spec/)不再是一个提示词。规格说明是产品思维变得显式。这就是为什么强大的软件工程师从这些工具中获得[更多杠杆](https://addyosmani.com/blog/agentic-engineering/)而非弱小的工程师。输入代码的机械工作正在被自动化。理解系统的认知工作正在整个自主工作者舰队中被放大。

## 工厂模型

**你不再只是编写代码。你在构建构建软件的工厂。那个工厂有一条生产线：规划、生成、监控、验证、集成、回顾。**

工厂有质量控制。工厂有流程文档。工厂有需要精确指定的输入，否则输出会出错。当环境不可靠时，工厂会停滞。所有这些属性直接映射到智能体式软件开发。

六步生产线：

1. **规划**——编写带有验收标准的规格说明。你的规格说明是杠杆。
2. **生成**——创建你的团队并分配智能体。
3. **监控**——每5-10分钟查看进度并解决阻塞。不要紧盯着。
4. **验证**——运行测试，审查代码。验证是瓶颈，而非生成。
5. **集成**——合并分支，解决冲突。
6. **回顾**——用新模式更新AGENTS.md。复合学习。

运行工厂的实用技巧：

* **设置在制品限制：** 不要运行超过你能有意义审查的智能体数量。3-5是理想数量。
* **定义终止标准：** 如果智能体在同一个错误上卡住3次以上迭代，停止并重新分配。
* **异步签到：** 每5-10分钟检查进度。让智能体自主工作。
* **一个文件，一个所有者：** 绝不让两个智能体编辑同一个文件。冲突会扼杀速度。

有关此框架的更多信息，请参见[工厂模型](https://addyosmani.com/blog/factory-model/)。
