        > *摘要：AI编码代理总是走通往"完成"的最短路径，这通常意味着跳过那些让软件在大规模下保持可靠的规范、测试和审查。Agent Skills将这些高级工程师的行为编码为代理必须遵循的工作流程，并内置了反合理化机制。*

*高级工程师的工作大部分是那些不会出现在代码差异中的部分。规范。测试。审查。范围纪律。拒绝发布无法验证的内容。AI编码代理默认跳过这些部分。Agent Skills是我让它们变得不可跳过的尝试。*

---

任何AI编码代理的默认行为都是走通往"完成"的最短路径。要求一个功能，它就编写这个功能。它不会询问你是否有一个规范，不会在实现之前编写测试，不会考虑这个变更是否跨越了信任边界，也不会检查这个PR在审查者眼中会是什么样子。它生成代码，宣布胜利，然后继续前进。

这是每个高级工程师花费整个职业生涯学习避免的相同失败模式。任何任务的高级版本都包括那些不会出现在代码差异中的工作：揭示假设、编写规范、将工作分解成可审查的块、选择无聊的设计、留下结果正确的证据、调整变更规模以便人类能够实际审查。这些步骤正是区分那些能在大规模下交付可靠软件的工程师和那些推送会出问题的代码的人的关键。

代理跳过这些步骤的原因与任何初级工程师一样。它们是不可见的。奖励信号指向的是"任务完成"，而不是"任务完成且设计文档存在"。因此，我们必须重新加上高级工程师的框架。

[Agent Skills](https://github.com/addyosmani/agent-skills) 是我对这种框架的尝试。它刚刚突破了27K星标，所以显然我不是唯一想要它的人。**这篇文章是README没有完全涵盖的部分**：每个设计选择存在的原因，它如何映射到标准SDLC和谷歌已发布的工程实践，以及即使你从未安装任何技能，你也应该从这个项目中借鉴什么。

## "技能"到底是什么

"技能"这个词在Claude Code / Anthropic的词汇表中承担了很多工作，精确理解很有帮助。一个技能是一个带有前置元数据的markdown文件，当情况需要时会被注入到代理的上下文中。介于系统提示片段和运行手册之间。

技能*不是*参考文档。它不是"你应该知道的关于测试的一切"。它是一个工作流程：代理遵循的一系列步骤，带有产生证据的检查点，并以定义的退出标准结束。

这个区别就是整个游戏的关键。如果你把一个2000字的关于测试最佳实践的文章放入代理的上下文中，代理会阅读它，生成看起来合理的文本，然后跳过实际的测试。如果你把一个*工作流程*放在那里（先编写会失败的测试，运行它，看着它失败，编写最少代码使其通过，看着它通过，重构），代理就有事情要做，而你也有东西可以验证。

**流程优于散文。工作流程优于参考。带有退出标准的步骤优于没有退出标准的文章。** 这一个区别就将有用的技能与漂亮的markdown文件区分开来。它也解释了为什么这么多"AI规则"仓库最终在实践中毫无作用。那些规则是文章。

## 技能编码的SDLC

仓库中的二十个技能围绕六个生命周期阶段组织，上面有七个斜杠命令。定义（`/spec`）是你决定实际构建什么的地方。计划（`/plan`）将工作分解。构建（`/build`）以垂直切片方式实现。验证（`/test`）证明它能工作。审查（`/review`）捕捉漏网之鱼。发布（`/ship`）安全地将其交付给用户。`/code-simplify`横跨整个体系的底部。

这不是巧合。这是每个正常运作的工程组织都在运行的相同SDLC，只是词汇不同。谷歌称之为设计文档→审查→实现→可读性审查→启动清单。亚马逊称之为反向工作备忘录和把关人。每个健康的团队都有这个循环的某种版本。

AI编码代理的新情况是*大多数代理默认跳过这些阶段中的大多数*。你要求一个功能，你得到一个实现，而规范、计划、测试、审查和启动清单都没有发生。**技能推动代理经历高级工程师强迫自己经历的相同阶段，因为不经过这些阶段就发布代码是产生事故的方式。**

一个复杂的功能可能依次激活十一个技能。一个小错误修复可能使用三个。路由器（`using-agent-skills`）决定哪些适用。关键在于工作流程适应实际范围，而不是假设的范围。

## 五个起关键作用的原则

项目中的五个设计决策是承重墙。系统的其余部分都遵循它们。

### 1. 流程优于散文

已经涵盖。工作流程是代理可执行的；文章不是。对于人类团队也是如此。如果你的团队手册有200页，没有人会在时间压力下阅读它。如果它是一小套带有检查点的工作流程，人们实际上会运行它们。

### 2. 反合理化表格

这是项目中最独特的设计决策，也是我最希望其他团队借鉴的。

每个技能都包含一个表格，列出了代理（或疲惫的工程师）可能用来跳过工作流程的常见借口，并配以书面的反驳。几个接近原文的例子：

* *"这个任务太简单了，不需要规范。"* → 验收标准仍然适用。五行是可以的。零行是不行的。
* *"我稍后会写测试。"* → "稍后"是承重词。没有稍后。先编写会失败的测试。
* *"测试通过了，发布吧。"* → 通过的测试是证据，不是证明。你检查运行时了吗？你验证用户可见的行为了吗？人类阅读过差异了吗？

这之所以有效，是因为LLM非常擅长合理化。它们会产生一段听起来合理的段落，解释为什么*这个特定的*任务不需要规范，或者为什么*这个特定的*变更无需审查就可以合并。**反合理化表格是对代理尚未说出的谎言的预先写好的反驳。**

这种模式对人类团队同样有效。大多数工程退化不是有人选择做糟糕的工作。而是人们接受听起来合理的理由来跳过他们不想做的部分。一个写下其反合理化的团队是一个拥有更少合理化的团队。

### 3. 验证不可协商

每个技能都以具体证据结束。测试通过。构建输出干净。运行时跟踪显示预期行为。审查者签字。"*看起来正确*"永远不够。

这是使Anthropic的框架能从失败中恢复、使Cursor的计划者/工作者/评审者拆分能实际捕捉错误、使任何[长时间运行的代理](https://addyosmani.com/blog/long-running-agents/)可恢复的相同原则。代理是一个生成器。你需要一个独立的信号表明工作已完成。技能将那个信号烘焙到每个工作流程中。

### 4. 渐进式披露

不要在会话开始时将所有二十个技能加载到上下文中。根据阶段激活它们。一个小的元技能（`using-agent-skills`）充当路由器，决定哪个技能适用于当前任务。

这是以技能粒度应用的[框架工程](https://addyosmani.com/blog/agent-harness-engineering/)课程。加载到上下文中的每个token都会在某个地方降低性能，所以你加载相关的内容，将其他内容留在磁盘上。**渐进式披露是你如何将一个二十技能的库放入5K-token的槽中而不污染整个系统。**

### 5. 范围纪律

元技能编码了一个不可协商的规则，如果可能的话我会把它钉在每个代理上：*"只动你被要求动的东西。"* 不要重构相邻系统。不要删除你不完全理解的代码。不要碰到一个TODO就决定重写整个文件。

这听起来显而易见，直到你看着一个代理决定修复一个错误需要现代化三个不相关的文件。**范围纪律是决定代理的PR是可合并还是必须被撤销的最大单一因素。** 它也是与谷歌代码审查规范最清晰对应的原则，在谷歌，审查者会因为一个PR做了不止一件事而阻止它。

## 谷歌的DNA

这些技能充满了来自*Software Engineering at Google*和谷歌公开工程文化的实践。这是有意为之。使谷歌规模软件工作的大部分内容都有文档记录且公开，而且这*正是*代理最可能跳过的部分。

哪个技能编码了哪个实践的部分映射：

* **Hyrum定律**在`api-and-interface-design`中。你API的每个可观察行为最终都会被某人依赖，所以设计时要考虑到这一点。
* **测试金字塔（约80/15/5）和Beyoncé规则**在`test-driven-development`中。*"如果你喜欢它，你就应该给它加个测试。"* 基础设施变更不会捕捉错误；测试才会。
* **测试中的DAMP优于DRY。** 谷歌的测试哲学明确表示，测试代码应该读起来像规范，即使以一些重复为代价。过度抽象的测试是一个已知的反模式。
* **约100行的PR大小，带有Critical / Nit / Optional / FYI严重性标签**在`code-review-and-quality`中。直接来自谷歌的代码审查规范。大的PR不会被审查；它们会被橡皮图章式地批准。
* **Chesterton的围栏**在`code-simplification`中。在你理解某物为什么被放在那里之前，不要移除它。
* **主干开发和原子提交**在`git-workflow-and-versioning`中。
* **左移和功能标志**在`ci-cd-and-automation`中。尽可能早地发现问题，将部署与发布解耦。
* **代码即负债**在`deprecation-and-migration`中。你保留的每一行代码都需要你永远维护，所以优先选择更小的表面积。

这些都不是新想法。**关键在于它们默认都不在代理中。** 一个前沿模型在其训练数据中读到过"Hyrum定律"这个短语，但当它在凌晨3点设计你的API时，它并不会应用Hyrum定律。技能就是你确保它应用这些原则的方式。

## 如何实际使用它

三种模式，按大致递增的承诺程度。

**模式1：通过市场安装。** 如果你使用Claude Code：

```
/plugin marketplace add addyosmani/agent-skills
/plugin install agent-skills@addy-agent-skills

```

你会得到斜杠命令（`/spec`、`/plan`、`/build`、`/test`、`/review`、`/ship`、`/code-simplify`），代理会根据上下文自动激活相关技能。这是我会推荐大多数人开始使用的路径。

**模式2：将markdown放入你选择的工具中。** 这些技能是带有前置元数据的纯markdown。Cursor用户将它们放在`.cursor/rules/`中。Gemini CLI有自己的安装路径。Codex、Aider、Windsurf、OpenCode，任何接受系统提示的工具都可以读取它们。工具本身不如底层的工作流程重要。

**模式3：将其作为规范阅读。** 即使你从未安装任何东西，这些技能也是*对使用AI代理的良好工程实践的文档化描述*。阅读`code-review-and-quality.md`并将五轴框架应用到你的团队审查流程中。阅读`test-driven-development.md`并用它来解决与初级工程师的下一次"我们需要先编写测试吗"的争论。阅读元技能并为你的AGENTS.md借鉴五个不可协商的规则。

这第三种模式是我实际上会建议开始的地方。选择最接近你当前痛点的四到五个技能。决定你想要强制执行哪些工作流程。然后安装运行时，或者自己构建，来执行强制执行。

## 即使你从不安装也应该借鉴什么

无论你是否使用AI编码代理，我都会借鉴项目中的几个模式。

**反合理化作为团队实践。** 写下你的团队对自己说的谎言。*"我们会在发布后修复测试。" "这个变更太小了，不需要设计文档。" "没关系，我们有监控。"* 将每个与反驳配对。把它放在你的AGENTS.md或工程维基中。它会为你节省争论，并且会捕捉下一个疲惫的周五下午的捷径。

**对于你内部编写的任何内容，流程优于散文。** 如果你发现自己正在写一个2000字的文档，标题为"我们如何处理X"，你写的是参考材料。将其转换为带有检查点的工作流程。文档会缩小到400字，人们实际上会运行它。这同样适用于入职指南和运行手册，也适用于代理技能。

**验证作为硬性退出标准。** 使"产生证据"成为每个任务的退出步骤。对于代理，对于工程师，对于你自己。证据是任何证明工作已完成的东西：一个通过的测试运行、一个截图、一个日志、一个审查批准。没有它，任务就没有完成。*"看起来正确"*永远不会闭环。

**任何规则手册的渐进式披露。** 不要写一本50页的手册。写一个小型路由器，指向适合情况的小章节。这对于AGENTS.md、运行手册、事故剧本以及在时间压力下会被阅读的任何内容都是如此。

**五个不可协商的规则，从元技能中提取，我会在明天放入任何AGENTS.md中：**

1. 在构建之前揭示假设。默默持有的错误假设是最常见的失败模式。
2. 当需求冲突时停下来询问。不要猜测。
3. 在必要时提出反对意见。代理（或工程师）不是唯命是从的机器。
4. 优先选择无聊、明显的解决方案。聪明是昂贵的。
5. 只动你被要求动的东西。

这就是五行代码中一个有价值的工程文化，你不需要安装任何东西来采纳它。

## 这在框架中的位置

在更广阔的图景中，技能是[代理框架工程](https://addyosmani.com/blog/agent-harness-engineering/)的一个层面。框架是模型加上你围绕它构建的一切；技能是那些被渐进式披露到系统提示中的可重用工作流程块。它们与`AGENTS.md`（滚动规则手册）、hooks（确定性执行层）、tools（代理可以采取的行动）和会话日志（持久内存）并列。每个层面都有特定的工作。技能做的是高级工程师流程的工作。

技能对于[长时间运行的代理](https://addyosmani.com/blog/long-running-agents/)比对于聊天式的代理更重要，因为长时间运行会放大每一个捷径。一个在10分钟会话中跳过测试的代理会产生一个错误。一个在30小时会话中跳过测试的代理会在运行结束时产生一个调试考古项目，那时没有人记得原始意图是什么。**运行时间越长，高级工程师框架就越需要被强制执行而不是建议。**

技能格式的可移植性也很重要。同一个SKILL.md文件可以在Claude Code、Cursor（使用规则）、Gemini CLI、Codex和任何其他接受系统提示内容的框架中工作。编写一次工作流程，运行时强制执行它。这就是带有前置元数据的markdown格式为你带来的东西，而定制化的提示工程则做不到。

## 结语

我最希望人们从这个项目中带走的，比技能本身更重要的是，这个框架。

AI编码代理是极其有能力的初级工程师，对工作中那些不会出现在代码差异中的部分没有直觉。高级工程师的工作（揭示假设、调整变更规模、编写规范、留下证据、拒绝合并无法审查的内容）正是代理会跳过的，除非你让它不可能跳过。这项工作越来越成为将那种纪律编码为代理无法说服自己摆脱的东西。

技能是那种纪律的一种形式。反合理化表格。渐进式披露。流程优于散文。验证作为承重退出标准。已经有效的谷歌实践，变得可移植。

你可以安装[我的版本](https://github.com/addyosmani/agent-skills)。你可以自己构建。**无论哪种方式，教训都成立：工作中高级工程师的部分不再是可选的，即使工程师是一个模型。**
