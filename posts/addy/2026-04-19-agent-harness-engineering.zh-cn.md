# 代理框架工程

            **日期：** 2026-04-19 00:00 UTC
            **链接：** https://addyosmani.com/blog/agent-harness-engineering/

            ---

            *一个编码代理是模型加上你围绕它构建的一切。框架工程将这种脚手架视为真正的产物，每当代理出错时，它就会收紧。*

---

大致来说：每当你发现代理犯了一个错误，你就花时间设计一个解决方案，使该代理永远不会再犯同样的错误。

过去两年我们一直在争论模型。哪个最聪明，哪个能写出最干净的 React，哪个幻觉更少。这种讨论本身没问题，但它忽略了系统的另一半。模型只是运行中代理的一个输入。其余部分是*框架*：包裹在模型周围的提示词、工具、上下文策略、钩子、沙箱、子代理、反馈循环和恢复路径，以便代理能够真正完成某些事情。

**一个不错的模型配上优秀的框架，胜过优秀的模型配上糟糕的框架。** 我在自己的工作中一次又一次地目睹了这一点。而且，越来越有趣的工作不在于选择模型，而在于设计围绕模型的脚手架。

这门学科现在有了名字。Viv Trivedy 创造了*框架工程*这个术语，他的[《代理框架的解剖》](https://x.com/Vtrivedy10/status/2031408954517971368)一文是对框架究竟是什么以及每个部分存在的原因最清晰的推导。[Dex Horthy](https://x.com/dexhorthy/status/1985699548153467120) 一直在追踪这种模式的出现。[HumanLayer](https://www.humanlayer.dev/blog/skill-issue-harness-engineering-for-coding-agents) 将大多数代理失败归结为“技能问题”，即归根结底是配置问题而非模型权重问题。[Anthropic 的工程团队](https://www.anthropic.com/engineering/harness-design-long-running-apps)发表了我认为对如何设计长期运行工作的框架的最佳公开分析。[Birgitta Böckeler](https://martinfowler.com/articles/exploring-gen-ai/harness-engineering.html) 从用户角度对这个问题做了很好的概述。

这篇文章是我试图将这些线索整合在一起的尝试。

---

## 框架究竟是什么？

Viv 的一句话概括了大部分内容：

> 代理 = 模型 + 框架。如果你不是模型，你就是框架。

框架是除模型本身之外的所有代码、配置和执行逻辑。原始模型不是代理。只有当框架赋予它状态、工具执行、反馈循环和可强制执行的约束时，它才成为代理。

具体来说，框架包括：

* 系统提示词、`CLAUDE.md`、`AGENTS.md`、技能文件和子代理提示词
* 工具、技能、MCP 服务器及其描述
* 捆绑的基础设施（文件系统、沙箱、浏览器）
* 编排逻辑（子代理生成、交接、模型路由）
* 用于确定性执行的钩子和中间件（压缩、延续、代码检查）
* 可观测性（日志、追踪、成本和延迟计量）

[Simon Willison](https://simonwillison.net/2025/Sep/30/designing-agentic-loops/) 将循环部分归结为其本质：代理是一个*“在循环中运行工具以实现目标”*的系统。技能在于工具和循环两者的设计。

如果这听起来像很大的工作范围，确实如此。而且这是*你的*工作范围，而不是模型提供商的。Claude Code、Cursor、Codex、Aider、Cline：这些都是框架。**底层的模型有时是相同的，但你体验到的行为主要由框架决定。**

```
编码代理 = AI 模型 + 框架

```

这个由 Viv 阐述并由 HumanLayer 响应的等式，才是实际工作的所在。关于等式左侧的争论很激烈。但大部分实际杠杆作用在右侧。

## “技能问题”的重新框架

我注意到工程师们会陷入一种模式。代理做了蠢事，工程师责怪模型，然后把责任归咎于“等下一个版本。”

框架工程的思维方式拒绝这种默认做法。失败通常是可理解的。代理不知道某个约定，所以你把它添加到 `AGENTS.md` 中。代理运行了一个破坏性命令，所以你添加一个钩子来阻止它。代理在一个 40 步的任务中迷失了方向，所以你把它拆分为规划器和执行器。代理一直“完成”有问题的代码，所以你在循环中接入类型检查的反向压力信号。

HumanLayer 说：*“这不是模型问题。这是配置问题。”* 框架工程就是当你认真对待这一点时所发生的事情。

有一个引人注目的数据点同时出现在 Viv 的文章和 HumanLayer 的文章中。在 Terminal Bench 2.0 上，在 Claude Code 内部运行的 Claude Opus 4.6 得分远低于在自定义框架中运行的同一模型。Viv 的团队仅通过改变框架就将一个编码代理从前 30 名提升到了前 5 名。模型在训练后会与它们所训练的框架耦合。将它们移入不同的框架，配备更适合你的代码库的工具、更紧凑的提示词和更锐利的反向压力，可以释放原始框架未能充分利用的能力。

这与“只需等待 GPT-6”的叙事相反。**当今模型的能力与你所看到的表现之间的差距，很大程度上是框架的差距。**

## 棘轮：每个错误都变成一条规则

框架工程中最重要的习惯是将代理的错误视为永久信号。不是可以一笑置之的趣事，也不是可以重试的“糟糕运行”。而是信号。

如果代理提交了一个包含被注释掉的测试的 PR，而我不小心合并了它，这就是一个输入。我的 `AGENTS.md` 的下一个版本会说“永远不要注释掉测试；删除它们或修复它们。” 我的预提交钩子的下一个版本会在差异中搜索 `.skip(` 和 `xit(`。我的审查者子代理的下一个版本会将被注释掉的测试标记为阻塞项。

你只在看到实际失败时才添加约束。你只在有能力的模型使它们变得多余时才移除它们。**一个好的 `AGENTS.md` 中的每一行都应该可以追溯到某个具体出错的事情。**

这也是为什么框架工程是一门学科而不是一个框架。适合你的代码库的正确框架是由你的失败历史塑造的。你无法下载它。

## 从行为反向推导

Viv 提出的框架中，当我在实际设计框架时发现最有用的，是从你想要的行为开始，然后推导出能够实现该行为的框架部分。他的模式：*我们想要（或想要修复）的行为 → 帮助模型实现这一目标的框架设计。*

这样推导的好处在于，每个框架组件都有特定的职责。**如果你说不出某个组件存在是为了实现什么行为，那么它可能就不应该存在。**

本节剩余部分大致按照 Viv 的顺序逐一介绍这些组件，并附上我觉得值得借鉴的具体模式。

### 文件系统和 Git：持久状态

文件系统是最基础的原始构件，而且往往因为太普通而被低估。模型只能直接操作上下文中的内容。没有文件系统，你就是在复制粘贴到聊天窗口，那不是一个工作流程。

一旦有了文件系统，代理就获得了读取数据、代码和文档的工作空间；一个卸载中间工作而不是将其保存在上下文中的地方；以及多个代理和人类可以通过共享文件进行协调的表面。在其上添加 Git 可以免费获得版本控制，因此代理可以跟踪进度、回滚错误和分支实验。

大多数其他框架原语最终都会指向文件系统。

### Bash 和代码执行：通用工具

今天主要的代理循环是 ReAct 循环：模型推理，通过工具调用采取行动，观察结果，然后重复。但框架只能执行它有逻辑的工具。你可以尝试为每个可能的动作预先构建一个工具，或者你可以给代理 bash，让它即时构建所需的工具。

Willison 对此的看法是，代理已经擅长 shell 命令；大多数任务可以归结为几个精心选择的 CLI 调用。框架仍然提供有针对性的工具，但 bash 加上代码执行已成为自主解决问题的默认通用策略。这就像教某人使用一个厨房小工具和递给他们一个厨房之间的区别。

### 沙箱和默认工具集

Bash 只有在安全的地方运行才有用。在笔记本电脑上运行代理生成的代码是有风险的，而且单个本地环境无法扩展到许多并行代理。

沙箱为代理提供了隔离的操作环境。代理不是本地执行，而是连接到沙箱来运行代码、检查文件、安装依赖项和验证工作。你可以允许列表命令、强制执行网络隔离、按需启动新环境，并在任务完成后将其拆除。

一个好的沙箱带有良好的默认配置：预安装的语言运行时和包、Git 和测试 CLI、用于 Web 交互的无头浏览器。浏览器、日志、截图和测试运行器让代理能够观察自己的工作并闭合自我验证循环。

模型不配置其执行环境。决定代理在哪里运行、有什么可用以及如何验证其输出，都是框架层面的决策。

### 记忆和搜索：持续学习

模型除了其权重和当前上下文中的内容外，没有额外的知识。无法编辑权重的情况下，添加知识的唯一方法是通过上下文注入。

文件系统再次成为原始构件。框架支持像 `AGENTS.md` 这样的记忆文件标准，这些文件在每次启动时被注入。当代理编辑该文件时，框架会重新加载它，一个会话的知识会带入下一个会话。这是一种粗糙但有效的持续学习形式。

对于训练时不存在的知识（新库版本、当前文档、今天的数据），Web 搜索和像 Context7 这样的 MCP 工具可以弥合知识截止期。这些是值得内置于框架中而不是留给用户的有用原语。

### 对抗上下文腐烂

上下文腐烂是指随着上下文窗口填满，模型在推理和完成任务方面变得更差的现象。上下文是稀缺的，而框架在很大程度上是良好上下文工程的传递机制。

有三种技术反复出现：

**压缩。** 当窗口接近满时，必须有所取舍。让 API 出错不是生产框架的选项，因此框架智能地总结和卸载较旧的上下文，以便代理可以继续工作。

**工具调用卸载。** 大的工具输出（想想 2000 行的日志文件）会混乱上下文而没有增加太多信号。框架保留高于阈值的头部和尾部标记，并将完整输出卸载到文件系统，代理可以在需要时读取。

**渐进式披露的技能。** 在启动时将每个工具和 MCP 加载到上下文中会在代理采取任何行动之前就降低性能。技能让框架仅在任务实际需要时才显示指令和工具。

Anthropic 的框架文章为真正长时间的工作增加了一种技术：完全上下文重置，框架拆除会话并从紧凑的交接文件中重建它。他们明确表示*仅靠压缩不足以应对长时间任务*；有时你需要用一个结构化的简报重新开始。这更接近人类如何让新工程师入职，而不是我们通常对“记忆”的理解。

### 长期执行：Ralph 循环、规划、验证

自主长期工作是圣杯，也是最难做对的事情。当今的模型存在过早停止、复杂问题分解能力差，以及工作跨越多个上下文窗口时失去连贯性的问题。框架必须围绕所有这些进行设计。

我之前在[自我改进代理](https://addyosmani.com/blog/self-improving-agents/)和我的[2026 趋势文章](https://beyond.addy.ie/2026-trends/)中写过像 Ralph 循环这样的自主编码循环，但在这个框架中值得重述：一个钩子拦截模型尝试退出的行为，并将原始提示词重新注入一个新的上下文窗口，迫使代理继续朝着完成目标前进。每次迭代都是干净的开始，但通过文件系统读取前一次的状态。这是一个令人惊讶的简单技巧，可以将单会话代理转变为多会话代理，而且这是你永远不会从“只需使用更智能的模型”中推导出来的原语。

**规划**是指模型将目标分解为一系列步骤，通常分解到磁盘上的一个规划文件中。框架通过提示词和关于如何使用规划文件的提醒来支持这一点。在每个步骤之后，代理通过自我验证检查其工作：钩子运行预定义的测试套件，并将失败循环回模型并附上错误文本，或者模型根据明确的标准审查自己的输出。

**规划器 / 生成器 / 评估器分离。** Anthropic 的长期运行框架工作明确指出，将生成与评估分离到不同的代理中优于自我评估，因为代理在评估自己的工作时总是倾向于给出正面评价。这是散文领域的 GAN。相关的模式是**冲刺契约**，其中生成器和评估器在代码编写之前就协商好“完成”的实际含义。在我自己的工作流程中，在开始之前写下完成条件比任何我做过提示词更改更能捕获范围蔓延。

### 钩子：执行层

钩子将“我告诉代理做 X”与“系统强制执行 X”区分开来。

钩子是在特定生命周期点运行的脚本：在工具调用之前、文件编辑之后、提交之前、会话启动时。它们是放置代理永远不应该忘记但经常忘记的事情的正确位置。在每次编辑后运行类型检查、代码检查和测试并暴露失败。阻止破坏性 bash（`rm -rf`、`git push --force`、`DROP TABLE`）。在打开 PR 或推送到 `main` 之前要求批准。在写入时自动格式化，这样代理就不会在空白字符上浪费标记。

HumanLayer 强调并且我也逐渐同意的原则是：**成功是沉默的，失败是冗长的。** 如果类型检查通过，代理什么也听不到。如果失败，错误文本被注入循环，代理自我纠正。这使得反馈循环在常见情况下几乎免费，并且在出现问题时直接可操作。

### `AGENTS.md` 和工具选择

仓库根目录下的扁平 Markdown 规则手册仍然是单一最高杠杆的配置点，因为它每轮都会进入系统提示词。约定放在这里：包管理器、测试框架、格式化、“永远不要碰 `/legacy`”、“始终使用我们的日志记录器”。两个来之不易的经验教训：

保持简短。HumanLayer 将其保持在 60 行以下。每一行都在争夺注意力，规则越多，每条规则的重要性就越低。**飞行员的检查清单，而不是风格指南。**

每一行都要有依据。规则应追溯到特定的过去失败或硬性外部约束。如果不是，那就是噪音。使用棘轮，而不是头脑风暴。

同样的纪律也适用于工具。每个工具的名称、描述和模式都会在每个请求中被印入提示词。十个有针对性的工具胜过五十个重叠的工具，因为模型可以在脑海中记住菜单。HumanLayer 还指出了一个真正的安全问题：工具描述填充了提示词，因此你安装的任何 MCP 服务器都是模型会读取的可信文本。一个草率或恶意的 MCP 可以在你输入任何内容之前对你的代理进行提示注入。

### 这在生产中是什么样子

我所见过的成熟框架最清晰的公开图景是 Fareed Khan（估计）对 [Claude Code 架构](https://levelup.gitconnected.com/building-claude-code-with-harness-engineering-d2e8c0da85f0)的分解，值得花一分钟仔细看看这个图。

前一节中的几乎所有概念都作为命名组件出现在这个图上。上下文注入是知识层。循环状态存在于记忆存储和工作树隔离器中。破坏性动作钩子位于权限门之后。子代理上下文防火墙是整个多代理层。工具分发注册表是 MCP 服务器和 bash 都插入的地方。Khan 的论点与 Viv 相同，只是通过一个已发布的产品来阐述：**Claude Code 的发展轨迹至少与底层模型一样多地取决于框架。**

## 框架不会缩小，它们会移动

Anthropic 文章中的一个较好观察是，随着模型的改进，有趣的框架组合空间不会缩小。它会移动。

天真的说法是，更好的模型使框架变得过时。如果模型可以规划，就不需要规划器。如果模型在长时间范围内保持连贯，就不需要上下文重置。是的，Opus 4.6 在很大程度上消除了上下文焦虑失败模式（Sonnet 4.5 曾经在接近其认为的上下文限制时过早结束工作），这意味着我六个月前编写的整类焦虑缓解脚手架现在已经是死代码。

但天花板随着模型移动了。以前无法触及的任务现在可以尝试了，而且它们有自己的失败模式。焦虑脚手架消失了，取而代之的是你需要一个多天记忆策略，或者一个协调三个专门代理的框架，或者用于评估生成 UI 设计质量的评估器。假设发生了变化，编码这些假设的脚手架也随之变化。

Anthropic 清晰地表述：*“框架中的每个组件都编码了一个关于模型自己无法完成什么的假设。”* 当模型在某方面变得更好时，该组件就不再承担任何负载，应该被移除。当模型解锁了新能力时，需要新的脚手架来达到新的天花板。

### 模型-框架训练循环

另一件正在发生的事情，Viv 明确指出了，是框架设计和模型训练之间的反馈循环。

今天的代理产品是在框架参与循环的情况下进行后训练的。模型会特别擅长框架设计者认为它应该擅长的动作：文件系统操作、bash、规划、子代理调度。这就是为什么 Opus 4.6 在 Claude Code 内部与在其他人的框架内部感觉不同，也是为什么改变工具的逻辑有时会导致奇怪的性能倒退。一个真正通用的模型不会在意你使用 `apply_patch` 还是 `str_replace`，但联合训练会造成过拟合。

实际影响是双重的。**框架是一个活的系统，而不是一个你设置一次就完事的配置文件。** 而且，“最佳”框架不一定是模型在其内部训练的那个；它是为你的任务设计的那个。Viv 的 Terminal Bench 从前 30 名跃升至前 5 名是我见过的最清晰的证据。

## 框架即服务

Viv 的另一个贡献是 **[HaaS](https://www.vtrivedy.com/posts/claude-code-sdk-haas-harness-as-a-service)** 框架：框架即服务。观察结果是，我们正在从基于 LLM API（给你一个补全）构建，转向基于框架 API（给你一个运行时）构建。Claude Agent SDK、Codex SDK 和 OpenAI Agents SDK 都指向同一个方向。你开箱即用地获得循环、工具、上下文管理、钩子和沙箱原语，然后你进行定制。

这种转变很重要，因为过去的默认路径是：构建你自己的循环，连接你自己的工具调用，处理你自己的对话状态，发明你自己的审批流程。现在的默认路径是：选择一个框架框架，沿着四个支柱（系统提示词、工具、上下文、子代理）进行配置，然后将剩余的努力投入到领域特定的提示词和工具设计中。

这就是使“技能问题”变得可处理的原因。你不是在每次出错时都从头重建一个代理。你是在调整一个已经良好分解的配置面。

Viv 对此的表述也是从混乱开始的最佳理由：*“好的代理构建是一个迭代的练习。如果你没有一个 v0.1，你就无法进行迭代。”*

## 未来的发展方向

并列看看顶级的编码代理（Claude Code、Cursor、Codex、Aider、Cline），**它们彼此之间的相似程度超过了它们底层模型之间的相似程度。** 模型是不同的。框架模式正在趋同。我不认为这是偶然的。这是整个行业在慢慢寻找那些将生成模型转变为能够交付产品的东西的承重脚手架组件。

Viv 对开放问题的框架是我觉得最令人兴奋的：在共享代码库上协调许多并行工作的代理；分析自身追踪以识别和修复框架级别失败模式的代理；能够为给定任务动态即时组装正确工具和上下文，而不是在启动时预配置的框架。

最后一个，尤其感觉像是**框架从静态配置转变为更接近编译器的东西。**
