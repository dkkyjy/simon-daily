我一直在观察开发者门户中发生的一些事情，我认为这值得更多关注。

一位工程师打开Claude Code，要求它实现一个规范，然后按下回车键。代理获取了您的一些文档。它可能抓取了一些所需内容，将其解析为原始文本，剥离HTML，计算token数量，然后要么将其用作上下文——要么因为token数量超过其上下文窗口而静默丢弃。

您的分析工具没有记录任何有用信息。滚动深度为零。页面停留时间为400毫秒。没有链接点击，没有教程完成，没有UI交互。您优化多年的漏斗显示为空。

但代理确实在那里。它读取了您的文档。而根据这些文档的结构方式，它要么成功完成了任务——要么因为内容token过多、结构不佳或被配置错误的`robots.txt`阻止而产生了幻觉。

我开始将应对这一问题的学科称为**代理引擎优化**。

## 什么是代理引擎优化？

**代理引擎优化（AEO）** 是一种结构化、格式化并提供技术内容，使AI编码代理能够实际使用——而不仅仅是人类读者——的实践。

我反复使用的类比是SEO。我们花了多年时间学习如何为搜索引擎爬虫和人类点击模式进行优化。AEO是同样的理念，但针对不同的消费者：自主获取、解析和推理您内容的AI代理。

重要的事项实际上相当具体：

* **可发现性** - 代理能否在不渲染JavaScript的情况下找到您的文档？
* **可解析性** - 内容是否无需视觉布局解释即可机器读取？
* **Token效率** - 内容是否适合典型的代理上下文窗口而无需截断？
* **能力信号** - 文档是否告诉代理您的API能*做什么*，而不仅仅是如何调用它？
* **访问控制** - 您的`robots.txt`是否实际上允许AI流量通过？

如果其中任何一项失败，代理要么完全跳过您的内容，要么产生细微错误的输出。棘手的是您可能永远不会知道，因为没有分析事件触发。

## AI代理如何实际读取您的文档

值得在此阐明行为差异，因为它比我最初预期的要大。

### 人类模式

人类开发者访问您的文档首页。他们导航到相关部分。他们浏览标题，阅读几段，可能在交互式控制台中运行代码示例，点击两三个内部链接，并在会话中花费4-8分钟。您的分析工具捕获了所有内容。

### 代理模式

一篇[最近的研究论文](https://arxiv.org/html/2604.02544v1)（使用AI编码代理的开发者体验）研究了九个主要AI编码代理——包括Claude Code、Cursor、Cline、Aider、VS Code和Junie——获取开发者文档时的HTTP流量。研究结果相当惊人。

代理通常将多页导航压缩为一到两个HTTP请求。在人类需要花费数分钟点击浏览您的文档层级的地方，代理发出单个`GET`请求，接收完整页面，然后继续。整个"用户旅程"的概念崩溃为单个服务器端事件。

实际后果：每个客户端分析事件——滚动深度、页面停留时间、按钮点击、教程完成、链接跟踪、表单交互——都变得不可见。代理完全绕过了所有这些。

### AI流量的指纹

该研究还识别出独特的行为特征，您可以用它们来识别服务器日志中的AI代理流量：

| 代理 | HTTP运行时 | 预取行为 | 特征 |
| --- | --- | --- | --- |
| Aider | 无头Chromium (Playwright) | 按需GET | 完整Mozilla/Safari用户代理 |
| Claude Code | Node.js / Axios | 按需GET | `axios/1.8.4` |
| Cline | curl | GET + OpenAPI/Swagger扫描 | `curl/8.4.0` |
| Cursor | Node.js / got | HEAD探测 → GET | got (sindresorhus/got) |
| Junie | curl | 顺序多页GET | `curl/8.4.0` |
| OpenCode | 无头Chromium (Playwright) | 按需GET | 完整Mozilla/Safari用户代理 |
| VS Code | Electron / Chromium | 按需GET | Chromium风格带Electron标记 |
| Windsurf | Go / Colly | 按需GET | `colly` |

除了编码代理之外，AI助手网络服务（ChatGPT、Claude、Google Gemini、Perplexity）在用户分享聊天界面中的URL时也会生成独特的指纹——触发它们自己的服务器端获取。

一旦知道要寻找什么，您就可以开始在分析工具中分割AI代理流量。我惊讶于我自己日志中已经存在多少这样的流量。

## Token问题：您的文档可能对代理不可见

这可能是整个图景中最被低估的部分：**Token经济学**。

代理没有无限的上下文。大多数具有100K–200K token之间的实际限制，而上下文管理是每个任务中的活跃约束。该论文强调了一个具体例子：Cisco Secure Firewall Management Center REST API快速入门指南（版本10.0）达到了**193,217个token**——近718,000个字符。单个文档威胁要消耗或超过大多数代理的整个可用上下文窗口。

当代理遇到太长的文档时，可能发生几件事——没有一件是好的：

* 它可能静默截断，切断关键信息
* 它可能完全跳过文档，转而选择更短的内容
* 它可能尝试分块，这增加了延迟和错误面
* 它可能回退到参数化知识——即，编造一些内容

我认为这意味着**token数量现在是一级文档指标**。如果您没有跟踪文档页面的token数量，您就错过了代理实际用来决定是否尝试阅读您内容的信号。

### 实际Token目标

以下内容可作为粗略指南：

* **快速入门/入门页面**：< 15,000个token
* **单个API参考页面**：< 25,000个token
* **完整API参考**：按资源/端点分块，而非按产品
* **概念指南**：< 20,000个token；链接到详细信息而非嵌入

## AEO堆栈：实际要构建什么

AEO不是单一事物——它是一组分层信号和标准。我一直在将其视为一个堆栈，从基础到表面：

### 第一层：访问控制（`robots.txt`）

这是代理的第一站。在获取内容之前，许多代理检查`robots.txt`以确定它们被允许访问什么。

一个配置错误的`robots.txt`阻止已知的AI爬虫，将静默地完全拒绝代理访问您的文档。没有流量，没有错误，没有任何迹象表明出了问题。我看到过团队因此受挫，他们不知道自己的文档对代理不可见。

实际步骤：

* 审计您的`robots.txt`，检查是否有针对AI代理用户代理的意外阻止
* 考虑显式允许已知的AI代理模式（Anthropic、OpenAI、Google、Perplexity爬虫）
* 如果您需要更精细的控制，请查看`agent-permissions.json`——一个新兴规范，允许您声明式地指定允许哪些自动化交互、速率限制、首选API端点等

### 第二层：通过`llms.txt`进行发现

即使代理可以访问您的内容，它仍然需要找到*正确的*内容。这就是`llms.txt`的用武之地。

我将`llms.txt`视为AI代理的站点地图。它是一个平面的、Markdown格式的文件，托管在`yourdomain.com/llms.txt`，提供您的文档的结构化目录——包括描述，以便代理无需爬取您的整个网站就能确定什么相关。

一个格式良好的`llms.txt`看起来像这样：

```
# YourProduct文档

## 入门
- [快速入门指南](/docs/quickstart)：5分钟内安装并发出您的第一个API调用
- [认证](/docs/auth)：OAuth 2.0和API密钥认证模式
- [核心概念](/docs/concepts)：数据模型、实体和术语

## API参考
- [REST API概述](/docs/api)：基础URL、版本控制、分页、错误代码
- [用户API](/docs/api/users)：用户管理的CRUD操作（12K token）
- [事件API](/docs/api/events)：事件流和webhook配置（8K token）

## MCP集成
- [MCP服务器](/docs/mcp)：用于直接代理集成的模型上下文协议服务器

```

好的`llms.txt`的特点：

* 描述告诉代理它将*找到*什么，而不仅仅是页面叫什么
* 在有用处提供每页的token数量（以便代理可以做出明智的上下文决策）
* 按任务组织，而非按产品层级
* 自身保持在5,000个token以下（它不应该仅仅作为索引就耗尽预算）

### 第三层：通过`skill.md`进行能力信号

`llms.txt`告诉代理东西在哪里。`skill.md`告诉它们您的产品实际能*做什么*。

这是一个我认为比最初看起来更重要的区别。代理不必从散文式文档中推断能力，`skill.md`声明式地呈现它们——将意图映射到端点和资源。

一个认证服务的`skill.md`可能看起来像这样：

```
---
name: auth-service
description: 处理用户认证、OAuth 2.0流程和会话管理
---

## 我能完成什么
- 通过OAuth 2.0认证用户（授权码、客户端凭证、PKCE）
- 签发和验证JWT token
- 管理用户会话和刷新token轮换
- 与SSO提供商集成（SAML、OIDC）

## 所需输入
- 客户端ID和客户端密钥（来自开发者控制台）
- 重定向URI（必须预先注册）
- 请求的范围（read:user、write:data、admin）

## 约束
- 速率限制：每个应用每分钟1000个token请求
- Token过期：访问token 1小时，刷新token 30天
- 公共客户端需要PKCE

## 关键文档
- [OAuth 2.0指南](/docs/oauth)：包含代码示例的完整流程演练
- [Token参考](/docs/tokens)：Token结构、声明、验证
- [Postman集合](/docs/postman)：即用型请求模板

```

这就是让代理能够做出有意义决策的关键——不仅仅是获取文档，而是在花费上下文预算进行完整阅读之前，理解您的API是否能够满足用户的意图。

### 第四层：为代理解析进行内容格式化

即使有完美的发现和能力信号，实际内容也需要是代理可读的。我发现有几件事很重要：

**提供Markdown，而不仅仅是HTML。** 许多文档平台允许您通过在URL后附加`.md`或通过查询参数来访问原始Markdown。使这一点可被发现。代理处理Markdown的token开销远低于HTML（没有标签噪音，没有导航chrome，没有页脚冗余）。

**为扫描而非阅读而结构化。** 代理不线性阅读——它们解析结构：

* 使用一致的标题层级（H1 → H2 → H3，不要跳跃）
* 每个部分以结果开头，而非背景
* 将代码示例紧跟在它们所说明的主张之后
* 对参数引用使用表格——它们比散文式列表压缩得更好

**消除导航噪音。** HTML中出现的侧边栏、面包屑和页脚链接在Markdown/文本中只是噪音。将它们排除在可解析的内容路径之外。

**前置有用的内容。** 任何页面的前500个token应回答：这是什么，它能做什么，以及我需要什么才能开始。代理对前言的耐心有限。

### 第五层：Token展示

这一层比听起来简单，但出人意料地具有高杠杆作用：在您的文档页面上展示token数量。理想情况下，在`llms.txt`索引和页面本身（作为元数据或页面标题）都展示。

这为代理提供了做出明智决策所需的信息：

* "这个页面是8K token——我可以完全将其包含在上下文中"
* "这个页面是150K token——我应该只获取相关部分"
* "这个页面超过了我的上下文窗口——我将使用llms.txt中的摘要"

实现很简单：在服务器端计算字符数，除以约4得到粗略的token估计，然后作为meta标签或HTTP响应头公开。

### 第六层："为AI复制"

这更像是一个UX桥梁而非基础设施层，但我认为值得包含：**为AI复制**按钮。

当开发者在IDE内使用AI助手工作并希望将文档作为上下文包含时，他们目前从渲染的HTML中复制粘贴——这包括导航噪音、页脚等所有内容。一个"为AI复制"按钮，将干净的Markdown复制到剪贴板，是一件小事，但能显著提高代理接收到的上下文质量。

Anthropic、Cloudflare等公司已经推出了此功能的变体。它投入低，信号强。

## AGENTS.md：新兴的默认文件

有一件事特别值得指出：`AGENTS.md`。

正如`README.md`成为人类开发者探索仓库的默认入口点一样，`AGENTS.md`正在成为AI代理的入口点。当编码代理打开一个项目时，它会在根目录中查找`AGENTS.md`，并将其指令拉入每个后续任务。

我[在其他地方写过这个](https://addyosmani.com/blog/agents-md/)，但简而言之，一个好的`AGENTS.md`包括：

* 项目结构和关键文件位置
* 相关API或服务文档的直接链接
* 可用的开发沙箱和测试环境
* 代理应了解的速率限制和约束
* 代码库的首选模式和约定
* 如果可用，MCP服务器的链接

Cisco DevNet已经将其作为其开源项目GitHub模板中的默认文件——新创建的项目附带一个`AGENTS.md`，预填充了项目特定内容、OpenAPI文档链接、DevNet沙箱和测试环境。

## 对开发者体验的更广泛影响

我想退一步思考，因为我认为AEO指向了比技术清单更大的东西。

在网络历史的大部分时间里，开发者门户都是围绕人类认知模式设计的：渐进式披露、视觉层次、交互式示例、引导式教程。所有这些都假设人类在每个步骤中都在循环中。

在代理密集的世界中，这些假设中的许多都崩溃了：

* **视觉层次无关紧要** - 代理阅读文本，而非布局
* **渐进式披露成为障碍** - 代理想要一次性获得所有内容
* **交互式示例失去价值** - 除非有静态/API等效物
* **用户旅程崩溃** - 一个多章节的教程变成了一次上下文加载

这并不意味着以人为中心的设计不再重要。人类仍然阅读文档。但他们越来越多地在*AI助手的上下文中*阅读——这意味着代理通常是直接消费者，即使人类是最终受益者。

未来最好的文档可能将需要同时服务两个受众：对人类来说可扫描且结构良好，对代理来说机器可读且token高效。

## AEO审计清单

以下是我今天评估文档网站的代理就绪性时会检查的内容：

**发现**

* `llms.txt`存在于根目录，包含所有文档的结构化索引
* `robots.txt`没有意外阻止已知的AI代理用户代理
* `agent-permissions.json`定义了自动化客户端的访问规则
* `AGENTS.md`存在于代码仓库中，链接到相关文档

**内容结构**

* 文档页面可作为干净的Markdown使用（不仅仅是渲染的HTML）
* 每个页面在前200个词中以清晰的结果陈述开头
* 标题一致且层级正确
* 代码示例紧跟在它们的散文描述之后
* 参数引用使用表格，而非嵌套的散文

**Token经济学**

* 每个文档页面的token数量被跟踪
* 没有单个页面超过30,000个token而没有分块策略
* 关键页面的token数量在`llms.txt`中公开
* token数量可作为页面元数据使用（meta标签或HTTP头）

**能力信号**

* `skill.md`文件描述每个服务/API能*做什么*，而不仅仅是如何调用它
* 每个技能包括：能力、所需输入、约束、关键文档链接
* MCP服务器可用于直接代理集成（如适用）

**分析**

* AI引荐来源在Web分析中被分段
* 服务器日志被监控以查找已知的AI代理HTTP指纹
* 建立了AI与人类流量比率的基线

**UX桥梁**

* 文档页面上有"为AI复制"按钮
* Markdown源可通过URL约定访问（例如，附加`.md`）

**工具**

为了帮助自动化其中一些检查，我已发布了[agentic-seo](https://github.com/addyosmani/agentic-seo)——一个轻量级审计工具，扫描您的网站以寻找AEO机会。它检查`llms.txt`、`robots.txt`代理阻止、token数量、Markdown可用性等。将其视为Lighthouse，但针对代理就绪性。

## 从哪里开始

如果您正在查看这个清单并想知道从哪里开始，以下是我推荐的顺序：

1. **审计您的`robots.txt`** - 十分钟的工作，防止静默代理锁定
2. **添加`llms.txt`** - 几个小时，立即获得可发现性收益
3. **测量并展示token数量** - 一个周末的项目，具有高杠杆作用
4. **为您的前3个API编写`skill.md`** - 从代理最可能触及的内容开始

## 总结

SEO教会我们，好的内容是不够的——你必须以符合时代实际流量模式的方式使其可被发现。我认为AEO是同样的教训，只是针对不同的消费者。

AI编码代理已经是文档流量中重要且不断增长的一部分。它们的行为与人类读者根本不同。而大多数开发者门户尚未为它们构建。

早期行动的团队可能会拥有真正的优势：他们的API将成为代理推荐、成功集成并反复使用的API。而不行动的团队将看到文档质量与实际代理任务成功之间的差距不断扩大——这是一个难以调试的静默失败模式。

好消息是，为代理构建通常也会使文档对人类更好。这些学科的重叠多于分歧。
