# 长时间运行的智能体

            **日期：** 2026-04-28 00:00 UTC
            **链接：** https://addyosmani.com/blog/long-running-agents/

            ---

            **一个长时间运行的AI智能体可以在数小时、数天或数周内持续取得进展。它可以跨越多个上下文窗口和沙盒执行此操作，从故障中恢复，留下结构化的工件，并在中断处继续执行。**

---

两年来，“AI智能体”的主流形象一直是一个带有巧妙循环的聊天窗口。你输入一个目标，智能体调用一些工具，你看着令牌流经过，当工作耗尽耐心或上下文窗口填满时，你停止观看。这种范式让我们走了很远，但它有一个天花板。模型会遗忘。它会在任务未完成时宣布“任务完成”。它会重新引入它在九轮之前修复过的一个错误。整个结构都围绕着单次会话构建。

长时间运行的智能体是接下来的发展方向。这个想法很容易表述：一个智能体能够在多个会话和多个沙盒中持续朝着一个目标取得进展，可能持续数天或数周，同时保持工作空间足够整洁，以便下一个会话可以从上一个会话中断的地方继续。工程实现则更难。你必须以一种不仅仅是掩盖问题的方式解决持久性、恢复和验证问题。你必须构建一个存在于模型上下文窗口之外的状态层，并且你必须设计会话之间的交接，以便智能体在醒来并发现自己处于一个具有不同上下文窗口的不同沙盒中时不会迷失方向。

这篇文章是我试图阐述哪些方面发生了变化，谁在推动这一进展，以及工程师今天如何在不从头开始编写所有内容的情况下使用长时间运行的智能体。

---

## “长时间运行”的实际含义

在实践中，“长时间运行”至少被用来指代三种不同的事物，将它们区分开来会有所帮助。

**长视界推理。** 智能体必须规划并执行许多相互依赖的步骤。这主要是一个模型质量的问题：连贯性、规划能力、从十步前的错误转弯中恢复的能力。METR 一直在使用他们的*时间视界*指标来追踪这一点，该指标估算前沿模型能够以 50% 的可靠性完成的任务时长。主要发现是，自 2019 年以来，该指标大约[每七个月翻一番](https://metr.org/time-horizons/)，而今年早些时候他们的 [TH1.1 更新](https://metr.org/blog/2026-1-29-time-horizon-1-1/)将评估集中 8 小时以上任务的数量翻了一番。**如果这条曲线保持下去，前沿智能体将在 2028 年之前完成以天为规模的任务，在 2034 年之前完成以年为规模的任务。**

**长时间运行的执行。** 智能体的*进程*运行数小时或数天。可能是一个编码任务，可能是一次研究扫描，也可能是一个 24/7 的监控服务。模型可能在一次运行中被调用数千次。这主要是一个*框架*的故事，也是这篇文章主要讨论的内容。

**持久的能动性。** 智能体拥有超越任何单个任务的身份。它积累记忆，学习用户偏好，并且始终可用。这就是 [Memory Bank](https://docs.cloud.google.com/agent-builder/agent-engine/memory-bank/overview) 风格的长时间运行。

在实践中，这三者会相互融合。一个真正的生产级智能体会在*由*持久能动性*支撑的*长时间运行执行*内部*进行长视界推理。但每个方面的工程问题都不同，解决这些问题的产品也不同。

## 为什么这很重要

我认为这项工作现在非常重要，有两个原因。

第一个是经济上可委托事项的阶段性变化。一个运行十分钟的智能体可以回答问题、总结文档、修复一个小错误。一个运行十小时的智能体可以负责整个功能特性、完成积压了六个季度的迁移工作，或者进行那种过去需要初级分析师才能完成的通宵研究扫描。Anthropic 去年秋天在其 [Claude Sonnet 公告](https://www.anthropic.com/news/claude-sonnet-4-5)中给出了具体数字：内部测试中超过 30 小时的自主编码，包括[一次运行](https://venturebeat.com/ai/anthropics-new-claude-can-code-for-30-hours-think-of-it-as-your-ai-coworker)生成了一个 11,000 行的 Slack 风格应用。**这已经超过了“我应该委托这个吗？”这个问题的答案不再显而易见的阈值。**

第二个是持久性改变了智能体的*本质*。一个无状态智能体回答你的问题然后消失。一个长时间运行的智能体会积累上下文：上周哪个竞争对手朝哪个方向移动了，周二哪个测试两次不稳定，你通常说的“仪表盘”是什么意思。Anthropic 的 [Project Vend](https://www.anthropic.com/research/project-vend-1) 是这方面最公开的早期演示。他们让一个 Claude 实例实际运营了一个办公室自动售货业务一个月，管理库存、设定价格、与供应商沟通。它以有启发性的方式失败了，并且[第二阶段](https://www.anthropic.com/research/project-vend-2)运行得好得多，但重点不在于盈利能力。重点在于观察当一个智能体需要跨越数周（而不是数轮）来维持身份时，会出现哪些奇怪的连贯性问题。

这些问题正是现在每个构建生产级智能体的团队都会遇到的。

## 每个长时间运行的智能体都会遇到的三个障碍

今年我读过的几乎所有文章中都出现了三个障碍。

**有限的上下文。** 即使是一个 100 万个令牌的窗口也会被填满。而且[上下文腐烂](https://addyosmani.com/blog/agent-harness-engineering/)，即随着窗口变满模型性能的稳定下降，在达到硬限制之前就已经开始。一个 24 小时的运行无法适应该领域路线图上的任何上下文窗口。必须有所妥协。

**没有持久状态。** 新的会话从空白开始。Anthropic 在其[科学计算文章](https://www.anthropic.com/research/long-running-Claude)中的表述是我见过最清晰的：*“想象一个软件项目，由轮班工作的工程师组成，每位新工程师到来时对上一班次发生的事情毫无记忆。”* 如果没有明确的持久性方案，每一次轮班交接都是一场生产力灾难。

**没有自我验证。** 模型在评估自己工作时可靠地偏向积极。当被问到“你完成了吗？”时，它们回答“是”的频率高于应有的水平。如果没有一个独立的信号表明工作达到了标准，你就会得到一个充满信心地交付了 30% 完成度的智能体。

长时间运行的智能体设计主要是对这些三个问题的回答。**各大实验室已经收敛到类似的答案形状，但具有非常不同的表面区域。**

## Ralph 循环：长时间运行智能体较简单的实践者版本之一

**Ralph 循环**（有时称为 Ralph Wiggum 技术）是长时间运行智能体的“较简单”实践者版本之一，由 [Geoffrey Huntley](https://ghuntley.com/ralph/) 和 [Ryan Carson](https://github.com/snarktank/ralph) 推广。参考实现[本质上是一个 bash 脚本](https://ghuntley.com/ralph/)，它循环执行：

1.  从列表（`prd.json` 或等效文件）中选择下一个未完成的任务。
2.  使用任务、相关上下文和任何持久性笔记构建提示。
3.  调用智能体。
4.  运行测试或其他检查。
5.  将发生的事情追加到 `progress.txt`。
6.  更新任务列表（已完成、失败、受阻）。
7.  返回步骤 1。

它有效的原因与下面任何框架有效的原因相同：状态存在于智能体的上下文之外。`prd.json` 是计划，`progress.txt` 是实验笔记，`AGENTS.md` 是滚动规则手册。**智能体本身是失忆的，但文件系统不是。** 每次迭代都重新开始，并从磁盘读取足够的状态以继续。Carson 的 [Compound Product](https://github.com/snarktank/compound-product) 通过链接多个循环（一个读取每日报告的分析循环，一个发出 PRD 的规划循环，一个编写代码的执行循环）扩展了这个想法，这大致相当于 Anthropic 独立得出的规划器-生成器-评估器三元组的开源版本。

我在[自我改进的智能体](https://addyosmani.com/blog/self-improving-agents/)中深入探讨了所有这些：任务列表结构、进度文件、QA 门控、监控、你实际会遇到的故障模式。简而言之，你可以用一个 bash 脚本和一个 JSON 文件在一个晚上构建一个可工作的长时间运行智能体。Google 和 Anthropic 已经产品化的大部分工作，就是使这种模式在规模上可恢复、安全且可观察。

下面的大实验室故事是为这种生产就绪性买单的不同方式。

## Anthropic：框架，然后是大脑/手/会话分离

Anthropic 在工程方面一直最为公开。有两篇文章值得从头到尾阅读。

第一篇是[“长时间运行智能体的有效框架”](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)，其中阐述了一个用于自主全栈开发的双智能体框架。一个**初始化智能体**在项目开始时运行一次，用于设置环境、将提示扩展为结构化的 `feature-list.json`，并编写一个 `init.sh` 供未来会话在启动时运行。然后，一个**编码智能体**被反复唤醒，每个会话被要求在一个特性上取得增量进展、运行测试、留下 `claude-progress.txt` 笔记并提交。一个测试棘轮（*“移除或编辑测试是不可接受的，因为这可能导致功能缺失或出现错误”*）被放置在提示中，以阻止智能体删除失败测试以使其“通过”这一非常常见的故障。[InfoQ 的文章](https://www.infoq.com/news/2026/04/anthropic-three-agent-harness-ai/)将其扩展为规划器、生成器和评估器三元组，其逻辑与将生成与评估分开相同，因为模型对自己工作的评分过于宽松。

第二篇是[“扩展托管智能体：将大脑与手解耦”](https://www.anthropic.com/engineering/managed-agents)，这是 [Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview)（Anthropic 的托管运行时，于 4 月初推出）背后的架构文章。其论点是，智能体有三个应该独立可替换的组件。大脑是模型和调用它的框架循环。手是沙盒化的、短暂的执行环境，工具在其中实际运行。会话是一个仅追加的事件日志，记录每一个思考、工具调用和观察结果。

这听起来很抽象，但并非如此。Anthropic 的表述：*“框架中的每个组件都编码了一个关于模型自身无法完成什么的假设。”* 当你将它们耦合在一起时，一个过时的假设（例如，模型过去需要一个明确的规划器，而现在原生地进行规划）意味着整个系统必须一次性改变。当你将它们解耦时，框架变得无状态，沙盒变成*可替代的，而非宠物*，大脑崩溃不会丢失运行。一个新的容器调用 `wake(sessionId)` 并从日志中重建状态。他们报告称，[仅凭能够在沙盒准备好之前开始推理，首次令牌生成时间在 p50 下降了约 60%，在 p95 下降了超过 90%](https://www.anthropic.com/engineering/managed-agents)。

**会话即事件日志的想法是大多数团队低估的部分。** 正是这一点使得长时间运行的智能体可恢复。没有它，容器故障就是会话故障，你会在调试一个过时的快照。有了它，智能体的记忆是一个可查询的工件，存在于任何碰巧正在运行的进程之外。

对于科学计算人群，Anthropic 的[长时间运行 Claude 文章](https://www.anthropic.com/research/long-running-Claude)将所有这些简化为一个更简单的堆栈：`CLAUDE.md` 作为智能体在学习时编辑的实时计划，`CHANGELOG.md` 作为可移植的实验笔记，`tmux` 加 `SLURM` 加 `git` 作为执行和协调层，以及 **Ralph 循环**，一个 `for` 循环，每当智能体声称完成时将其踢回上下文并询问它是否*真的*完成了。他们的旗舰案例研究是 Claude Opus 4.6 在几天内构建的一个玻尔兹曼求解器，达到了与参考 CLASS 实现低于百分之一的一致性。数月到数年的研究人员时间，被压缩了。

所有三篇文章中的模式相同：一个明确的计划文件，一个明确的进度文件，会话之间的结构化交接，将生成与评估分开，以及一个拒绝让智能体提前停止的循环。

## Cursor：规划器、工作者、裁判

[Cursor 的“扩展长时间运行的自主编码”](https://cursor.com/blog/scaling-agents)是今年另一篇必读文章。他们遇到了 Anthropic 大多掩盖的障碍。

他们的第一次尝试是一个扁平协调模型：同等地位的智能体使用锁写入共享文件。这成为了一个瓶颈，并使智能体变得规避风险，在提交之前不断翻来覆去。他们的第二次尝试用乐观并发控制取代了锁，这消除了瓶颈，但没有解决协调问题。第三种设计是现在生产环境中运行的设计，他们描述为解决大部分问题的设计：

*   **规划器** 持续探索代码库并发出任务。它们可以递归地生成子规划器。
*   **工作者** 是专注的执行者。它们不相互协调，也不关心大局。
*   **裁判** 决定迭代何时完成以及何时重新启动。

文章中有两点很突出。一：*“系统行为的很大一部分归结为我们如何提示智能体”*，而不是框架或模型。二：不同的模型被分配到不同的角色。他们报告发现，GPT 模型在*扩展自主工作*方面比 Opus 更好，特别是因为 Opus 倾向于提前停止并走捷径。**相同的任务，不同的角色，不同的模型。** 这种匹配正在成为设计表面的一部分。

这与 [Composer 2](https://cursor.com/blog/composer)（他们的专有前沿编码模型，随 [Cursor 3](https://cursor.com/changelog/2-0) 一起发布）以及他们的**后台云智能体**配对：在 Anysphere 的云基础设施上运行，而不是在你的笔记本电脑上运行的长时间任务。八小时的重构和代码库范围的迁移在合上笔记本盖子后仍然存活。你可以在本地启动一个任务，当你意识到它将需要 30 分钟时点击*在云中运行*，然后稍后从你的手机重新连接。每个智能体在一个隔离的 git 工作树中运行，并通过 PR 合并回来。本地和远程之间的交接是大多数团队尚未解决的问题，而 Cursor 的赌注是它必须成为自己的产品表面。

最终形状与 Anthropic 的接近：角色被拆分，会话是持久的，裁判位于工作者旁边，长时间任务在云沙盒中运行，以 git 作为协调基础。

## Google：Agent Platform 上的长时间运行智能体

两周前，Google 在 [Cloud Next ‘26](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform) 上的公告将 Vertex AI 并入 **Gemini Enterprise Agent Platform**，并将长时间运行智能体变成了一个命名产品，带有命名的 SLA。

对于本文而言，重要的部分包括：

*   **Agent Runtime** 支持*“自主运行数天”*的智能体，具有亚秒级冷启动和按需沙盒配置。发布文章中的示例用例是一个需要一周时间完成的销售勘探序列，这大致是合适的形状。
*   **Agent Sessions** 持久化对话和事件历史。你可以将它们固定到一个自定义会话 ID，该 ID 映射到你自己的 CRM 或数据库记录，这样智能体的状态就存在于业务状态旁边，而不是在一个单独的 AI 孤岛中。
*   **[Agent Memory Bank](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank)** 是持久的长期记忆层，自 Next ‘26 起普遍可用。它从会话中整理记忆，将其范围限定到用户身份，并公开一个搜索 API，以便下一次智能体调用可以拉取相关的内容。Payhawk 报告称，通过一个由 Memory Bank 支持的智能体自动提交费用，将提交时间缩短了超过 50%。
*   **Agent Sandbox** 处理强化的代码执行。
*   **Agent-to-Agent Orchestration**、**Agent Registry**、**Agent Identity**、**Agent Gateway**、**Agent Observability** 和 **Agent Simulation** 涵盖了基本上所有你原本需要为生产级智能体集群手动构建的操作关注点，包括企业实际需要交付的加密身份和审计日志故事。

在架构上，这与 Anthropic 描述的大脑/手/会话分离相同，只是以平台规模产品化，并与 [ADK](https://google.github.io/adk-docs/)（代码优先的开发工具包）和 Agent Studio（可视化工具）捆绑在一起。如果你在 Google Cloud 内部构建，你不再需要从头设计会话日志或记忆存储。你将一个 ADK 智能体连接到 Memory Bank 和 Sessions，部署到 Agent Runtime 上，持久性问题就解决了。

注意这与 Anthropic 和 Cursor 描述的模式有多么相似，只是被拆解为带有 SLA 的命名服务。三年前，你会自己构建所有这些。**现在你选择你想要租用的“解耦的大脑、手和会话”的哪个版本。**

## 生产环境中长时间运行智能体的五种模式

Shubham Saboo 和我[撰写了](https://x.com/GoogleCloudTech/status/2046989964077146490)五种我们观察到将可工作的长时间运行智能体与演示区分开来的设计模式。它们并非 Google 特有，但清晰地映射到 Agent Runtime 现在公开的原语上，因此值得在此以简化形式进行介绍。

**检查点与恢复。** 最常见的多日故障是上下文丢失。一个智能体在四小时内处理了 200 个文档，在第 201 个文档处遇到错误，如果没有检查点，你就得从头开始。将智能体视为一个长时间运行的服务器进程：将中间状态写入磁盘，每 N 个工作单元设置一个检查点，从故障中恢复。Agent Runtime 沙盒为你提供了一个持久化文件系统，但选择正确的检查点粒度（不是每一步，也不是只在最后）取决于你。

**委托审批（人在回路中）。** 大多数“人在回路中”的实现是：将状态序列化为 JSON，触发一个 webhook，希望有人响应。状态变得过时，通知被埋没，智能体重新反序列化到一个略有不同的世界。长时间运行的运行时允许智能体在原地暂停，并保留完整的执行状态：推理链、工作记忆、工具历史、待处理操作。数小时的人类时间过去了，智能体消耗零计算资源，并以亚秒级延迟恢复。Mission Control 是 Google 为此提供的收件箱。该模式无论供应商如何都有效。

**记忆分层上下文。** 一个为期七天的智能体需要的不仅仅是会话状态。Memory Bank 处理长期整理记忆，Memory Profiles 添加低延迟查找，你在生产环境中会遇到的主要故障模式是**记忆漂移**：智能体从一些非典型的交互中学习到一个程序性捷径，并开始广泛地应用它。**像治理微服务一样治理记忆。** Agent Identity 控制谁可以读写哪些银行。Agent Registry 跟踪哪个版本的哪个智能体正在运行。Agent Gateway 在传输过程中强制执行策略。审计问题不再是“我的智能体在做什么？”，而变成了“我的智能体在记住什么，这如何改变它们的行为？”

**后台处理。** 并非每个长时间运行的智能体都与人类交互。有些智能体驻留在 Pub/Sub 流或 BigQuery 表上，并在事件到达时对其采取行动：内容审核、异常检测、收件箱分类。值得尽早做出的架构决策是不要将策略硬编码到智能体中。在 Gateway 中定义它，整个智能体集群无需重新部署即可获取策略更改。后台智能体长时间无监督运行，而更新一百个这样的智能体唯一合理的方法是更新策略层一次。

**集群编排。** 在真实系统中，你很少只有一个智能体。一个协调器将子任务委派给专家（一个首席研究员智能体、一个评分智能体、一个外展智能体），每个智能体独立运行不同的持续时间。每个专家都有自己的身份（这样外展智能体就不能读取旨在用于评分的财务数据）、自己的策略执行、自己的 Registry 条目。这与分布式系统几十年来使用的协调器/工作者形状相同。新的地方在于 ADK 使用基于图的工作流声明式地处理它，并且一个专家中的不良部署不会级联到其他专家。

这些模式可以组合。一个合规系统可能使用检查点进行文档处理，使用委托审批进行审查门控，使用记忆分层进行跨会话知识，以及使用集群编排来协调专家。开始的总是同一个问题：*你的智能体需要执行的最长不间断工作单元是什么？* 几分钟，你不需要长时间运行的智能体。几小时或几天，这些模式是开始的地方。包含代码示例的[完整文章](https://x.com/GoogleCloudTech/status/2046989964077146490)深入介绍了每种模式。

## 那么，你今天到底如何构建一个？

这是一个实际问题，答案取决于你在构建什么。

**你是一个开发者，希望在自己的仓库上进行长时间运行的编码工作。** 直接使用 [Claude Code](https://addyosmani.com/blog/agent-harness-engineering/)（或 Antigravity、Cursor 或 Codex）。框架已经在那里了。将你的 `AGENTS.md` 视为飞行员的检查清单：简短，每一行都由一次真实的失败赢得。添加将失败反馈给智能体的类型检查和 lint 钩子。在智能体开始之前编写一个计划文件。当智能体声称完成而你不相信时，使用 [Ralph 循环](https://addyosmani.com/blog/self-improving-agents/)。对于多小时或隔夜任务，在工作树中运行，这样合上笔记本不会杀死运行，并让它提交每个有意义工作单元的进度。**这是大多数人应该采取的路径，也是目前杠杆作用最大的地方。**

**你正在构建一个托管的智能体产品。** 不要构建运行时。选择一个托管的。今天有三个真正的选择：[Google 的 Agent Platform](https://cloud.google.com/products/gemini-enterprise-agent-platform)（Agent Engine + Memory Bank + Sessions）、[Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview)，或者基于 [ADK](https://google.github.io/adk-docs/)、[Claude Agent SDK](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk) 或 [Codex SDK](https://platform.openai.com/docs/codex) 自己搭建并托管。权衡是常见的。托管让你开箱即用地获得大脑/手/会话分离、可观测性、身份和审计追踪。自托管让你获得控制权，以及能够为不同角色使用奇怪模型的能力（Cursor 的模式）。对于大多数团队来说，正确的起点是一个托管运行时，加上你自己的 ADK 或 SDK 代码来处理实际的循环。

**你正在做一些自主和操作性的工作**（监控、研究、运维）。Memory Bank 风格的持久性是你想要的，而这是 Claude Code 中不存在的部分。ADK + Memory Bank + Cloud Run + Cloud Scheduler 是我见过的用于“智能体每 N 小时运行一次，积累状态，在阈值时发出警报”的最干净的堆栈。这也是 Cursor 的规划器/工作者/裁判分离开始比在 IDE 编码中更重要的时候，因为工作是真正并行的，并且故障模式不同。

无论你选择哪条路径，有几件事都很重要。

*在智能体开始之前写下完成条件。* 这是长时间运行中单个杠杆作用最高的举措。Anthropic 框架文章称之为特性列表；Cursor 称之为规划器的任务规范。无论如何，它是一个带有明确、可测试完成标准的外部文件，它的存在使得智能体无法在运行过程中悄悄地重新定义*完成*。

*将评估器与生成器分开。* 自我评分是故障模式。一个规划器/工作者/裁判管道，或一个生成器/评估器对，是一个真正的架构模式，而不是风格偏好。即使它是同一个模型在不同角色中带有不同提示。

*投资于会话日志，而不仅仅是提示。* 仅追加的事件日志是使智能体可恢复、可调试和可审计的关键。如果你无法从持久存储中重建智能体在过去 24 小时内做了什么，那么你拥有的只是一个碰巧调用 LLM 的长时间运行 shell 脚本，而不是一个长时间运行的智能体。

*将压缩和上下文重置视为一等公民。* Anthropic 明确指出，作为压缩的摘要对于非常长的任务来说是不够的；他们必须进行完整的上下文重置，其中框架拆除会话并从结构化的交接文件中重建它。这本质上就是人类如何让新工程师入职的方式。

## 目前存在一些真正的局限性

有几件事仍然是真正未解决的。

**成本。** 使用前沿模型和几个工具进行 24 小时运行并不便宜。没有预算、断路器和工具支出的硬性上限，一个智能体可以在一个下午悄悄烧掉一周的 API 预算。这是可以解决的，但这是一个你必须明确采取的步骤。

**安全性。** 一个拥有 API 密钥、云访问权限和运行 shell 命令能力的长时间运行智能体，其攻击面比聊天会话大得多。大脑/手分离模式在这里也很重要：凭证应该无法从模型生成的代码运行的沙盒中访问，这是 Anthropic 为 Managed Agents 指出的好处之一。

**对齐漂移。** 在多个上下文窗口中，智能体会漂移。最初的目标被总结，然后被重新总结，然后失去保真度。这是钩子和裁判存在以防御的部分。这也是“智能体偏离轨道，做了我没有要求的事情”的最常见原因。

**验证。** 审计 24 小时的自主活动是一个真实的人类时间问题。可观测性和结构化工件（PR、提交、简报、测试运行）是你使其易于处理的方式。没有它们，你就是在滚动浏览日志，你会错过重要的东西。

**人类角色。** 这是我不断回到的一点。足够清晰地定义工作，以便智能体可以在此基础上运行一天，这比自己做这项工作更难。价值正在升值的技能不是编写代码。而是编写能够经受住与自主执行者接触的规范。

## 未来的发展方向

Google、Anthropic 和 Cursor 已经收敛到大致相同的形状。**将模型循环与执行沙盒与持久会话日志分开。将规划与生成与评估分开。内置压缩、钩子和上下文重置。将记忆作为任何智能体调用都可以查询的托管服务公开。**

不同之处在于表面区域。Google 的 Agent Platform 是企业级堆栈版本，内置了身份和审计追踪故事。底层的模式是相同的。Claude Managed Agents 是“Anthropic 的框架，托管”。Cursor 的后台智能体是“长时间运行的编码，从 IDE 中拉出并放入云端”。

未来一年更难的问题不在这些层中的任何一个。它们在于这些层之上的协调。共享代码库上的多个长时间运行智能体。读取自身追踪并修补自身框架的智能体。能够为任务即时组装工具和上下文，而不是在启动时预先配置的框架。那时，智能体看起来不再像一个更智能的聊天窗口，而开始看起来像一个比你更早参与项目的同事。

模型仍然承担着重任。但是，一个聊天窗口和一个你可以让其通宵运行的智能体之间的差距，主要在于围绕它的状态、会话和结构化交接。这就是我现在会投入学习时间的地方。
