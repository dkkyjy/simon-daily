# 循环工程

        **日期：** 2026-06-07 00:00 UTC
        **链接：** https://addyosmani.com/blog/loop-engineering/

        **来源：** [Addy Osmani](https://addyosmani.com/blog/)

        ---

        > *摘要：你其实不再需要擅长提示词工程了。真正需要擅长的是替你完成提示工作的那个循环。它由五个构建模块加上一个记笔记的地方组成，而 Codex 和 Claude Code 现在都具备这五个要素。*

**循环工程是用你自己来取代那个向智能体发出提示的人。你设计的是完成这一工作的系统。** 这里的循环可以被理解为一个递归目标：你定义一个目的，AI 反复迭代直至完成。我相信这可能是我们与编码智能体协作方式的未来。不过，这仍处于早期阶段，我持怀疑态度，而且你绝对*必须*对 token 成本（如果你 token 充裕或匮乏，使用模式可能差异巨大）[保持谨慎](https://x.com/weswinder/status/2063700289710964906)，因此我想深入剖析它是什么以及它意味着什么。

---

Peter Steinberger 最近[说](https://x.com/steipete/status/2063697162748260627)：“你不应该再向编码智能体发出提示了。你应该设计循环来提示你的智能体。”同样，Anthropic 公司 Claude Code 的负责人 Boris Cherny [说](https://x.com/rohanpaul_ai/status/2063289804708835412)：“我不再向 Claude 发出提示了。我有循环在运行，它们提示 Claude 并决定该做什么。我的工作是编写循环。”

好的，那么这到底是什么意思呢？

大约两年来，你从编码智能体那里获得结果的方式是编写一个好的提示词并提供足够的上下文。你输入内容，阅读返回结果，再输入下一个内容。智能体是一个工具，你全程握着它，一轮接着一轮。这部分已经结束了，或者至少有人认为它即将结束。

现在你构建一个小型系统，它负责发现工作、分配任务、检查结果、记录完成情况，然后决定下一步做什么，你让这个系统去调用智能体，而不是你自己亲自去做。我之前写过它的近亲——[智能体框架工程](https://addyosmani.com/blog/agent-harness-engineering/)，即打造单个智能体运行的环境，以及[工厂模式](https://addyosmani.com/blog/factory-model/)——构建软件的系统。循环工程位于框架之上一个层级。框架本身，但它在定时器上运行，它会生成小帮手，并且能自我供给。

让我惊讶的是，这已经不再是一个工具问题了。一年前，如果你想要一个循环，你会编写一大堆 bash 脚本，然后永远维护那堆脚本，它只属于你一个人。现在，这些组件直接内置在产品中。Steinberger 的列表几乎完全对应 Codex 应用，然后又几乎相同地对应 Claude Code。一旦你注意到结构是相同的，你就不会再争论用哪个工具了，你只需设计一个无论你碰巧使用哪个工具都能正常工作的循环。

## 五个组成部分，再加上笔记

一个[循环](https://x.com/reach_vb/status/2063713960495558940)需要五样东西，外加一个用来记住信息的地方。让我先列出它们，然后再进行映射。

1.  **自动化**：按计划自动运行，自行执行发现和分类。
2.  **工作树**：确保并行工作的两个智能体不会互相干扰。
3.  **技能**：记录智能体原本只能猜测的项目知识。
4.  **插件和连接器**：将智能体连接到你已经使用的工具。
5.  **子智能体**：让其中一个负责构思，另一个负责检查。

然后是第六样东西——记忆。一个 Markdown 文件，或者一个 Linear 看板，任何存在于单次对话之外并能记录已完成事项和下一步计划的东西。听起来太简单，无关紧要。但这是每个长时间运行的智能体都依赖的相同技巧，我在[长时间运行的智能体](https://addyosmani.com/blog/long-running-agents/)中详细探讨过：模型会在运行之间忘记一切，所以记忆必须存储在磁盘上，而不是上下文中。智能体会忘记，但代码仓库不会。

现在，两款产品都具备这五个要素。

| 原语 | 在循环中的职责 | Codex 应用 | Claude Code |
| --- | --- | --- | --- |
| **自动化** | 按计划进行发现 + 分类 | [自动化标签页](https://developers.openai.com/codex/app/automations)：选择项目、提示词、频率、环境；结果存入分类收件箱；`/goal` 用于“运行直到完成” | 定时任务和 cron，`/loop`，`/goal`，钩子，GitHub Actions |
| **工作树** | 隔离并行功能 | 每个线程内置工作树 | `git worktree`，`--worktree`，子智能体的 `isolation: worktree` |
| **技能** | 将项目知识编码化 | [智能体技能](https://developers.openai.com/codex/skills)（`SKILL.md`），通过 `$name` 或隐式调用 | [智能体技能](https://addyosmani.com/blog/agent-skills/)（`SKILL.md`） |
| **插件/连接器** | 连接你的工具 | 连接器（MCP）加用于分发的插件 | MCP 服务器加插件 |
| **子智能体** | 构思和验证 | [子智能体](https://developers.openai.com/codex/subagents)，在 `.codex/agents/` 中定义为 TOML | `.claude/agents/` 中的任务子智能体，智能体团队 |
| **状态** | 跟踪已完成事项 | 通过连接器使用 Markdown 或 Linear | 通过 MCP 使用 Markdown（`AGENTS.md`，进度文件）或 Linear |

名称上可能略有不同，但功能是相同的。让我逐一说明，因为老实说，细节决定了循环是能稳固运行，还是会悄无声息地到处泄漏。

## 自动化，这是心跳

自动化是让一个循环成为真正循环的关键，而不仅仅是一次性运行。在 Codex 应用中，你在自动化标签页创建一个自动化，然后选择项目、要运行的提示词、运行频率，以及它是在你的本地检出上运行还是在后台工作树上运行。发现问题的运行结果会进入分类收件箱，没发现问题的运行结果会自动归档，这很不错。OpenAI 内部使用它们来处理一些枯燥的任务，比如每日问题分类、总结 CI 失败、编写提交简报、查找上周有人添加的 bug。而且自动化可以调用技能，这样你就能让重复性任务保持可维护性，你只需触发 `$skill-name`，而不是将一长串指令粘贴到一个永远不会有人更新的计划表中。

Claude Code 通过调度和钩子实现了同样的功能。你可以使用 `/loop` 按间隔运行提示词或命令，你可以安排 cron 任务，你可以在智能体生命周期的特定点触发 shell 命令（通过钩子），或者如果你希望在你关闭笔记本电脑后它继续运行，你可以将整个任务推送到 GitHub Actions。完全相同的想法：你定义一个自主任务，给它一个节奏，结果会反馈给你，这样你就不必亲自去检查了。

还有一个值得了解的会话内原语，它更接近本文的核心主题。`/loop` 按节奏重新运行。`/goal` 持续运行，直到你编写的条件真正满足，并且在每一轮之后，会有一个独立的小模型检查你是否完成了，这样编写代码的智能体就不会给自己评分。你给它类似“test/auth 中的所有测试通过且 lint 干净”这样的条件，然后就可以走开了。Codex 也有同样的功能，也叫做 `/goal`，它会跨轮次持续工作，直到一个可验证的停止条件成立，并支持暂停、恢复和清除。相同的原语，两个工具都有，这几乎是本文的模式。

所以，这部分是发现工作的地方。循环的其余部分则是对这些工作采取行动。

## 工作树，让并行不会变成混乱

一旦你运行超过一个智能体，文件就会开始冲突，这就会变成失败。两个智能体写入同一个文件，与两个工程师在没有事先沟通的情况下提交到同一行代码是完全一样的麻烦。git 工作树解决了这个问题，它是一个独立的工作目录，位于自己的分支上，共享相同的仓库历史，因此一个智能体的编辑根本无法触及另一个智能体的检出。

Codex 内置了工作树支持，因此多个线程可以同时访问同一个仓库而不会互相冲突。Claude Code 通过 `git worktree`、用于在独立检出中打开会话的 `--worktree` 标志，以及你可以设置在子智能体上的 `isolation: worktree` 设置（这样每个助手都会获得一个全新的、可自行清理的检出），提供了相同的隔离机制。我在[编排税](https://addyosmani.com/blog/orchestration-tax/)中写过这一切的人性化方面，工作树消除了机械冲突，但你仍然是瓶颈，你的审查带宽决定了你实际能运行多少个，而不是工具本身。

## 技能，这样你就不必每次都解释你的项目

技能让你不再需要像金鱼一样每次会话都重新解释相同的项目上下文。两个工具使用相同的格式：一个包含 `SKILL.md` 的文件夹，里面存放指令和元数据，以及可选的脚本、参考资料、资源文件。Codex 在你使用 `$` 或 `/skills` 调用技能时运行它，或者当你的任务与技能描述匹配时自动运行，这就是为什么一个精确、枯燥的描述胜过巧妙的描述。Claude Code 以相同的方式运行，我在[智能体技能](https://addyosmani.com/blog/agent-skills/)中写过这种模式。

技能也是意图不再让你反复付出成本的地方。我在[意图债务](https://addyosmani.com/blog/intent-debt/)中论证过，智能体每次会话都是从零开始的，它会用自信的猜测来填补你意图中的任何空白。技能就是写在外部的那份意图——约定、构建步骤、“因为那次事故我们不再这样做”——写一次，智能体每次运行都会读取。没有技能，循环每次都会从零重新推导你的整个项目；有了技能，它就能产生复利效应。

有一点需要搞清楚：技能是创作格式，插件是你分发它的方式。当你想要跨仓库共享一个技能，或者将几个技能打包在一起时，你就将它们打包成一个插件。这在 Codex 和 Claude Code 中都是如此。

## 插件和连接器，循环触及你的真实工具

一个只能看到文件系统的循环是一个微小的循环。连接器，基于 MCP 构建，允许智能体读取你的问题追踪器、查询数据库、访问暂存 API、在 Slack 中发送消息。Codex 和 Claude Code 都支持 MCP，因此你为一个工具编写的连接器通常可以直接在另一个工具中使用。而插件将连接器和技能捆绑在一起，这样你的队友可以一次性安装你的设置，而不是凭记忆重建整个配置。

这就是一个说“这是修复方案”的智能体与一个能自动打开 PR、关联 Linear 工单并在 CI 通过后自动通知频道的循环之间的区别。连接器是循环能够在你实际环境中行动的原因，而不是仅仅告诉你它能做什么。

## 子智能体，让制造者远离检查者

循环中最重要的结构性功能，是区分编写代码的人和检查代码的人。编写代码的模型在给自己的作业打分时过于宽容。第二个智能体，使用不同的指令，有时使用不同的模型，能捕捉到第一个智能体自欺欺人时遗漏的问题。

Codex 只在你要求时才会生成子智能体，它们同时运行，然后将结果合并回一个答案。你在 `.codex/agents/` 中将自己的智能体定义为 TOML 文件，每个都有名称、描述、指令以及可选的模型和推理努力程度，这样你的安全审查员可以使用高努力度的强模型，而你的探索者则可以是某种快速的只读智能体。Claude Code 通过 `.claude/agents/` 中的子智能体和在它们之间传递工作的智能体团队来实现相同功能。两者中常见的分工是：一个智能体负责探索，一个负责实现，一个根据规范进行验证。

我之前已经两次阐述过这个观点，一次是在[代码智能体管弦乐队](https://addyosmani.com/blog/code-agent-orchestra/)中，另一次是在[对抗性代码审查](https://addyosmani.com/blog/adversarial-code-review/)中。它在循环内部特别重要的原因是，循环是在你不在场时运行的，因此一个你真正信任的验证者是你能够走开的唯一理由。子智能体确实会消耗更多 token，因为每个子智能体都要进行自己的模型和工具工作，所以要把 token 花在值得获得第二意见的地方。这基本上也是 Claude Code 的 `/goal` 在底层所做的：由一个全新的模型来决定循环是否结束，而不是由完成工作的那个模型来决定——这是将制造者和检查者分离应用于停止条件本身。

## 一个循环看起来是什么样子

把所有这些组合在一起，一个单独的线程就变成了一个小型控制面板。这是我一直在使用的一个模式。

一个自动化每天早上在仓库上运行。它的提示词调用一个分类技能，该技能读取昨天的 CI 失败、未解决的问题、最近的提交，并将发现结果写入一个 Markdown 文件或 Linear 看板。对于每个值得处理的问题，该线程会打开一个隔离的工作树，并派一个子智能体去起草修复方案，再由第二个子智能体根据项目技能和现有测试来审查该草案。

连接器允许循环打开 PR 并更新工单。任何循环无法处理的问题都会进入我的分类收件箱。状态文件是整个循环的主干，它记录了哪些尝试过、哪些通过了、哪些仍然未解决，这样第二天早上运行时，就能从今天停止的地方继续。

看看你实际做了什么。你只设计了一次。你没有为任何这些步骤发出提示。这就是 Steinberger 观点的现实体现，而且在 Codex 或 Claude Code 中都是同一个循环，因为组件是相同的。

## 循环仍然不能为你做什么

循环改变了工作方式，但它并没有把你从工作中剔除。而且，随着循环变得更好，三个问题实际上会变得更尖锐，而不是更简单。

验证仍然取决于你。一个无人值守运行的循环，也是一个无人值守犯错的循环。你将验证者子智能体与制造者子智能体分开的全部原因，就是为了让循环的“已完成”声明更有意义，即便如此，“已完成”也只是一个声称，而不是一个证明。我一直在重复[AI 时代的代码审查](https://addyosmani.com/blog/code-review-ai/)中的同一句话：你的工作是交付你确认能正常工作的代码。

如果你放任不管，你对代码的理解仍然会退化。循环交付你未编写的代码速度越快，现有代码与你实际理解之间的差距就越大。这就是[理解债务](https://addyosmani.com/blog/comprehension-debt/)，一个顺畅的循环只会让它增长得更快，除非你阅读循环生成的内容。

而舒适的姿态是危险的姿态。当循环自行运行时，你很容易停止持有自己的观点，只是接受它返回的任何东西。我称之为[认知投降](https://addyosmani.com/blog/cognitive-surrender/)。当你带着判断力去设计循环时，它是一种解药；当你用它来逃避思考时，它是一种催化剂——同样的行为，截然相反的结果。

## 构建循环。保持工程师的身份。

我认为这是我们工作方式演变的一个预演。话虽如此，如果我不亲自审查代码，或者如果我完全依赖自动化循环来修复问题，我产品的质量就会下降。我很可能会陷入一个恶性循环，不断把自己挖进更深的坑里。

话虽如此，去设置你的循环吧，但不要忘记直接向你的智能体发出提示也同样有效。关键在于找到正确的平衡。

循环也可能根据你的不同而产生不同的结果。两个人可以构建完全相同的循环，却得到截然相反的结果。一个人用它来在自己深刻理解的工作上更快地推进。另一个人用它来完全逃避理解工作。循环不知道其中的区别。但你知道。

这就是为什么循环设计比提示工程更难，而不是更容易。Cherny 的观点并不是说工作变容易了。而是说杠杆点转移了。

构建循环。但要像打算保持工程师身份的人那样去构建它，而不仅仅是按下“开始”按钮的人。
