# 自我改进的编码代理

**日期：** 2026-01-31 00:00 UTC
**链接：** https://addyosmani.com/blog/self-improving-agents/

**想象一下，结束一天的工作，醒来后发现新功能已被编码、测试，并准备好接受审查。** 这就是自主AI编码代理的承诺——利用像 **Claude Code** 这样的工具在连续循环中，在你睡觉时改进和交付代码。

在这篇文章中，我将介绍如何设置这些自我改进的代理循环——从编排循环和构建上下文文件，到内存持久化、质量保证验证、扩展、调试和风险管理。希望这里的内容对其他人有所帮助。

***本文是对 Ryan Carson 的精彩文章 [如何让你的代理在你睡觉时学习和交付代码](https://x.com/ryancarson/status/2016520542723924279) 的补充，我强烈推荐阅读。** 我们最近在晚餐时进行了一些关于代理编码未来的精彩对话，我想对他概述的一些技术进行扩展。*

## **“持续编码循环”（Ralph Wiggum 技术）**

这种方法的核心是一个迭代的 **代理循环**，通常被称为“Ralph Wiggum”技术（由 Geoffrey Huntley 和 Ryan Carson 等人推广）。关键思想是将开发分解为许多小任务，并运行一个AI代理在循环中逐一处理它们。

循环的每次迭代都遵循一个 **周期**：

1. **从待办事项列表（例如 [任务 JSON](https://github.com/snarktank/compound-product#:~:text=Each%20iteration%20of%20the%20loop%3A)）中选取下一个任务**，该任务尚未完成。
2. **实施任务** - 代理为该特定功能/修复编写或修改代码。
3. **验证更改** - 运行该任务的测试、类型检查或其他质量检查。
4. **提交代码**（如果检查通过），将更改集成到代码库中。
5. **更新任务状态**（标记为已完成）并记录任何学习内容。
6. **重置代理上下文**，并对下一个任务重复上述步骤，直到所有任务完成或达到停止条件。

通过每次迭代重置其内存，代理[避免了因先前任务而积累混乱](https://www.aifire.co/p/automated-coding-build-apps-while-you-sleep-using-ai-agent#:~:text=This%20approach%20solves%20the%20common,both%20founders%20and%20experienced%20developers)，并保持专注。这种“无状态但迭代”的设计是可靠性的关键——它**解决了困扰一次性要求AI构建整个功能的上下文溢出问题**。

与其使用一个可能导致模型偏离或忘记细节的巨大提示，不如反复为代理提供一个针对单个明确定义任务的、新鲜的、有边界的提示。

结果是更干净的代码和更少的幻觉，因为每次运行都从一个清晰的起点和明确的指令开始。

这里，一个代理持续地选取任务、编写代码、运行测试，并更新任务列表，直到所有任务通过。

### **具有明确标准的小任务**

将工作分解为 **原子用户故事** 或任务很重要。每个任务应该**足够小以适应一次AI会话**，并具有明确的通过/失败标准。

例如，与其“构建整个仪表板”，不如设置诸如“添加一个包含主页、关于、联系链接的导航栏”这样的任务，并附带指定确切期望的验收标准（例如“当前页面链接以蓝色高亮显示”）。

这种粒度方式确保代理知道每个步骤的“完成”是什么样子。它还减少了代理偏离轨道的可能性——如果某个任务未通过其测试或标准，循环可以立即捕获它并纠正路线。

*实施提示：* **定义一份规格说明并将其转换为任务 JSON。** 首先为功能编写清晰的规格说明，可能借助AI来完善边缘情况。

然后将其转换为结构化的任务列表（例如 prd.json 文件），其中包含所有小的用户故事和验收标准。像 Carson 的用于 Amp/Claude 的 [**/prd 和 /tasks 技能**](https://github.com/snarktank/compound-product#:~:text=Two%20skills%20are%20included%20for,PRD%20creation%20and%20task%20generation) 这样的工具可以[自动化此转换](https://github.com/snarktank/compound-product#:~:text=Key%20features%3A)。

结果是一个机器可读的待办事项列表，你的代理循环将逐步执行它。

### **编排循环**

可以通过一个简单的脚本来运行循环。在 [Carson 的实现](https://github.com/snarktank/ralph) 中，这[实际上就像一个 Bash 脚本](https://ghuntley.com/ralph/#:~:text=If%20you%27ve%20seen%20my%20socials,Ralph%20is%20a%20Bash%20loop) 或 Python 脚本（例如 ralph.sh），它反复调用带有提示模板的AI代理。使用 Amp 或 Claude Code，你可以使用它们的 CLI 命令或插件来实现相同的效果。例如，使用 Amp 的 CLI，可以运行一个伪代码循环，如下所示：

```
while :; do    
   amp run \-s prompt.md \-o progress.txt  \# 运行 Amp 并带上提示，保存输出    
   if grep \-q "\<promise\>COMPLETE\</promise\>" progress.txt; then break; fi    
done

```

在实践中，循环脚本将加载任务列表，选取下一个未完成的任务，格式化一个提示（包括相关代码文件和指南等上下文），并调用AI模型。当模型的响应指示成功或失败时，脚本处理应用代码更改和运行测试。这会重复，直到所有任务完成或达到最大迭代限制。

关键是每次迭代都是隔离的——代理**每次都是新生成的**，通常作为一个新的 Claude 或 GPT 进程，所以你真正地清空了记录，但每次都要重新为其提供必要的上下文。

**复合循环：** 除了单一的任务序列，高级工作流还编排多个阶段的循环。

[**Compound Product**](https://github.com/snarktank/compound-product#:~:text=A%20self,priority%2C%20and%20autonomously%20implements%20it) 例如，是一个开源系统，它首先运行一个**分析循环**（一个AI读取每日报告以确定要构建什么），然后是一个**规划循环**（生成 PRD 和任务），最后是一个**执行循环**（实现任务的编码代理）。这个复合管道意味着代理不仅编码功能，还决定最高优先级的功能*是什么*。

虽然并非每个项目都需要这种自动化水平，但它展示了循环如何被链接起来：一个代理的输出（例如任务列表或分支名称）成为另一个代理在更大持续交付系统中的输入。

## **上下文和内存的最佳实践：AGENTS.md 手册**

这些代理循环中最强大的机制之一是使用持久的**上下文文件**，这些文件在迭代之间传递知识。

与其试图“拉伸”单个AI会话来记住所有内容（这在上下文窗口之外是不可能的），我们显式地将重要信息写入磁盘，以便可以在未来的提示中*重新注入*。此用途的主要文件通常命名为 **AGENTS.md**（尽管有些人使用 [MEMORY.md](https://ericmjl.github.io/blog/2025/11/8/safe-ways-to-let-your-coding-agent-work-autonomously/#:~:text=When%20you%20catch%20an%20agent,An%20example%20prompt) 或类似名称）。

**什么是 AGENTS.md？** 它本质上是一个关于代理发现、项目约定以及你希望所有未来代理知道的任何指南的运行笔记本。

在每个任务之后，循环可以附加关键学习内容：例如，“注意：代码库使用库 X 进行 Y，因此遵循该模式”或“陷阱：每当更新用户模型时，也要更新审计日志”。

随着时间的推移，这成为一个提示宝库，引导代理避免重复过去的错误。在 Carson 的 Compound Product 理念中，[*“代理更新 AGENTS.md - 发现的模式被记录下来以供未来迭代使用”*](https://github.com/snarktank/compound-product#:~:text=Compound%20Product%20is%20based%20on,should%20make%20future%20improvements%20easier)。这意味着每一次改进都使未来的改进更容易，因为代理积累了一个关于代码库外观以及如何与之协作的知识库。

**构建知识库：** 将 AGENTS.md 组织成章节，使其易于人类和AI阅读。例如：

* **模式与约定：** 高级模式（例如“此项目使用 SSR，UI 组件位于 /components，API 位于 /routes”）。
* **陷阱：** 曾使代理或开发人员陷入困境的事情（“添加新枚举时，更新 constants.ts 文件，否则测试将失败”）。
* **风格/偏好：** 编码风格说明（“遵循配置的 ESLint 规则；优先使用函数式组件而非类组件”，“像现有测试一样使用 pytest fixtures 进行测试”）。
* **近期学习/更改：** 近期问题及其解决方式的摘要。

保持条目简洁且事实性——它们应作为**提示添加剂**来指导模型。许多AI编码工具（Claude Code、Cursor、Amp）如果存在，会[自动将某些文件](https://github.com/snarktank/ralph#:~:text=After%20each%20iteration%2C%20Ralph%20updates,discovered%20patterns%2C%20gotchas%2C%20and%20conventions)（如 AGENTS.md 或 README.md）包含在提示上下文中。例如，当代理开始新的迭代时，Amp 将扫描仓库并拉取 AGENTS.md 内容，为模型提供关于项目的上下文。

**上下文注入策略：** 注意上下文大小。随着你的知识文件增长，你可能并不总是希望为每个任务注入所有内容（上下文膨胀会降低性能或导致模型忽略指令）。

一个好的做法是保持 AGENTS.md 的聚焦和最新，将过时的信息存档到另一个文件中（如果需要）。一些高级设置使用检索：例如，将 AGENTS.md 拆分为多个主题文件，并且只包含与当前任务相关的章节。但一个更简单的方法通常就足够了——保持文件精简到最相关的提示，并随着项目的发展逐渐增长。

**使用示例：** 假设代理尝试使用过时的API，而你发现了它。

你可以停止循环并在 AGENTS.md 中添加一条注释，例如：

*“v1/users 端点已弃用；改用 v2/users。”*

下次代理处理相关任务时，它会看到这条注释并避免使用已弃用的API。事实上，你可以指示代理自己这样做：

*“不，不要使用旧端点。相反，使用新的 v2/users API。将此记录在 AGENTS.md 中，然后继续。”*

这种[实时反馈技术](https://ericmjl.github.io/blog/2025/11/8/safe-ways-to-let-your-coding-agent-work-autonomously/#:~:text=Correct%20agent%20behavior%20in%20real) 被开发者 Eric J. Ma 强调为一种*“创建偏好持久记录的方法，可改善未来代理行为”*。

代理将忠实地将更正附加到 AGENTS.md 并继续执行新指令——有效地从错误中学习。

最后，考虑跨代理或运行共享 AGENTS.md 知识。如果你运行多个循环（针对不同项目或并行任务），你可以集中一些通用知识。Eric Ma 的 [**MCP（模型上下文协议）服务器**](https://ericmjl.github.io/blog/2025/11/8/safe-ways-to-let-your-coding-agent-work-autonomously/#:~:text=This%20approach%20creates%20a%20persistent,preferences%20across%20different%20agent%20platforms) 是一个系统示例，用于存储并将此类上下文统一提供给不同的代理。简单来说，即使是一个共享的 wiki 或一组你的所有代理会话都引用的 markdown 文件，如果你有多个自主代理协同工作，也可以确保一致性。

## **内存持久化和复合学习策略**

除了 AGENTS.md，健壮的代理循环还使用几种**持久化机制**来保持状态并避免跨迭代的健忘。Carson 的 Ralph 循环实现使用至少[四个内存通道](https://github.com/snarktank/compound-product#:~:text=Memory%20Between%20Iterations) 在运行之间：

* **Git 提交历史：** 每次迭代的代码更改都被提交，因此下一次迭代可以执行 git diff 或检查仓库以查看更改了什么。这样，代理不需要回忆之前的代码——它可以从仓库中读取。提交消息本身也可以提供上下文（“迭代 5：添加了导航栏组件”）。像 Amp 或 Cursor 这样的工具允许代理[自主运行 git log 或 git diff](https://ericmjl.github.io/blog/2025/11/8/safe-ways-to-let-your-coding-agent-work-autonomously/#:~:text=Safe%20to%20auto)（具有适当的权限）以从版本控制中收集上下文。
* **进度日志（progress.txt）：** 一个纯文本日志，每个周期追加一次，描述发生了什么——例如，尝试了哪个任务以及它是通过还是失败，以及任何错误消息或发现。这充当了时间顺序记忆。如果循环停止或你需要调试，你可以检查 progress.txt 以查看哪里出了问题。代理本身也可以被提示在迭代开始时（或相关部分）读取 progress.txt，以提醒它之前尝试过什么。把它想象成代理的日记。
* **任务状态（prd.json 或任务列表）：** 包含任务的 JSON 文件会随着任务被标记为完成或 passes: true/false 字段被切换而更新。此文件持久化了每个需求的*状态*。如果代理崩溃并重新启动，它可以加载 prd.json 并确切知道哪些任务剩余。代理循环脚本将跳过已经完成的任务，并专注于待处理的任务。这防止了返工并提供了进展感。
* **代理知识（AGENTS.md）：** 如前所述，这是长期语义记忆——过去运行的积累智慧。

总之，这些创建了一个**复合学习循环**：代理不是在机器学习意义上的“在线学习”，而是*系统地记录结果*，以便下一次迭代（或下一个项目！）从这些学习成果中受益。

代理解决的每个修复或模式都会被纳入下一次的上下文中。正如 Compound Product README 所述，其理念是[*每次改进都应使未来的改进更容易*](https://github.com/snarktank/compound-product#:~:text=Compound%20Product%20is%20based%20on,should%20make%20future%20improvements%20easier)。

经过数十次迭代，代理的有效性实际上可以增加，因为它停止了重复错误并遵循了它学到的约定。

还有一些**基于插件的内存扩展**可以利用。

例如，Claude Code 支持“技能”甚至市场插件——你可以想象（或构建）一个技能，自动保存每次编码会话的摘要并在下次加载。Amp 的自动交接功能实际上充当了短期记忆——当[上下文窗口](/agentic-engineering/context-window/)即将溢出时，它可以将对话交接给一个新的会话，并附带一个到目前为止的压缩摘要。这防止了任务中的上下文丢失，对于非常大的任务或复杂的重构非常有用。

在更具实验性的设置中，开发者使用了**向量数据库**来存储和检索记忆。例如，每次迭代后，你可以嵌入差异或错误消息，并将向量与描述一起保存。在下次迭代之前，查询数据库以查找类似的过去案例，并将其提供给代理。

这可以帮助识别，例如，“哦，我以前见过类似的失败测试以及它是如何修复的。”然而，这种方法增加了复杂性，如果你勤勉地维护更简单的工件（代理可以直接读取的文件和日志），可能不需要。

**提示：** 无论你使用什么持久化方法，都要定期**验证代理是否实际使用了它**。内存文件只有在未来运行中被注入到提示中时才有帮助。

检查你的提示模板或代理配置，以确保例如 AGENTS.md 和最近的 progress.txt 条目被包含在内。在 Amp 和 Claude 中，默认情况下，像 progress.txt 这样的文件可能不会自动加载，因此你可以修改你的提示说：*“以下是先前运行的笔记：”* 并包含内容。

在 Carson 的设置中，鼓励为你的项目自定义提示模板（例如 prompt.md 或 CLAUDE.md）——你可以添加加载项目特定上下文或强调特定说明的章节。

## **质量保证：测试和验证循环**

对于一个自主代理来说，要可靠地产生工作代码，**自动化验证至关重要**。没有检查，代理可能会愉快地引入错误或破坏构建，同时认为它成功了。一个健壮的代理循环将测试和其他验证作为循环中的一等公民：

* **单元和集成测试：** 拥有一个可靠的测试套件可以显著改善结果。代理可以在实现任务后运行 npm test 或 pytest。如果测试失败，循环就知道任务实际上没有完成，并可以提示代理修复代码。理想情况下，prd.json 中的每个用户故事至少有一个关联的测试，要么作为验收标准的一部分，要么在仓库的测试文件中。一些系统更进一步——例如，指示代理在编码之前编写一个新测试（测试驱动风格）或为应用程序的 UI 状态创建快照以进行比较。但至少，**在每次迭代中运行现有测试**。
* **类型检查和代码检查：** 静态分析工具（类型检查器如 MyPy 或 tsc，代码检查器如 ESLint/Flake8）是很好的自动化反馈。它们能快速捕获错误。这些可以作为循环质量检查的一部分运行，在提交代码之前。例如，你可以在 config.json 中配置，循环应在代理编写代码后执行 npm run typecheck && npm run lint，并且仅当这些命令成功退出时才继续。这防止了代理在错误之上堆积错误。
* **循环中的持续集成（CI）：** 一些高级设置甚至与 CI 管道集成。例如，Cursor 的多代理实验有一个[“裁判”代理，可以决定](https://cursor.com/blog/scaling-agents#:~:text=,planning%20itself%20parallel%20and%20recursive)项目是否完成，这可能涉及确保 GitHub Actions CI 是绿色的。在更简单的单代理循环中，你可以通过作为验证的一部分在本地运行构建脚本或任何 CI 检查来模拟这一点。**循环应在出现红旗时暂停**——如果检查失败，代理应处理它（或者在尝试 N 次后如果卡住，将任务标记为仍然失败并可能继续）。
* **AI 自我评估（可选）：** 在你无法轻松编写自动化测试的情况下（例如，对于没有测试框架的 UI 更改），你可以使用代理本身进行验证。例如，对于前端任务，Carson 的代理使用一个**开发浏览器技能**：代理可以启动一个无头浏览器，导航到一个页面，并确认 UI 元素存在或交互有效。这本质上是一个代理驱动的集成测试。如果验证失败，代理知道重试。虽然这可能很强大，但请确保你已具备沙箱环境（稍后会详细介绍安全性），因为这意味着代理正在执行代码或控制浏览器。

**专家见解：** *如何让 AI 代理首先编写好的测试？* 根据 Simon Willison 的说法，最好的方法是[**以身作则**](https://simonwillison.net/tags/coding-agents/#:~:text=Generally%20though%20the%20best%20way,any%20extra%20prompting%20at%20all)——在你的代码库中维护高质量的测试，代理自然会模仿这些模式。基于 LLM 的编码者倾向于遵循他们看到的风格。如果你的仓库为现有组件提供了清晰、简单的测试，当代理被要求添加新功能时，它通常会为新代码生成类似的测试。

Willison 指出，一旦项目有了干净的测试，[*“代理添加的新测试往往在质量上与它们匹配”*](https://simonwillison.net/tags/coding-agents/#:~:text=sure%20it%27s%20working%20in%20a,any%20extra%20prompting%20at%20all)。他还建议[主动告诉代理引用已知的良好示例](https://simonwillison.net/tags/coding-agents/#:~:text=One%20last%20tip%20I%20use,a%20lot%20is%20this)：例如*“使用来自[某个文件]的测试风格”*，甚至指示它克隆另一个仓库以查看某些模式。这种上下文播种可以极大地改善代理的输出，并减少以后修复编写不佳的测试所花费的时间。

在实践中，你可能并不总是信任代理从头开始创建测试——许多开发者更喜欢自己编写或至少审查测试。但即便如此，**在循环中运行这些测试是必不可少的**。它创建了一个反馈循环，其中代理只有在代码真正满足规格说明时（测试通过作为代理）才“认为”它完成了。这个代理质量保证循环将天真的“生成一些代码”过程转变为可靠的工程工作流。

## **扩展：并发代理和多循环编排**

到目前为止，我们专注于一个代理串行处理一个任务列表。如果你想更快地处理多个任务甚至多个项目呢？该领域最近的实验尝试了[在代码库上同时运行数十或数百个代理](https://cursor.com/blog/scaling-agents#:~:text=This%20post%20describes%20what%20we%27ve,code%20and%20trillions%20of%20tokens)。

虽然这处于前沿，在日常开发中尚不常见，但对于理解扩展这些循环的限制和可能性具有启发性。

**并行代理的挑战：** 如果你天真地在同一个仓库上运行许多代理，你会遇到**协调和冲突**的问题。例如，两个代理可能选取相同的任务，或者一个代理可能更改代码，破坏另一个正在做的事情。早期尝试使用[共享文件锁机制](https://cursor.com/blog/scaling-agents#:~:text=Our%20initial%20approach%20gave%20agents,we%20used%20a%20locking%20mechanism) 揭示了代理卡住或浪费时间互相等待。它们也可能变得[**规避风险**](https://cursor.com/blog/scaling-agents#:~:text=We%20tried%20replacing%20locks%20with,there%20were%20still%20deeper%20problems)，每个代理只做微小的安全更改，避免大的复杂任务——因为在自由竞争的系统中，没有单个代理感觉对困难部分“负责”。

[**规划者-工作者模型**](https://cursor.com/blog/scaling-agents#:~:text=)：一种更成功的模式是在代理之间引入层次结构或专业化。例如，Cursor 的 Wilson Lin 描述了在群体中使用**规划者代理**和**工作者代理**。规划者就像项目经理：他们阅读整个代码库，决定需要做什么，并生成任务（甚至递归地创建子任务）。然后工作者接受这些任务并实施它们，而不必担心更大的图景。

在迭代结束时，一个裁判代理评估目标（例如完成项目）是否达到。这种方法防止了无目的的徘徊，并极大地提高了吞吐量——Cursor 的团队成功让*数百个代理协同工作*来构建一个网络浏览器，在一周内产生了超过一百万行代码，跨越 1000+ 个文件。

虽然你可能不需要那种规模，但你**可以为不同目的并行运行多个循环**。例如，你可以同时将一个代理循环专用于前端任务，另一个专用于后端任务（在代码库的不同部分或不同分支上操作）。

如果这样做，请确保清晰地划分工作以最小化冲突。

另一种场景是为不同的功能分支运行单独的夜间循环——例如，10 个功能排队，你触发 10 个代理进程在 10 个分支上运行。Ryan Carson 预测[*最终创始人将每晚运行 10 个以上的这样的循环*](https://x.com/ryancarson/status/2016797196222370226#:~:text=,turns%20prioritized%20reports%20into) 来加速开发。每个循环仍然遵循相同的原则，但你需要良好的 CI 实践来集成所有这些输出（就像你与多个人类工程师同时工作一样）。

**协调工具：** 如果多个代理必须接触同一个项目，考虑使用协调文件或简单的 API 进行通信。一个带有锁定方案的共享 tasks.json 是一种方法（尽管如前所述，文件锁可能很棘手）。另一种轻量级方法是有一个“交通警察”脚本，将任务分配给代理并使用队列。

还有一些新兴的代理编排平台可以处理多代理工作流，但目前这些大多是定制构建或研究项目，而不是现成的解决方案。

对于今天的大多数高级用户来说，**扩展意味着更深入地迭代，而不是纯粹地扩大范围**。让一个能干的代理循环在复杂项目上运行更长时间（一夜或多天）通常比启动一个难以管理的群体更有成效。随着模型能力的增长，长时间运行的单代理也在改进。

## **监控、调试和反馈仪表化**

当你将编码委托给自主代理时，你需要对其行为有可见性。像对待你正在审查其工作的真实工程师一样对待你的代理。以下是监控和调试代理循环的一些最佳实践：

* **实时日志：** 保持一个终端打开，实时 tail 代理的输出或 progress.txt 日志。循环应打印出它正在处理的任务，并且你应该看到测试或任何错误的结果。如果你注意到代理多次循环同一个错误，它可能卡住了——你可以干预（停止它或给出提示）。许多框架允许你查看AI的消息；例如，Claude Code 桌面应用程序在代理工作时显示对话线程，而 Amp 的 CLI 逐步打印模型输出。
* **检查点提交：** 由于每次迭代都提交到 git，你拥有一个优秀的审计跟踪。经常使用 git log 和 git diff。快速的 git log --oneline -5 将显示代理最近几次的提交。如果在差异中看起来有问题，你可以在它走得太远之前捕获它。你甚至可以自动化差异审查——例如，如果差异比预期大得多或触及了任务范围之外的关键文件（表明代理可能已经“失控”），则中止循环。
* **检查命令：** 在你的循环中加入一些调试命令，或者使它们易于运行。例如，一个显示所有任务状态的脚本（jq '.tasks[] | {id, story, passes}' prd.json）可以快速总结进度。检查 progress.txt 中是否有“ERROR”一词，或读取最后 N 行，可以告诉你任务失败的原因。
* **代理自省：** 如果需要，你可以要求代理解释自己。例如，如果它卡在一个任务上，你可以修改提示说“如果测试在 3 次尝试后仍然失败，输出你的推理和计划。”这可以揭示代理的内部[思维链](/agentic-engineering/chain-of-thought/)（所谓的“自我反思”），这可能会提供线索。谨慎使用——过多的自省也可能混淆循环——但它是调试器工具箱中的一个工具。
* **性能指标：** 记录每次迭代花费的时间和成本（API 令牌）是很有用的。你可以仪表化循环以记录每个任务和整体的时间。如果你看到某个特定任务花费的时间是其他任务的 10 倍，这表明它很复杂或卡住了。经过多个夜晚，你可以收集诸如“每小时功能数”之类的统计数据，这可以告知升级（模型更改、提示调整）是否产生了影响。
* **自动停止条件：** 有时事情会出错——例如，代理陷入徒劳的循环（可能是由于它无法解决的棘手错误）或外部依赖项宕机导致测试总是失败。除了正常的完成条件外，设置停止条件。一个简单的条件是**最大迭代限制**——例如，即使未完成也在 50 次循环后停止。这可以防止成本失控和无限循环。你也可以在时间限制上停止（“如果运行超过 3 小时，杀死它”）或在空闲条件上停止（“如果过去 5 次迭代中没有新的提交，则中断”）。这些确保你回到一个停滞的代理，而不是让它整夜运行做无用功。
* **手动覆盖：** 即使有所有的自主性，在关键时刻也要保留人工覆盖。一个好的模式是让代理在最后打开一个**拉取请求**，而不是自动合并。这意味着你每天早上可以进行最终的代码审查。你很可能会捕获任何通过测试的问题（逻辑问题，或符合验收标准字面意思但不符合精神的问题）。这个“人工质量保证”步骤目前是宝贵的——它让你信任代理做繁重的工作，但不放弃最终控制权。

如果代理持续失败某种类型的任务，将其视为反馈。也许你的验收标准模棱两可或过于严格。或者也许代理需要 AGENTS.md 中关于特定框架的更好提示。使用失败作为**对你自己和代理**的学习信号。

例如，如果代理因为缺乏如何使用第三方 API 的上下文而挣扎，考虑在 AGENTS.md 中添加一个简短的使用示例，或在代码中添加注释以备下次使用。经过几天和几周，这种反思性改进（类似于结对编程回顾）将使系统更加健壮。

## **风险管理和安全措施**

运行具有提交访问权和 shell 执行权限的代码生成代理是强大的——也是有风险的。你必须刻意管理这些风险。以下是关键领域以及如何解决它们：

### **防止破坏性操作**

一个自主代理如果配置不当，可能会删除文件、损坏你的仓库或推送不安全的代码。为了减轻这种情况：

* **限制范围：** 在功能分支或 fork 上运行代理，永远不要直接在 main 上运行。这样，即使它做了疯狂的事情，你的生产代码在审查之前也不会受到影响。
* **只读与写入权限：** 大多数代理平台对危险操作有确认门控。Amp 和 Claude Code 有像 --dangerously-allow-all 这样的标志来绕过自动化确认。

谨慎使用这些。更安全的方法是[**仅自动批准只读命令**](https://ericmjl.github.io/blog/2025/11/8/safe-ways-to-let-your-coding-agent-work-autonomously/#:~:text=Auto)，并要求手动批准写入操作。例如，允许代理运行 grep、git log 或 npm test 而无需询问，但*不要*允许 git push 或 rm -rf 而没有你的明确同意。通过白名单安全操作，你可以让代理自由收集信息，同时控制副作用。

* **[沙箱化](/agentic-engineering/sandboxing/)：** 理想情况下，在受限环境中运行代理——例如 Docker 容器或虚拟机——特别是如果它具有执行代码的能力（它通常用于测试）。

这限制了任何意外命令造成的损害。此外，使用最小范围的 API 密钥：如果代理需要 API 密钥来例如发布 GitHub 评论，给它一个只能执行该操作而不能做其他事情的令牌。

* **紧急停止：** 始终知道如何在运行中杀死代理。这可能就像在你的终端中按 Ctrl+C 或在代理 UI 中执行特定命令一样简单（Claude Code 使用 Escape 键停止生成）。

如果你看到它正在做有害的事情，先终止，再提问。同时考虑监控资源使用情况——如果代理进程消耗异常高的 CPU 或内存（可能如果它触发了代码中的疯狂无限循环），自动化监控器可能会杀死它。

### **处理幻觉和偏离**

AI 模型有时会产生语法上合理但语义上错误的输出（**[幻觉](/agentic-engineering/hallucination/)**）。在编码中，这可能意味着调用一个不存在的函数、使用不正确的算法或编写无意义的注释。还存在**任务偏离**的风险：代理可能错误地解释需求并实现错误的东西。

缓解措施：

* **强规格说明和提示：** 清晰的验收标准和明确定义的任务是你的第一道防线。如果任务说“POST 到 /api/login 并得到 200 OK”，代理几乎没有空间去幻觉一个不同的端点。歧义是敌人。事先花时间使任务明确无误，并使提示模板明确说明做什么和不做什么（系统提示/前言可以列举“除非指定，否则不要引入任何新的依赖项”或“遵循此仓库中使用的编码风格”）。
* **验证以捕获幻觉：** 前面提到的测试和类型检查将捕获许多幻觉部分（如调用未定义的函数）。类型错误、引用错误、失败的测试——这些是代理做了不真实事情的信号。循环的逻辑应然后提示代理修复这些问题。通常，只需运行代码并将错误输出反馈给模型，就足以让模型意识到错误并纠正它。
* **定期重新聚焦：** 长时间运行的循环可能会随时间漂移——也许一个小误解会累积。对抗偏离的一种技术是**定期用新的规划重新开始**。例如，在完成一定数量的任务后，你可以暂停并重新运行 /prd 技能或重新扫描代码库，以确保剩余任务仍然有效。Carson 的团队指出，在[非常长的代理运行](https://cursor.com/blog/scaling-agents#:~:text=we%27re%20nowhere%20near%20optimal,combat%20drift%20and%20tunnel%20vision)中，需要*“定期重新开始以对抗漂移和隧道视野”*。实际上，这可能意味着在代理完成一大块工作后停止它，审查中间产品，如果需要更新任务列表，然后继续。
* **多模型交叉检查：** 如果可用，为不同角色使用不同模型。Cursor 的实验发现，使用模型混合（一个非常能干的用于规划，一个代码专业化的用于编码）比一个模型做所有事情效果更好。根据你的工具，你可能没有多个模型选项，但即使对关键步骤使用第二意见模型（例如，在 Claude 生成的差异上运行 GPT-4 检查）也可以减少错误。一些开发者手动这样做：例如，在循环完成后，在你合并之前要求 ChatGPT 审查 PR。

### **上下文膨胀和优化**

随着项目增长，提供给代理的上下文量可能变得巨大。如果 AGENTS.md 和 progress.txt 积累了数百行，你无法总是将所有这些内容放入 100k 令牌的窗口中。一些建议：

* **总结较旧的内容：** 代理本身可以在这里提供帮助。你可以提示它：“总结上面进度日志中的关键点”并存储它，然后截断日志。如有必要，保留总结的总结。这以更短的形式保留了重要信息。
* **分而治之上下文：** 使用任务 ID 仅显示日志或代码的相关部分。如果任务 7 是关于登录页面的，你不需要在提示中包含关于结账功能的注释。一些自动化方法搜索仓库中与任务相关的关键字，并仅包含那些文件作为上下文。
* **明智地利用训练知识：** 记住，模型已经拥有大量通用知识（关于常见库、算法等）。除非项目使用非常新或晦涩的东西，否则你不需要提供它可能已经“知道”的文档。例如，你可能不需要粘贴整个 React 文档；只需注明“这是一个使用 Hooks 和 Vite 的 React 项目”，模型就可以从它的训练中填充其余部分。利用模型的优势，为项目特定的细节节省上下文。

### **人工监督和持续改进**

最后，将整个系统视为一个活的过程。监控它，调整它，并频繁地应用人工判断。Ryan Carson 在他使用这些循环构建的经验中，强调了进入调整提示和工作流集成的[*“费力”*](https://freeplay.ai/blog/real-talk-on-building-coding-agents-a-conversation-with-amp-s-builder-in-residence-ryan-carson#:~:text=%3E%20,%28watch%20here) 工作。没有一劳永逸的完全自主魔法。这更像是持续的改进。

你作为开发者的角色从编写代码转变为策划过程——编写规格说明、审查结果，并在高层次上指导 AI 代理（几乎就像你 AI 开发者团队的工程经理）。

密切关注**成本**（API 使用情况）。卡在循环中的代理可能会烧掉令牌；设置合理的限制，也许还有预算警报。然而，在实践中，如果做得好，投资回报率可能巨大——Ralph 社区报告了[巨大的生产力提升](https://ghuntley.com/ralph/#:~:text=,%24297%20USD.%20pic.twitter.com%2F0JgT8Q19bV)，有轶事案例表明一个价值 5 万美元的项目仅用几百美元的 API 调用就交付了。

自主编码代理已经到来，通过仔细的设置，它们可以持续承担编码的繁重工作。

每次迭代，你和代理都会变得更好。

欢迎来到 AI 增强软件工程的下一个层次：在你睡觉时交付代码，让你的代理复合你的进步。
