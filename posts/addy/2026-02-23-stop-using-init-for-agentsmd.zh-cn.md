# 停止为 AGENTS.md 使用 /init

            **日期：** 2026-02-23 00:00 UTC
            **链接：** https://addyosmani.com/blog/agents-md/

            ---

            **太长不看版：一个良好的思维模型是将 AGENTS.md 视为一份你尚未修复的代码库坏味道的活清单，而不是一份永久配置。自动生成的 AGENTS.md 文件会损害智能体性能，并使成本增加 20% 以上，因为它们重复了智能体本已能自行发现的信息。人工编写的文件只有在包含不可发现的信息时才有所帮助——工具使用陷阱、非显而易见的约定、雷区。其他每一行都是噪音。**

在采用 [AI 编码智能体](/agentic-engineering/ai-coding-agent/) 的开发人员中，几乎已经普遍存在一种仪式。你设置一个新仓库，运行 `/init`，看着智能体扫描你的代码库，然后得到一个闪亮的 AGENTS.md 文件。它描述了你的目录结构、技术栈、测试约定。你快速浏览一下，看起来合理，就提交了。你觉得自己做了负责任的事情。你的智能体配置好了。

2026 年初发表的两篇论文表明，你可能刚刚让你的智能体变得更慢、更昂贵，而且并没有更准确。而其影响远不止是否包含代码库概述那么简单。

除了放什么内容之外，还有一个结构性问题值得尽早指出：对于任何真正复杂的代码库，在仓库根目录下放一个单一的 AGENTS.md 文件是不够的。你实际需要的是一个 AGENTS.md 文件的层级结构——放置在相关的目录或模块级别——并自动维护，这样每个智能体都能获得精确限定于其正在处理的代码的上下文，而不是一个混淆了整个项目关注点的单一庞大文件。

---

## **研究实际说了什么**

[Lulla 等人 (ICSE JAWs 2026)](https://arxiv.org/abs/2601.20404) 进行了一项干净配对的实验：124 个真实的 GitHub 拉取请求，分别在有和没有 AGENTS.md 文件的情况下执行，其他所有条件保持不变。相同的任务、相同的仓库快照、相同的智能体。他们发现，存在 AGENTS.md 文件使**中位挂钟运行时间减少了 28.64%**，**输出令牌消耗减少了 16.58%**。具有统计显著性。智能体变得更便宜、更快。

这听起来像是一个明确的胜利。先记住这一点。

苏黎世联邦理工学院的[另一项独立研究](https://arxiv.org/abs/2602.11988)在 SWE-bench 和一个自定义基准测试（包含已拥有开发者编写上下文文件的仓库）上测试了四个智能体。他们的发现则指向相反的方向：LLM 生成的上下文文件使任务成功率降低了 2-3%，同时成本增加了 20% 以上。开发者编写的文件使成功率提高了约 4%——但成本也增加了高达 19%。

那么到底是哪种情况？AGENTS.md 是帮助还是损害？

两者皆有，取决于你在里面放了什么。而这实际上是更有趣的结果。

苏黎世联邦理工学院的论文发现了一些重新定义了整个争论的事情：当他们从仓库中剥离所有文档——README、docs 文件夹、markdown 文件——然后*再*用 LLM 生成的上下文文件进行测试时，这些文件突然将性能提高了 2.7%。自动生成的内容并非无用。它是多余的。智能体无论如何都能通过阅读仓库找到所有这些信息。将同样的信息交给它两次，你只是增加了噪音。

相比之下，Lulla 的论文使用了人工编写的 AGENTS.md 文件，这些文件来自开发者实际一直在维护的仓库。真正的项目特定知识。非显而易见的工具要求。实际的陷阱。这才是能节省智能体时间的上下文，因为它不必推断它无法发现的东西。

问题不在于是否要有一个 AGENTS.md。问题在于什么内容才值得在它里面占一行。

## **粉红大象问题**

AGENTS.md 文件有一个更微妙的成本，它不会体现在效率指标中：锚定效应。

如果你的 AGENTS.md 提到你在后端使用 tRPC——即使只是在架构概述中顺带提一句——模型现在在每个提示的上下文中都有了 tRPC。如果 tRPC 仅用于少数遗留端点，而所有新东西都在其他东西上运行，那么你刚刚让你的智能体对当前代码库产生了错误的模式偏见。你说了它，它就在那里，而 LLM 不会区分“这是我们过去做的”和“这是你应该做的。”

这与[提示工程](/agentic-engineering/prompt-engineering/)智慧一直所说的要小心系统提示中放什么内容是同一个原因。你添加的每一样东西都在与实际任务竞争。更广泛关于 LLM 上下文的研究显示了一个一致的模式——更多的上下文通常会降低性能，不仅通过成本，还通过稀释注意力。Liu 等人的“迷失在中间”结果（2024 年）表明，LLM 难以处理放置在长上下文中间的信息。Levy 等人表明，即使内容完全相关，更长的上下文也会降低任务性能。AGENTS.md 中的每一行都在与你实际要求智能体做的事情竞争。

## **反对 /init 的具体理由**

这是自动生成上下文文件的核心问题。`/init` 产生了什么？代码库概述。目录结构。技术栈描述。模块解释。苏黎世联邦理工学院的论文发现，100% 的 Sonnet 4.5 自动生成的上下文文件包含代码库概述。99% 的 GPT-5.2 也是如此。

这些正是智能体可以通过列出目录和阅读你现有的 README 自行发现的东西——无论 AGENTS.md 是否存在，它都会这样做。所以，你添加了一个智能体读取的文件，然后它通过阅读你的实际代码去确认，现在它必须协调两个信息来源。更多的推理令牌。更多的步骤。相同的结果，只是更慢、更贵。

---

## **什么才真正值得占一行**

苏黎世联邦理工学院的论文展示了关于什么有效的一些具体内容。当开发者编写的上下文文件提到 `uv` 时，智能体平均每个任务使用它 1.6 次。当没有提及时，智能体使用它的次数少于 0.01 次。其他仓库特定工具也出现了相同的模式：提及时每个任务使用 2.5 次，而未提及时少于 0.05 次。

`uv` 对比 `pip` 是一个完美的例子，说明了什么属于 AGENTS.md。它是：

*   无法从代码库中通过推理发现
*   操作上意义重大（它改变了智能体运行的命令）
*   智能体无法通过惯例正确猜测

相比之下，“这个项目使用一个单仓库结构，包放在 /packages 中”——这是智能体在其运行的第一个目录列表中找到的东西。其中一个值得占一行。另一个是噪音。

实际的过滤条件很简单：智能体能否通过阅读你的代码自行发现这个信息？如果能，就删除它。每一行都应该代表仓库中尚未存在的信息。

这意味着你的 AGENTS.md 应该看起来更像这样：

-   使用 `uv` 进行包管理
-   始终使用 `–no-cache` 运行测试，否则你会从夹具设置中得到误报
-   认证模块使用自定义中间件模式；不要重构为标准 Express 中间件
-   `legacy/` 目录已弃用，但被三个生产模块导入——不要删除其中的任何东西

几乎不需要其他东西。

## **静态文件问题**

即使你编写了一个紧凑、无冗余的 AGENTS.md，它也有一个结构性弱点：它是静态的，但任务是动态的。

你的文件说“在提交前始终运行测试套件。”智能体正在做一个文档更改。它忠实地运行了整个测试套件。令牌烧掉了，时间浪费了，在一个对代码更改有意义但对这个任务无意义的指令上。

这不是一个假设的失败模式。它已内置于架构中。一组扁平的指令集无法根据正在运行的任务类型进行条件判断。一个处理 CSS 重构的智能体不需要你的数据库迁移警告。一个实施安全修复的智能体可能应该跳过性能优化提示。一个单一的庞大文件每次都以相同的方式被加载。

[ACE 框架](https://arxiv.org/abs/2510.04618)（智能体上下文工程，ICLR 2026）直接解决了这个问题，它将上下文视为一个不断演变的剧本，通过生成器/反射器/策展器管道进行适应，而不是一个静态文件。在智能体基准测试中，它比静态方法高出 12.3%。架构很重要。

## **人们尚未构建的更好架构**

AGENTS.md 讨论中的几个人独立地趋近于大致相同的想法：正确的结构不是一个庞大文件，而是一个按需加载聚焦上下文的路由层。

该结构看起来大致如下：

**第 1 层：协议文件**（AGENTS.md 实际应该是什么）不是代码库概述。不是风格指南。而是一个路由文档。可用的人物角色以及何时调用它们。可用的技能以及它们涵盖的任务类别。可用的 MCP 连接以及它们的用途。智能体真正无法发现的最小必要仓库事实——仅此而已。

**第 2 层：聚焦的人物角色/技能文件**每个文件根据任务类型选择性加载。一个处理组件架构的 UX 聚焦智能体加载的上下文，与一个调试数据管道的后端智能体不同。两者都不会加载对方的上下文。任何给定任务的总上下文保持有界。

**第 3 层：一个维护子智能体**其唯一工作是随着代码库的演变保持协议文件的准确性。因为这里有一个没人谈论的事情：文档会腐烂。苏黎世联邦理工学院的研究使用了新生成的上下文文件，仍然发现了性能下降。现实世界中六个月未动过的 AGENTS.md 文件——描述一个你早已替换的依赖，一个已经改变的目录结构——会更糟。糟糕得多。

没有一个主要的编码智能体公开了使这个架构易于构建的生命周期钩子。你可以用子智能体和限定范围的上下文来近似实现，但还没有一个干净的解决方案。这是一个等待被填补的工具空白。

## **自动优化角度**

这个领域最引人注目的发现来自 [Arize AI 的提示学习工作](https://arize.com/blog/claude-md-best-practices-learned-from-optimizing-claude-code-with-prompt-learning/)。他们没有手动编写 CLAUDE.md 指令，而是使用了一个自动优化循环——在训练任务上运行智能体，评估输出，生成关于解决方案为何失败的 LLM 反馈，使用元提示来优化指令。重复。

结果：在跨仓库测试拆分上准确率提高了 +5.19%。在仓库内拆分上提高了 +10.87%（在过去的 Django 问题上训练，在未来的问题上测试）。

优化器发现的是令人不安的含义：帮助人类理解代码库的东西和帮助 LLM 导航代码库的东西往往是不同的。一个对你来说看似明显有用的指令——“这个服务使用仓库模式”——对模型来说可能是噪音。而模型实际需要的东西——某个特定的导入路径消歧，某个非显而易见的文件命名约定——你可能永远不会想到要写下来，因为你已经内化了它。

手动处理 AGENTS.md 的方法假设你知道智能体需要什么。经验证据表明你可能不知道。优化器找出了你认为重要的东西和实际起推动作用的东西之间的差距。

这并不意味着你应该放弃编写上下文文件——自动优化研究仍处于早期阶段，5% 是有意义的，但并非变革性的。这意味着你应该对你认为应该包含什么内容的直觉保持松散态度，并且很可能应该测试它们。

## **AGENTS.md 的正确心态**

将 AGENTS.md 视为一份你尚未修复的摩擦点的活文档。

你添加的每一行都是一个信号，表明你的代码库中有某个东西足够令人困惑，以至于会绊倒 AI 智能体——这意味着它可能也足够令人困惑，以至于会绊倒新的人类贡献者。对该信号的正确反应不是增加上下文文件。而是修复实际的问题。

智能体总是把新工具放在错误的目录里？也许目录结构令人困惑，应该重新组织。智能体总是去拿一个已弃用的依赖？也许导入结构让错误的那个太容易拿到了。智能体忘记运行类型检查？也许构建管道应该自动捕获这个问题，而不是依赖一段散文式的指令。

AGENTS.md 变成了一种诊断工具，而不是永久配置。你添加一行，你调查为什么智能体一直犯这个错误，你修复底层问题，然后你可能就可以删除这一行了。

一个值得尝试的技巧：让你的 AGENTS.md 几乎为空，然后添加一条指令：“如果你在这个项目中遇到令人惊讶或困惑的事情，请将其标记为注释。”智能体提出的大多数补充都不是你想要永久保留的东西——它们是代码库不清晰之处的指标。修复那些问题。保持文件最小化。

## **研究未能解决的问题**

两篇论文都有值得指出的真实局限性。

Lulla 的论文根本没有衡量正确性——只衡量了效率。你不能从中得出结论说 AGENTS.md 提高了输出质量。作者对此很清楚：他们进行了一次健全性检查，以确认智能体产生了非平凡的输出，但完整的正确性评估是未来的工作。更快更便宜是有意义的，但如果代码是错误的，那就没意义。

苏黎世联邦理工学院的论文使用了全新的上下文文件，这对于实验控制来说是理想的，但可以说测试了一个大多数开发者并不实际处于的场景。现实世界的情况是上下文文件已经在仓库中存放了数月，并且部分过时了。这应该比论文测量的表现更差。

两篇论文都没有测试多位从业者论证为正确架构的层级化、动态加载方法。“扁平单一上下文文件”是唯一被评估的东西。一个具有选择性上下文加载的适当分层系统是否会表现不同，仍然是一个开放的经验性问题。

还有模型轨迹问题：每隔几个月，开发者报告说他们需要在上下文文件中放的东西更少了，因为底层模型在代码库导航方面变得更好。六个月前必不可少的指令，随着模型的改进而变得多余。你今天写的 AGENTS.md 到下个季度可能纯粹是开销。

---

## **实际要点**

停止运行 `/init`。自动生成的输出与你现有的文档是冗余的，并且增加了开销而没有好处，除非你的仓库确实零文档——在这种情况下，它比什么都没有略好一点。

在向 AGENTS.md 添加任何一行之前，问：智能体能否通过阅读代码找到这个？如果能，就不要写。

当一个智能体反复在某个问题上挣扎时，先将其视为代码库问题，然后再视为上下文问题。重构代码。添加 linter 规则。改进测试覆盖率。只有在用尽这些选项之后，才考虑使用 AGENTS.md。

如果你在 CI/CD 或自动审查管道中大规模运行智能体，上下文文件带来的 15-20% 成本开销会在数千次运行中累积。在假设权衡值得之前先计算一下。

考虑构建一个维护智能体，其工作是保持上下文文件的准确性，而不是让它腐烂。

并且对你认为智能体需要什么的直觉保持松散态度。对你来说似乎明显有用的东西，对模型来说可能是噪音。经验证据表明，我们认为智能体需要的东西与实际帮助它们的东西之间的差距是巨大的——而且可能不是我们期望的方向。

像入职新员工那样引导你的编码智能体的本能——带它参观办公室，解释组织结构图，带它走一遍架构——来自一个合理的地方。但编码智能体不是新员工。它们可以在你打完提示之前 grep 整个代码库。它们需要的不是一张地图。它们需要知道雷区在哪里。

而且，也许，它们越来越不需要那个了。
